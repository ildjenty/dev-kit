# Development workflows

The owner decides what matters, changes stay local, and observed failures improve the process. Archon runs ten workflows; `devkit` performs mechanical checks and records transitions. The installed `devkit-discuss` and `devkit-runs` session skills handle conversation, starting runs and relaying results. Workflows never start each other.

## Installing and updating

`devkit init [--yes | --no] [--dry-run] [dir]` compares everything before writing. For the workflow folder and each installed skill folder, it lists differing and extra files and asks `replace N files and delete M files? [y/N]`. No preserves those files and allows missing files to be added. Stale files are deleted only after Yes, only within these kit-owned folders and a renamed skill's previous folder. Each differing configuration file has its own question. Existing standards at the configured path are replaced as a whole only after Yes; No adds nothing, including missing files. Identical files are silent; absent files need no confirmation.

After normalizing paths, init rejects a standards folder that overlaps the workflow directory, an installed or previous skill directory, `.devkit/config.json`, `.archon/config.yaml`, or a configured `decisions` or `eval` folder. Equal paths and ancestor/descendant overlaps are rejected with the conflicting paths before comparison output, questions or writes. Nonconflicting locations under documentation folders, such as `docs/standards`, remain allowed.

Use repeatable `--skill` flags to choose distinct installed names made of lowercase letters, digits and hyphens. The `skills` mapping in `.devkit/config.json` remembers them. Installed skill folders, front matter, cross-references and watch-script paths use those names. An explicit flag updates only `skills` even when config replacement is declined. The standards destination is retained when config is replaced. Use `devkit config` to read effective names and paths.

When `--provider`, `--sessions`, `--language` or `--skill` is explicit, init rejects an existing `.devkit/config.json` object containing duplicate keys before asking questions, writing or deleting files. It checks the entire object recursively, including unrelated settings and objects inside arrays, and compares names after decoding JSON escapes. The error names the duplicated key and asks the owner to remove it. This also applies with `--yes` and `--dry-run`; rejection leaves existing files and formatting unchanged. Full replacement of config that cannot be parsed as a JSON object retains its existing behavior.

Destination and ancestor symbolic links are named and asked about. Yes replaces the link itself without touching its target; No skips affected destinations. A declined group prevents replacing a shared ancestor link that would remove its files. `--yes` and `--no` answer all questions; stdin without a terminal defaults to No with a notice. `--force` is unsupported. `--dry-run` prints comparisons and questions and changes nothing. Init lists written, deleted and retained paths and exits successfully when changes are declined. Malformed JSON config can be kept or replaced using default destinations for comparison; applying only `skills` requires a JSON object. Invalid destination settings are errors. Review and commit the result before running workflows.

## Sequence and handoffs

Init writes `.devkit-installed.json` in this folder with `devkit_version` and `kit_digest` when the workflows match its kit after a fresh install, Yes, or no differences. No keeps the previous stamp, including when missing files are added. The stamp belongs to the workflow comparison and is never an extra file; hand edits do not update it. `devkit version` prints the binary version and the embedded kit's SHA-256 digest, stable for the same paths and contents across builds.

Every start checks this workflow's YAML and command files in `$PACK_DIR` for unregistered commands before saving records or answers. A missing command returns `not_started` with the command, the kit/binary mismatch explanation, and remedies: run `devkit init` in the repository with the matching binary or install the binary that installed these workflows (the stamp names its version). Relay this to the owner and do not retry. Digest differences alone do not prevent a start.

Run `devkit-optimize` after init or when repository conventions or owner workflow preferences change.
The skill invokes `devkit-runs`, passes verbatim `instructions` through a file and starts
`optimize` on `optimize/<name>`. Inputs are `instructions`, `answers`, `approve`, `continue`;
empty instructions request the full fit. The writer drafts config, worktree preparation, standards
reconciliation, routing and short agent instruction sections; workflow edits require the owner's
request. It also triages every open Issue without the kit's labels as a unit with observable,
request-supported completion conditions, a grouped topic, or a reasoned exclusion.

Start and prepare lead to at most three write → check → fresh read-only judge → round iterations.
The Go machine validates config, concerns, scope, PR titles and Issue structure, and runs every
configured check on the base in a temporary worktree prepared by the proposed postCreate.
Archon validates workflows without warnings; if unavailable, the reported fallback checks command
plumbing and YAML parsing. Failures and skipped base checks retain log paths and block approval.
The judge uses fixed harness, authority and purpose standards, comparing the actual proposal to
the owner's instructions. Security, data-loss and authority blocking cannot be weakened.

Finish returns the short four-part approval question described below; full changes, triage,
summary, owner_points, PR text, version, commit and verification remain in the proposal details.
Approval publishes through shared proposal code, then applies
labels, body edits, new topic groups under existing parents, sub-issues and blocked-by links.
Topic held_units and unit links must match. Progress and stable new-topic markers let retries
resume missing operations without duplicating Issues. No external writes precede approval.
The owner merges the PR; status reports the approval question or published PR.

Use `devkit-discuss` from invocation until the discussion has become Issues. Keep a running memo of decided, overturned (with decision IDs) and still-open points; update it as choices change, preserve it through summarisation and restate it when resuming. Handle unrelated requests, then return to the discussion. Starting refine with the confirmed memo, relaying questions and exact-version approval are part of this mode.

Run `refine` on a `refine/<name>` branch with `topic=<number>` for an open Issue carrying the topic label, or omit it for a new request. It reads the full decision log, requests, memo and answers with fixed criteria. A single phase has at most three machine-check/judge rounds. The draft proposes decision records, binding edits about how agents work to standards, agent instructions, skills or checks, and unit/topic Issues. Each unit fits one PR with a goal and observable completion conditions; `blocked_by` names Issue keys within the proposal. Machine checks generate proposed records and commit them with binding edits before fresh read-only judgment. A cleared proposal asks approval with the short question below.

Group open questions into one topic when they hold the same units at the same time and cannot be decided apart: stack, hosting and a monthly cost cap can hold the foundation unit together, with the cap shaping hosting. Separate questions holding different units or independently decidable questions. Questions holding no unit go into separate, non-blocking topics for when work needs them; closely related ones may share a topic, such as contract signers and account administrators under "contracts and operating arrangements". Group by this rule to keep Issue counts manageable, rather than one Issue per question. Each topic draft names the unit keys it holds or explicitly says it holds none; waiting units include its key in `blocked_by`. Unit drafts, including retro's, contain no open questions: their work content is only the goal, observable completion conditions and product properties to preserve. Judges block mixed unit needs, unnecessary questions in a unit's blocking topic, open questions in units and mismatched blocked-by links.

In discuss, choose the topic holding the unit the owner wants to start. Within the topic, ask only what its waiting units need; listed points are candidates, not a checklist. Keep points holding no unit open in the memo for refine to put into a non-blocking topic.

Binding changes concern process, tools, conventions or verification. A rule is mechanically checkable when a command or file/config fact can decide compliance; never write it as prose in standards, AGENTS.md, CLAUDE.md or skills. Register existing commands as checks in `.devkit/config.json` with `name`, `command`, `timeout_seconds` and applicable `paths`. Refine validates the config and runs added or changed checks on the base in a temporary worktree prepared with postCreate, reusing optimize's execution and ignoring path selection. Failure, skipping or inability to prepare or run blocks the draft; results and logs are in `refine/verification.json` and per-round reports. If the command does not exist yet, make creating and registering it a completion condition of the unit that creates it: for example, the foundation unit registers the type check and automated tests as checks, with tests using only local PostgreSQL and running without external credentials or network. Prose bindings are only for work rules needing judgment. Refine, retro and optimize judges block mechanically checkable rules written as prose in binding changes.

Product data shapes, invariants and feature rules go into the implementing unit's testable `completion_conditions`, such as rejecting overlapping shifts for one person. A shared property belongs in the first unit that builds it; later units that touch it repeat the condition they must preserve. Code and tests then carry the specification. Judges check this separation and block product rules in binding changes or missing product completion conditions, including in retro.

Both refine and retro drafts require `pr_title` (one line, at most 100 characters) and `pr_summary` (a few sentences explaining what merging puts on the base and why). Writers use the language named by `language` in their input and address the PR reviewer. Judges check meaning, wording and language; machine checks validate required, nonblank text and title limits. Both fields remain in the full proposal details. The machine uses them unchanged, without shortening or replacing them with a proposal summary or approval instructions.

Refine, retro and optimize return one short approval question containing only:

1. Every choice or rule added or derived beyond the confirmed memo and owner's words, including provisional decisions, derived agent rules and defaults: a key, recommendation and reason in one or two lines each. Retro and optimize have no memo; list every proposed change not mechanically implied by backlog/repository evidence or owner instructions.
2. Every risk the owner must accept, keyed and summarised in one or two lines each.
3. One line saying everything else follows the confirmed memo and owner's words (or evidence and instructions), with `devkit proposal show <branch>` for details.
4. How to answer: `approve=<version>`, or `answers` naming the key to change. The version appears only here.

Version history, provenance inventories, machine fields, JSON, full bodies, exhaustive binding/Issue lists and facts needing no decision (including cost estimates) stay out of the question. Judges block missing items or risks; settled content repeated in the question or other unnecessary content gets a nonblocking finding asking to cut it. Writers still supply the full draft. Each cleared proposal saves decision bodies, binding paths and their decisions, Issue drafts with parent and blocked-by, PR title/summary, version, commit and verification in `proposals/<version>.details.json` under branch records. `devkit proposal show <branch>` prints the latest proposal's details using the same state discovery as `devkit status`, including `STATE_DIR`. The runs, discuss and optimize skills relay questions unchanged and show that command's output when the owner asks for details. Approval version checks are unchanged.

`approve=<version>` checks the latest approval question, started run, recorded owner answer and clean proposal HEAD. Refine commits agreed records and superseded predecessors, pushes the branch and opens or updates the PR with the approved title and summary, then creates Issues. If absent, it creates a parent topic from the request; units become its sub-issues, and remaining questions become new topic Issues. It connects blocked-by links and comments on the parent with decision IDs and created Issues, closing the parent only when no new topics remain, then updates the PR's Issue list. Results include `decision_ids`, `issue_numbers` (including the parent), `pr_number` and `pr_url`. Revisions make new proposal commits, preserving kept decision IDs and removing withdrawn unapproved records. The owner merges the PR; units wait for that merge and their blocked-by dependencies.

The PR body starts with the approved `pr_summary` unchanged. `What to review` lists binding paths, their decision IDs/titles and reasons. `Decision records` links IDs and titles to files on the proposal branch and explains that the log is for people and does not bind delivery. `Issues created` links the parent, units and remaining topics with titles and blocked-by references, explaining that units become ready after PR merge and dependency completion. Empty lists are omitted. Headings and fixed explanations follow `language` for Japanese (`ja` and regional variants) and English; other languages use English fixed text without translating authored titles, summaries or reasons. Absolute file links use the repository URL from `gh repo view --json url --jq .url` initially, or the recorded PR URL on update, with encoded branch names and paths. Do not copy approval questions, proposal versions or internal failure/change history into the body.

Only after that merge, start each ready unit on its own branch: `requirements` with `issue=<number>` → `plan` → `implement` → `judge` ⇄ `fix` → `pr`. `devkit issues ready [--json]` lists open units and topics with every blocked-by Issue closed, including unlabelled blockers and later API pages; the parent need not be closed. JSON has `units` and `topics` arrays of `number`, `title`, `url` and nullable `parent`; text lists units first. `devkit issues show <number> [--json]` reads body, state, labels, parent, `sub_issues`, `blocked_by` and `blocking`; empty relationships are `[]`, no parent is `null` and states are lowercase `open` or `closed`. Direct settled requests use `owner_words`; observations go in `supplement`. Plan is required for delivery. Review-only judge also works without requirements or a plan. Use sync to rebase, then judge when `needs_judge` is true and return to PR.

After backlog reaches the base branch, run `retro` on a `retro/<name>` branch from that base. It proposes unit Issue drafts, check additions, standard edits or reasoned dismissals. Standards and check settings change only agent work; product properties go into testable unit completion conditions. Machine-checked real files and consumed backlog deletions become a proposal commit; drafts remain in the proposal record without file snapshots. Fresh read-only judgment inspects that commit. After at most three rounds, it returns the short four-part approval question and saves full details, including version, commit, PR title/summary and evaluation results. Approval requires the clean proposal HEAD, pushes and opens or updates the PR, creates unit Issues without a parent topic and blocked-by links, then updates the PR's Issue list and records pass, `issue_numbers`, `pr_number` and `pr_url` without editing files or creating another commit. Revisions and withdrawals use subsequent commits. Old snapshot proposals require a new retro branch. The owner merges the correction PR before its units start, subject to their dependencies.

Retro's body uses the same approved summary and language/link rules. `What to review` lists standard paths, reasons and evidence and added config checks with reasons. `Escapes` lists source entries, stages, qualities, reasons and evidence; `Eval cases` links case names to the proposal branch with source escapes. `Issues created` lists units and blocked-by links. Japanese uses translated headings and fixed explanations.

Both workflows save Issue creation progress in branch records at `issue-creation/<version>.json`: initial approval run, commit, parent, created Issue mapping and completed links/comments. Refine uses the agreement commit; retro uses the proposal commit. Retrying the same approved version resumes missing work and checks the original approval answer, subject to normal restart limits. Hidden body markers identify commit, proposal version and draft key, distinguishing an automatic parent. Before creating an unrecorded Issue, all open and closed pages are searched for its label and marker; matches are adopted, including closed Issues, without reopening them. Failed lookup stops creation. Missing links are completed and existing links accepted, including after a lost response. No automatic creation retry, concurrent-creation exclusion or parent-comment deduplication is provided; old unmarked Issues cannot be adopted.

Both workflows reject approval of old proposals missing PR title/summary, or with an overlong or multiline title, at approval start and execution before any agreement commit, push or PR/Issue write. Make a new proposal for approval. Existing approval/commit checks and Issue resume records remain in force; reruns update the existing PR title and body from the currently approved content.

Record defects found after merge, including small direct fixes, with
`devkit backlog escape --defect-file <file> --entered <commit-or-PR> [--fixed <commit-or-PR>]`.
The file preserves the owner's description without command-line text. References accept locally
resolvable commits (stored as full hashes), commit hashes, GitHub PR URLs or positive PR numbers.
Commit the printed `.devkit/backlog/escapes/<random-hex>.json` with the fix or through the PR process.
Retro reads it as `kind: escape`, with ID `<path>#escape/0`, and requires a used/dismissed decision
and a trace of the entering change and missed stage. Routing misses correct the quality's `routing`
sentence in the standards folder's `concerns.json`. Each used escape the judge should have caught
adds a minimal `base/`, `change.patch` and `case.json` under the configured `<eval>/judge/<name>/`.
The retro check reuses judge-evaluation validation. After checks and judgment pass, `verify` runs
only the new cases against a temporary copy of the committed proposal's standards and concern map,
checking the clean proposal head and that the draft and approval question have not changed since
judgment. The AI reports found/missed expectations, routing misses and provider failures in the proposal details'
configured language. Misses and provider errors do not block the proposal. This incurs provider
calls only for escape cases. Cases, config and standards share the proposal commit with
consumed backlog and escape deletions. Existing cases remain protected; retaining, revising or
withdrawing cases from a previous proposal uses the next proposal commit. Results remain in run
artifacts and the proposal record.

A `question` result ends the run. Relay every question and ID and restart its named `next_workflows` workflow with verbatim owner answers. Refine and retro approval use the exact recorded version. Requirements and plan ask unresolved request/design questions; implementation, judge and fix return `back` to plan for owner decisions. PR asks only for uncovered `ask` changes. Follow `back.to`; `stop` describes unresolved work, and `not_started` means prerequisites rejected the start. `carry` is a plan result carrying detail findings forward. Counted restarts and fix runs obey configured limits; supply owner words as `continue` only when the restart limit is reached.

When every failing check is `preexisting`, implement/fix stop immediately without stuck, step-back or pass consumption. Judge includes base failures in its judgment and stops when any check is preexisting instead of recommending fix. The stop records `base_failed: true`; loops end `base_failed`. Relay the failing checks and their log paths and tell the owner to fix the base branch first, then start the same workflow again. `devkit record limit` classifies that restart as `retry_after_base`, not counted against `limits.restarts`, even at the limit. `devkit status` explains this. Retrying before the base is fixed is pointless. Regressed and unavailable comparisons retain the existing implement/fix behavior. Implement and fix call `devkit checks --base-on-repeat`: a failing check is compared with the base only when it also failed in the previous pass (others record `base: not_compared`); judge and sync compare every failing check.

## After the pull request

Read `gh pr view <branch> --comments` and `gh pr checks <branch>`, then read the actual inline comments
or failing job logs. An in-scope repair or CI failure goes to `fix` on the same branch as `review`,
verbatim with provenance (`Review comment by <login> on path:line: ...` or
`CI job <name> failed: <log excerpt>`). Review starts need passed requirements and plan and the latest
judge's change matching HEAD by PR identity, including after the backlog commit.
The run stores the review text and starting commit; its fix findings have source `review`.
Items outside requirements or plan, and disputed review items, appear in `outside_requirements`
with `item` and `reason` and return `back` to requirements with those items as premise and the full
review as observation. Review objections bypass the dispute judge. Checks and fix/restart limits
still apply; this return makes no fix commit. A pass needs a new judge run before PR, even if the
change identity stayed the same; PR then updates the existing pull request.

A comment that changes or adds to the request goes directly to requirements on the same branch as
`owner_words`, then follows the usual flow. Never answer or resolve comments on the reviewer's
behalf. For a CI failure, suggest adding the job through `devkit-optimize` as a configured check.

After a passing PR, status optionally runs `gh pr view <branch> --json state,url,reviewDecision,statusCheckRollup`
with a 15-second timeout. It shows state, URL, review decision and failing checks in text and JSON;
lookup failures are shown and never fatal. `next` routes open failures to fix with `review`, requested
changes to fix with `review` or requirements when the request changes, merged PRs to
`archon complete <branch>` followed by `devkit issues ready`, and closed PRs to closed without merging.
`archon complete <branch>` removes the worktree and local branch and keeps the remote; periodically
run `archon isolation cleanup --merged`.

## Concerns, decisions and structure

The code quality set is `internal/concerns`; the repository-owned `<standards>/concerns.json` assigns principles and plan/code criteria to structure, data, contract, security, ui, cost, test, delivery, scope, readability and document. Every numbered standard principle has exactly one assignment: one quality, `every_quality`, or a named writer/non-quality judge in `others`. Every named document exists and every review document except `review/README.md` is mapped. `devkit concerns check` validates the map, including during plan, judge, refine and retro prepare on fixed criteria.

Readability owns names, comments, conventions and shared rule definitions under `engineering.md#8`. For each added function, conversion, check or rule, it searches the whole judged tree named in `judge/target.json` for existing behaviour that must change together. Re-implementation blocks only when the rule or behaviour must change together; similar text with independent reasons for change or contracts stays independent. Placement and dependencies remain structure's responsibility. Structure routing includes function responsibilities and call paths as well as module placement; data routing includes valid states and domain rules as well as stored data.

Materials come from that map. `review/README.md` owns common judgment rules; `authority.md` owns owner decision boundaries. Commands specify inputs, writes and output contracts and refer to standards for rules. Quality criteria separate Decisions from Code, Blocking and Not reported. A choice passed in plan is checked for conformance in code rather than chosen again.

Workflow criteria are pinned to the base commit recorded at request start. The shared `internal/criteria` copier selects `standards` from that commit's `.devkit/config.json`, defaulting to `.devkit/standards` if the file is absent. Requirements, plan, implement, judge, fix, refine, retro, pr and sync use its returned source paths for concern maps and materials; reused copies retain `base` and `paths` in `criteria/source.json`. Criteria paths recorded in targets and inputs follow this source information, so moving the current standards folder does not change the run's materials. Current language settings, check selection and refine/retro edit destinations still apply. `devkit eval judge` has no request-pinned criteria commit and uses the standards selection described below; retro verification evaluates the proposed standards.

Repository decisions live only in `<decisions>/D-<id>.md` as a log for people, devkit-discuss and refine. IDs derive from branch and draft key, starting at six lowercase hexadecimal characters and extending on collision. `supersedes` records replacement; dependency traversal covers decision files only. Delivery workflows do not receive, cite or check decision records, including superseded records. Agent work rules go into owner-reviewed standards, instructions, skills or checks; product properties go through unit Issue completion conditions into code and tests. Plan rows remain delivery records and generate no decision files; provisional choices stay in the plan and PR body.

Writing a document as the deliverable uses normal delivery. The code-phase `document` judge owns `writing.md` principles 2–6, 8 and 9 through `review/document.md`; principle 1 belongs to PR-body judgment and 7 to refine's approval proposal. It covers reader context, standalone explanations, actions, structure, ownership, current versus historical content, diagrams and disclosure. It has no plan judge. Default paths are `**/*.md`, `docs/**`, `!.devkit/**` and `!.archon/**`; matching exclusions take precedence regardless of order. Document's routing threshold 0.6 is unmeasured; existing qualities retain their measured thresholds.

Structure comes first in plan. Nature evidence explains placement; its fresh structure judge must pass before detail adds other rows, release units and tests. Each phase has its own three-round loop. Detail can alter signatures but changing file membership or structure rows stops the run. Detail's `uncertain` is reserved for necessary changes to the judged structure, naming the completion condition and evidence with a verification location. General doubts and details fixable within that structure do not belong there. Non-empty entries end detail without passing and reach the owner verbatim with the existing structure question; the next plan starts from structure. Prepare writes the embedded plan draft schema and its reference dependency to artifacts. Writers cite facts in row evidence.

Judge computes `outside_plan`, folder spread and siblings on ancestor paths. Structural defects on the change's path block, including existing defects; those elsewhere are deferred. The bash `devkit judge route` node selects qualities from each changed file's diff with Jev (`jev-latest`). It asks one question per routable quality from the fixed concern map's `routing` description and selects the quality at or above its `routing_threshold`; a source/test question selects test and readability at 0.3. It uses at most four concurrent requests, 8 KiB diff chunks split at line boundaries and a 24 KiB encoded request bound. Each request has a 10-second timeout and one retry after 100 ms on timeout, 429 or 5xx. All probabilities, including those below the threshold and successful chunks from an unavailable result, are recorded in `judge/route-jev.json`. If any request fails or an answer is malformed, the entire selection falls back to the configured provider CLI with read-only tools/sandbox and schema validation. If both are unavailable, route selects every routable quality for every changed file with both failures in its reason. Its `source` is `jev`, `claude`, `codex` or `all`; launch reads this single result. The machine unions route, configured globs and plan rows; scope always runs, and source/test changes select test and readability. AI judges use the configured provider and fresh contexts on fixed criteria. Claude judges have read-only tool restrictions; Codex runs with full access. Both keep `mutates_checkout: false`: Archon fails a node after a detected checkout write. Codex does not prevent that write.

`devkit judge launch` writes `judge/launched.json` from the same decision as its `launch_<quality>` flags; `devkit eval judge` uses the same launch processing. Code quality judges read it and the fixed `concerns.json` ownership. They report failures of their own principles, or another quality's failure only when its owner was not launched. They receive no `every_quality` principles; these remain in requirements, plan, implement and fix materials. The machine checks `decision_paths` changes absent from plan rows, and scope checks authorization under `working.md#6`. A missing test or changed caller contract remains the respective quality's failure, even when another judge reports the defect itself.

Prepare keeps a single full judged tree at `$STATE_DIR/trees/<encoded branch>/`, outside records and run artifacts. `judge/target.json` and quality materials contain its absolute `tree` path. Judges read that tree with Read, Grep and Glob while concurrent checks may alter the checkout. Claude nodes retain `allowed_tools: [Read, Grep, Glob]` without path restrictions; Codex nodes have full read access. First use exports the whole commit; later runs apply only the Git diff, preserving bytes, executable bits and symlinks and deleting empty folders. Markers at `$STATE_DIR/trees/.commits/<encoded branch>` avoid reserving any repository filename. The marker is removed before updating and written last. Missing/interrupted markers, unavailable old commits or update failures cause a full re-export. Prepare also prunes trees for deleted local branches after `archon complete` or branch deletion, except the branch currently being judged.

## Commands and artifacts

`devkit help` is the command inventory; `cmd/devkit` registers the mechanical packages. YAML passes Archon's `STATE_DIR`, `WORKFLOW_ID`, `BASE_BRANCH`, `ARTIFACTS_DIR`, declared `INPUTS_*` and producer outputs through environment variables. Commands return JSON on stdout, errors on stderr with a nonzero status; `record dir`, help and version return text.

Judge, PR and sync commands that read or write artifacts require `ARTIFACTS_DIR` before accessing files. Provider CLI calls also require `PACK_DIR`; missing settings name the variable and stop rather than reading stale checkout-relative files or creating artifacts there. Standalone checks may still allocate a temporary output folder. `doctor`, `status` and `eval judge` return stdout write failures separately from diagnostic and scoring outcomes.

- Refine: `devkit refine start`, `prepare`, `check`, `round`, `finish`, `approve`, `not-started`. `refine/` contains full-log input, schemas, draft, check, baseline, rounds and approval text. Checks validate schemas, decision and Issue graphs, binding scope and decision references, direct decision edits, config and concerns. Only checks may change in config. Reused IDs and withdrawn unapproved records are resolved and the final decision set validated before materialization.
- Requirements: `devkit record start requirements`, then `devkit requirements prepare`, `round`, `finish`, `not-started`. Input and round artifacts are under `requirements/`; the writer returns requirements as structured output. Failed or unavailable criteria cannot pass. Start and prepare read `issue=<number>` and require it to exist, be open, have the configured unit label and have every blocker closed. Refusals name the Issue and any blocker. Input includes the unit and parent topic titles and bodies as request data, stripping only the trailing devkit marker and separator. Prepare records a fresh input ID, the run ID and the number of requests read; round preserves these with its draft and judgment. Before saving anything, finish verifies that the round matches the current prepared input, run and request boundary. Repeating prepare, switching runs or adding requests after prepare invalidates the old round. Rejection leaves records and artifacts unchanged. Run prepare and round again before finishing, including for older artifacts without binding metadata. Round treats only a missing `requirements/rounds/latest.json` as the first round; index read or JSON parsing errors stop without changing history. Numbered history files are created exclusively and never overwritten. If the index update fails after history is saved, that history remains and another save at the same number is rejected. A missing or stale index does not trigger automatic recovery by overwriting existing history.
- Plan: `devkit record start plan`, then `devkit plan prepare`, `facts`, `check`, `settle`, `advance`, `finish`, `not-started`. `plan/input.json`, `draft.schema.json`, `facts-before.json`, `draft.json`, `findings.json` and `structure.json` carry the two phases. Answers bind to requirements version and row content. Allowed provisional implementation updates record `derived_from` the accepted plan.
- Implement: `devkit record start implement`, then `devkit implement prepare`, `next`, `tests-written`, `uncertain`, `end`, `state`, `finish`, and `devkit checks`. Separate sessions write tests and code per release unit. Repeated check failure invokes step-back. Non-empty implementation `uncertain` entries also reach that judge verbatim before committing, regardless of check success. An `implement` decision continues under the usual check gate; `requirements` or `plan` returns the diagnosis without committing the unit; `environment` stops. An empty array adds no AI judgment. The workflow commits completed units; new owner choices go back to plan.
- Judge: `devkit record start judge`, then `devkit judge prepare`, `changes`, `launch`, `completion`, `collect`, `finish`, and `devkit checks`. `judge/` contains target, committed source snapshots, diff, decisions, locality facts, answers and per-quality materials. Without a plan, decision changes become `without_plan` materials.
- Fix: `devkit record start fix`, then `devkit fix prepare`, `proceed`, `objections`, `dispute-end`, `round-end`, `state`, `finish`, and `devkit checks`. An independent judge settles evidence-backed objections. Finding references include the original judge run, judge and local ID; acceptance cannot suppress another run's finding. An existing `objections.json` must be an object with an `objections` array whose entries contain string `finding` and `evidence` fields. If it cannot be read, parsed or validated, `fix objections` returns an error without moving it to consumed artifacts or saving round state. A missing file or a valid empty objections array means zero objections.
- PR: `devkit record start pr`, then `devkit pr answers`, `facts`, `assemble`, `judgment`, `state`, `open`, `finish`, and `output`. `pr/` holds facts, machine lists, body and title, report findings and publication result. Publication pushes to `origin` and uses `gh`; it does not merge.
- Sync: `devkit sync start`, `continue`, `state`, `finish`, `output`, and `devkit checks`. Before rebasing, sync writes mapped materials from the request's fixed standards into `sync/input.json`; conflict resolution receives them through `sync/conflict.json`. A rebase that fails before reaching a conflict, including rejection by a pre-rebase hook, fails sync rather than marking it done. Before marking a rebase done, sync verifies that the recorded target commit is an ancestor of HEAD. Conflict paths are read as NUL-delimited Git output, preserving non-ASCII names, embedded newlines and surrounding spaces. Remaining conflict markers prevent staging and continuing the rebase. Failed resolution aborts the rebase and restores the original commit; successful conflict resolution sets `needs_judge`. Sync does not push.
- Retro: `devkit retro start`, `prepare`, `check`, `round`, `verify`, `finish`, `approve`, `empty`, `not-started`. `retro/` contains backlog input, schemas, draft, check, rounds, evaluation results and approval text. `check` commits each valid proposal version before judgment and verification; an empty backlog passes without approval.

Shared commands include `devkit config`, `devkit criteria`, `devkit concerns check`, `devkit decisions list`, `check`, `affected`, `dependents`, `next-id`, `devkit issues ready`, `show`, and `devkit record start`, `write`, `latest`, `dir`, `limit`, `result`. Consult help for arguments.

A judge target with `plan_version` requires the matching `judge/plan.json` through changes, launch, completion and finish. Missing or mismatched plans require prepare again; a review that began without a plan permits its absence. A named checks result must be readable before judgments or results are saved; readable empty JSONL means zero checks. Failure to save `judge/route-jev.json` stops routing with the path and cause, even when Jev is unavailable. Otherwise the documented Jev → provider CLI → all-quality fallback remains available.

Implement and fix reject missing, empty, multiline or wrong-prefix `CODE.commit_message` and require the writer to rewrite it. Implement also rejects unit and criterion IDs in subjects. Only provenance trailers are added mechanically; replacement content is not composed.

The skill watcher calls `devkit watch <run-id> [<run-id> ...]`: print status changes, check unfinished runs every 30 seconds, and exit when all runs end. Retrieval failure or a missing Status field ends monitoring with a nonzero status, run ID and diagnostic including stderr. Partial Status output from a failed command is not adopted, and retrieval failures are not retried automatically.

## Records and judged identity

Runtime records stay outside Git at `$STATE_DIR/records/<encoded-branch>/`; `feature/filter` encodes as `feature%2Ffilter`. Resolve the path with `devkit record dir` in the run environment. AI nodes receive selected artifacts rather than this directory. `devkit status [--json] [branch]` reads them from a session: it finds the state folder through `archon project list --json` (or `STATE_DIR`), and prints each branch's Issue number and URL from its request record, last outcome, unanswered questions, stop or back details, and the next instruction.

Reads of numbered records and questions/answers validate the same kind-specific schemas as writes. Null records, missing keys, wrong types and gaps in question IDs return the path and cause. Initial absence and unanswered questions remain normal; saved requests retain the existing optional or zero `issue` field. Issue list/page responses and Archon's `projects` must be arrays; normal empty arrays are accepted, while null, non-arrays and malformed pages are rejected. Status skips deleted project paths with a reason, reports other path-resolution failures, and rejects invalid branch encoding with its path and cause.

Each branch in `devkit status --json` includes an `errors` array of strings alongside the existing fields. An unreadable answer adds its question ID, answer file path and failure reason. A configuration read or validation failure adds the configuration file name, failure reason and a statement that the restart limit is unknown to each branch; `restart_limit` is `-1` to represent an unknown limit. The array is empty when neither failed. Text output shows these failures under the branch as `unreadable: ...`. An unreadable answer is not listed as an ordinary unanswered question. The `next` instruction asks you to resolve unreadable answers and check status again. When the configuration is unreadable, it asks you to resolve the configuration first and check status again. When configuration loading succeeds, `restart_limit` reports the effective value of at least 1. Zero, negative and wrong-typed limits are configuration validation errors reported in `errors`. Status does not change records or configuration.

When the last result is a passing `judge` with `inputs.requirements_version: null`, `next` says the review is complete and asks you to relay the report to the owner. A passing judge with requirements directs you to start `pr`.

`request/` preserves owner words, supplement and the initial criteria commit. `proposals/`, `requirements/` and `plans/` hold immutable versions; `judgments/` holds targets, findings and evidence. `runs/` records successful starts and restart accounting; `results/` records outcomes and input versions. `questions/` and `answers/` use question IDs, `allowed/` holds PR permissions, and `continuations/` holds owner authorization past restart limits. The canonical schemas are embedded from `internal/record/schemas/`. Failed starts save no answers; starting an earlier stage invalidates later results.

Passing judgments cover HEAD or an identical merge-base change: file names and every added/removed line including whitespace match, hunk positions are ignored. Only the current branch's schema-valid backlog file is excluded from identity and decision detection. Done markers are neither generated nor excluded; old files remain ordinary changes. Code judgments store `change_id`.

Plan completion requires every round's `settled.json` with matching round, run, phase and judgments; latest state cannot replace missing history. Failed refine/retro rounds before a proposal commit explicitly record `target.proposal_version: null`, `verdict: not_assessed` and the reason in observations. Committed proposal versions must be positive integers; missing or zero versions are never supplied from a later proposal. Existing draft JSON parse failures return the path and cause rather than becoming absent drafts.

The PR report judgment identifies every byte of `pr-title.txt` and `pr.md` with SHA-256, separately from the code commit and the requirements and plan versions. Alongside the existing paths, its `materials` records `pr/pr-title.txt#sha256=<64 hex digits>` and `pr/pr.md#sha256=<64 hex digits>`; code `target.change_id` does not identify report content. Before rewriting, `pr assemble` invalidates the existing report state's pass status while preserving the round count. Regeneration requires another judgment even if the content is identical. `pr open` checks the pass state and these identifiers in addition to HEAD, clean checkout and the latest report judgment. Mismatches, missing files or state, and legacy judgments without identifiers are rejected before committing backlog, pushing or invoking gh. Publication retains the validated title and body, supplying the body through standard input to `gh pr create/edit --body-file -`, so later source file changes cannot alter the published content.

## Backlog contract

Retro treats backlog as empty only when its folders are absent or enumeration succeeds with no entries. An enumeration failure returns its path and cause; it cannot become an approval-free pass.

Before pushing, PR commits `.devkit/backlog/<encoded-branch>.json` with a `chore:` subject. For an Issue request, the PR body ends with the machine-added `Closes #<number>` footer, included in report judgment and hashing; merging closes the unit. The backlog's four required arrays are `deferred`, `carried`, `mechanical`, `accepted_objections`. Each entry has `finding` (the original recorded object) and `source` (`run_id`, positive integer `judgment` record number, `judge`, `kind`, full `target`). Accepted objections are nonblocking dispute findings with the original finding reference. An entry may occur in multiple arrays. Retro input IDs are `<backlog-path>#<category>/<zero-based-index>` and preserve this content and provenance. The optional `review` array stores each review fix input as a finding with its full text, with source `kind: review`, fix `run_id` and `target.commit`; it refers to a run rather than a judgment. Retro validates these arrays with the canonical backlog schema; each finding requires an ID and nonempty string text. Legacy outer metadata and omission of the review array remain accepted. Consumed files are deleted in the retro proposal commit.

PR publication rejects a symbolic link at the backlog destination or any ancestor within the checkout. Backlog data is written to an exclusively created regular file inside an `os.Root` anchored at the checkout and published by rename only after writing and closing succeed. Rooted operations prevent path resolution outside the checkout if an ancestor link changes after validation, and do not write directly through an existing destination symlink or hard link. A failed backlog save stops before committing the backlog, pushing or invoking gh.

## Configuration and verification

Every base-branch consumer uses one resolver: Archon's `BASE_BRANCH`, then `worktree.baseBranch` in the repository's `.archon/config.yaml`, then origin's default from `git symbolic-ref refs/remotes/origin/HEAD`. A missing file or absent setting advances to origin; an unreadable or malformed existing file fails with its path and cause. If all are absent, the error names all three sources without guessing `main`. Starts record `base_branch` and `base_branch_source` in run records; judge targets, checks gate output and sync state retain the same fields.

`limits.passes`, `limits.fixes` and `limits.restarts` must be integers of at least 1; each omitted value defaults to 3. Invalid or unreadable configuration stops consumers instead of supplying replacement limits. Checks consider only an absent round index with no numbered history an initial run. Empty or invalid indexes, missing indexed results and an existing next-round result require history repair; results are not overwritten to reset history.

Git ref/path absence, unrelated history and an unset origin must be verified normal negative results. Execution, object and configuration failures retain their diagnostics. Sync does not silently repeat a failed `rebase --continue` or generate an empty conflict; missing or unreadable `REBASE_HEAD` during a conflict is an error.

Repository-specific behavior belongs in `.devkit/config.json` and standards. Settings are `provider`, `sessions`, `language`, `skills`, `standards`, `decisions`, `issues`, `eval`, `checks`, `skeleton_check`, `qualities`, `decision_paths` and `limits`. `issues.labels.unit` and `issues.labels.topic` default to `devkit:unit` and `devkit:topic`; each must be non-empty, omitted labels retain defaults, and labels are not created automatically. Retired `docs`, `units`, `topics` and `refine.relevance_threshold` settings are accepted but ignored and absent from effective values. Old files are not migrated or deleted, and legacy request `unit` and plan-row `ref` fields are not converted; start new Issue requests from requirements. Use `devkit config` for effective values. Defaults install no checks. Check commands decide mechanical outcomes; exit 75 retries once as an environment error, 77 skips, 0 passes, and other exits fail. Both merge-base and current configurations supply checks so removal cannot bypass verification. Only failing checks are compared with the merge-base commit in a temporary detached worktree; passing checks and environment errors are not rerun there. The current repository's `.archon/config.yaml` supplies `worktree.postCreate`, run in order with `postCreateTimeout` milliseconds per command (default 300000). Preparation failure makes comparison unavailable, and the worktree is removed. Skeleton checks must leave HEAD, the working tree and the index unchanged, including untracked files. ## Evaluate quality judgments

Run `devkit eval judge [--case <name>]... [--dir <cases folder>] [--out <folder>]
[--standards <folder>]` by hand after editing standards, routing or judge prompts. This calls the
real configured provider CLI and costs real provider calls. It measures prompts and standards;
Archon node wiring is not exercised, and checks are not run; judges get no configured checks, so they cannot leave a defect to one.

Cases live under `<eval>/judge/` (`eval` defaults to `.devkit/eval` in `.devkit/config.json`). The
kit source keeps its own cases in `eval/judge/`; init does not install those cases. Each folder has
strictly validated `case.json`, a small `base/` repository and `change.patch` applied with `git apply`.
`case.json` requires `description` and `expected`; each finding has `id`, `quality`, `file`, and a
`summary` explaining the defect and consequence. Optional `not_expected` uses the same shape for
specific false positives. IDs are unique across lists, file paths are repository-relative, and
`expected: []` represents a clean change. Optional `requirements` is verbatim request text passed
as the normal requirements goal and completion condition; there is no plan. All cases in the kit
source's `eval/judge/` include it so scope judges against an agreed request, including the clean change. Without it the case
uses review-only materials. Judges do not receive descriptions or expected findings.

The evaluator builds a base commit plus a committed patch branch and runs the actual `judge prepare`,
`changes`, `route` and `launch` command implementations. It uses the same configured path rules,
Jev and read-only CLI routing fallback as the workflow. Every launched quality gets the installed
`judge/commands/quality.md`, with `$INPUTS.quality` resolved, and the `output_format` read from its
`judge-<quality>` YAML node. If no workflow pack is installed it uses the embedded pack. Standards
come from the explicit flag, installed standards, or embedded standards, in that order. Both
providers use their existing read-only CLI adapters, including schema validation and log files.

One additional read-only CLI call per case matches every reported quality, file, line, failure
scenario and evidence against both lists. Its strict schema requires a reported ID or no match
for every expected and not-expected ID. Stdout and `<out>/result.json` contain found and missed
expectations with summaries, not-expected findings reported, launched versus expected qualities,
routing misses, and case/quality totals. Findings matching neither list are shown as `other` and
are not scored as wrong. The output path defaults to a new printed temporary folder; materials,
answers and logs remain there. Scores do not change exit status: a completed run exits 0, errors
exit non-zero. Continue using `archon workflow test` to validate wiring with stubbed AI.
