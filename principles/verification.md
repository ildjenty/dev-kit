# 事実確認の原則

## 1. 確かめていないことを、確かめたように書かない

- **適用場面**: ツール・API・バージョン・動き・原因について述べるとき。
- **原則**: 確信のない実装、外部仕様の推測、未確認の前提は、その状態を明記し、確定事項として記述しない。事実は一次情報（コード、設定、公式ドキュメント、変更履歴、実際の挙動）で確認する。ブログ、Q&A サイト、要約、記憶は一次情報ではない。以前確認した情報も変化している可能性があるため、利用前に再確認する。文書と実際の挙動が異なる場合は、実際の挙動を事実として扱い、不一致を記録する。判定を出した後には、その判定が誤っている可能性を自ら検討し、一部はツールを使って再確認する。未記録の知識を確かな前提として扱わない。記録のない調査結果は、ほかのセッションや後続のステップで使う前に再確認する。
- **違反・兆候**:
  - 確かめていない外部 API の仕様を、確定事項として実装する（存在しないメソッドやパラメータを書く）。
  - ツールや依存のバージョンを、記憶や手元の環境のバージョンで決める。
  - 「たぶんこう動く」を確かめずに、それを前提に次の作業をする。
  - エラーの原因を推測で「修正」し、直ったことを確かめない。
  - 仮の実装やスタブに印がなく、本物の実装と見分けがつかない。
  - 1回しか起きていないことを、確かな事実として扱う。
  - 仕組みが実際に確かめている範囲より広く書く（置き場所だけを制限する検査を「中身を検査している」と書く）。
  - ほかでそうしていることを、正しいことの根拠にする。
  - 判定を出したあと、反証を検討していない。
  - 「前に調べた」という記憶だけを、確かな前提として扱っている。
- **変更前・変更後**: 「このライブラリは自動でリトライする」→「このライブラリの v3.2 の文書(URL)には、リトライの記述がない。手元で試すと、失敗は1回で例外になった」
- **blocking**: 確かめていない事実を前提にした実装が、差分に含まれる。
- **根拠**: 一次情報の参照（ファイルと行、URL と該当する文、実験の手順と結果）。

## 2. 観測と推論を分けて書く

- **適用場面**: 原因や理由を書くとき。
- **原則**: 観測したことと、そこから導いた推論を分けて記述する。各主張には、同じ文の中に確信度を付記する。確信度は [規則と強制手段](../docs/rules.md#文章と記録) の値から、一次情報を直接示せるか、複数の証拠が結論を支えるか、ほかの説明も成り立つかによって選ぶ。「〜のため」「〜を直す」「〜と決めた」は、「直接」または「裏付けあり」の場合だけ使う。コードだけでは、その実装意図の根拠にはならない。質問に含まれる仮説は、候補であって結論ではない。
- **違反・兆候**:
  - 「ログに出ていないので原因は X だ」を、確かめた事実として書く。
  - 確信度の記載がない主張が並ぶ。
- **変更前・変更後**: 「キャッシュが原因でした」→「キャッシュを無効にすると再現しなくなった(直接)。キャッシュのキーに tenant が含まれていないことが原因と思われる(推論)」
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 主張ごとの確信度。

## 3. 不具合の原因は、観測で確かめる

- **適用場面**: 不具合の原因を探すとき。
- **原則**: 発生している事象を正確に記述する。エラーメッセージをすべて読み、発生時期と発生条件を記録し、再現手順を作成する。「この仮説が正しければ、この結果が観測されるはずである」という形で仮説を立て、実測値を確認する。仮説を繰り返し検証しても原因が分からない場合は、推測をやめて観測を増やす。条件を1つずつ除き、問題が発生する最小条件を特定する。原因として記載するのは、観測で確認できたことだけとする。同じ前提に基づく修正が同じ検査で2回失敗した場合は、修正を重ねず、前提を見直す。
- **違反・兆候**:
  - 同じ前提で修正を書き続けている。
- **変更前・変更後**: 「タイムアウトを延ばしたら直った」→「再現: 10件以上の注文で発生。観測: クエリが N+1 で 10件 × 300ms。原因: 注文ごとの顧客の取得。修正: JOIN に変更。再現せず」
- **blocking**: 原因を観測で確かめずに修正している。
- **根拠**: 再現手順、観測した値、修正後に再現しないこと。

## 4. 計測値を評価する前に、制限要因を特定する

- **適用場面**: 性能・速度・件数などの計測値を報告するとき。
- **原則**: 計測値を報告する前に、次の問いに答える。
  1. なぜ2倍にならないのか: プロファイルやカウンタに基づいて制限要因（limiter）を特定する。コードを読んだ推測だけでは limiter を特定したことにならない。
  2. 条件の違いは結論を変えないか: 比較条件が本番の処理を代表しているかを判断する。
  3. 限界を超えていないか: ディスク・ネットワーク・コア数。「10% の部分を消して 11% 以上速くなる」ことはない。
  4. 失敗していないか: 失敗の数と、出力の正しさ（拒否は速い、タイムアウトは遅い）。
  5. 差を効果と見なせるか: 観測した差が、ばらつきで説明できないかを判断する。
  6. 意味があるか: 全体の中での割合。
  7. 実行の記録は主張を裏付けるか: 計測した処理が、性能を述べる対象に当たるかを判断する。
  limiter を特定できない、比較条件が本番を代表しない、出力の正しさや対象処理との対応を確かめられないなら「判定できない」。
- **違反・兆候**:
  - 計測の前に「決定を変える結果」と「ノイズの範囲」を決めていない。
- **変更前・変更後**: 「2倍速くなりました」→「中央値 1.2s → 0.6s(各5回、範囲 0.55〜0.65)。limiter は DB の往復回数(10 → 1)。全体の応答の 40% がこの区間」
- **blocking**: 制限要因や比較条件を説明できず、計測値が性能の主張を裏付けていない。
- **根拠**: 7つの問いへの答え。
