# 確かめることの原則

コード・コメント・報告・文書に、事実を書くときの原則。ツール、ライブラリ、API、バージョン、実際の動き、不具合の原因、計測値が対象になる。

## 1. 確かめていないことを、確かめたように書かない

- **いつ当てるか**: ツール・API・バージョン・動き・原因について述べるとき
- **原則**: 確信のない実装、外部の仕様の推測、確かめていない前提には印を残し、確かな体で書かない。事実は一次情報(コード、設定、公式の文書、変更履歴、実際の動き)で確かめる。ブログ、Q&A サイト、要約、記憶は一次情報ではない。前に確かめたものでも、今も同じとは限らないので、使う前に確かめ直す。文書と実際の動きが食い違うときは、実際の動きを事実とし、食い違いを記録する
- **違反や兆候**:
  - 確かめていない外部 API の仕様を、確かな体で実装する(存在しないメソッドやパラメータを書く)
  - ツールや依存のバージョンを、記憶や手元の環境のバージョンで決める
  - 「たぶんこう動く」を確かめずに、それを前提に次の作業をする
  - エラーの原因を推測で「修正」し、直ったことを確かめない
  - 仮の実装やスタブに印がなく、本物の実装と見分けがつかない
  - 1回しか起きていないことを、確かな事実として扱う
  - 仕組みが実際に確かめている範囲より広く書く(置き場所だけを制限する検査を「中身を検査している」と書く)
  - ほかでそうしていることを、正しいことの根拠にする
- **before / after**: 「このライブラリは自動でリトライする」→「このライブラリの v3.2 の文書(URL)には、リトライの記述がない。手元で試すと、失敗は1回で例外になった」
- **blocking**: 確かめていない事実を前提にした実装が、差分に含まれる
- **根拠**: 一次情報の参照(ファイルと行、URL と該当する文、実験の手順と結果)

## 2. 観測と推論を分けて書く

- **いつ当てるか**: 原因や理由を書くとき
- **原則**: 見たこと(観測)と、そこから考えたこと(推論)を分けて書く。主張ごとに、確信度を同じ文の中に付ける。段階は次の5つ
  - **直接**: 一次情報をそのまま引用できる(作者の文、実行の出力)
  - **裏付けあり**: 複数の間接的な証拠が同じ方向を向いている
  - **推論**: 解釈。「〜と思われる」「おそらく」
  - **推測**: ほかの説明も同じくらいありうる
  - **不明**: 何をどう探して見つからなかったかを書く
  「〜のため」「〜を直す」「〜と決めた」は、直接か裏付けありのときだけ使う。「明らかに」「当然」「単に」は使わない。コードは、それ自体の意図の証拠にはならない。問いに埋め込まれた仮説は、候補であって結論ではない
- **違反や兆候**:
  - 「ログに出ていないので原因は X だ」を、確かめた事実として書く
  - 確信度の印がない主張が並ぶ
- **before / after**: 「キャッシュが原因でした」→「キャッシュを無効にすると再現しなくなった(直接)。キャッシュのキーに tenant が含まれていないことが原因と思われる(推論)」
- **blocking**: なし(手がかりとして記録する)
- **根拠**: 主張ごとの確信度

## 3. 不具合の原因は、観測で確かめる

- **いつ当てるか**: 不具合の原因を探すとき
- **原則**: 何が起きているかを正確に書く。エラーのメッセージは全部読む。いつから、どういう条件で起きるかを書く。再現する手順を作る。「こうだとすれば、これが見えるはずだ」という形で仮説を立て、実際の値を確かめる。仮説を2〜3回試しても分からなければ、推測をやめて観測を増やす。条件を1つずつ外し、問題が起きる最小の条件を見つける。原因として書くのは、観測で確かめたことだけにする。同じ前提の修正が2回同じ検査で落ちたら、修正を重ねず前提を疑う
- **違反や兆候**:
  - 再現の手順がないまま直している
  - 仮説を試した結果を記録せずに、次の仮説に移る
  - 3つ目の修正を、同じ前提で書いている
- **before / after**: 「タイムアウトを延ばしたら直った」→「再現: 10件以上の注文で発生。観測: クエリが N+1 で 10件 × 300ms。原因: 注文ごとの顧客の取得。修正: JOIN に変更。再現せず」
- **blocking**: 原因を観測で確かめずに修正している
- **根拠**: 再現の手順、観測した値、修正後に再現しないこと

## 4. 数字を信じる前に、何がその数字を決めているかを言う

- **いつ当てるか**: 性能・速度・件数などの計測値を報告するとき
- **原則**: 計測値を報告する前に、7つの問いに答える
  1. なぜ2倍にならないのか: 何が制限しているか(limiter)を、プロファイルやカウンタから名指しする。コードを読んだ推測は limiter ではない
  2. 条件はそろっているか: 比較の両側を、本番と同じ build・フラグ・キャッシュ・データで測ったか
  3. 限界を超えていないか: ディスク・ネットワーク・コア数。「10% の部分を消して 11% 以上速くなる」ことはない
  4. 失敗していないか: 失敗の数と、出力の正しさ(拒否は速い、タイムアウトは遅い)
  5. 再現するか: 各側5回以上、交互に(A, B, A, B)、中央値と範囲
  6. 意味があるか: 全体の中での割合
  7. 本当に実行されたか: 計測した区間で仕事が実際に走ったか(遅延評価、await されていない Promise)
  結論は「速い / 遅い / 差がない / 判定できない」のどれか。limiter を言えない、条件がそろっていない、4 と 7 を確かめられないなら「判定できない」
- **違反や兆候**:
  - 1回の計測で「速くなった」と書く
  - 実行回数、ばらつき、limiter のない数字を報告する
  - 計測の前に「決定を変える結果」と「ノイズの範囲」を決めていない
- **before / after**: 「2倍速くなりました」→「中央値 1.2s → 0.6s(各5回、範囲 0.55〜0.65)。limiter は DB の往復回数(10 → 1)。全体の応答の 40% がこの区間」
- **blocking**: 性能の主張に、実行回数と limiter がない
- **根拠**: 7つの問いへの答え

## 5. 調べた結果は、使う前に外に書く

- **いつ当てるか**: 調査の結果を、ほかのセッションや後のステップで使うとき
- **原則**: ほかのセッションや後のステップで使う結果は、使う前に ledger か Issue か PR に書く。ほかのセッションでは、書かれていない結果を無いものとして扱い、確かめ直す
- **違反や兆候**:
  - 「前に調べた」とだけ言い、どこに書いたかを示せない
- **before / after**: 「前のセッションで API の仕様を確かめた」→「ledger の決定 #12 に、仕様の URL と確かめた日を書いてある」
- **blocking**: なし
- **根拠**: 書いた場所
