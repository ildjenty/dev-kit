# 設計の進め方

## 1. 不可逆な決定を先に行う

- **適用場面**: 設計の最初に、何から決めるかを選ぶとき。
- **原則**: 決定には、後から変更できるものと、元に戻せない不可逆なものがある。不可逆な決定を先に特定し、決定する。対象は、DB スキーマ、識別子、公開する契約の型、イベントの内容、外部に公開するもの、データの保持・削除方針、ファイルフォーマットである。後から変更できるものは、実装を進めながら決めてよい。内部の契約は可逆であり、作りながら決めてよい。今決めるか、後で決めるかも、設計上の判断として明示する。
- **違反・兆候**:
  - 不可逆な決定に当たるものが「後で直せる」扱いになっている。
  - 後で差し替えられるもの（使用するツール、表示、しきい値）を最初に議論している。
  - どちらでもよい決定に時間を使い、不可逆な決定が誰にも決められないまま進んでいる。
- **変更前・変更後**: 「まずボタンの色を決める。テーブルの列は実装しながら決める」→「まず料金テーブルの列と識別子を決める。色は後で変えられる」
- **blocking**: 不可逆な決定が「後で直せる」扱いになっている。
- **根拠**: 不可逆な決定の一覧と、それぞれを誰がいつ決めたか。

## 2. 2つ目の実例が出るまで抽象化しない

- **適用場面**: 差し替えの仕組み、プラグイン、汎用化を作ろうとするとき。
- **原則**: 変更される部分と変更されない部分の境界を見極め、その位置とインターフェースだけを定める。差し替えやプラグインの仕組み、汎用化は、2つ目の実例が現れるまで実装しない。「将来必要になりそう」は実装の理由にならない。必要になった時点で実装できる構造を保てばよい。早すぎる抽象化より、類似した記述が複数あるほうがよい。
- **違反・兆候**:
  - 実装が1つしかない interface や抽象基底クラスがたくさんある。
  - 使われていないオプション引数・設定項目・ジェネリクスがある。
  - 「将来の拡張のため」のイベントフックやプラグインの仕組みがある。
  - 汎用にしたせいで、唯一の使い道にとって不自然なインターフェースになっている。
  - （設計案で）2つ目の実例がないまま、差し替えやプラグインの仕組みを作る計画になっている。
- **変更前・変更後**: `interface Notifier` + `EmailNotifier` のみ → `sendEmail()` の関数1つ。2つ目(Slack)が要るときに interface を切る
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 抽象ごとに、2つ目の実例があること。

## 3. まず1機能を画面から DB まで通す

- **適用場面**: 作る順番を決めるとき。
- **原則**: 画面から DB まで、全レイヤーを通る1つの機能を先に動かし、構造上の誤りを早期に発見する。レイヤーごとに作り込むと、誤りは最後の結合時にまとめて表面化する。最初に動作させた機能を、その後の実装の見本とする。複数のステップで使う型やモジュールは、最初のステップで作る場合も、1つの機能を全レイヤーで動かす形で作る。
- **違反・兆候**:
  - 動くものがないまま、複数のレイヤー・複数の機能を同時に作っている。
  - 結合を最後にまとめて行う計画になっている。
  - 使う側から一度も呼ばれていないレイヤーを「完成した」としている。
  - （設計案で）最初のステップがレイヤー単位であり、全レイヤーを通る1つの機能になっていない。
- **変更前・変更後**: 「ステップ1: 全テーブル、ステップ2: 全 API、ステップ3: 全画面」→「ステップ1: プラン一覧を画面から DB まで通す。ステップ2: プラン追加を通す」
- **blocking**: なし（手順の観点で見る）。
- **根拠**: 最初のステップが、画面から DB まで通る機能であること。

## 4. 移行は一気に終え、互換レイヤーを残さない

- **適用場面**: 書き換え・移行・API の置き換えを計画するとき。
- **原則**: 計画的な書き換えや移行では、中間状態の維持よりも最終形を優先する。破壊的な変更を許容するスコープを明示し、各段階の終了時に全体を検証する。新しい API の導入、呼び出し元の移行、旧 API の削除を同じ変更で行い、互換レイヤーを残さない。この原則は、外部利用者がおらず、破壊的な変更を吸収できる場合に適用する。外部の利用者がいる公開 API では、追加 → デプロイ → 移行 → 削除を別のリリースに分ける（expand → contract）。
- **違反・兆候**:
  - 「とりあえず互換のために」残した層が、移行後も消えない。
  - 新旧の API が両方使われたまま、どちらが正本であるか分からない。
  - 捨てる前提のコードに、本番の品質を求めている。
  - （設計案で）外部利用者がいない移行で、呼び出し元の移行と旧 API の削除が別の変更に分かれ、互換レイヤーを残す計画になっている。
- **変更前・変更後**: 「新 API を足し、旧 API は deprecated にして残す」→「新 API を足し、呼び出し元を全部移し、旧 API を同じ差分で消す」
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 移行の後に、旧 API の参照が0件であること。

## 5. 追加する前に削除する

- **適用場面**: 機能や仕組みを足そうとするとき。
- **原則**: 追加より先に削除する。デッドコード、重複した検証、スタブ、未使用のオプションを先に削除する。推測に基づくガードや、「エレガントな」ボイラープレートを追加しない。必要最小限の変更を選ぶ。
- **違反・兆候**:
  - 新しい仕組みを足した差分に、消したものがない。
  - 使われない分岐・オプションが残ったまま、似た仕組みが隣に足される。
  - （設計案で）既存の仕組みを消す案が検討されていない。
- **変更前・変更後**: 「設定の読み込みに新しい層を足す」→「古い読み込みの2経路を1つに消してから、要るなら足す」
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 差分で消したものの一覧。

## 6. 性能・観測性・ロールアウト・脅威モデルも設計で決める

- **適用場面**: ステージ1〜2で設計するとき。
- **原則**: 性能の予算、観測性（どのログと指標を設計に含めるか）、ロールアウト（フラグ、段階的な適用）、脅威モデル（誰が攻撃者で、何を守るか）を、構造と同じステージで決めるか、決めないことを明示する。
- **違反・兆候**:
  - 「性能は後で」「ログは実装時に」「フラグは要るときに」としている。
- **変更前・変更後**: 「性能は後で、ログは実装時に決める」→「性能の予算は応答時間の p95 が200ms以下。ログと指標は失敗理由とエラー率。ロールアウトはフラグで段階的に適用する。脅威モデルは外部の利用者による他テナントのデータへの不正アクセスを対象とする」
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 各軸について、決めた内容か、決めない理由。

## 7. 既存の流儀に揃える

- **適用場面**: 既存のリポジトリに新しいコードや設計を足すとき。
- **原則**: 書く前に、同じ種類の処理がこのリポジトリでどう書かれているか（命名、エラー処理の形、レイヤーの切り方、既存のユーティリティと抽象、テストの書き方、使っているライブラリ）を探し、それに揃える。既存の流儀に問題があって変えるなら、新しい流儀を隣に置かず、既存を移行する（原則4・5）。揃えた既存の箇所、または揃えなかった理由を成果物に示す。
- **違反・兆候**:
  - 同じ種類の処理が、2つの書き方で存在する。
  - 既存のユーティリティや抽象があるのに、同じ役割の新しいヘルパーを足している。
  - エラー処理やログの形式が、周囲のコードと違う。
  - 既存のライブラリと同じ役割の新しいライブラリを、並行して導入している。
  - （設計案で）揃える既存の箇所も、揃えない理由も示されていない。
- **変更前・変更後**: 「新しい API のエラーを独自の例外クラスで返した」→「既存の API が使っている `Result` 型の形を調べ、同じ形で返した。例外クラスは足さない」
- **blocking**: 既存の同種の処理と違う流儀で書かれていて、理由が示されていない。
- **根拠**: 揃えた既存の箇所への参照。
