# テストの原則

言語やフレームワークに依存しない、テストを書くときの原則。

テストは仕様を確かめる。実装をなぞるだけのテストは書かない。テストが書きにくいときは、テストの書き方で回避する前に、設計に問題がないかを疑う。

## 1. テストを書く対象を絞る

- **いつ当てるか**: テストを書くかどうかを決めるとき
- **原則**: テストを書くのは、対象のコードが本番のエントリポイントから到達でき、次のどれかに当たるときだけである。どの誤りも検出しないテストは、仕様を変えるたびに直す手間を増やし、誤りを検出するテストを読みにくくする
  - セキュリティ上の処理: 認可、テナントの分離、fail-closed、冪等性、トランザクション境界、信頼境界での入力の検証。宣言(RLS のポリシー、GRANT、制約)で書いたものと、それが前提にしている DB やライブラリの保証も含む
  - 消すと例外にならずに誤った結果を返すロジック(silent failure)。起動時の例外・型エラー・毎回の実行の失敗で必ず検出されるものは、テストしない
  - 外部仕様との契約: 外部のサービスが決めるヘッダー、ステータスコードなど。モックでは確かめたことにならないので、実際のサービスかエミュレータで確かめる
  - 網羅性: 「すべてのテーブルに RLS がある」のように、後から足したものに付け忘れると silent failure になる規則
  - 陽性対照: 「拒む」「見えない」を確かめるテストが、条件の書き間違いなどで対象の処理を実行しないまま通ることを防ぐ、最小限の「許す」「見える」のテスト
- **違反や兆候**:
  - セキュリティに関わらない宣言(列の型、NOT NULL、CHECK、既定値、定数のマップ)を、そのまま言い換えて確かめる
  - ライブラリ・フレームワーク・DB 自体の動きを確かめる
  - 値を受け渡すだけの処理や、if 文を、そのまま言い換えて確かめる
  - 本番から到達しないコード・捨てる前提の試作・説明のための例にテストを書く
  - テストのヘルパーそのものを確かめる
  - 「拒む」テストを消して、同じ対象の「許す」テストが残っていない
- **before / after**: `expect(schema.name.nullable).toBe(false)` → 消す。代わりに「他テナントの行が読めない」を確かめる
- **blocking**: セキュリティ上の処理にテストがない
- **根拠**: テストごとに、上の5種類のどれに当たるか

## 2. 同じ振る舞いは、最も下のレイヤーで1回だけ確かめる

- **いつ当てるか**: どのレイヤーにテストを置くかを決めるとき
- **原則**: 同じ振る舞いは、それを確かめられる最も下のレイヤーで1回だけテストする。上のレイヤーのテストでは、そのレイヤーが足す処理(ルートの登録、値の変換)だけを確かめる。型と実行時の両方で検証しているものは、強いほうだけをテストする
- **違反や兆候**:
  - 同じ振る舞いを、複数のレイヤーや複数の SQL のコマンドで繰り返し確かめる
  - 大量のスナップショットテストで、何が仕様なのかが分からない
- **before / after**: サービス層とハンドラ層の両方で「金額が負なら拒む」→ サービス層で1回。ハンドラ層は「400 を返す」だけ
- **blocking**: なし(手がかりとして記録する)
- **根拠**: 振る舞いごとに、確かめているレイヤーが1つであること

## 3. 期待値は完了条件から決め、実装から写さない

- **いつ当てるか**: テストの期待値を書くとき
- **原則**: 期待値は、実装からではなく完了条件(仕様)から決める。同じ理解でコードとテストを書くと、同じ誤解で両方が一致し、誤りが見つからない。実装の前にテストが一度失敗することを確かめる。実装の前に失敗を確かめられなかったテストと、セキュリティ上の処理のテストは、テストが確かめている箇所を1か所だけ壊し、テストが失敗することを確かめる(壊し方: 条件を反対にする、チェックを1つ消す、失敗の代わりに既定値を返す。1か所変えて1回実行し、すぐ戻す)。regression test は、修正前のコードで失敗するのを見てから信じる
- **違反や兆候**:
  - 関数の出力をそのまま期待値に写す
  - テストを通すために、期待値を実装の出力に合わせて書き換える
  - 実装の前に、テストが失敗するのを一度も確かめていない
  - 「0件」「拒まれる」「変わらない」を確かめるテストが、対象のデータが無いときにも通る
- **before / after**: `expect(calc(input)).toEqual(calc(input))` に等しい書き方 → 完了条件から `expect(calc({ qty: 3, unit: 100 })).toBe(300)`
- **blocking**: セキュリティ上の処理のテストで、壊して失敗することを確かめていない
- **根拠**: 実装前の失敗、または壊したときの失敗の記録

## 4. 振る舞いを確かめ、実装をなぞらない

- **いつ当てるか**: 何を assert するかを決めるとき
- **原則**: 利用者が観察できることを assert する。内部の関数を呼んだ回数や内部の状態には頼らない。テストが振る舞いのテストかどうかは、2つの仮想の変更で判定する。(a) 振る舞いを壊す変更をしたら、テストは落ちるか。(b) 内部だけを変える変更(リファクタリング)をしたら、テストは通るか。両方が yes なら振る舞いのテストである。モックした外部サービスの要求の内容は振る舞いであり、内部のヘルパーの呼び出しは実装である
- **違反や兆候**:
  - モックの戻り値をそのまま assert する(対象ではなくモックを確かめている)
  - 呼び出しの回数や順序だけを assert し、結果を確かめていない
  - 1つのテストが、2つ以上の理由で失敗しうる
  - テストの名前から、何を保証しているかが読めない
- **before / after**: `expect(repo.save).toHaveBeenCalledTimes(1)` → `expect(await repo.findById(id)).toEqual(expected)`
- **blocking**: なし(手がかりとして記録する)
- **根拠**: 2つの仮想の変更への答え

## 5. 正常系だけで終えない

- **いつ当てるか**: テストを書くと決めた振る舞いの、ケースを決めるとき
- **原則**: テストを書くと決めた振る舞いでは、正常系に加えて、境界の値と失敗する場合を含める。入力を同値クラスに分け、クラスごとの代表値と境界値を挙げる。空・0・1件・多数・null や undefined の場合を含める。1つの振る舞いにつき1つのテスト。名前は「どういうときに、何が起きるか」にする。準備・実行・確認を分けて書く
- **違反や兆候**:
  - 正常系1本だけで「テスト済み」とする
- **before / after**: `it("works")` 1本 → `it("returns 0 for empty cart")`, `it("rejects negative quantity")`, `it("caps at 100 items")`
- **blocking**: なし(手がかりとして記録する)
- **根拠**: 同値クラスと境界の一覧

## 6. 結果が実行のたびに変わらないようにする

- **いつ当てるか**: 時刻・乱数・順序・外部との通信・DB に依存するテストを書くとき
- **原則**: 時刻・乱数・実行の順序・外部との通信・ほかのテストが残した DB の行で、テストの結果が変わらないようにする。テストから固定または差し替えられるようにする。たまに失敗するテストは、失敗する条件を見つけて原因を直す。もう一度実行して通っても、直ったことにはならない
- **違反や兆候**:
  - 時刻・乱数・順序・外部との通信・ほかのテストが残した DB の行で、結果が変わる
  - たまに失敗するテストを、もう一度実行して通ったので直ったとする
- **before / after**: `new Date()` を直接使う → `clock.now()` を注入し、テストで固定する
- **blocking**: なし(手がかりとして記録する)
- **根拠**: 依存の固定の方法

## 7. 既存のコードを変える前に、今の振る舞いを残す

- **いつ当てるか**: 既存のコードを変えるとき
- **原則**: 触る範囲の今の振る舞いのうち、原則1で書くと決まるものを、テストに書いて残す。今ある誤りも、そのまま残す。このテストは実装の前に失敗を確かめられないので、原則3の「壊して確かめる」で確かめる。変えた後、残したテストの結果が、意図した所だけ変わったことを確かめる
- **違反や兆候**:
  - テストを書く対象に当たる今の動きを、テストに残さずに、既存のコードを変える
- **before / after**: 「リファクタリングしてから、動作を目視で確認した」→「先に特性テストを書き、リファクタリングの前後で同じ結果になることを確かめた」
- **blocking**: セキュリティ上の処理を含むコードを、今の振る舞いを残さずに変えている
- **根拠**: 変更の前に書いたテストと、変更の後の結果

## 8. テストが失敗したら、テストを書き換えない

- **いつ当てるか**: テストが失敗したとき
- **原則**: 失敗した理由を読み、実装の誤りか、テストの誤りか、前提が変わったのかを見分ける。実装が誤っているなら実装を直す。テストが誤っている、または前提が変わったと思うなら、テストを書き換えず、理由を添えて人に判断を求める。期待値の書き換え、テストの省略、assert の削除は、仕様を黙って変えることになる
- **違反や兆候**:
  - 落ちたテストの期待値を、今の出力に合わせて直している
  - `skip` や `only` が残っている
- **before / after**: 「期待値を 300 から 330 に直した」→「税の扱いが変わって 330 になった。仕様の変更かどうかを確かめてほしい」
- **blocking**: 期待値・assert を、人の判断なしに書き換えている
- **根拠**: 失敗の理由の分類と、誰が判断したか

## 9. 安く書けないテストは書かない

- **いつ当てるか**: 失敗するテストを先に書くか(TDD)を決めるとき
- **原則**: 失敗するテストを先に書いて直す進め方は、テストの経路が安く・明確にあるときだけ使う。経路が不明確、高価、または対象が原則1に当たらないときは、テストを書かずに進め、動かして確かめる(design.md の観点「動かして確かめる」)。悪いテストより、テストがないほうがよい
- **違反や兆候**:
  - テストのために本番コードに穴(テスト用の分岐、公開)を開けている
  - テストの準備が、テスト本体より長い
- **before / after**: 「画面の見た目のテストを DOM のスナップショットで書いた」→「スクリーンショットを撮って見る」
- **blocking**: なし
- **根拠**: 書かなかった理由
