# テストの原則

テストでは仕様を検証する。実装をそのまま再現するだけのテストは書かない。テストを書きにくい場合は、書き方で回避する前に、設計に問題がないかを検討する。

## 1. テストを書く対象を絞る

- **適用場面**: テストを書くかどうかを決めるとき。
- **原則**: テストを作成するのは、対象コードが本番のエントリポイントから到達可能で、次のいずれかに該当する場合だけである。誤りを検出しないテストは、仕様変更時の修正コストを増やし、誤りを検出するテストの可読性を下げる。
  - セキュリティ上の処理: 認可、テナント分離、fail-closed、冪等性、トランザクション境界、信頼境界での入力検証。宣言（RLS ポリシー、GRANT、制約）で記述したものと、その前提となる DB やライブラリの保証も含む。
  - 削除すると例外を発生させずに誤った結果を返すロジック（silent failure）。起動時の例外・型エラー・実行時に必ず発生する失敗で検出できるものは、テストしない。
  - 外部仕様との契約: 外部サービスが定めるヘッダー、ステータスコードなど。モックでは検証したことにならないため、実際のサービスかエミュレータで確認する。
  - 網羅性: 「すべてのテーブルに RLS がある」のように、追加時の適用漏れが silent failure につながる規則。
  - 陽性対照: 「拒否される」「表示されない」を確認するテストが、条件の記述ミスなどによって対象の処理を実行せずに成功することを防ぐ、最小限の「許可される」「表示される」のテスト。
- **違反・兆候**:
  - セキュリティに関わらない宣言（列の型、NOT NULL、CHECK、既定値、定数のマップ）を、そのまま言い換えて確かめる。
  - ライブラリ・フレームワーク・DB 自体の動きを確かめる（セキュリティの前提となる保証（原則1の対象）を除く）。
  - 値を受け渡すだけの処理や、if 文を、そのまま言い換えて確かめる。
  - 本番から到達しないコード・捨てる前提の試作・説明のための例にテストを書く。
  - テストのヘルパーそのものを確かめる。
  - 「拒否される」テストを削除した時点で、同じ対象の「許可される」テストが残っていない。
- **変更前・変更後**: `expect(schema.name.nullable).toBe(false)` → 消す。代わりに「他テナントの行が読めない」を確かめる
- **blocking**: セキュリティ上の処理にテストがない。
- **根拠**: テストごとに、上の5種類のどれに当たるか。

## 2. 同じ振る舞いは、最も下位レイヤーで1回だけ確かめる

- **適用場面**: どのレイヤーにテストを置くかを決めるとき。
- **原則**: 同じ振る舞いは、検証できる最下位のレイヤーで1回だけテストする。上位レイヤーでは、そのレイヤーが追加する処理（ルート登録、値の変換）だけを検証する。型と実行時の両方で検証している場合は、保証の強いほうだけをテストする。
- **違反・兆候**:
  - 同じ振る舞いを、複数のレイヤーや複数の SQL のコマンドで繰り返し確かめる。
  - 大量のスナップショットテストで、何が仕様なのかが分からない。
- **変更前・変更後**: サービス層とハンドラ層の両方で「金額が負なら拒む」→ サービス層で1回。ハンドラ層は「400 を返す」だけ
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 振る舞いごとに、確かめているレイヤーが1つであること。

## 3. 期待値は完了条件から決め、実装から写さない

- **適用場面**: テストの期待値を書くとき。
- **原則**: 期待値は実装から転記せず、完了条件（仕様）から定める。同じ理解に基づいてコードとテストを作成すると、同じ誤解によって両者が一致し、誤りを検出できない。
- **違反・兆候**:
  - 関数の出力をそのまま期待値に写す。
  - テストを通すために、期待値を実装の出力に合わせて書き換える。
- **変更前・変更後**: `expect(calc(input)).toEqual(calc(input))` に等しい書き方 → 完了条件から `expect(calc({ qty: 3, unit: 100 })).toBe(300)`
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 期待値の出どころ（完了条件のどの記述か）。

## 4. テストが落ちることと、落ちないことを確かめる

- **適用場面**: テストが本当に何かを確かめているかを検証するとき。
- **原則**: テストが本当に何かを確かめているかを、2つの実験で証明する。
  - 落ちること: 実装前にテストが一度失敗することを確認する。実装前に失敗を確認できなかったテストと、セキュリティ上の処理のテストでは、検証対象を1か所だけ意図的に壊し、テストが失敗することを確認する（条件を反転する、チェックを1つ削除する、失敗の代わりに既定値を返す。1か所を変更して1回実行し、直ちに元に戻す）。回帰テストは、修正前のコードで失敗することを確認してから信頼する。
  - 落ちないこと: 振る舞いを変えずに内部だけを組み替えても（関数の分割、名前の変更、処理の順序の入れ替え）、テストが通ることを確認する。内部の組み替えだけで落ちるテストは、振る舞いではなく実装に縛られている証拠であり、原則5（振る舞いを確かめ、実装をなぞらない）に違反している。
- **違反・兆候**:
  - 実装の前に、テストが失敗するのを一度も確認していない。
  - 「0件」「拒否される」「変わらない」を確認するテストが、対象のデータがない場合にも通る。
  - 内部を組み替えただけでテストが落ちる。
  - 壊して確かめた記録がない。
- **変更前・変更後**: 「テストを書いて実装し、通ったので完了とした」→「実装前にテストが落ちることを見た。実装後、関数を2つに分けてもテストが通ることを見た」
- **blocking**: セキュリティ上の処理のテストで、壊して失敗することを確かめていない。
- **根拠**: 実装前の失敗、または壊したときの失敗の記録。内部を組み替えたときに通った記録。

## 5. 振る舞いを確かめ、実装をなぞらない

- **適用場面**: 何を assert するかを決めるとき。
- **原則**: 利用者が観察できる結果を assert する。内部関数の呼び出し回数や内部状態に依存しない。振る舞いを検証するテストかどうかは、2つの仮想的な変更で判定する。（a）振る舞いを壊す変更によってテストが失敗するか。（b）内部だけを変更するリファクタリング後もテストが成功するか。両方が yes であれば、振る舞いを検証するテストである。モックした外部サービスへのリクエスト内容は振る舞いに含まれ、内部ヘルパーの呼び出しは実装に含まれる。実際に確かめる手順は原則4に従う。
- **違反・兆候**:
  - モックの戻り値をそのまま assert する（対象ではなくモックを確かめている）。
  - 呼び出しの回数や順序だけを assert し、結果を確かめていない。
  - 1つのテストが、2つ以上の理由で失敗しうる。
  - テストの名前から、何を保証しているかが読めない。
- **変更前・変更後**: `expect(repo.save).toHaveBeenCalledTimes(1)` → `expect(await repo.findById(id)).toEqual(expected)`
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 2つの仮想の変更への答え。

## 6. 正常系だけで終えない

- **適用場面**: テストを書くと決めた振る舞いの、ケースを決めるとき。
- **原則**: テスト対象とした振る舞いでは、正常系に加えて境界値と異常系を含める。入力を同値クラスに分け、各クラスの代表値と境界値を挙げる。空・0・1件・多数・null・undefined の場合を含める。1つの振る舞いにつき1つのテストを作成し、名前は「どのような条件で、何が起きるか」を表すものとする。準備・実行・確認を分けて記述する。
- **違反・兆候**:
  - 正常系1本だけで「テスト済み」とする。
- **変更前・変更後**: `it("works")` 1本 → `it("returns 0 for empty cart")`, `it("rejects negative quantity")`, `it("caps at 100 items")`
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 同値クラスと境界の一覧。

## 7. 結果が実行のたびに変わらないようにする

- **適用場面**: 時刻・乱数・順序・外部との通信・DB に依存するテストを書くとき。
- **原則**: 時刻・乱数・実行順序・外部通信・ほかのテストが残した DB の行によって、テスト結果が変わらないようにする。これらの依存は、テストから固定または差し替えられるようにする。不定期に失敗するテストは、失敗条件を特定して原因を修正する。再実行して成功しても、修正できたことにはならない。
- **違反・兆候**:
  - 時刻・乱数・順序・外部との通信・ほかのテストが残した DB の行で、結果が変わる。
  - たまに失敗するテストを、もう一度実行して通ったので直ったとする。
- **変更前・変更後**: `new Date()` を直接使う → `clock.now()` を注入し、テストで固定する
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 依存の固定の方法。

## 8. 既存コードを変更する前に、現在の振る舞いを記録する

- **適用場面**: 既存のコードを変えるとき。
- **原則**: 変更対象の現在の振る舞いのうち、原則1でテスト対象となるものをテストに記録する。既存の誤りも、そのまま記録する。このテストは実装前の失敗を確認できないため、原則4に従って検証する。変更後は、テスト結果が意図した箇所だけ変わっていることを確認する。
- **違反・兆候**:
  - テストを書く対象に当たる今の動きを、テストに残さずに、既存のコードを変える。
- **変更前・変更後**: 「リファクタリングしてから、動作を目視で確認した」→「先に特性テストを書き、リファクタリングの前後で同じ結果になることを確かめた」
- **blocking**: セキュリティ上の処理を含むコードを、今の振る舞いを残さずに変えている。
- **根拠**: 変更の前に書いたテストと、変更の後の結果。

## 9. テストが失敗したら、テストを書き換えない

- **適用場面**: テストが失敗したとき。
- **原則**: 失敗理由を確認し、実装の誤り、テストの誤り、前提の変化のどれに該当するかを判断する。実装が誤っている場合は実装を修正する。テストが誤っている、または前提が変わったと考えられる場合は、テストを変更せず、理由を添えて人に判断を求める。期待値の変更、テストの省略、assert の削除は、仕様の暗黙的な変更になる。テストの期待値や assert の書き換えは、router の「設計文書との食い違い」に当たり、作業を停止して確認する対象である。
- **違反・兆候**:
  - 落ちたテストの期待値を、今の出力に合わせて直している。
  - `skip` や `only` が残っている。
- **変更前・変更後**: 「期待値を 300 から 330 に直した」→「税の扱いが変わって 330 になった。仕様の変更かどうかを確かめてほしい」
- **blocking**: 期待値・assert を、人の判断なしに書き換えている。
- **根拠**: 失敗の理由の分類と、誰が判断したか。

## 10. 作成コストの高いテストは書かない

- **適用場面**: 失敗するテストを先に書くか（TDD）を決めるとき。
- **原則**: この原則は、新しい振る舞いにテストを先に書くかを判断するものである。既存コードを変更する前に現在の振る舞いを記録すること（原則8）は、省略の対象外である。失敗するテストを先に作成してから実装する進め方は、テストを実行する経路が明確で、低コストに用意できる場合だけ採用する。経路が不明確、コストが高い、または対象が原則1に該当しない場合は、テストを書かずに進め、動作検証を行う（[../docs/checks.md](../docs/checks.md#動作検証) の観点「動作検証」）。ただし、原則1のセキュリティ上の処理は例外であり、作成コストが高くてもテストを書く。不適切なテストを追加するより、テストを作成しないほうがよい。
- **違反・兆候**:
  - テストのために、本番コードにテスト用の分岐や公開箇所を追加している。
  - テストのセットアップが、テスト本体より長い。
- **変更前・変更後**: 「画面の見た目のテストを DOM のスナップショットで書いた」→「スクリーンショットを撮って見る」
- **blocking**: なし。
- **根拠**: 書かなかった理由。
