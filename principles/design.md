# 構造を決めるときの原則

目標は、名前・配置・依存関係を見れば、それぞれが何のためにあるかが分かる構造にすることである。そうなっていれば、個々のモジュールの実装は単純になる。実装が込み入る、条件分岐が増える、説明のコメントが要る、テストが書きにくい、と感じたら、書き方ではなく構造が間違っている可能性が高い。その場合は構造に戻って直す。

各原則の「違反・兆候」には、実装後のコードから判定できるものと、設計案の文章から判定できるものの両方を含める。設計案の check（[../docs/checks.md](../docs/checks.md#構造) の観点「構造」）では後者を使う。

## 1. 名前と配置で役割が分かるようにする

- **適用場面**: モジュール・ファイル・フォルダを新しく作るとき、どこに置くかを決めるとき。
- **原則**: 何をするモジュールで、なぜその場所にあるのかが、名前・配置・依存関係から分かる構造にする。説明がなければ理解できない場合は、構造に問題がある。モジュールの責務を1文で説明できない場合は、分割するか削除する。配置は、リポジトリの「配置ガイド」（各パッケージの README または CLAUDE.md に記載した、配置するもの・配置しないもの）に従う。次の開発担当者は、開いたファイルしか参照しないエージェントであるという前提で確認する。
- **違反・兆候**:
  - モジュールの説明が「〜と〜と〜をする」と並ぶ（役割が複数ある）。
  - どこに置けばよいか決められないコードがある。置きやすい場所に置かれている。
  - 構造を説明するための文書が増え続ける。
  - （設計案で）新しいモジュールの配置を、責務から正当化する一文が書けない。
- **変更前・変更後**: `utils/helpers.ts` に `formatPrice` と `retryFetch` → `pricing/format.ts` と `http/retry.ts`
- **blocking**: 配置を責務から正当化できない。
- **根拠**: 新しく作ったモジュールごとに、役割の一文と、配置の理由。

## 2. 不可逆な決定を先に行う

- **適用場面**: 設計の最初に、何から決めるかを選ぶとき。
- **原則**: 決定には、後から変更できるものと、元に戻せない不可逆なものがある。不可逆な決定を先に特定し、決定する。対象は、DB スキーマ、識別子、公開する契約の型、イベントの内容、外部に公開するもの、データの保持・削除方針、ファイルフォーマットである。後から変更できるものは、実装を進めながら決めてよい。内部の契約は可逆であり、作りながら決めてよい。今決めるか、後で決めるかも、設計上の判断として明示する。
- **違反・兆候**:
  - 不可逆な決定に当たるものが「後で直せる」扱いになっている。
  - 後で差し替えられるもの（使用するツール、表示、しきい値）を最初に議論している。
  - どちらでもよい決定に時間を使い、不可逆な決定が誰にも決められないまま進んでいる。
  - （設計案で）不可逆な決定の一覧がない。
- **変更前・変更後**: 「まずボタンの色を決める。テーブルの列は実装しながら決める」→「まず料金テーブルの列と識別子を決める。色は後で変えられる」
- **blocking**: 不可逆な決定が「後で直せる」扱いになっている。
- **根拠**: 不可逆な決定の一覧と、それぞれを誰がいつ決めたか。

## 3. 外部入力は境界で一度だけ検証する

- **適用場面**: 外部（利用者の入力、API、ファイル、環境変数）から値を受け取る処理を設計するとき。
- **原則**: 外部と内部、信頼できないデータと信頼できるデータの境界を先に定める。検証・変換・隔離は境界で一度だけ行い、内部では検証済みとして扱う。境界で内部の型に変換し、それより内側では型の保証に依存する。同じチェックが2か所に現れた場合は、チェックを追加せず、境界の位置を見直す。
- **違反・兆候**:
  - 多くの関数の冒頭に、同じ null チェック・型チェックがある。
  - 欠損する可能性のある値が、内部処理の深い階層まで渡されている。
  - 検証エラーの扱いが場所ごとに違う。
  - 外部入力を、外部のコマンド・パス・SQL にそのまま組み込んでいる。
  - 通信の型（リクエスト・レスポンス）を内側で再利用している。
  - （設計案で）外部入力を検証する境界と、内部の型に変換する箇所が書かれていない。
- **変更前・変更後**: `handler(req) { if (!req.body.id) ...; service(req.body) }` と `service(body) { if (!body.id) ... }` → `handler` で `parsePlanRequest(req.body): PlanRequest` に変換し、`service(plan: PlanRequest)` は検証しない
- **blocking**: 外部入力が検証なしにコマンド・パス・SQL に入る。
- **根拠**: 境界の位置（どの関数が検証するか）と、内側に検証がないこと。

## 4. 依存は一方向にする

- **適用場面**: モジュール間の import の向き、レイヤーの分け方を決めるとき。
- **原則**: 提供側は利用側に依存せず、下位レイヤーは上位レイヤーに依存しない。抽象（ポート）は利用側に定義し、実装側には置かない。循環参照は回避策で処理せず、構造上の誤りとして修正する。依存を避ける対象は import に限らず、コメント・エラー・ログの文言も含む。下位レイヤーの文言に、特定の利用側の名前や事情を書かない。
- **違反・兆候**:
  - 下位レイヤーのコメントが、制約の理由を特定の使う側の言葉で説明している。
  - ドメインが、フレームワーク・インフラ・アプリの設定の型を import している。
  - 共有の部品が、特定の使う側の事情（フラグ、分岐）を持っている。
  - 循環を re-export や遅延 import で回避している。
  - 便利だからという理由で、下位レイヤーに上位レイヤーのためのヘルパがある。
  - （設計案で）下位レイヤーの説明に、特定の利用側の名前が出てくる。
- **変更前・変更後**: `db/users.ts` が `features/billing` のフラグで分岐 → `features/billing` が `db/users` を呼び、分岐は `billing` 側に置く
- **blocking**: 循環参照がある。下位レイヤーが上位レイヤーを import している。
- **根拠**: 依存の向きの検査（lint）が通ること。

## 5. 正本は1か所にする

- **適用場面**: 同じ情報を複数の場所に持たせそうなとき。似た処理を共通化しようとするとき。
- **原則**: 各情報の正本は1か所に定める。ほかの値から算出できる値は保存せず、計算する。複製が避けられない場合は、正本、同期の責任者、不整合が生じた場合の処理を定める。一方、形式が偶然一致するだけの別々の情報は共通化しない（誤った共通化）。スコープや条件だけが異なり、処理内容が同じロジックは1つにまとめる。
- **違反・兆候**:
  - 同じ事実を表すデータが複数の場所にあり、それぞれ別の経路で更新される。
  - 状態を表す boolean のフラグが増え続ける（実際は1つの状態遷移で表せる）。
  - どちらが正しいかを、実行時に多数決やタイムスタンプの比較で決めている。
  - 形がたまたま同じなだけの別々の決まりを、1か所にまとめている（片方だけを変えたくなったとき、分け直すことになる）。
  - 手動で同期する一覧がある（派生できないならビルドを落とす）。
  - （設計案で）同じ事実を複数の場所に保存するが、正本と同期の責任者が書かれていない。
  - 同じ知識（形式、順序）を2つのモジュールが持つ。
  - 同じ処理を行う2つの経路があり、どちらを使うべきか、読む人が決められない。
- **変更前・変更後**: `user.isPremium` と `subscription.plan` の両方を保存 → `subscription.plan` だけを保存し、`isPremium` は計算する
- **blocking**: 同じ事実が複数の場所で別々に更新される。
- **根拠**: 事実ごとの正本の場所。

## 6. 全経路に効かせる処理はチョークポイントに置く

- **適用場面**: 検証・隔離・記録・計測・権限のように、すべての経路に効かせたい処理を置くとき。
- **原則**: すべての経路に適用する処理は、すべての経路が必ず通る1か所（チョークポイント）に配置する。各所に分散して実装すると、適用漏れがないことを保証できず、漏れも検知されない。その箇所を通らない経路を作れる構造であれば、経路を1本に統合する。
- **違反・兆候**:
  - 「この処理でも同じチェックを忘れずに」という、規約やレビュー頼みになっている。
  - 同じ処理のコピーが、機能ごとに少しずつ違う形である。
  - 新しい経路を足すたびに、その処理を手で付ける必要がある。
  - 権限の確認を、経路ごとに書いている。
  - （設計案で）権限・検証を置く箇所が経路ごとに分かれ、全経路が通る1か所がない。
- **変更前・変更後**: 各 handler の冒頭で `assertTenant(req)` → ルーターの middleware で1回
- **blocking**: 権限・検証を通らない経路が作れる。
- **根拠**: 全経路がその1か所を通ることの検査（テストか lint）。

## 7. 2つ目の実例が出るまで抽象化しない

- **適用場面**: 差し替えの仕組み、プラグイン、汎用化を作ろうとするとき。
- **原則**: 変更される部分と変更されない部分の境界を見極め、その位置とインターフェースだけを定める。差し替えやプラグインの仕組み、汎用化は、2つ目の実例が現れるまで実装しない。「将来必要になりそう」は実装の理由にならない。必要になった時点で実装できる構造を保てばよい。早すぎる抽象化より、類似した記述が3つあるほうがよい。
- **違反・兆候**:
  - 実装が1つしかない interface や抽象基底クラスがたくさんある。
  - 使われていないオプション引数・設定項目・ジェネリクスがある。
  - 「将来の拡張のため」のイベントフックやプラグインの仕組みがある。
  - 汎用にしたせいで、唯一の使い道にとって不自然なインターフェースになっている。
  - （設計案で）2つ目の実例がないまま、差し替えやプラグインの仕組みを作る計画になっている。
- **変更前・変更後**: `interface Notifier` + `EmailNotifier` のみ → `sendEmail()` の関数1つ。2つ目(Slack)が要るときに interface を切る
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 抽象ごとに、2つ目の実例があること。

## 8. 外部のフレームワーク・サービス・ライブラリの型を内側に入れない

- **適用場面**: 外部のフレームワーク・サービス・ライブラリに依存するコードを書くとき。
- **原則**: 外部のフレームワーク・サービス・ライブラリの型や記述方式を、内部のコードに持ち込まない。境界で内部の型に変換し、外部への依存は差し替え可能なコンポーネントとして扱う。実際に差し替えなくても、この構造を保つ意味はある。
- **違反・兆候**:
  - ドメインの型に、フレームワークの型やアノテーションが混ざっている。
  - 外部のフレームワーク・サービス・ライブラリの都合（名前、制約、ライフサイクル）に合わせて、内側の設計が変わっている。
  - 乗り換えの見積もりが「全部書き直し」になる。
  - （設計案で）内部の型や契約に、外部のフレームワーク・サービス・ライブラリの型が含まれている。
- **変更前・変更後**: `function charge(customer: Stripe.Customer)` → `function charge(customer: Customer)` と、境界で `toCustomer(stripeCustomer)`
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 外部の型が使われている場所が境界だけであること。

## 9. 失敗を通常の入力として扱う

- **適用場面**: 外部との通信、メッセージの処理、途中で止まりうる処理を設計するとき。
- **原則**: 外部サービスの停止、メッセージの重複、処理の中断は、例外的な出来事ではなく通常の入力として扱う。正常系の構造にエラー処理を後付けせず、失敗時にも正しく動作する構造（冪等な受信処理、実行前の記録、照合による復旧）を最初から選ぶ。
- **違反・兆候**:
  - 失敗時の挙動が「たぶん起きない」として決まっていない。
  - リトライ・タイムアウトを、問題が起きるたびに足している。
  - タイムアウトのない待機（外部呼び出し、ロック、キュー）。
  - 途中で止まると、中途半端な状態が残る。
  - 外部と自分の状態がずれたときに、それを検知する仕組みがない。
  - （設計案で）外部との通信が途中で止まったときに残る状態と、回復の手段が書かれていない。
- **変更前・変更後**: 「決済 API を呼んでから DB に書く」→「先に『決済を要求した』を DB に書き、API を呼び、結果を書く。突き合わせのバッチで食い違いを拾う」
- **blocking**: 外部との通信を含む処理で、途中で止まったときの状態が決まっていない。
- **根拠**: 途中で止まる各点について、残る状態と回復の手段。

## 10. まず1機能を画面から DB まで通す

- **適用場面**: 作る順番を決めるとき。
- **原則**: 画面から DB まで、全レイヤーを通る1つの機能を先に動かし、構造上の誤りを早期に発見する。レイヤーごとに作り込むと、誤りは最後の結合時にまとめて表面化する。最初に動作させた機能を、その後の実装の見本とする。複数のステップで使う型やモジュールは、最初のステップで作る場合も、1つの機能を全レイヤーで動かす形で作る。
- **違反・兆候**:
  - 動くものがないまま、複数のレイヤー・複数の機能を同時に作っている。
  - 結合を最後にまとめて行う計画になっている。
  - 使う側から一度も呼ばれていないレイヤーを「完成した」としている。
  - （設計案で）最初のステップがレイヤー単位であり、全レイヤーを通る1つの機能になっていない。
- **変更前・変更後**: 「ステップ1: 全テーブル、ステップ2: 全 API、ステップ3: 全画面」→「ステップ1: プラン一覧を画面から DB まで通す。ステップ2: プラン追加を通す」
- **blocking**: なし（手順の観点で見る）。
- **根拠**: 最初のステップが、画面から DB まで通る機能であること。

## 11. 誤用を型で防ぐ

- **適用場面**: 型・データ構造・インターフェースを決めるとき。
- **原則**: あり得ない組み合わせを表現できない型を定義し、失敗の種類も型で示す。誤用は規約やレビューに頼って防ぐのではなく、型・依存の向き・機械的な検査によって記述できないようにする。注意だけに頼る対策では、いずれ誤りが発生する。プリミティブ型（文字列、数値）に固有の意味がある場合は、区別できる型を定義する。外部データは、変換するまで型を付けない。
- **違反・兆候**:
  - 同時に成り立たないはずの値が、どちらも任意の項目として並んでいる。
  - 状態によって意味を持つ値が、状態と別に置かれている（「承認済みのときだけ承認者が入る」を型が知らない）。
  - 失敗が `null` や `boolean` で返り、何が起きたかを呼び出し元が区別できない。
  - 「〜の後でしか呼ばないこと」のような呼び出し方の約束が、コメントにしか書かれていない。
  - 分かっている型を `unknown` で受けたり、キャストで塗りつぶしている。
  - 誤った値が1行書かれるだけで、より強い権限が得られる。
  - （設計案で）同時に成り立たない状態や値を、同時に表せる型やデータ構造になっている。
- **変更前・変更後**: `{ status: string; approvedBy?: string }` → `{ status: "draft" } | { status: "approved"; approvedBy: UserId }`
- **blocking**: あり得ない状態を表せる型が、データの保存か外部の契約に使われている。
- **根拠**: 型の定義と、あり得ない状態が型エラーになること。

## 12. 変わりうる決定はモジュールに隠す

- **適用場面**: モジュールが外に見せるもの（公開する関数・型）を決めるとき。
- **原則**: データの保持方法、使用するツール、処理方式など、後から変わりうる決定は、その責務を持つモジュールの内部に隠す。外部に公開するのは、変更頻度の低い契約だけとする。公開したものはほかのモジュールから利用されて変更しにくくなるため、公開範囲を最小限にする。内部に隠すことは、抽象（ポート）の追加を意味しない（原則7）。
- **違反・兆候**:
  - 内部の表現（テーブルの列、外部 API の応答の形）が、そのまま他のモジュールに渡っている。
  - どこからも使われていない関数・型が公開されている。
  - 1つのモジュールの中身を変えると、使う側も一緒に変えなければならない。
  - 内部のものを import できる（importable internals）。
  - （設計案で）データの保持方法や外部 API の応答の形を、そのまま公開する契約になっている。
  - 浅いモジュールであり、インターフェースが実装と同じくらい大きく、隠しているものがない。
  - 要求と方式を同じ種類のものとして並べ、「何を満たすか」と「どう実現するか」が1つの一覧に混ざり、方式を変える判断と要求を守る判断を区別できない。
- **変更前・変更後**: `export const db` → `export function findPlan(id)`
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 公開しているものの一覧と、それぞれが約束である理由。

## 13. ドメインの規則を、散らばった分岐ではなく1つの構造で表す

- **適用場面**: 条件分岐を足そうとするとき。状態や種類を扱う設計をするとき。
- **原則**: 分散した条件分岐ではなく、構造（ステートマシン、テーブル、直和型、reducer）でドメインの規則を表現する。分岐を減らさない抽象化は導入しない。設計の最初にデータ構造を定めることで、後続の処理が明確になる。
- **違反・兆候**（この原則を適用していない兆候）:
  - `if / else` が1本ずつ伸びていく。
  - 同期しなければならない2つ目の boolean が現れる。
  - 同じ種類の判定が、複数の関数に散っている。
  - （設計案で）状態や種類ごとの規則が、共通の構造で表されず、複数のモジュールの条件分岐として書かれている。
- **変更前・変更後**: `if (plan === "free") ... else if (plan === "pro") ...` が5か所 → `PLAN_RULES[plan]` のテーブル1つ
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 分岐の数が減ったこと。

## 14. ドメインモデルの軸（エンティティ、所有と生存期間、整合性の境界）を決める

- **適用場面**: ステージ2（構造）でデータの構造を決めるとき。
- **原則**: ドメインモデリングの軸として、エンティティの切り方、所有と生存期間、整合性の境界（トランザクション、同時更新）を決める。
- **違反・兆候**:
  - 処理の段階の名前（`phase1`, `step2`）がモジュール名になっている。
  - 所有者が決まっていないデータがある。
  - 生存期間が決まっていない状態がある。
  - トランザクションの境界が暗黙である。
  - 実行順で分割したモジュールになっており、「読む」「変換する」「書く」が別モジュールで、同じデータ構造を3つが知る。
- **変更前・変更後**: 「注文と明細を別々に更新し、所有者も生存期間もトランザクションの境界も未定」→「注文が明細を所有し、明細は注文と同じ生存期間とし、注文と明細を1トランザクションで更新する」
- **blocking**: 整合性の境界が決まっていないまま同時更新がある。
- **根拠**: エンティティの切り方、所有と生存期間、整合性の境界について、決めた内容の記録。

## 15. たどるレイヤーと覚える状態を減らす

- **適用場面**: レイヤーを追加するとき。リファクタリングの効果を判定するとき。
- **原則**: 可読性は「たどるレイヤーの数」と「把握しておく必要がある状態の量」の2軸で評価する。呼び出し元が1つだけのラッパーはインライン化し、処理を中継するだけのレイヤーは削除する。状態のスコープを縮小する（純粋関数 > ローカル > フィールド > モジュール > グローバル）。行数や循環的複雑度は代理指標にすぎない。リファクタリングによってこの2軸の値が下がらない場合は、ロールバックする。
- **違反・兆候**:
  - 1つの処理を追うのに、4つ以上のファイルをたどる。
  - 引数をそのまま渡すだけの関数がある。
  - 既存コードを変更せずに済ませるために、レイヤーを1つ追加している。
  - （設計案で）制約を1つ満たすごとに、仕組みが1つ増えている。
- **変更前・変更後**: `Controller → Service → Manager → Repository → db`(Service と Manager は通過するだけ)→ `Controller → Repository → db`
- **blocking**: 同じ目的をより単純な構造で満たせる（処理を中継するだけのレイヤーがある）。
- **根拠**: たどるレイヤーの数と、把握しておく必要がある状態の量が、変更の前後でどう変わったか。

## 16. ロックより先に共有をなくす

- **適用場面**: 複数の処理（並列の作業、エージェント、ワーカー）が同じ状態に触れる設計をするとき。
- **原則**: 共有された可変状態は、まず共有をなくす。書き込み主体ごとにファイル・キー・ブランチ・worktree を分け、読み取り側で統合する。ロックは最後の手段である。ロックが必要な状態は設計上の問題の兆候であり、「注意して書く」という規約では並行性を制御できない。
- **違反・兆候**:
  - 同じ状態に複数の書き手がいる（split ownership）。
  - 並列の作業が同じ worktree で動いている。
  - 「同時に実行しないでください」という注意書きがある。
  - （設計案で）同じ状態を複数の処理が更新するが、書き込み主体ごとの分離も直列化も書かれていない。
- **変更前・変更後**: 2つのサブエージェントが同じ `progress.md` に追記 → それぞれ `progress-<id>.md` に書き、親が統合する
- **blocking**: 同じ状態に複数の書き手がいて、分離も直列化もされていない。
- **根拠**: 書き手ごとの保存先。

## 17. 移行は一気に終え、互換レイヤーを残さない

- **適用場面**: 書き換え・移行・API の置き換えを計画するとき。
- **原則**: 計画的な書き換えや移行では、中間状態の維持よりも最終形を優先する。破壊的な変更を許容するスコープを明示し、各段階の終了時に全体を検証する。新しい API の導入、呼び出し元の移行、旧 API の削除を同じ変更で行い、互換レイヤーを残さない。この原則は、外部利用者がおらず、破壊的な変更を吸収できる場合に適用する。外部の利用者がいる公開 API では、追加 → デプロイ → 移行 → 削除を別のリリースに分ける（expand → contract）。
- **違反・兆候**:
  - 「とりあえず互換のために」残した層が、移行後も消えない。
  - 新旧の API が両方使われたまま、どちらが正本であるか分からない。
  - 捨てる前提のコードに、本番の品質を求めている。
  - （設計案で）外部利用者がいない移行で、呼び出し元の移行と旧 API の削除が別の変更に分かれ、互換レイヤーを残す計画になっている。
- **変更前・変更後**: 「新 API を足し、旧 API は deprecated にして残す」→「新 API を足し、呼び出し元を全部移し、旧 API を同じ差分で消す」
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 移行の後に、旧 API の参照が0件であること。

## 18. 追加する前に削除する

- **適用場面**: 機能や仕組みを足そうとするとき。
- **原則**: 追加より先に削除する。デッドコード、重複した検証、スタブ、未使用のオプションを先に削除する。推測に基づくガードや、「エレガントな」ボイラープレートを追加しない。必要最小限の変更を選ぶ。
- **違反・兆候**:
  - 新しい仕組みを足した差分に、消したものがない。
  - 使われない分岐・オプションが残ったまま、似た仕組みが隣に足される。
  - （設計案で）既存の仕組みを消す案が検討されていない。
- **変更前・変更後**: 「設定の読み込みに新しい層を足す」→「古い読み込みの2経路を1つに消してから、要るなら足す」
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 差分で消したものの一覧。

## 19. 性能・観測性・ロールアウト・脅威モデルも設計で決める

- **適用場面**: ステージ1〜2で設計するとき。
- **原則**: 性能の予算、観測性（どのログと指標を設計に含めるか）、ロールアウト（フラグ、段階的な適用）、脅威モデル（誰が攻撃者で、何を守るか）を、構造と同じステージで決めるか、決めないことを明示する。
- **違反・兆候**:
  - 「性能は後で」「ログは実装時に」「フラグは要るときに」としている。
- **変更前・変更後**: 「性能は後で、ログは実装時に決める」→「性能の予算は応答時間の p95 が200ms以下。ログと指標は失敗理由とエラー率。ロールアウトはフラグで段階的に適用する。脅威モデルは外部の利用者による他テナントのデータへの不正アクセスを対象とする」
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 各軸について、決めた内容か、決めない理由。

## 優先順位とトレードオフ

- **7「2つ目の実例が出るまで抽象化しない」と 8「外部の型を内側に入れない」**: 優先: 8。理由とトレードオフ: 外部の型の変換は、2つ目の実例を待たずに最初から行う。トレードオフは、変換の関数が1つ増えること。差し替えの interface までは作らない
- **5「正本は1か所にする」と 12「変わりうる決定はモジュールに隠す」**: 優先: 5。理由とトレードオフ: 性能のために派生した値を保存することはあるが、そのときは正本と同期の責任者を書く。12 は公開の範囲の話で、保存の場所の話ではない
- **6「全経路に効かせる処理はチョークポイントに置く」と 4「依存は一方向」**: 優先: 4。理由とトレードオフ: 横断処理は、使う側の名前を知らずに書く（汎用の middleware）。使う側ごとの分岐が要るなら、それはチョークポイントではなく使う側の処理である
- **17（内部向けの移行）と 17（外部利用者がいる公開 API の移行）**: 優先: 利用者の有無で決める。理由とトレードオフ: 外部の利用者がいなければ 17 の中間状態を保たない移行。いれば 17 の公開 API の移行に従う
- **18「追加する前に削除する」と 12「頼まれていない変更をしない」（working）**: 優先: 12。理由とトレードオフ: 消すのも変更である。依頼のスコープの外なら、消す案を提案として報告する
