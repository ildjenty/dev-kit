# 構造を決めるときの原則

コードを書く前に、構造(モジュール、配置、依存、データの形)をどう決めるかの原則。

目標は、名前・配置・依存関係を見れば、それぞれが何のためにあるかが分かる構造にすることである。そうなっていれば、個々のモジュールの実装は単純になる。実装が込み入る、条件分岐が増える、説明のコメントが要る、テストが書きにくい、と感じたら、書き方ではなく構造が間違っている可能性が高い。その場合は構造に戻って直す。

各原則の「違反や兆候」には、コードができた後に見えるものと、設計案の文章を見て当てられるものの両方を含める。設計案の check(design.md の観点「構造」)は後者を使う。

## 1. 名前と配置で役割が分かるようにする

- **いつ当てるか**: モジュール・ファイル・フォルダを新しく作るとき、どこに置くかを決めるとき
- **原則**: それが何をするものか、なぜそこにあるかが、名前・配置・依存関係から分かるようにする。説明がないと分からない構造は、構造が間違っている。モジュールの役割を一文で言えないなら、分けるか消す。配置は、リポジトリの「配置の地図」(各パッケージの README に書いた、ここに置くもの・置かないもの)に従う
- **違反や兆候**:
  - モジュールの説明が「〜と〜と〜をする」と並ぶ(役割が複数ある)
  - どこに置けばよいか決められないコードがある。置きやすい場所に置かれている
  - 構造を説明するための文書が増え続ける
  - (設計案で)新しいモジュールの配置を、責務から正当化する一文が書けない
- **before / after**: `utils/helpers.ts` に `formatPrice` と `retryFetch` → `pricing/format.ts` と `http/retry.ts`
- **blocking**: 配置を責務から正当化できない
- **根拠**: 新しく作ったモジュールごとに、役割の一文と、配置の理由

## 2. 後から戻せない決定を先に決める

- **いつ当てるか**: 設計の最初に、何から決めるかを選ぶとき
- **原則**: 決定には、後から変えられるものと、後から戻せないもの(一方通行)がある。後から戻せないものを先に見分けて決める。一方通行に当たるのは、DB のスキーマ、識別子、契約の型、イベントの中身、外部に公開するもの、データの保持と削除の方針、ファイルの形式である。後から変えられるものは、作りながら決めてよい。今決めるか後で決めるかも、設計の判断として明示する
- **違反や兆候**:
  - 一方通行に当たるものが「後で直せる」扱いになっている
  - 後で差し替えられるもの(使う道具、表示、しきい値)を最初に議論している
  - どちらでもよい決定に時間を使い、戻せない決定が誰にも決められないまま進んでいる
  - (設計案で)戻せない決定の一覧がない
- **before / after**: 「まずボタンの色を決める。テーブルの列は実装しながら決める」→「まず料金テーブルの列と識別子を決める。色は後で変えられる」
- **blocking**: 戻せない決定が「後で直せる」扱いになっている
- **根拠**: 戻せない決定の一覧と、それぞれを誰がいつ決めたか

## 3. 外から来たものは入口で一度だけ検証する

- **いつ当てるか**: 外部(利用者の入力、API、ファイル、環境変数)から値を受け取る処理を設計するとき
- **原則**: 外部と内部、信頼できないものと信頼できるものの境界をどこに置くかを先に決める。検証・変換・隔離は境界で一度だけ行い、内側では検証済みとして扱う。境界で自分の型に変換し、内側では型を信じる。同じチェックが2か所に出てきたら、チェックを足すのではなく境界の位置を直す
- **違反や兆候**:
  - 多くの関数の冒頭に、同じ null チェック・型チェックがある
  - 「無いかもしれない」値が、内側の奥まで運ばれている
  - 検証エラーの扱いが場所ごとに違う
  - 外から来た値を、外部のコマンド・パス・SQL にそのまま組み込んでいる
  - 通信の型(リクエスト・レスポンス)を内側で再利用している
- **before / after**: `handler(req) { if (!req.body.id) ...; service(req.body) }` と `service(body) { if (!body.id) ... }` → `handler` で `parsePlanRequest(req.body): PlanRequest` に変換し、`service(plan: PlanRequest)` は検証しない
- **blocking**: 外から来た値が検証なしにコマンド・パス・SQL に入る
- **根拠**: 境界の位置(どの関数が検証するか)と、内側に検証がないこと

## 4. 依存は一方向にする

- **いつ当てるか**: モジュール間の import の向き、レイヤーの分け方を決めるとき
- **原則**: 提供する側は、使う側を知らない。下のレイヤーは上のレイヤーを知らない。抽象(ポート)は使う側が持ち、実装する側には置かない。循環参照は回避策で逃げず、構造の誤りとして直す。知らないことは、import だけでなく、コメント・エラーやログの文言にも当てはまる。下のレイヤーの文に、使う側の名前や事情を書かない
- **違反や兆候**:
  - 下のレイヤーのコメントが、制約の理由を特定の使う側の言葉で説明している
  - ドメインが、フレームワーク・インフラ・アプリの設定の型を import している
  - 共有の部品が、特定の使う側の事情(フラグ、分岐)を持っている
  - 循環を re-export や遅延 import で回避している
  - 便利だからという理由で、下のレイヤーに上のレイヤーのためのヘルパがある
- **before / after**: `db/users.ts` が `features/billing` のフラグで分岐 → `features/billing` が `db/users` を呼び、分岐は `billing` 側に置く
- **blocking**: 循環参照がある。下のレイヤーが上のレイヤーを import している
- **根拠**: 依存の向きの検査(lint)が通ること

## 5. 事実ごとに正本を1か所に決める

- **いつ当てるか**: 同じ情報を複数の場所に持たせそうなとき。似た処理を共通化しようとするとき
- **原則**: すべての事実について、正本をどこに置くかを1か所に決める。ほかの値から計算できる値は保存せず、計算する。やむを得ず複製するときは、どちらが正本か、誰が同期するか、食い違ったときにどうするかを決める。逆に、形がたまたま同じなだけの別々の事実は、1か所にまとめない(偽の共通化)。範囲や条件が違うだけで、やっていることが同じロジックは、1つにまとめる
- **違反や兆候**:
  - 同じ事実を表すデータが複数の場所にあり、それぞれ別の経路で更新される
  - 状態を表す boolean のフラグが増え続ける(実際は1つの状態遷移で表せる)
  - どちらが正しいかを、実行時に多数決やタイムスタンプの比較で決めている
  - 形がたまたま同じなだけの別々の決まりを、1か所にまとめている(片方だけを変えたくなったとき、分け直すことになる)
  - 手で同期する一覧がある(派生できないなら build を落とす)
- **before / after**: `user.isPremium` と `subscription.plan` の両方を保存 → `subscription.plan` だけを保存し、`isPremium` は計算する
- **blocking**: 同じ事実が複数の場所で別々に更新される
- **根拠**: 事実ごとの正本の場所

## 6. すべての経路に効かせる処理は、全経路が通る1か所に置く

- **いつ当てるか**: 検証・隔離・記録・計測・権限のように、すべての経路に効かせたい処理を置くとき
- **原則**: すべての経路に効かせたい処理は、すべての経路が必ず通る1か所(チョークポイント)に置く。各所に書くと、漏れがないことを保証できず、漏れても誰も気づかない。その1か所を通らない経路が作れる構造なら、経路を1本にまとめる
- **違反や兆候**:
  - 「この処理でも同じチェックを忘れずに」という、規約やレビュー頼みになっている
  - 同じ処理のコピーが、機能ごとに少しずつ違う形である
  - 新しい経路を足すたびに、その処理を手で付ける必要がある
  - 権限の確認を、経路ごとに書いている
- **before / after**: 各 handler の冒頭で `assertTenant(req)` → ルーターの middleware で1回
- **blocking**: 権限・検証を通らない経路が作れる
- **根拠**: 全経路がその1か所を通ることの検査(テストか lint)

## 7. 変わる部分との境目の位置だけを決める

- **いつ当てるか**: 差し替えの仕組み、プラグイン、汎用化を作ろうとするとき
- **原則**: 変わる部分と変わらない部分の境目を見極め、境目の位置とインターフェースだけを決める。差し替えの仕組み・プラグインの仕組み・汎用化は、2つ目の実例が出るまで作らない。「後で必要になりそう」は作る理由にならない。必要になったときに作れる形を保てばよい。3つの似た文は、早すぎる抽象より良い
- **違反や兆候**:
  - 実装が1つしかない interface や抽象基底クラスがたくさんある
  - 使われていないオプション引数・設定項目・ジェネリクスがある
  - 「将来の拡張のため」のイベントフックやプラグインの仕組みがある
  - 汎用にしたせいで、唯一の使い道にとって不自然なインターフェースになっている
- **before / after**: `interface Notifier` + `EmailNotifier` のみ → `sendEmail()` の関数1つ。2つ目(Slack)が要るときに interface を切る
- **blocking**: なし(手がかりとして記録する)
- **根拠**: 抽象ごとに、2つ目の実例があること

## 8. 外部のフレームワーク・サービス・ライブラリの型を内側に入れない

- **いつ当てるか**: 外部のものに依存するコードを書くとき
- **原則**: 外部のフレームワーク・サービス・ライブラリの型と書き方を、自分のコードの内側に入れない。境界で自分の型に変換し、外部のものは差し替えられる部品として扱う。実際に差し替えなくても、この形を保つ意味はある
- **違反や兆候**:
  - ドメインの型に、フレームワークの型やアノテーションが混ざっている
  - 外部のものの都合(名前、制約、ライフサイクル)に合わせて、内側の設計が変わっている
  - 乗り換えの見積もりが「全部書き直し」になる
- **before / after**: `function charge(customer: Stripe.Customer)` → `function charge(customer: Customer)` と、境界で `toCustomer(stripeCustomer)`
- **blocking**: なし(手がかりとして記録する)
- **根拠**: 外部の型が使われている場所が境界だけであること

## 9. 失敗が起きる前提で構造を選ぶ

- **いつ当てるか**: 外部との通信、メッセージの処理、途中で止まりうる処理を設計するとき
- **原則**: 外部は落ちる、メッセージは重複する、処理は途中で止まる。これらは例外ではなく、通常の入力として扱う。正常系の構造に失敗の処理を後から足すのではなく、失敗が起きても正しく動く構造(冪等な受け口、記録してから実行、突き合わせによる回復)を最初から選ぶ
- **違反や兆候**:
  - 失敗したときの動きが「たぶん起きない」として決まっていない
  - リトライ・タイムアウトを、問題が起きるたびに足している
  - 途中で止まると、中途半端な状態が残る
  - 外部と自分の状態がずれたときに、それを検知する仕組みがない
- **before / after**: 「決済 API を呼んでから DB に書く」→「先に『決済を要求した』を DB に書き、API を呼び、結果を書く。突き合わせのバッチで食い違いを拾う」
- **blocking**: 外部との通信を含む処理で、途中で止まったときの状態が決まっていない
- **根拠**: 途中で止まる各点について、残る状態と回復の手段

## 10. 1つの機能をすべてのレイヤーで動かしてから、機能を増やす

- **いつ当てるか**: 作る順番を決めるとき
- **原則**: 画面から DB まで、すべてのレイヤーを通る1つの機能を先に動かし、構造の誤りを早い時期に見つける。レイヤーごとに作り込むと、誤りは最後の結合でまとめて出てくる。最初に動かした機能は、その後の実装が従う見本になる。複数のステップが使う型やモジュールは最初のステップで作るが、それも1本の機能を通す形で作る
- **違反や兆候**:
  - 動くものがないまま、複数のレイヤー・複数の機能を同時に作っている
  - 結合を最後にまとめて行う計画になっている
  - 使う側から一度も呼ばれていないレイヤーを「完成した」としている
- **before / after**: 「ステップ1: 全テーブル、ステップ2: 全 API、ステップ3: 全画面」→「ステップ1: プラン一覧を画面から DB まで通す。ステップ2: プラン追加を通す」
- **blocking**: なし(手順の観点で見る)
- **根拠**: 最初のステップが、画面から DB まで通る機能であること

## 11. 誤りを起こせない形にする

- **いつ当てるか**: 型・データの形・インターフェースを決めるとき
- **原則**: あり得ない組み合わせを表せない型にし、失敗の種類も型で示す。間違った使い方は、規約やレビューで防ぐのではなく、型・依存の向き・機械的な検査で書けないようにする。「気をつける」でしか防げない誤りは、いずれ起きる。原始的な型(文字列、数値)に意味があるなら、区別できる型にする。外部のデータは、変換するまで型を付けない
- **違反や兆候**:
  - 同時に成り立たないはずの値が、どちらも任意の項目として並んでいる
  - 状態によって意味を持つ値が、状態と別に置かれている(「承認済みのときだけ承認者が入る」を型が知らない)
  - 失敗が `null` や `boolean` で返り、何が起きたかを呼び出し元が区別できない
  - 「〜の後でしか呼ばないこと」のような呼び出し方の約束が、コメントにしか書かれていない
  - 分かっている型を `unknown` で受けたり、キャストで塗りつぶしている
  - 誤った値が1行書かれるだけで、より強い権限が得られる
- **before / after**: `{ status: string; approvedBy?: string }` → `{ status: "draft" } | { status: "approved"; approvedBy: UserId }`
- **blocking**: あり得ない状態を表せる型が、データの保存か外部の契約に使われている
- **根拠**: 型の定義と、あり得ない状態が型エラーになること

## 12. 変わりうる決定はモジュールの内側に置く

- **いつ当てるか**: モジュールが外に見せるもの(公開する関数・型)を決めるとき
- **原則**: データの持ち方・使う道具・処理の方式のように、後で変わりうる決定は、それを持つモジュールの内側に置く。外に見せるのは、めったに変わらない約束だけにする。外に見せたものは他から使われて変えにくくなるので、公開するものは最小にする。内側に置くとは、抽象(ポート)を足すことではない(原則7)
- **違反や兆候**:
  - 内部の表現(テーブルの列、外部 API の応答の形)が、そのまま他のモジュールに渡っている
  - どこからも使われていない関数・型が公開されている
  - 1つのモジュールの中身を変えると、使う側も一緒に変えなければならない
  - 内部のものを import できる(importable internals)
- **before / after**: `export const db` → `export function findPlan(id)`
- **blocking**: なし(手がかりとして記録する)
- **根拠**: 公開しているものの一覧と、それぞれが約束である理由

## 13. ドメインを構造で表す

- **いつ当てるか**: 条件分岐を足そうとするとき。状態や種類を扱う設計をするとき
- **原則**: 散った条件分岐ではなく、構造(状態機械、テーブル、直和型、reducer)にドメインを書き込む。分岐を減らさない抽象は入れない。設計の最初にデータの形を決めれば、下流の処理は自明になる
- **違反や兆候**(とばしたサイン):
  - `if / else` が1本ずつ伸びていく
  - 同期しなければならない2つ目の boolean が現れる
  - 処理の段階の名前(`phase1`, `step2`)がモジュール名になっている
  - 同じ種類の判定が、複数の関数に散っている
- **before / after**: `if (plan === "free") ... else if (plan === "pro") ...` が5か所 → `PLAN_RULES[plan]` のテーブル1つ
- **blocking**: なし(手がかりとして記録する)
- **根拠**: 分岐の数が減ったこと

## 14. 読む人の負荷を減らす

- **いつ当てるか**: 層を足そうとするとき。リファクタリングの効果を判定するとき
- **原則**: 可読性は「辿る層の数」と「頭に持つ状態の量」の2軸で測る。呼び出し元が1つしかない wrapper は inline する。通過するだけの層は潰す。状態の範囲を縮める(純粋関数 > ローカル > フィールド > モジュール > グローバル)。行数や循環的複雑度は代理指標にすぎない。リファクタリングの結果、この2軸が下がらなければ戻す
- **違反や兆候**:
  - 1つの処理を追うのに、4つ以上のファイルを辿る
  - 引数をそのまま渡すだけの関数がある
  - 既存コードを変えずに済ませるために、層を1つ足している
  - (設計案で)制約を1つ満たすごとに、仕組みが1つ増えている
- **before / after**: `Controller → Service → Manager → Repository → db`(Service と Manager は通過するだけ)→ `Controller → Repository → db`
- **blocking**: 同じ目的をより単純な構造で満たせる(通過するだけの層がある)
- **根拠**: 辿る層の数と、頭に持つ状態の量が、変更の前後でどう変わったか

## 15. 共有状態は、直列化する前に分ける

- **いつ当てるか**: 複数の処理(並列の作業、エージェント、ワーカー)が同じ状態に触れる設計をするとき
- **原則**: 共有の可変状態は、まず共有をなくす。書き手ごとにファイル・キー・ブランチ・worktree を分け、読む側で統合する。ロックは最後の手段である。「ロックが要る」は設計の臭いであり、「気をつけて書く」という規約は並行性の制御ではない
- **違反や兆候**:
  - 同じ状態に複数の書き手がいる(split ownership)
  - 並列の作業が同じ作業ツリーで動いている
  - 「同時に実行しないでください」という注意書きがある
- **before / after**: 2つのサブエージェントが同じ `progress.md` に追記 → それぞれ `progress-<id>.md` に書き、親が統合する
- **blocking**: 同じ状態に複数の書き手がいて、分離も直列化もされていない
- **根拠**: 書き手ごとの保存先

## 16. 計画した移行では、中間状態を保たない

- **いつ当てるか**: 書き換え・移行・API の置き換えを計画するとき
- **原則**: 計画した書き換えや移行では、途中の状態の滑らかさより、最終形を優先する。壊してよい範囲を宣言し、各段階の最後に全体を検証する。新しい API を入れるときは、呼び出し元の移行と古い API の削除を同じ波で行い、互換層を残さない。これは、外部の利用者がいない・破壊的な変更を吸収できるときに当てる。外部の利用者がいる公開 API では、追加 → デプロイ → 移行 → 削除を別のリリースに分ける(engineering.md の運用に従う)
- **違反や兆候**:
  - 「とりあえず互換のために」残した層が、移行後も消えない
  - 新旧の API が両方使われたまま、どちらが正本か分からない
  - 捨てる前提のコードに、本番の品質を求めている
- **before / after**: 「新 API を足し、旧 API は deprecated にして残す」→「新 API を足し、呼び出し元を全部移し、旧 API を同じ差分で消す」
- **blocking**: なし(手がかりとして記録する)
- **根拠**: 移行の後に、旧 API の参照が0件であること

## 17. 足す前に引く

- **いつ当てるか**: 機能や仕組みを足そうとするとき
- **原則**: 先に削ってから作る。死んだコード、重複した検証、スタブ、使われていないオプションを先に消す。推測で guard を書かない。「エレガントな」ボイラープレートを増やさない。最小の変更に倒す
- **違反や兆候**:
  - 新しい仕組みを足した差分に、消したものがない
  - 使われない分岐・オプションが残ったまま、似た仕組みが隣に足される
  - (設計案で)既存の仕組みを消す案が検討されていない
- **before / after**: 「設定の読み込みに新しい層を足す」→「古い読み込みの2経路を1つに消してから、要るなら足す」
- **blocking**: なし(手がかりとして記録する)
- **根拠**: 差分で消したものの一覧

## 優先と代償

ぶつかる組と、どちらを優先するか。

| ぶつかる組 | 優先 | 理由と代償 |
|---|---|---|
| 7「汎用化しない」と 8「外部の型を内側に入れない」 | 8 | 外部の型の変換は、2つ目の実例を待たずに最初から行う。代償は、変換の関数が1つ増えること。差し替えの interface までは作らない |
| 5「正本を1か所」と 12「変わりうる決定を内側に」 | 5 | 性能のために派生した値を保存することはあるが、そのときは正本と同期の責任者を書く。12 は公開の範囲の話で、保存の場所の話ではない |
| 6「チョークポイント」と 4「依存は一方向」 | 4 | 横断処理は、使う側の名前を知らずに書く(汎用の middleware)。使う側ごとの分岐が要るなら、それはチョークポイントではなく使う側の処理である |
| 16「中間状態を保たない」と engineering の運用(expand → contract) | 利用者の有無で決める | 外部の利用者がいなければ 16。いれば段階的に |
| 17「足す前に引く」と 6「頼まれていない変更をしない」(engineering) | 6 | 消すのも変更である。依頼の範囲の外なら、消す案を提案として報告する |
