# principles

check の観点ファイルでは、これらの原則を評価基準とする。機械で決定的に判定できる規則は原則にしない。ループの仕組みに関するものは[部品の契約](../docs/design.md#部品)に、対象のコードと文書に関するものは[規則と強制手段](../docs/rules.md)の一覧に置き、手段が実装されるまでは「未実装」として残す。

- **[engineering.md](engineering.md)**: コードを書くとき
- **[designing.md](designing.md)**: 設計の進め方を決めるとき
- **[structure.md](structure.md)**: モジュールの配置と依存を決めるとき
- **[data.md](data.md)**: データと状態を決めるとき
- **[testing.md](testing.md)**: テストを書くとき、既存のコードを変える前
- **[verification.md](verification.md)**: ツール・API・バージョン・原因・計測値について述べるとき
- **[working.md](working.md)**: 作業の進め方を決めるとき
- **[context.md](context.md)**: コンテキストと記録を扱うとき
- **[harness.md](harness.md)**: メタループでループの仕組み（部品、組み立て、計画）を変更するとき、観点「harness」の check を行うとき
- **[ui.md](ui.md)**: 画面を設計する・作るとき
- **[writing.md](writing.md)**: 人が読む文章（報告、PR 本文、文書）を書くとき

## 原則のフォーマット

各原則は、次の項目で記述する。

- **名前**: 会話で参照できる短い名前。人は「『2つ目の実例が出るまで抽象化しない』で見直して」のように名前で指示できる。
- **適用場面**: 適用場面を「〜のとき」の1文で示す。
- **適用除外**: この原則の要求のうち、従うとかえって悪くなるものを、条件付きで外す。「〜のとき」の条件、外す要求の範囲、該当すると判断するために成果物に示すものを書く。条件が複数あるときは、条件ごとに入れ子の箇条書きにする。該当しても、外した要求に限って違反としない。原則の他の要求と blocking は残る。本文がすでに認めている通常の行為は除外に書かない。思いつかなければ「なし」と書き、「なし」は批評で反例を探す対象となる。
- **原則**: 実施する内容と、その理由。
- **違反・兆候**: 差分や設計案を見て、該当するかどうかを判断できる形で記述する。
- **変更前・変更後**: 変更前と変更後の例を1組示す。
- **blocking**: check で、この原則の違反を blocking にする条件。
- **根拠**: 原則を満たしたと判断するために提示する根拠。

エージェントは返答で、どの原則によってどの決定が変わったかを明示する。名前を挙げるだけで決定に変化がなければ、適用したことにはならない。適用除外を使って原則を外した場合も、どの除外に当たるか、外した要求の範囲、理由を明示する。

## 原則が競合する場合

- **designing 2「2つ目の実例が出るまで抽象化しない」と structure 5「フレームワーク・外部サービスの型を公開契約・保存データ・ドメインの型に含めない」**: designing 2 の適用除外として structure 5 に従う。理由とトレードオフ: 公開契約・保存データ・ドメインの型を外部固有の知識から隔離する変換は、2つ目の実例を待たずに行う。汎用ライブラリの値型など、structure 5 の適用除外に当たる場合は変換を強制しない。トレードオフは変換と保守の負担であり、隠す知識と変更の波及範囲に見合うかを示す。差し替えの interface までは作らない
- **data 1「同じ対象・時点・意味の事実の正本を定める」と structure 6「変わりうる決定はモジュールに隠す」**: 優先: data 1。理由とトレードオフ: 過去時点の事実は保存し、性能のために複製する場合は正本と同期の責任者、更新方法、許容する不整合とその範囲を超えた場合の処理を定める。structure 6 は公開の範囲を定め、保存方法はその責務を持つモジュールに隠す
- **structure 4「全経路に必要な保証を迂回できない構造にする」と structure 3「下位レイヤーの契約と実装を特定の利用側に依存させない」**: 優先: structure 3。理由とトレードオフ: 横断処理は、使う側の名前を知らずに書く（汎用の middleware）。使う側ごとの分岐が要るなら、それは共通の通過点に置く処理ではなく使う側の処理である
- **designing 5「新しい仕組みを足す前に削除・置き換えを検討する」と working 7「頼まれていない変更をしない」**: 優先: working 7。理由とトレードオフ: 消すのも変更である。今回の変更で不要になるものや要求を満たすために削除が必要なものを検討し、無関係な整理は混ぜない。依頼のスコープの外なら、消す案を提案として報告する
- **designing 7「既存の流儀に揃える」と designing 4「安全に一括で切り替えられる移行は互換レイヤーを残さず終える」**: 優先: 既存の流儀を変えると決めた範囲の移行は designing 4、今回の要求と保証を満たす既存の流儀に揃える場合は designing 7。理由とトレードオフ: 移行は今回の変更に不可分な範囲に限り、安全に一括で切り替えられるなら互換レイヤーを残さない。段階移行が必要なら一時互換の対象と撤去条件を定める。全体の統一が独立した改善になるなら別の課題にする

## 更新方法

原則を追加・変更する場合は、一度に少しだけにする。個別の事例をそのまま記載せず、ほかの場面にも適用できる形にする。既存の原則と重複する場合は、新設せず既存の項目に追記する。一定期間、違反を1件も検出しなかった原則は、整理・削減の候補にする（[../docs/meta-loop.md](../docs/meta-loop.md) のメタループ）。「一定期間」の長さはリポジトリ側で決める（kit に設定項目はない）。
