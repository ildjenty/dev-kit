# principles

check の観点ファイルでは、これらの原則を評価基準とする。機械で決定的に判定できる規則は原則にしない。ループの仕組みに関するものは[部品の契約](../docs/design.md#部品)に、対象のコードと文書に関するものは[規則と強制手段](../docs/rules.md)の一覧に置き、手段が実装されるまでは「未実装」として残す。

- **[engineering.md](engineering.md)**: コードを書くとき
- **[design.md](design.md)**: 構造（モジュール、配置、依存、データ構造）を決めるとき
- **[testing.md](testing.md)**: テストを書くとき、既存のコードを変える前
- **[verification.md](verification.md)**: ツール・API・バージョン・原因・計測値について述べるとき
- **[working.md](working.md)**: 作業の進め方を決めるとき
- **[harness.md](harness.md)**: メタループでループの仕組み（部品、組み立て、計画）を変更するとき、観点「harness」の check を行うとき
- **[ui.md](ui.md)**: 画面を設計する・作るとき
- **[writing.md](writing.md)**: 人が読む文章（報告、PR 本文、文書）を書くとき

## 原則のフォーマット

各原則は、次の項目で記述する。

- **名前**: 会話で参照できる短い名前。人は「『追加する前に削除する』で見直して」のように名前で指示できる。
- **適用場面**: 適用場面を「〜のとき」の1文で示す。
- **原則**: 実施する内容と、その理由。
- **違反・兆候**: 差分や設計案を見て、該当するかどうかを判断できる形で記述する。
- **変更前・変更後**: 変更前と変更後の例を1組示す。
- **blocking**: check で、この原則の違反を blocking にする条件。
- **根拠**: 原則を満たしたと判断するために提示する根拠。

エージェントは返答で、どの原則によってどの決定が変わったかを明示する。名前を挙げるだけで決定に変化がなければ、適用したことにはならない。

## 原則が競合する場合

原則は規則であるが、同じ場面で2つの原則が競合することがある。競合する原則と、どちらを優先するかは [design.md](design.md) の末尾「優先順位とトレードオフ」にまとめる。

## 更新方法

原則を追加・変更する場合は、一度に少しだけにする。個別の事例をそのまま記載せず、ほかの場面にも適用できる形にする。既存の原則と重複する場合は、新設せず既存の項目に追記する。一定期間、違反を1件も検出しなかった原則は、整理・削減の候補にする（[../docs/meta-loop.md](../docs/meta-loop.md) のメタループ）。「一定期間」の長さは、リポジトリ側で設定する。
