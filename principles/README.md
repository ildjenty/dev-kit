# principles

check の観点ファイルでは、これらの原則を評価基準とする。機械で決定的に判定できる規則は原則にしない。ループの仕組みに関するものは[部品の契約](../docs/design.md#部品)に、対象のコードと文書に関するものは[規則と強制手段](../docs/rules.md)の一覧に置き、手段が実装されるまでは「未実装」として残す。

- **[engineering.md](engineering.md)**: コードを書くとき
- **[designing.md](designing.md)**: 設計の進め方を決めるとき
- **[structure.md](structure.md)**: モジュールの配置と依存を決めるとき
- **[data.md](data.md)**: データと状態を決めるとき
- **[testing.md](testing.md)**: テストを書くとき、既存のコードを変える前
- **[verification.md](verification.md)**: ツール・API・バージョン・原因・計測値について述べるとき
- **[working.md](working.md)**: 作業の進め方を決めるとき
- **[context.md](context.md)**: コンテキストと記録を扱うとき
- **[harness.md](harness.md)**: メタループでループの仕組み（部品、組み立て、計画）を変更するとき、観点「harness」の check を行うとき
- **[ui.md](ui.md)**: 画面を設計する・作るとき
- **[writing.md](writing.md)**: 人が読む文章（報告、PR 本文、文書）を書くとき

## 原則のフォーマット

各原則は、次の項目で記述する。

- **名前**: 会話で参照できる短い名前。人は「『追加する前に削除する』で見直して」のように名前で指示できる。
- **適用場面**: 適用場面を「〜のとき」の1文で示す。
- **原則**: 実施する内容と、その理由。
- **違反・兆候**: 差分や設計案を見て、該当するかどうかを判断できる形で記述する。
- **変更前・変更後**: 変更前と変更後の例を1組示す。
- **blocking**: check で、この原則の違反を blocking にする条件。
- **根拠**: 原則を満たしたと判断するために提示する根拠。

エージェントは返答で、どの原則によってどの決定が変わったかを明示する。名前を挙げるだけで決定に変化がなければ、適用したことにはならない。

## 原則が競合する場合

- **designing 2「2つ目の実例が出るまで抽象化しない」と structure 5「外部の型を内側に入れない」**: 優先: structure 5。理由とトレードオフ: 外部の型の変換は、2つ目の実例を待たずに最初から行う。トレードオフは、変換の関数が1つ増えること。差し替えの interface までは作らない
- **data 1「正本は1か所にする」と structure 6「変わりうる決定はモジュールに隠す」**: 優先: data 1。理由とトレードオフ: 性能のために派生した値を保存することはあるが、そのときは正本と同期の責任者を書く。structure 6 は公開の範囲の話で、保存の場所の話ではない
- **structure 4「全経路に効かせる処理はチョークポイントに置く」と structure 3「依存は一方向」**: 優先: structure 3。理由とトレードオフ: 横断処理は、使う側の名前を知らずに書く（汎用の middleware）。使う側ごとの分岐が要るなら、それはチョークポイントではなく使う側の処理である
- **designing 4（内部向けの移行）と designing 4（外部利用者がいる公開 API の移行）**: 優先: 利用者の有無で決める。理由とトレードオフ: 外部の利用者がいなければ designing 4 の中間状態を保たない移行。いれば designing 4 の公開 API の移行に従う
- **designing 5「追加する前に削除する」と working 7「頼まれていない変更をしない」**: 優先: working 7。理由とトレードオフ: 消すのも変更である。依頼のスコープの外なら、消す案を提案として報告する
- **designing 7「既存の流儀に揃える」と designing 4「移行は一気に終え、互換レイヤーを残さない」**: 優先: 既存の流儀を変えると決めたときは designing 4、変えないときは designing 7。理由とトレードオフ: 変えるときは新旧を並存させない。変えないときは、よりよい書き方でも既存に揃える

## 更新方法

原則を追加・変更する場合は、一度に少しだけにする。個別の事例をそのまま記載せず、ほかの場面にも適用できる形にする。既存の原則と重複する場合は、新設せず既存の項目に追記する。一定期間、違反を1件も検出しなかった原則は、整理・削減の候補にする（[../docs/meta-loop.md](../docs/meta-loop.md) のメタループ）。「一定期間」の長さは、リポジトリ側で設定する。
