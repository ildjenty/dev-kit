# principles

言語やリポジトリに依存しない原則。コードを書く前、構造を決める前、テストを書く前、事実を述べる前、画面を作る前、文章を書く前に読む。check の観点ファイルは、ここに照らす。

| 文書 | いつ読むか |
|---|---|
| [engineering.md](engineering.md) | コードを書くとき |
| [design.md](design.md) | 構造(モジュール、配置、依存、データの形)を決めるとき |
| [testing.md](testing.md) | テストを書くとき、既存のコードを変える前 |
| [verification.md](verification.md) | ツール・API・バージョン・原因・計測値について述べるとき |
| [working.md](working.md) | 作業の進め方を決めるとき |
| [ui.md](ui.md) | 画面を設計する・作るとき |
| [writing.md](writing.md) | 人が読む文章(報告、PR 本文、文書)を書くとき |
| review.md | レビューで照らす1枚。上の文書の各原則の「blocking」と「根拠」の行から生成する(生成の仕組みは `tools/` で作る。それまでは手で揃える) |

## 原則の形

各原則は次の項目で書く。

- **名前**: 会話で呼べる短い名前。人は「『足す前に引く』で見直して」のように名前で指示できる
- **いつ当てるか**: 「〜のときに当てる」の1文
- **原則**: 何をするか、なぜか
- **違反や兆候**: 差分や設計案を見て、当たる・当たらないを決められる形で書く
- **before / after**: 1組
- **blocking**: check で、この原則の違反を blocking にする条件
- **根拠**: 満たしたと言うために、何を示すか

エージェントは返答で、どの原則によってどの決定が変わったかを明示する。名前を挙げただけで、変わった決定がなければ、適用したことにはならない。

## 原則どうしがぶつかるとき

原則は規則であり、同じ場面で2つがぶつかることがある。ぶつかる組と、どちらを優先するかは [design.md](design.md) の末尾「優先と代償」にまとめる。

## 直し方

原則を足す・変えるときは、1回に1〜2件にする。起きた事例そのものは書かず、ほかの場面にも当てはまる形にする。既存の原則と重なるなら、新しく作らず既存の項目に足す。一定期間、違反を1件も検出しなかった原則は、刈り込みの候補にする(design.md のメタループ)。
