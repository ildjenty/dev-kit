# コードを書くときの原則

言語やフレームワークに依存しない、コードを書くときの原則。構造を決める原則は [design.md](design.md)、テストは [testing.md](testing.md)、事実を確かめることは [verification.md](verification.md) に書く。

## 1. 失敗を隠さない

- **いつ当てるか**: エラー、空、0件、上限超過、値がない、重複のときの動きを決めるとき
- **原則**: 処理を続けてよいのは、失敗が起きても結果が正しいと言い切れるときだけである。判断できないときは、安全な側に倒してはっきり失敗させる(fail-closed)。失敗は、エラーの型やログで後から分かる形に残す。「この失敗に、誰がいつ気づくか」に答えられないコードは書かない。空・0件・上限・値がない・重複・失敗のときに、黙って既定値で続けない。そのときの動きがコードの意味を決めるので、既定値で続けると、意味が変わったことに誰も気づかない
- **違反や兆候**:
  - `catch` してログだけ出し、処理を続ける(呼び出し元は成功したと思っている)
  - `catch { return null }` や `catch { return [] }` で、失敗を「データがなかった」にすり替える
  - 空の識別子を既定値で処理し、分かれているはずのデータが混ざる
  - 値があるかどうかだけで分岐し、無いときに何を意味するかを決めていない
  - 種類の違う失敗を1つにまとめる(入力の誤りと内部の故障、見つからないと権限がない)
  - 検査・認可・外部の呼び出しが失敗したのに、そのまま通す
  - 失敗の原因を探すのに要る情報を残さない。または、秘密の値をログやエラーに残す
  - 開いたもの(ファイル・接続・タイマー・購読)を、失敗したときに閉じない
  - 何にでもリトライを付ける(冪等でない処理や、やり直しても直らない失敗にも付ける)
  - 非同期の処理の失敗を誰も待っておらず、落ちても何も起きない
  - 設定や前提が不確かなときに、外部に書く・通す
- **before / after**:
  ```ts
  // before
  try { return await fetchPlan(id) } catch { return null }   // 失敗が「プランがない」になる
  // after
  try { return await fetchPlan(id) }
  catch (e) { throw new PlanFetchError(id, { cause: e }) }   // 失敗の種類が呼び出し元に伝わる
  ```
- **blocking**: 失敗が通る経路がある(検査・認可・外部呼び出しの失敗を通す、失敗を既定値にすり替える)
- **根拠**: 失敗の経路ごとに、誰がどこで気づくか(例外の型、ログ、テスト)を示す

## 2. 二度実行しても、同時に実行しても、結果が変わらないようにする

- **いつ当てるか**: 外部に作用する処理、非同期に呼ばれる処理、同じデータを同時に扱う処理を書くとき
- **原則**: 同じ入力で二度実行されても結果が変わらないように書く(冪等)。同じメッセージが二度届くこと、リトライ、タイムアウト後の再実行は、起きるものとして書く。現在の状態を読んで目標との差分だけを適用し、「前回の意図」に依存しない。途中で止まったときの残骸(ロック、一時ファイル、半端なレコード)は、次回が古いと判定できるようにする(一時ファイルは書いてから rename する、内容を比較する)
- **違反や兆候**:
  - 受け取ったイベントを無条件に INSERT する(二度届くと二重に登録される)
  - 冪等キーなしで外部に送る(リトライで二重に送られる)
  - 「前回の実行からの経過時間」のように、1回しか動かない前提の時刻の計算
  - 一連の更新が途中で止まると、中途半端な状態が残る(トランザクションや取り消しの処理がない)
  - 読んで確かめてから書くまでの間に、別の処理が割り込める(確認と更新が分かれている)
- **before / after**:
  ```sql
  -- before
  INSERT INTO payments (event_id, amount) VALUES ($1, $2);
  -- after
  INSERT INTO payments (event_id, amount) VALUES ($1, $2) ON CONFLICT (event_id) DO NOTHING;
  ```
- **blocking**: 外部に作用する処理、または非同期に呼ばれる処理に冪等性がない
- **根拠**: 二度実行したときの結果が同じであることを、テストか実行で示す

## 3. 名前は初めて読む人に分かるように付ける

- **いつ当てるか**: 変数・関数・型・ファイル・フォルダに名前を付けるとき
- **原則**: コードと文書で使われている言葉を使い、会話の中で作った言葉を持ち込まない。1つのものには1つの名前を使い、同じものを場所によって別の名前で呼ばない。中身が変わったら名前も変える。名前は、そのものが受け持つ範囲を表すように付ける。範囲より狭い名前は、範囲が広がったときに中身と合わなくなる。範囲より広い名前は、何でも入れられてしまう。テストの名前とエラーメッセージは英語で書く。ログやエラーを追うときに、検索の言葉がそろうためである
- **違反や兆候**:
  - 置いた場所と合わせても、何を受け持つかが分からない名前(`data` `info` `result` `item` `temp` `helper` `util` `manager` `handler`)
  - 同じものを指す名前の揺れ(customer / client / user が同じものを指す)
  - 中身と合わない boolean の名前(`isValid` が実際は「保存済みか」を表す)
  - `processData2` `newHelper` のように、既存の名前との違いだけで付けた名前
  - 全体を扱うものに、今扱っている1件の名前を付ける
- **before / after**: `const data = await getUser(id)` → `const customer = await findCustomerById(id)`
- **blocking**: なし(手がかりとして記録する)
- **根拠**: 名前から、受け持つ範囲が1文で言えること

## 4. コメントは、知らないと誤る制約を、コードで守れないときだけ書く

- **いつ当てるか**: コメントを書くとき、コメントを残すかを決めるとき
- **原則**: コメントは書かないのを基本にする。書くのは、次の両方に当たるときだけである。(1) このコードを変える人・呼ぶ人・書いたデータを読む人が、知らないと誤る制約がある(外のライブラリの動き、呼ぶ順序、セキュリティ上の前提、外の設定から決めた値、列の値の意味)。(2) その制約を、型・名前・テストのどれでも守れない。型やテストで表した制約は、破るとエラーになる。コメントに書いた制約は、破っても何も起きない。外のライブラリの不具合を避けるコードには、何を避けているかと、消してよい条件(直ったバージョン、上流の Issue)を書く。lint の抑制には理由を必ず書く。設計の選び方・理由・経緯は、コメントではなく PR・Issue・設計文書に残す。コメントを読むのは後でコードを読む人であり、今回の変更を見る人ではない
- **違反や兆候**:
  - コードをそのまま言い換えたコメント(`// ユーザーを取得する` の下に `getUser()`)
  - 引数名を言い換えただけの docstring
  - 設計の選び方とその理由を書いたコメント(「〜は、〜のため、〜にする」)
  - 型が守っている制約を、コメントでも書く
  - 「〜に変更」「〜を修正」という経緯のコメント
  - コメントアウトしたコードが残る。片付かない TODO が溜まる
  - `IMPORTANT` や `do not remove` だけで、理由がない
- **before / after**:
  ```ts
  // before
  // 先に init() を呼ぶこと
  export function send() { ... }
  // after(型で守る)
  export function send(client: InitializedClient) { ... }
  ```
- **blocking**: なし(手がかりとして記録する)
- **根拠**: 足した・残したコメントごとに、どの制約を守るか、なぜ型・名前・テストで守れないかを1行で言えること

## 5. 変更した場所の外と、同じ原因の誤りを探す

- **いつ当てるか**: 関数・型・契約を変えたとき。誤りを1つ見つけたとき
- **原則**: 変更で壊れるのは、変えた場所よりも、それを使っている場所や、変えた前提に頼っている場所であることが多い。関数・型・契約を変えたら、使っている場所をすべて調べる。公開している契約(型、スキーマ、設定の形式)を変えたら、使う側と保存済みのデータへの影響を見る。誤りを1つ見つけたら、その原因を言葉にして、同じ原因の誤りをほかの場所からも探す
- **違反や兆候**:
  - 気づいた1か所だけを直して終える(同じ関数を使うバッチやツールが古いまま)
  - 契約を変え、使っている側と保存済みのデータへの影響を調べていない
  - 同じ原因の誤りを、指摘されるたびに1つずつ直す
- **before / after**: 「`parseDate` の戻り値を `Date | null` に変えた」→「`parseDate` の呼び出し元12か所を調べ、`null` を扱っていない3か所を同じ差分で直した」
- **blocking**: 契約を変えたのに、使っている側を調べていない
- **根拠**: 使っている場所の一覧(検索のコマンドと結果)と、それぞれどう扱ったか

## 6. 頼まれていない変更をしない

- **いつ当てるか**: 差分に、依頼の範囲の外の変更を含めるかを決めるとき
- **原則**: 頼まれた範囲の外の変更は、意図も影響も確かめられていない。変更したモジュールの中で、変更のために要る直し(名前の付け直し、構造の直し、同じ原因の誤り)は同じ差分に含める。モジュールの外の改善と、変更に要らない改善は実装せず、提案として報告する。指示に書かれていない動き(上限、既定値、失敗したときの動き)を自分で決めたときは、自分で決めたこととして報告する
- **違反や兆候**:
  - 変更に要らない名前の変更・整形・リファクタリングが、本来の変更と同じ差分に混ざる
  - 調べるために足したログやコメントが残っている
  - 上限・既定値・失敗したときの動きを自分で決め、報告に書かない
- **before / after**: 「ついでに import の順序を整えた」→「import の順序は別の変更として提案する」
- **blocking**: 依頼の範囲の外で、動きを変える変更がある
- **根拠**: 差分の各ファイルが、依頼のどの部分のためかを示す

## 7. 件数と待ち時間に上限を置く

- **いつ当てるか**: 件数に比例して増える処理、何かを待つ処理を書くとき
- **原則**: 件数に比例して増える処理と、何かを待つ処理には、上限を置く。件数の上限を置いてよいのは、上限を超えた分を読めなくても困らないときか、続きを読む手段(ページング)と組にするときだけである。上限を超えたときは、そのまま通さずに止める(原則1)
- **違反や兆候**:
  - 件数の上限なしに、全件を読む・送る
  - 件数の上限で読む範囲を切り、続きを読む手段を用意しない
  - ループの中で、外部の呼び出しや重い処理を1件ずつ行う
  - 時間の上限がない待ち(外部の呼び出し、ロック、キュー)
  - 上限を過ぎたときに、そのまま先に進む
- **before / after**: `await Promise.all(ids.map(fetchOne))` → `for (const batch of chunk(ids, 50)) await Promise.all(batch.map(fetchOne))` と、`ids.length` の上限の検査
- **blocking**: 外部の呼び出しか待ちに上限がない
- **根拠**: 上限の値と、超えたときの動き

## 8. 根本の原因を直す

- **いつ当てるか**: 不具合を直すとき。guard(値の検査)を足そうとするとき
- **原則**: 症状ではなく、最初に狂った場所を直す。再現してから、なぜを重ね、詰まったら観測を足す。guard を足すことが修正と言えるのは、その状態が正当に起こりうるときだけである。起こるはずのない状態を guard で通すのは、原因を隠すことになる。再起動の後だけ壊れるなら、保存された状態を疑う。同じ原因の誤りはすべて直す(原則5)。段落で説明が要る回避策は、コードが間違っている
- **違反や兆候**:
  - 原因を確かめずに、`if (x == null) return` を足して症状を消す
  - 直ったことを確かめずに、推測で「修正」する
  - 回避策に長いコメントが付いている
- **before / after**: 「`user` が `undefined` になることがあるので null チェックを足した」→「`undefined` になるのはセッションの期限切れのときだけだった。期限切れを明示のエラーにし、呼び出し元で再ログインに誘導した」
- **blocking**: 原因を確かめずに guard で症状を消している
- **根拠**: 原因を示す観測(再現の手順、ログ)と、直した後に再現しないこと
