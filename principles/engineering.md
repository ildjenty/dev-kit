# コードを書くときの原則

## 1. 失敗を隠さない

- **適用場面**: エラー、空、0件、上限超過、値の欠如、重複が発生した場合の挙動を決めるとき。
- **原則**: 失敗後も処理を継続してよいのは、結果の正しさを保証できる場合だけである。判断できない場合は、安全側に倒して明示的に失敗させる（fail-closed）。失敗は、エラーの型やログによって後から確認できる形で残す。「この失敗に、誰がいつ気づくか」に答えられないコードは書かない。空・0件・上限到達・値の欠如・重複・失敗が発生した際に、黙って既定値で処理を続けない。これらの場合の挙動はコードの意味を決めるため、既定値で継続すると、意味の変化を誰も検知できない。
- **違反・兆候**:
  - `catch` してログだけ出し、処理を続ける（呼び出し元は成功したと思っている）。
  - `catch { return null }` や `catch { return [] }` で、失敗を「データがなかった」にすり替える。
  - 空の識別子を既定値で処理し、分かれているはずのデータが混ざる。
  - 値の有無だけで分岐し、値がない場合の意味を定義していない。
  - 種類の違う失敗を1つにまとめる（入力エラーと内部障害、対象が存在しない場合と権限がない場合）。
  - 検査・認可・外部呼び出しが失敗したのに、そのまま通す。
  - 原因調査に必要な情報を残さない。または、機密情報をログやエラーに残す。
  - 確保したリソース（ファイル・接続・タイマー・購読）を、失敗時に解放しない。
  - 何にでもリトライを付ける（冪等でない処理や、やり直しても直らない失敗にも付ける）。
  - 非同期処理の失敗を待ち受ける処理がなく、失敗しても検知されない。
  - 設定や前提が不確かな状態で、外部への書き込みや処理の許可を行う。
- **変更前・変更後**:
  ```ts
  // before
  try { return await fetchPlan(id) } catch { return null }   // 失敗が「プランがない」になる
  // after
  try { return await fetchPlan(id) }
  catch (e) { throw new PlanFetchError(id, { cause: e }) }   // 失敗の種類が呼び出し元に伝わる
  ```
- **blocking**: 失敗を成功として扱う経路がある（検査・認可・外部呼び出しの失敗を通す、失敗を既定値にすり替える）。
- **根拠**: 失敗の経路ごとに、誰がどこで気づくか（例外の型、ログ、テスト）を示す。

## 2. 再実行と同時実行で結果が変わらないようにする

- **適用場面**: 外部に作用する処理、非同期に呼ばれる処理、同じデータを同時に扱う処理を書くとき。
- **原則**: 同じ入力で二度実行されても結果が変わらないよう、冪等に実装する。メッセージの重複配信、リトライ、タイムアウト後の再実行は、発生する前提で設計する。現在の状態を読み、目標との差分だけを適用し、「前回の意図」に依存しない。中断時に残るロック、一時ファイル、不完全なレコードは、次回の実行時に古い状態と判定できるようにする（一時ファイルへの書き込み後に rename する、内容を比較する）。
- **違反・兆候**:
  - 受け取ったイベントを無条件に INSERT する（二度届くと二重に登録される）。
  - 冪等キーなしで外部に送る（リトライで二重に送られる）。
  - 「前回の実行からの経過時間」のように、1回しか実行されないことを前提とする時刻計算。
  - 一連の更新が途中で止まると、中途半端な状態が残る（トランザクションやロールバック処理がない）。
  - 読んで確かめてから書くまでの間に、別の処理が割り込める（確認と更新が分かれている）。
- **変更前・変更後**:
  ```sql
  -- before
  INSERT INTO payments (event_id, amount) VALUES ($1, $2);
  -- after
  INSERT INTO payments (event_id, amount) VALUES ($1, $2) ON CONFLICT (event_id) DO NOTHING;
  ```
- **blocking**: 外部に作用する処理、または非同期に呼ばれる処理に冪等性がない。
- **根拠**: 二度実行したときの結果が同じであることを、テストか実行で示す。

## 3. 名前は初めて読む人に分かるように付ける

- **適用場面**: 変数・関数・型・ファイル・フォルダに名前を付けるとき。
- **原則**: コードと文書で使われている用語を使い、会話の中で作った用語を持ち込まない。同じものには一貫した名前を使い、内容が変わった場合は名前も変更する。名前は対象の責務の範囲を表すものとする。狭すぎる名前は、責務が広がると実態と合わなくなる。広すぎる名前は、責務を無制限に広げられてしまう。テスト名とエラーメッセージは英語で記述する。ログやエラーを調べる際の検索語を統一するためである。
- **違反・兆候**:
  - 配置と合わせても責務が分からない名前（`data` `info` `result` `item` `temp` `helper` `util` `manager` `handler`）。
  - 同じものを指す名前の揺れ（customer / client / user が同じものを指す）。
  - 実態に合わない boolean の名前（`isValid` が実際は「保存済みか」を表す）。
  - `processData2` `newHelper` のように、既存の名前との違いだけで付けた名前。
  - 全体を扱う処理やデータに、現在扱っている1件だけを表す名前を付ける。
- **変更前・変更後**: `const data = await getUser(id)` → `const customer = await findCustomerById(id)`
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 名前から、受け持つ範囲が1文で言えること。

## 4. コメントは、知らないと誤る制約を、コードで守れないときだけ書く

- **適用場面**: コメントを書くとき、コメントを残すかを決めるとき。
- **原則**: 原則としてコメントは書かない。次の両方に該当する場合に限って記述する。（1）コードの変更者・呼び出し元・保存したデータの利用者が、知らなければ誤る制約がある（外部ライブラリの挙動、呼び出し順序、セキュリティ上の前提、外部設定に基づく値、列の値の意味）。（2）その制約を、型・名前・テストのいずれでも保証できない。型やテストで表現した制約は、違反するとエラーになるが、コメントの制約は違反しても検知されない。外部ライブラリの不具合に対する回避策には、回避対象と削除できる条件（修正済みのバージョン、上流の Issue）を書く。設計上の選択・理由・経緯は、PR・Issue・設計文書に残す。コメントの読み手は、後でコードを読む人であり、今回の差分をレビューする人ではない。
- **違反・兆候**:
  - コードをそのまま言い換えたコメント（`// ユーザーを取得する` の下に `getUser()`）。
  - 引数名を言い換えただけの docstring。
  - 設計上の選択とその理由を書いたコメント（「〜は、〜のため、〜にする」）。
  - 型が守っている制約を、コメントでも書く。
  - 「〜に変更」「〜を修正」という経緯のコメント。
  - コメントアウトしたコードが残る。未解決の TODO が蓄積する。
  - `IMPORTANT` や `do not remove` だけで、理由がない。
- **変更前・変更後**:
  ```ts
  // before
  // 先に init() を呼ぶこと
  export function send() { ... }
  // after(型で守る)
  export function send(client: InitializedClient) { ... }
  ```
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 足した・残したコメントごとに、どの制約を守るか、なぜ型・名前・テストで守れないかを1行で言えること。

## 5. 変更の影響先と同じ原因の誤りを調べる

- **適用場面**: 関数・型・契約を変えたとき。誤りを1つ見つけたとき。
- **原則**: 変更の影響は、変更箇所よりも、その利用箇所や変更前の前提に依存する箇所に現れることが多い。関数・型・契約を変更した場合は、利用箇所をすべて調べる。公開している契約（型、スキーマ、設定のフォーマット）を変更した場合は、利用側と保存済みデータへの影響を確認する。誤りを1つ見つけた場合は、原因を言語化し、同じ原因による誤りがほかにないか調べる。
- **違反・兆候**:
  - 気づいた1か所だけを直して終える（同じ関数を使うバッチやツールが古いまま）。
  - 契約を変え、利用側と保存済みのデータへの影響を調べていない。
  - 同じ原因の誤りを、指摘されるたびに1つずつ直す。
- **変更前・変更後**: 「`parseDate` の戻り値を `Date | null` に変えた」→「`parseDate` の呼び出し元12か所を調べ、`null` を扱っていない3か所を同じ差分で直した」
- **blocking**: 契約を変えたのに、利用側を調べていない。
- **根拠**: 利用箇所の一覧（検索のコマンドと結果）と、それぞれどう扱ったか。

## 6. 根本の原因を直す

- **適用場面**: 不具合を直すとき。ガード（値の検査）を足そうとするとき。
- **原則**: 症状が現れた箇所ではなく、最初に異常が生じた箇所を修正する。まず再現し、原因を掘り下げ、行き詰まった場合は観測を追加する。ガードの追加が修正といえるのは、その状態が正当に起こりうる場合だけである。起こるはずのない状態をガードで処理すると、原因を隠してしまう。再起動後だけ失敗する場合は、保存された状態を疑う。同じ原因による誤りは、変更したモジュール内ではすべて修正する（原則5）。変更したモジュールの外にある同じ原因の誤りは、セキュリティ上の処理に当たる場合は同じ差分で修正し、それ以外は working.md の原則7に従って提案として報告する。回避策の説明に1段落を要する場合は、コード自体に誤りがある。
- **違反・兆候**:
  - 原因を確かめずに、`if (x == null) return` を足して症状を消す。
  - 直ったことを確かめずに、推測で「修正」する。
  - 回避策に長いコメントが付いている。
- **変更前・変更後**: 「`user` が `undefined` になることがあるので null チェックを足した」→「`undefined` になるのはセッションの期限切れのときだけだった。期限切れを明示のエラーにし、呼び出し元で再ログインに誘導した」
- **blocking**: 原因を確かめずにガードで症状を消している。
- **根拠**: 原因を示す観測（再現手順、ログ）と、直した後に再現しないこと。
