# ループの仕組みの原則

対象は、ループの仕組み（部品、組み立て、計画）である。メタループで harness を変更するときと、観点「harness」の check で読む。ループが作るコードなどの原則（design.md、testing.md など）や、ループの中の作業者の原則（working.md）とは対象が異なる。

## 1. 作成者と判定者を分ける

- **適用場面**: check を実行するとき。計画のレビューゲートで判定するとき。brief で委任した作業を受け入れるとき。
- **原則**: 成果物を作ったコンテキストと、それを判定するコンテキストを分ける。判定者は、作成時の会話や前提を引き継がず、対象の版と観点ファイルだけを受け取る。別系統のエンジン（Codex など）でもよい。作成者が自分の成果に出した `PASS` は、判定として扱わない。
- **違反・兆候**:
  - 作成に使った会話履歴を check にも渡している。
  - 作成者が同じセッションで観点ファイルを読んで自己レビューし、それを check の結果として記録している。
  - 判定者が、対象ではなく作成者の説明文を根拠にしている。
- **変更前・変更後**: 「実装したセッションで観点ファイルを読み、自分で `PASS` を出した」→「サブエージェントまたは Codex に、対象の版と観点ファイルだけを渡して判定させた」
- **blocking**: 必須の check が、作成と同じコンテキストで実行されている。
- **根拠**: check の実行設定（呼び出し方法、渡した入力）。

## 2. 判定は対象の版に結び付け、未評価を完了にしない

- **適用場面**: check の結果を記録するとき。router が「完了する」と判定するとき。ledger の check の結果を扱うとき。
- **原則**: 確かめていないことを確かめたように書かない点は、[verification.md](verification.md) の原則1に従う。harness では、判定を対象の版に結び付け、未評価を完了に変換しない。判定には対象の版を添え、対象の版が変われば、以前の判定は無効とする。実行できなかった check は `NOT ASSESSED` であり、`PASS` とは区別する。必須の check が未評価のままでは完了しない。
- **違反・兆候**:
  - 以前の版に対する `PASS` を現在の成果物に流用している。
  - router が `NOT ASSESSED` を「完了する」に振り分ける。
  - check の結果に対象の版がない。
- **変更前・変更後**: 「前回のレビューで通ったので完了にした」→「対象の版が変わったので check を再実行し、結果を対象の版とともに記録してから完了にした」
- **blocking**: 必須の check の結果が現在の版に対するものではない、または `NOT ASSESSED` のまま「完了する」に進む。
- **根拠**: check の結果の記録（対象の版、判定）。

## 3. check は、壊して検出できることを確かめるまで必須ゲートにしない

- **適用場面**: 観点ファイルを追加・変更するとき。check を採用するとき。hook を追加するとき。
- **原則**: テストについては、[testing.md](testing.md) の原則4に従う（実装前の失敗による確認で代替できる）。harness では、テスト以外の check（文書、設計案、skill、hook）にも同じ要求を適用し、セキュリティ上の処理に限定しない。新しい check・観点ファイル・hook は、意図的に blocking 違反を含めた対象に対して `FAIL`（hook なら block）を返した記録があるまで、必須ゲートとして信頼しない。
- **違反・兆候**:
  - 検出の記録がない観点ファイルが、計画で必須の check に設定されている。
  - check が対象を変えても常に `PASS` を返す。
  - hook が実際には block しない。
- **変更前・変更後**: 「観点ファイルを書いて計画に組み込んだ」→「blocking 違反を仕込んだ対象で `FAIL` が返ることを確認し、その記録を残してから組み込んだ」
- **blocking**: 検出の記録がない check・hook が必須ゲートになっている。
- **根拠**: 検出試験の記録（壊した対象、返った判定）。

## 4. セッションをまたぐ情報は、次のセッションが読める経路を持つ

- **適用場面**: ledger、runtime の hook、組み立て（assemblies）、checkpoint を設計・変更するとき。
- **原則**: 終了時に次の担当者が継続できる状態にすることは [working.md](working.md) の原則11、調査結果を利用前に外部へ記録することは [verification.md](verification.md) の原則5に従う。harness では、保存先と読み込み経路の一致を組み立てで確かめる。情報を外部に保存するだけでは足りない。保存先と、再開時にそれを読む経路（SessionStart の hook、再開の手順）が一致し、組み立てた状態で読み戻せることを確かめる。会話は記憶ではない。
- **違反・兆候**:
  - 保存先と読み込み先が異なる。
  - checkpoint を書くが、SessionStart が注入しない。
  - 再開の手順が会話の記憶を前提にしている。
- **変更前・変更後**: 「終了時に checkpoint を書く hook を足した」→「終了時に書き、SessionStart が同じファイルを読んで注入することを、組み立ての試験で確かめた」
- **blocking**: 必須の引き継ぎ情報について、保存先を読む経路が組み立てにない。
- **根拠**: 組み立ての試験の記録（保存し、別のセッションで読み戻した結果）。

## 5. 計画は、前提が崩れたときの戻り先を持つ

- **適用場面**: ループ計画を作成するとき。router が「前のステージに戻る」と判断するとき。複数ステージを組み立てるとき。
- **原則**: 複数ステージの計画では、各ステージの前提がどのステージの出力かを示し、前提が崩れたときの戻り先を定める。同じステージで対策を重ねない。[working.md](working.md) の原則4を harness に適用し、同じ前提に基づく修正が2回失敗したら前提を見直す。不可逆な決定を先に決めることは [design.md](design.md) の原則2に従う。ただし、開始するステージは変えるものから選び、計画は最小に保つ（[../docs/design.md](../docs/design.md) の「作成ルール」）。この原則を理由にステージを足してはならない。
- **違反・兆候**:
  - 同じステージの再実行しか選べない。
  - 同じステージで2回 check に失敗しても、前のステージを疑わない。
  - 前のステージに戻ったのに、残りの計画を作り直さない。
- **変更前・変更後**: 「実装のステージで3回修正を繰り返した」→「2回目の失敗で構造のステージに戻り、計画の残りを作り直した」
- **blocking**: 複数ステージの計画に、戻り先と再計画の規則がない。
- **根拠**: 計画の記録（ステージの入出力、戻り先）と router の表。
