# ループの仕組みの原則

## 1. 作成者と判定者を分ける

- **適用場面**: check を実行するとき。計画のレビューゲートで判定するとき。brief で委任した作業を受け入れるとき。
- **原則**: 作成者は自分の成果を過大評価しやすい。判定は作成者から独立させる。
- **違反・兆候**:
  - 判定者が、対象ではなく作成者の説明文を根拠にしている。
- **変更前・変更後**: 「作成者の説明に納得して判定した」→「対象そのものを調べ、説明に含まれない失敗のシナリオも検討して判定した」
- **blocking**: 判定が、対象そのものではなく作成者の説明を根拠にしている。
- **根拠**: 対象そのものから得た判定根拠。

## 2. 検出を実証するまで check を必須にしない

- **適用場面**: 観点ファイルを追加・変更するとき。check を採用するとき。hook を追加するとき。
- **原則**: 検出試験では、仕込んだ違反が狙った blocking 条件に当たり、返った判定がその違反を根拠にしているかを確かめる。失敗したという事実だけで、必要な検出能力があると判断しない。テストの検証は [testing.md](testing.md) の原則4に従う。
- **違反・兆候**:
  - 仕込んだ違反と無関係な理由で失敗した試験を、検出能力の根拠にしている。
  - check が対象を変えても常に `PASS` を返す。
- **変更前・変更後**: 「観点ファイルを書いて計画に組み込んだ」→「blocking 違反を仕込んだ対象で `FAIL` が返ることを確認し、その記録を残してから組み込んだ」
- **blocking**: 仕込んだ違反が狙った blocking 条件に当たらない、または判定が別の失敗を根拠にしている。
- **根拠**: 仕込んだ違反が blocking 条件に当たる理由と、検出試験の指摘内容。

## 3. 前提が崩れたときに戻るステージを決める

- **適用場面**: ループ計画を作成するとき。router が「前のステージに戻る」と判断するとき。複数ステージを組み立てるとき。
- **原則**: 複数ステージの計画では、各ステージの前提がどのステージの出力かを示し、前提が崩れたときの戻り先を定める。同じステージで対策を重ねない。[working.md](working.md) の原則4を harness に適用し、同じ前提に基づく修正が失敗を繰り返したら前提を見直す。不可逆な決定を先に決めることは [design.md](design.md) の原則2に従う。ただし、開始するステージは変えるものから選び、計画は最小に保つ（[../docs/loop-plan.md](../docs/loop-plan.md#作成ルール) の「作成ルール」）。この原則を理由にステージを足してはならない。
- **違反・兆候**:
  - 同じステージで check の失敗が続いても、前のステージを疑わない。
- **変更前・変更後**: 「実装のステージで修正を繰り返した」→「失敗が続いた時点で構造のステージに戻り、計画の残りを作り直した」
- **blocking**: 前提が崩れているのに、同じ前提のまま同じステージで修正を重ねている。
- **根拠**: 前提を見直した観測結果と、戻り先を選んだ理由。

## 4. 規則違反が再発したら、より強い強制手段に移す

- **適用場面**: 振り返り、指摘や失敗の反映先を決めるとき、規則と強制手段を見直すとき。
- **原則**: 文章で指示するだけでは、守られないことがある。文章だけで守らせている規則への違反が再発したら、「書いたのに防げなかった」と捉え、より強制力のある仕組み（文章 < skill の手順 < テスト < lint・型 < hook の順）に移せないかを検討する。
- **違反・兆候**:
  - 同じ違反が再び記録されているのに、文章の追記だけで済ませている。
- **変更前・変更後**: 「また同じ指摘が出たので、CLAUDE.md に注意書きを足した」→「再発したので、lint の規則にして文章から外した」
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 違反の記録（回数）と、移した先。
