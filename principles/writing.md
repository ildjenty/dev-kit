# 文章の原則

規則には固定の番号を付け、ほかの文書や check から番号で参照できるようにする（例: 「W4 に当たる」）。欠番が生じても番号を詰めない。

目的は、読み手が一度読んで理解できる文章にすることである。以下の規則はそのための手段であり、規則の文言を満たすこと自体を目的としない。

## 構成

- **W1 結論を先に書く**。最初の1〜2文で結論を示す。見出しや箇条書きで伝わる内容を、本文で繰り返さない。
  - 違反・兆候: 経緯から書き始め、結論が最後にある
- **W2 読み手が知らない名前には、説明を添える**。関数名、作業中に付けた名前、番号だけの参照（`#48`）には、目的の説明を添えるか、意味が分かる表現に言い換える。会話の中で作った用語を持ち込まない。
  - 違反・兆候: 「#48 に entitlements を追加」。変更後: 「プランに応じて使える機能を制御する仕組みを追加(#48)」
- **W3 人の判断に必要な情報を先に書く**。自分で判断した事項、未確認事項、リスクを、変更の詳細より先に記載する。人の判断に関係しない実装の詳細（関数の内部、変更ファイルの一覧）は記載しない。機械が読む固定フォーマット（終了ブロック、PR 本文の Verification）は、この規則の対象外である。
  - 違反・兆候: 変えたファイルの一覧が最初にあり、暫定判断が最後にある
- **W4 判断を求めるときは、選択肢を短い名前で並べ、推奨と理由を添える**。過去の回答から判断できることは質問しない。一度に確認する事項は少数に絞る。回答を受け取ったら、番号で指定された場合も選択肢の名前で言い直してから実行する。
  - 違反・兆候: 「どうしますか?」だけの問い
- **W5 根拠がないことは書き足さない**。依頼・会話・資料に根拠のない内容を追加しない。用語の説明など、根拠のある内容を補足した場合は、その旨を報告する。
- **W6 長さより、一度で分かることを優先する**。短さを優先して説明を圧縮しない。読み手が知らない内容や抽象的な内容は、具体例を使って説明する。
- **W7 表は比較に使う**。説明を列挙するために表を使わない。

## 言葉

- **W10 文書とコードで使われている言葉を使う**。同じものは同じ用語で呼ぶ。用語が異なると、読み手は別のものと解釈する。通常カタカナで使う用語（テーブル、レイヤー、リトライ、フォーマット）を、無理に日本語へ置き換えない。
  - 違反・兆候: 同じものを「配置」と「置き場所」の両方で呼ぶ
- **W11 比喩と擬人化を使わない**。誰が、または何が、どうするのか、どうなるのかを具体的に書く。
  - 違反・兆候: 「上に乗るもの」「名乗る」「守りを弱める」。変更後: 「後のステップと、これを使うコード」「出力に明記する」「別の店のデータが読めるようになる」
- **W12 英語の直訳の形を使わない**。物を主語にして人のように動作させる文や、「〜することができる」「〜を持つ」「〜することによって」といった表現を避ける。
  - 変更後: 「確かめることができる」→「確かめられる」
- **W13 名詞化して、誰が何をするかを消さない**。
  - 違反・兆候: 「重複登録の対処」。変更後: 「同じ店が二重に登録されないように直す」
- **W14 人によって判断が分かれる言い方をしない**。「適切に」「必要に応じて」「分かりやすいほう」といった表現は、具体的な判断基準に置き換える。
- **W15 具体的な主語と動詞で書く**。抽象名詞と動詞を組み合わせただけの表現で済ませない。
  - 違反・兆候: 「守りを弱める」。変更後: 「アプリが別の店のデータを読めるようになる」
- **W16 「〜ではなく〜」の対比は、誤解を正すときだけに使う**。同じ構文を繰り返さない。
- **W17 確信度を同じ文に付ける**。各主張に、直接 / 裏付けあり / 推論 / 推測 / 不明の5段階で確信度を示す（verification.md の原則2）。
- **W18 文書の中で矛盾させない**。「3つある」と記載しながら4つ列挙しない。見出しと内容、図と本文を一致させる。

## 文書

- **W20 同じ事実を2つの文書に書かない**。数値や決定は1つの文書だけに記載し、ほかの文書からリンクする。コードや設定から読み取れる仕組みも転記せず、正本となるコードを示す。
- **W21 同じテーマの文書を2つ作らない**。更新時は既存の文書を修正する。「v2」「改」など、世代を示す別ファイルを作らない。
- **W22 経緯を本文に混ぜない**。「当初は〜だったが〜に変更した」という経緯は、決定の記録に残す。本文には現在の結論だけを記載する。
- **W23 予定表を書かない**。途中の日程は変更のたびに更新が必要となり、更新を忘れると事実と異なる記載になる。文書に残す日付は、決定として合意した目標だけとする。日付は年から記載する。
- **W24 説明・参照・手順を1つの文書に混ぜない**。理由を理解する文書、仕様を参照する文書、操作手順を確認する文書では、読み手の目的が異なる。執筆前に、どれを記述するかを決める。
- **W25 確認していないことを、確認した事実のように書かない**。未確認であることを明記する（verification.md）。
- **W26 文書は、会話を知らない人がそれだけを読んで分かる状態で完成とする**。会話中に付けた名前・略語・比喩を持ち込まず、会話で共有した前提を省略しない。新しいセッションに文書だけを渡し、「初見で読んで、意味が取れない箇所を挙げて」と依頼して確認する。
- **W27 会話中の例だけに適用範囲を限定しない**。記述した内容に、会話に出ていない同種のケースを当てはめ、判断を読み取れるかを確認する。
- **W28 量を成果にしない**。文書を提示する前に、読み手に求める行動を一言で説明できるか確認する。説明できない場合は、提示できる状態ではない。

## 報告と PR 本文

- **W30 報告は、作業を見ていない人に向けて書く**。報告だけで内容を理解できるようにする。項目は3〜5点に絞る。check の指摘一覧は要約の対象外であり、全件を列挙する。
- **W31 PR 本文は Why / What changed / Scope / Tradeoffs / Blast Radius / Verification の順**。Why は1〜3文とする。Scope には対象に含めるもの・含めないものを必ず記載する。Tradeoffs には、読み手が確認すると考えられる却下案だけを記載する。Verification には実行したコマンドと結果を記載する。リポジトリ固有のフォーマットがある場合は、それに従う。
- **W32 一人称を使わない**。PR 本文とレビューコメントは人のアカウントから投稿されるため、「私は」と記述しない。変更や判断そのものを主語にする。決定者の情報が判断に必要な場合だけ、決定者を記載する。
- **W33 誤りを指摘されたら、誤りの内容と修正方法を具体的に示し、了承を得てから修正する**。言い訳をしない。この規則は、人が会話にいて誤りを指摘した場面に適用する。自律して作業している最中の可逆な修正は、working.md の原則10に従う。

## check との対応

../docs/design.md の観点「校閲」と、PR 本文と報告を対象にする観点「差分」に対応する。

- **blocking**: 観点「校閲」では、読み手が意味を取り違える箇所（W2、W11〜W15 の違反のうち意味が取れなくなるもの）。PR 本文と報告を対象にする観点「差分」では、W3（暫定判断が隠れる）、W25（未確認を確認済みのように書く）、W32（一人称）。
- **根拠**: 会話を知らない読み手が文書を理解できたこと（W26）、または校閲の check の結果。
