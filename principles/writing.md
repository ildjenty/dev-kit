# 文章の原則

目的は、読み手が一度読んで理解できる文章にすることである。

## 1. 結論と、人の判断に必要なことを先に書く

- **適用場面**: 文書、報告、PR 本文を提示するとき。
- **原則**: 最初の1〜2文で結論と判断材料を示す。自分で判断した事項、未確認事項、リスクを、変更の詳細より先に記載する。読み手に求める行動を一言で説明できるか確認し、説明できない場合は提示しない。人の判断に関係しない実装の詳細は記載しない。
- **違反・兆候**:
  - 経緯から書き始め、結論が最後にある。
  - 変えたファイルの一覧が最初にあり、暫定判断が最後にある。
  - 人の判断に関係しない関数の内部や変更ファイルの一覧を記載している。
  - 見出しや箇条書きで伝わる内容を、本文で繰り返している。
  - 読み手に求める行動が分からない。
- **変更前・変更後**: 「変えたファイルは次のとおりである。暫定判断は末尾に記載した」→「暫定判断で変更した。未確認事項とリスクを確認し、採否を判断してほしい」
- **blocking**: PR 本文と報告で、暫定判断・未確認事項・リスクが変更の詳細より後にあるか、書かれていない。
- **根拠**: 冒頭の1〜2文に結論と判断材料があること。

## 2. 読み手が知らない名前と、会話の文脈を持ち込まない

- **適用場面**: 名前や用語を使うとき、会話の内容を文書にするとき。
- **原則**: 関数名、作業中に付けた名前、番号だけの参照には、目的の説明を添えるか、意味が分かる表現に言い換える。文書とコードで使われている言葉を使い、同じものは同じ用語で呼ぶ。会話で共有した前提を省略しない。新しいセッションに文書だけを渡し、「初見で読んで、意味が取れない箇所を挙げて」と依頼して確認する。会話に出ていない同種のケースも当てはめ、判断を読み取れるかを確認する。
- **違反・兆候**:
  - 番号や名前だけで説明し、目的が分からない。
  - 会話中に付けた名前・略語・比喩や、会話を知らなければ分からない前提がある。
  - 同じものを「配置」と「置き場所」の両方で呼んでいる。用語が異なり、別のものと解釈される。
  - 通常カタカナで使う用語（テーブル、レイヤー、リトライ、フォーマット）を、無理に日本語へ置き換えている。
  - 会話中の例だけに適用範囲が限定され、同種のケースの判断が読み取れない。
- **変更前・変更後**: 「#48 に entitlements を追加」→「プランに応じて使える機能を制御する仕組みを追加(#48)」
- **blocking**: 読み手が意味を取り違える名前や用語の揺れがある。
- **根拠**: 会話を知らない読み手が文書だけで理解できたこと、または校閲の check の結果。

## 3. 誰が何をするかが分かる具体的な言葉で書く

- **適用場面**: 動作、状態、判断基準を文章にするとき。
- **原則**: 誰が、または何が、どうするのか、どうなるのかを、具体的な主語と動詞で書く。比喩・擬人化・英語の直訳・名詞化で意味を曖昧にせず、判断基準を具体的に示す。「〜ではなく〜」の対比は、誤解を正すときだけに使い、同じ構文を繰り返さない。
- **違反・兆候**:
  - 「上に乗るもの」「名乗る」「守りを弱める」のような比喩や擬人化がある。「後のステップと、これを使うコード」「出力に明記する」「別の店のデータが読めるようになる」と具体的に書く。
  - 物を主語にして人のように動作させる文や、「〜することができる」「〜を持つ」「〜することによって」といった直訳の形がある。「確かめることができる」は「確かめられる」とする。
  - 「重複登録の対処」のように名詞化し、誰が何をするかが消えている。「同じ店が二重に登録されないように直す」と書く。
  - 「適切に」「必要に応じて」「分かりやすいほう」のように、人によって判断が分かれる言い方がある。
  - 抽象名詞と動詞を組み合わせただけの表現で済ませている。
  - 誤解を正す目的のない対比や、同じ対比構文の繰り返しがある。
- **変更前・変更後**: 「守りを弱める」→「アプリが別の店のデータを読めるようになる」
- **blocking**: 比喩・直訳・名詞化・判断が分かれる言い方のうち、意味が取れなくなるものがある。
- **根拠**: 校閲の check の結果。

## 4. 確かめていないことは、確信度を添えて書く

- **適用場面**: 事実や推論を述べるとき、依頼・会話・資料に説明を補足するとき。
- **原則**: 確かめていないことを確かめたように書かない点は、[verification.md](verification.md) の原則1に従う。各主張には、同じ文に確信度を添える（同原則2）。依頼・会話・資料に根拠のない内容を追加しない。用語の説明などを補足した場合は、根拠の有無とともに、その旨を報告する。
- **違反・兆候**:
  - 未確認であることや確信度を記載せず、確認した事実のように書いている。
  - 確信度が主張と別の文にあり、どの主張に対応するか分からない。
  - 根拠のない内容を書き足している。
  - 補足した内容と、その根拠の有無を報告していない。
- **変更前・変更後**: 「確認済みである」→「未確認である(不明)」
- **blocking**: 未確認を確認済みのように書いている。
- **根拠**: 確信度の表記。

## 5. 一度で分かる長さと形にする

- **適用場面**: 説明の長さや、本文・箇条書き・表の使い分けを決めるとき。
- **原則**: 長さより、一度で分かることを優先する。読み手が知らない内容や抽象的な内容は、具体例を使って説明する。表は比較に使い、説明の列挙には使わない。
- **違反・兆候**:
  - 短さを優先して説明を圧縮し、理解に必要な内容が省かれている。
  - 読み手が知らない内容や抽象的な内容に、具体例がない。
  - 説明を列挙するために表を使っている。
- **変更前・変更後**: 「具体例を省いて説明を短くする」→「読み手が知らない内容には具体例を添え、一度で分かる長さにする」
- **blocking**: なし。
- **根拠**: 校閲の check の結果。

## 6. 文書の中と文書の間で、重複と矛盾を作らない

- **適用場面**: 文書を新しく作るとき、既存の文書を更新するとき。
- **原則**: 数値や決定は1つの文書だけに記載し、ほかの文書からリンクする。コードや設定から読み取れる仕組みは転記せず、正本となるコードを示す。同じテーマの文書を2つ作らず、既存の文書を修正する。理由を理解する文書、仕様を参照する文書、操作手順を確認する文書では読み手の目的が異なるため、執筆前にどれを記述するかを決め、1つの文書に混ぜない。見出しと内容、図と本文を一致させる。
- **違反・兆候**:
  - 「3つある」と記載しながら4つ列挙している。
  - 見出しと内容、図と本文が一致していない。
  - 同じ事実を2つの文書に書いたり、コードや設定から読み取れる仕組みを転記したりしている。
  - 「v2」「改」など、世代を示す別ファイルを作っている。
  - 説明・参照・手順を1つの文書に混ぜている。
- **変更前・変更後**: 「同じ数値を2つの文書に記載する」→「数値は1つの文書に記載し、もう一方からリンクする」
- **blocking**: なし（観点「整合」で検出する）。
- **根拠**: 整合の check の結果。

## 7. 本文に経緯と予定を混ぜない

- **適用場面**: 決定の経緯や日付を文書に残すとき。
- **原則**: 経緯は決定の記録に残し、本文には現在の結論だけを記載する。途中の日程は変更のたびに更新が必要となり、更新を忘れると事実と異なる記載になるため、予定表を書かない。文書に残す日付は、決定として合意した目標だけとし、年から記載する。
- **違反・兆候**:
  - 「当初は〜だったが〜に変更した」という経緯が本文にある。
  - 途中の日程が予定表として書かれ、現在の内容と混ざっている。
  - 合意していない目標の日付や、年のない日付がある。
- **変更前・変更後**: 「当初は〜だったが〜に変更した」→「本文には現在の結論を記載し、経緯は決定の記録に残す」
- **blocking**: なし。
- **根拠**: 本文が現在の内容だけであること。

## 8. 判断を求めるときは、短い選択肢に推奨と理由を添える

- **適用場面**: 人に判断を求めるとき。
- **原則**: 選択肢の違いと推奨の理由が、人の判断に役立つものかを確かめる。一度に確認する事項は少数に絞る。過去の回答から判断できることは質問しない。
- **違反・兆候**:
  - 過去の回答から判断できることを再び質問している。
  - 一度に多数の事項を確認している。
- **変更前・変更後**: 「どうしますか?」→「既存の文書を修正するか、別の文書を作るか。更新箇所を1つに保つため、既存の文書を修正する案を推奨する」
- **blocking**: なし。
- **根拠**: 選択肢と推奨の記載。

## 9. 報告と PR 本文は、作業を見ていない人に向けて書く

- **適用場面**: 報告、PR 本文、レビューコメントを書くとき、人から誤りを指摘されたとき。
- **原則**: 報告や PR 本文だけで、作業を見ていない人が変更と判断を理解できるようにする。PR 本文とレビューコメントは人のアカウントから投稿されるため、一人称を使わず、変更や判断そのものを主語にする。人が会話にいて誤りを指摘した場合は、誤りの内容と修正案を示し、了承後に修正する。自律して作業している最中の可逆な修正は、[working.md](working.md) の原則10に従う。
- **違反・兆候**:
  - 作業を見ていない人が、報告だけで内容を理解できない。
  - check の指摘一覧を要約し、全件を列挙していない。
  - Scope で、変更の対象に含めるものと含めないものを読み取れない。
  - Tradeoffs に、読み手が確認すると考えられる却下案以外を記載している。
  - 判断に必要のない決定者を記載している。
  - 人から指摘された誤りについて言い訳をしたり、内容と修正案を示さず、了承を得ずに修正したりしている。
- **変更前・変更後**: 「私は変更を終えた」→「プランに応じて使える機能を制御する仕組みを追加した。PR 本文に Why / What changed / Scope / Tradeoffs / Blast Radius / Verification を記載した」
- **blocking**: 一人称を使っている、または変更の範囲と検証結果を本文から読み取れない。
- **根拠**: 作業を見ていない人が、本文から変更の範囲と検証結果を理解できること。

## 10. 図は、箱の名前だけでなく関係と動作を示す

- **適用場面**: 図で関係や動作を説明するとき。
- **原則**: 矢印に動作のラベルを付け、箱の名前だけでは分からない関係と動作を示す。
- **違反・兆候**:
  - 箱の名前だけが並び、矢印に動作のラベルがない。
  - 矢印を見ても、何を書くか、何を無効化するか、いつ読むかが分からない。
- **変更前・変更後**: 「矢印にラベルがない図」→「矢印に『書く』『無効化する』『30秒ごとに読む』と記載した図」
- **blocking**: なし。
- **根拠**: 矢印のラベル。
