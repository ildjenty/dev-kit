# 画面の原則

画面を設計する・作るときの原則。画面は、利用者が判断する・行動するためにある。誰が、どんな状況で、何をしに来るかが決まらないうちは、画面に何を置くかも、その順番も決まらない。

## 1. 利用者の目的から始める

- **いつ当てるか**: 画面に何を置くかを決めるとき
- **原則**: 誰が、どんな状況で、何を判断し、何をするかを先に決める。画面に置くものは、その判断に要る情報から決まる
- **違反や兆候**:
  - 数字と文が並ぶだけで、何を決めるための画面かが分からない
  - 持っているデータを全部見せる作りになっている
  - 開いた人が、最初の数秒で何をすればよいか分からない
- **before / after**: 「注文の全項目を表に出す」→「出荷の担当が、今日出す注文を選ぶ画面。出荷日と状態を先頭に、残りは開いたら見える」
- **blocking**: 利用者と判断が決まっていない
- **根拠**: 利用者・状況・判断の1文

## 2. 慣習に従う

- **いつ当てるか**: 配置や操作を決めるとき
- **原則**: 利用者は、ほかの製品で覚えた型で画面を読む。よくある配置と操作から外れると、利用者は覚え直すことになる。同じ目的のよくある製品がどう置いているかを確かめ、それに従う
- **違反や兆候**:
  - よくある製品と違う場所に、同じ役割のもの(通知、戻る、保存)がある
  - 説明がないと使えない独自の操作がある
- **before / after**: 「保存ボタンを左上に」→「右下(同じ種類の製品の慣習)」
- **blocking**: なし(手がかりとして記録する)
- **根拠**: 参照した製品

## 3. 描く前に、置くものを文で合意する

- **いつ当てるか**: 画面を描き始める前
- **原則**: 描いた画面を作り直すのは手間がかかるが、文を直すのは簡単である。画面ごとに何を置くかを文で合意してから描く
- **違反や兆候**:
  - 何を置くかが決まらないまま、見た目の調整が始まっている
  - 描いた後で、画面の目的そのものが覆る
- **before / after**: 「モックを作ったので見てください」→「この画面に置くもの: 出荷日、状態、宛先、操作は『出荷済みにする』だけ。これでよければ描く」
- **blocking**: なし
- **根拠**: 合意した文

## 4. 判断に使わないものを置かない

- **いつ当てるか**: 要素を足すとき
- **原則**: 画面の要素が増えるほど、利用者が見るものが増える。判断に使わない要素は判断の邪魔になる。最初はよく使うものだけを見せ、詳しいことは必要なときに開けるようにする
- **違反や兆候**:
  - 消しても判断が難しくならない要素が残っている
  - 同じ情報が2か所に出ている
  - 配置や形で分かることを、文でも繰り返している
  - 詳しいことまで最初から全部見えている
- **before / after**: 一覧の各行に12列 → 判断に要る4列。残りは行を開くと見える
- **blocking**: なし(手がかりとして記録する)
- **根拠**: 要素ごとに、どの判断に使うか

## 5. 大事なものから目に入るようにする

- **いつ当てるか**: 大きさ・太さ・色・位置を決めるとき
- **原則**: 大きさ・太さ・色・位置で、判断に最も大事なものが最初に見えるようにする。関係するものは近くに、関係しないものは離して置く。近くにあるものや似た見た目のものは、同じグループとして読まれる
- **違反や兆候**:
  - すべてが目立っていて、どれも目立っていない
  - 関係のないものが近くに並び、同じグループに見える
- **before / after**: すべての数字を同じ大きさで → 判断に使う1つを大きく、残りは小さく
- **blocking**: なし
- **根拠**: 最初に目に入るべきものと、その見え方

## 6. 違いは形で示す

- **いつ当てるか**: 種類や状態の違いを表すとき
- **原則**: 種類や状態の違いは、言葉より位置・アイコン・形で示す。色だけに頼らず、色を使うときは形か文を添える
- **違反や兆候**:
  - 状態の違いが色だけで区別されている
  - 状態の違いを、毎回文で読まないと分からない
  - 押せないものが、ボタンのように見える
- **before / after**: 赤と緑の丸だけ → アイコン + 短い文言
- **blocking**: 状態の違いが色だけで区別されている
- **根拠**: 色を使った箇所と、添えた形か文

## 7. 利用者の言葉で書く

- **いつ当てるか**: ラベルと文言を決めるとき
- **原則**: ラベルと文言は、一般的な言葉と利用者自身の言葉で書く。状態を表す文言は、誰の何を待っているかをはっきり書く。読み手がどう受け取るか(要求、拒否、皮肉に読めないか)を確かめる
- **違反や兆候**:
  - 作る側の用語や、作業中に付けた名前がラベルに出ている
  - 「準備中です」だけで、利用者自身の作業を待っているように読める
  - 同じものが画面によって別の名前で呼ばれている
- **before / after**: 「entitlement の同期待ち」→「プランの反映を待っています(数分かかります)」
- **blocking**: なし(手がかりとして記録する)
- **根拠**: 文言の一覧

## 8. 状態が見え、誤りから戻れるようにする

- **いつ当てるか**: 操作の結果と失敗の扱いを決めるとき
- **原則**: システムの状態が見える、操作を取り消せる、誤りを防ぐ、覚えていなくても見れば分かる、慣れた人には近道がある、誤りに気づいて原因が分かり立ち直れる、説明がないと使えない所には助けがある。取り消せない操作の前には確認を置く
- **違反や兆候**:
  - 押した後に、何が起きたか分からない
  - 取り消せない操作が、確認なしで実行される
  - 失敗したときに、次に何をすればよいかが書かれていない
  - 説明がないと使えない所に、助けがない
  - よく繰り返す操作に、近道がない
- **before / after**: 「エラーが発生しました」→「保存できませんでした。通信が切れています。再接続して、もう一度保存してください」
- **blocking**: 取り消せない操作に確認がない
- **根拠**: 操作ごとの、結果の表示と失敗時の案内

## 9. すべての状態を設計する

- **いつ当てるか**: 画面を作るとき
- **原則**: 空・読み込み中・失敗・一部だけある・0件・1件・多数・長い文字列のときの見え方を決める。画面に出す値が、実際に取れるものかも確かめる
- **違反や兆候**:
  - データがそろった状態の見え方しか決まっていない
  - 文字列が長いと、重なる・はみ出す
  - 画面に出す値の取り先が決まっていない
- **before / after**: 「一覧を作った」→「0件・1件・100件・名前が80文字のときを確かめた」
- **blocking**: 0件と失敗の見え方が決まっていない
- **根拠**: 状態ごとのスクリーンショット

## 10. 誰でも使えるようにする

- **いつ当てるか**: 色、操作、読み上げを決めるとき
- **原則**: 文字と背景のコントラストを確保し(4.5:1 以上)、キーボードだけでも操作でき、読み上げにも対応する
- **違反や兆候**:
  - キーボードでは届かない操作がある
  - 薄い色の文字が背景に埋もれている
- **before / after**: `div` に `onClick` → `button`
- **blocking**: キーボードで届かない操作がある
- **根拠**: コントラストの値、キーボードでの操作の確認

## 11. 描いたもので確かめる

- **いつ当てるか**: 画面ができたと言う前
- **原則**: 見た目は、数値や説明ではなく、描画した結果を実際に見て判断する。スクリーンショットを撮り、画像として見る。見ていないページは判断できない
- **違反や兆候**:
  - 描画した結果を一度も見ずに「できた」としている
  - 文字の重なりやはみ出しに、利用者が先に気づく
- **before / after**: 「CSS を直したので直っているはずです」→「直した後のスクリーンショットを見て、重なりがないことを確かめた」
- **blocking**: 描画した結果を見ていない
- **根拠**: スクリーンショット

## 症状と直し方

よくある症状と、直し方の早見表。フレームワークに依存しない。

| 症状 | 直し方 |
|---|---|
| 古い時刻が「340日前」と出る | 1週間を過ぎたら絶対の日付にする |
| 数字が変わるたびに桁がずれる | `font-variant-numeric: tabular-nums` |
| 大きい見出しが間延びして見える | 字間を詰める(`letter-spacing: -0.02em` 程度) |
| 本文が読みにくい | 1行を 65 文字程度にする(`max-width: 65ch`) |
| ボタンの反応が鈍く感じる | `:active` で `transform: scale(0.97)` |
| アバターが楕円につぶれる | `flex-shrink: 0` |
| ドロップダウンがもたつく | 300ms 未満の `ease-out`。`ease-in` は使わない |
| ポップオーバーが違う所から出る | `transform-origin` をトリガーの位置に |
| 「1 members」と出る | `Intl.PluralRules` で複数形を扱う |
| アニメーションがかくつく | `transform` と `opacity` だけを動かす。`width` や `top` を動かさない |
| 長い一覧のスクロールが重い | 見えている分だけ描画する(仮想化) |
| `transition: all` で意図しないものが動く | 動かすプロパティを列挙する |
| 毎フレーム再描画される | `ref` の `style` に書き、state を使わない |

## Never / Instead

| Never | Instead |
|---|---|
| 入場のアニメーションに `ease-in` | `ease-out` |
| キーボードの操作にアニメーション | なし(1日に100回以上使う操作は動かさない) |
| hover の効果を touch の端末でも | `@media (hover: hover)` で囲む |
| `100vh` | `100dvh`、またはコンテンツに合わせた高さ |
| 入力欄のフォントを 16px 未満(モバイルでズームする) | 16px 以上 |
| 色だけで状態を表す | 形か文を添える |
| プレースホルダの文言(lorem、`TODO`)を残したまま納品 | 実際の文言 |
| 紫のグラデーション、光る球、ぼかしの塊を既定の装飾に | 内容から決めた色と形 |

## 画面が壊れる型

設計の段階で防ぐ、よくある壊れ方。

| 壊れ方 | 防ぎ方 |
|---|---|
| 暗い画面の読み込み時に白く光る | 最初の CSS で背景色を指定する |
| 画像や動画の上の文字が読めない | 文字の下に単色の帯か、コントラストの確保 |
| `100vh` で下が切れる | `dvh` か、コンテンツの高さ |
| 読み込み後にレイアウトが動く(layout shift) | 画像と埋め込みに大きさを指定する |
| JS が失敗すると空白になる | 静止状態で読める。アニメーションは `opacity: 0` で待たせない |
| touch の端末で hover に依存する操作 | hover なしで使える |
| 横にスクロールできてしまう | `min-width: 0`、`max-width: 100%`、はみ出す要素だけ `overflow-x: auto` |
| メニューを開いたまま背景がスクロールする | 背景のスクロールを止める |
| フォントが読み込まれず代替で表示される | 代替フォントを指定し、読み込みを確かめる |
| 長い名前・0件・大量・多言語で崩れる | 壊れやすいデータで確かめる |
