# 画面の原則

画面の目的は、利用者の判断と行動を支援することである。誰が、どのような状況で、何をするのかが決まらなければ、表示する内容も順序も決められない。

## 1. 利用者の目的から始める

- **適用場面**: 画面に何を置くかを決めるとき。
- **原則**: 誰が、どのような状況で、何を判断し、どのように行動するのかを先に定める。画面の要素は、その判断に必要な情報から決める。
- **違反・兆候**:
  - 数字と文が並ぶだけで、何を決めるための画面かが分からない。
  - 持っているデータを全部見せる作りになっている。
  - 開いた人が、最初の数秒で何をすればよいか分からない。
- **変更前・変更後**: 「注文の全項目を表に出す」→「出荷の担当が、今日出す注文を選ぶ画面。出荷日と状態を先頭に、残りは開いたら見える」
- **blocking**: 利用者と判断が決まっていない。
- **根拠**: 利用者・状況・判断の1文。

## 2. 慣習に従う

- **適用場面**: 配置や操作を決めるとき。
- **原則**: 利用者は、ほかの製品で覚えたパターンに基づいて画面を理解する。一般的な配置や操作から外れると、利用者に再学習を求めることになる。同じ目的の一般的な製品を参照し、その配置や操作に従う。
- **違反・兆候**:
  - よくある製品と違う場所に、同じ役割のもの（通知、戻る、保存）がある。
  - 説明がないと使えない独自の操作がある。
- **変更前・変更後**: 「保存ボタンを左上に」→「右下(同じ種類の製品の慣習)」
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 参照した製品。

## 3. デザインの作成前に、表示内容を文章で合意する

- **適用場面**: 画面を描き始める前。
- **原則**: 作成済みの画面を修正するには手間がかかるが、文章は容易に修正できる。画面ごとの表示内容を文章で合意してから、デザインを作成する。表示内容の合意は、router の「目的が合意されていない」に当たる確認である。
- **違反・兆候**:
  - 何を置くかが決まらないまま、外観の調整が始まっている。
  - 描いた後で、画面の目的そのものが覆る。
- **変更前・変更後**: 「モックを作ったので見てください」→「この画面に置くもの: 出荷日、状態、宛先、操作は『出荷済みにする』だけ。これでよければ描く」
- **blocking**: なし。
- **根拠**: 合意した文。

## 4. 判断に使わないものを置かない

- **適用場面**: 要素を足すとき。
- **原則**: 画面の要素が増えるほど、利用者が確認する対象も増える。判断に使わない要素は、判断を妨げる。最初は利用頻度の高い要素だけを表示し、詳細は必要なときに開けるようにする。
- **違反・兆候**:
  - 消しても判断が難しくならない要素が残っている。
  - 同じ情報が2か所に出ている。
  - 配置や形で分かることを、文でも繰り返している。
  - 詳しいことまで最初から全部見えている。
- **変更前・変更後**: 一覧の各行に12列 → 判断に要る4列。残りは行を開くと見える
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 要素ごとに、どの判断に使うか。

## 5. 重要な情報から目に入るようにする

- **適用場面**: 大きさ・太さ・色・位置を決めるとき。
- **原則**: サイズ・太さ・色・位置を使い、判断に最も重要な情報が最初に目に入るようにする。関連する要素は近づけ、関連しない要素は離して配置する。近接した要素や外観が似た要素は、同じグループとして認識される。
- **違反・兆候**:
  - すべてが目立っていて、どれも目立っていない。
  - 関係のないものが近くに並び、同じグループに見える。
- **変更前・変更後**: すべての数字を同じ大きさで → 判断に使う1つを大きく、残りは小さく
- **blocking**: なし。
- **根拠**: 最初に目に入るべきものと、その見え方。

## 6. 違いは形で示す

- **適用場面**: 種類や状態の違いを表すとき。
- **原則**: 種類や状態の違いは、言葉よりも位置・アイコン・形を優先して示す。色だけで区別せず、色を使う場合は形か文言を添える。
- **違反・兆候**:
  - 状態の違いが色だけで区別されている。
  - 状態の違いを、毎回文で読まないと分からない。
  - 押せないものが、ボタンのように見える。
- **変更前・変更後**: 赤と緑の丸だけ → アイコン + 短い文言
- **blocking**: 状態の違いが色だけで区別されている。
- **根拠**: 色を使った箇所と、添えた形か文。

## 7. 利用者の言葉で書く

- **適用場面**: ラベルと文言を決めるとき。
- **原則**: ラベルや文言には、一般的な用語と利用者自身の言葉を使う。状態を示す文言では、誰のどの操作や処理を待っているかを明記する。要求・拒否・皮肉と受け取られる可能性がないか、読み手の立場で確認する。
- **違反・兆候**:
  - 作る側の用語や、作業中に付けた名前がラベルに出ている。
  - 「準備中です」だけで、利用者自身の作業を待っているように読める。
  - 同じものが画面によって別の名前で呼ばれている。
- **変更前・変更後**: 「entitlement の同期待ち」→「プランの反映を待っています(数分かかります)」
- **blocking**: なし（参考情報として記録する）。
- **根拠**: 文言の一覧。

## 8. 状態を表示し、エラーから復旧できるようにする

- **適用場面**: 操作の結果と失敗の扱いを決めるとき。
- **原則**: システムの状態を表示し、操作を取り消せるようにし、誤操作を防ぐ。記憶に頼らず画面を見て理解できるようにし、熟練した利用者にはショートカットを用意する。エラーを認識して原因を理解し、復旧できるようにする。説明がなければ使えない箇所にはヘルプを用意する。取り消せない操作の前には確認を設ける。
- **違反・兆候**:
  - 押した後に、何が起きたか分からない。
  - 取り消せない操作が、確認なしで実行される。
  - 失敗したときに、次に何をすればよいかが書かれていない。
  - 説明がないと使えない所に、ヘルプがない。
  - よく繰り返す操作に、ショートカットがない。
- **変更前・変更後**: 「エラーが発生しました」→「保存できませんでした。通信が切れています。再接続して、もう一度保存してください」
- **blocking**: 取り消せない操作に確認がない。
- **根拠**: 操作ごとの、結果の表示と失敗時の案内。

## 9. すべての状態を設計する

- **適用場面**: 画面を作るとき。
- **原則**: 空・読み込み中・失敗・一部のみ存在する状態・0件・1件・多数・長い文字列の場合について、表示を定める。表示する値を実際に取得できるかも確認する。
- **違反・兆候**:
  - データがそろった状態の見え方しか決まっていない。
  - 文字列が長いと、重なる・はみ出す。
  - 画面に表示する値の取得元が決まっていない。
- **変更前・変更後**: 「一覧を作った」→「0件・1件・100件・名前が80文字のときを確かめた」
- **blocking**: 0件と失敗の見え方が決まっていない。
- **根拠**: 状態ごとのスクリーンショット。

## 10. アクセシビリティを確保する

- **適用場面**: 色、操作、読み上げを決めるとき。
- **原則**: 文字と背景のコントラストを確保する（4.5:1 以上）。キーボードのみで操作でき、読み上げにも対応する画面にする。
- **違反・兆候**:
  - キーボードでは届かない操作がある。
  - 薄い色の文字が背景に埋もれている。
- **変更前・変更後**: `div` に `onClick` → `button`
- **blocking**: キーボードで届かない操作がある。
- **根拠**: コントラストの値、キーボードでの操作の確認。

## 11. 描画結果を確認する

- **適用場面**: 画面ができたと言う前。
- **原則**: 外観は数値や説明だけで判断せず、描画結果を実際に確認して評価する。スクリーンショットを撮影し、画像として確認する。確認していないページは評価できない。
- **違反・兆候**:
  - 描画した結果を一度も見ずに「できた」としている。
  - 文字の重なりやはみ出しに、利用者が先に気づく。
- **変更前・変更後**: 「CSS を直したので直っているはずです」→「直した後のスクリーンショットを見て、重なりがないことを確かめた」
- **blocking**: 描画した結果を見ていない。
- **根拠**: スクリーンショット。

## 症状と対処方法

フレームワークには依存しない。

- **過去の日時が「340日前」と表示される**: 1週間を過ぎたら絶対日付にする
- **数字が変わるたびに桁がずれる**: `font-variant-numeric: tabular-nums`
- **大きい見出しが間延びして見える**: 字間を詰める（`letter-spacing: -0.02em` 程度）
- **本文が読みにくい**: 1行を 65 文字程度にする（`max-width: 65ch`）
- **ボタンの反応が鈍く感じる**: `:active` で `transform: scale(0.97)`
- **アバターが楕円形に変形する**: `flex-shrink: 0`
- **ドロップダウンがもたつく**: 300ms 未満の `ease-out`。`ease-in` は使わない
- **ポップオーバーが意図しない位置から表示される**: `transform-origin` をトリガーの位置に
- **「1 members」と出る**: `Intl.PluralRules` で複数形を扱う
- **アニメーションがかくつく**: `transform` と `opacity` だけを動かす。`width` や `top` を動かさない
- **長い一覧のスクロールが重い**: 見えている分だけ描画する（仮想化）
- **`transition: all` で意図しないものが動く**: 動かすプロパティを列挙する
- **毎フレーム再描画される**: `ref` の `style` に書き、state を使わない

## Never / Instead

- **表示時のアニメーションに `ease-in`**: `ease-out`
- **キーボードの操作にアニメーション**: なし（1日に100回以上使う操作は動かさない）
- **ホバー効果をタッチ端末でも**: `@media (hover: hover)` で囲む
- **`100vh`**: `100dvh`、またはコンテンツに合わせた高さ
- **入力欄のフォントを 16px 未満（モバイルでズームする）**: 16px 以上
- **色だけで状態を表す**: 形か文を添える
- **プレースホルダの文言（lorem、`TODO`）を残したまま納品**: 実際の文言
- **紫のグラデーション、光る球、ぼかしの塊を既定の装飾に**: 内容から決めた色と形

## 画面の表示・操作に関する典型的な不具合

- **暗い画面の読み込み時に白く光る**: 最初の CSS で背景色を指定する
- **画像や動画の上の文字が読めない**: 文字の下に単色の帯を置くか、コントラストを確保する
- **`100vh` で下が切れる**: `dvh` か、コンテンツの高さ
- **読み込み後にレイアウトが動く（layout shift）**: 画像と埋め込みに大きさを指定する
- **JS が失敗すると空白になる**: 静止状態でも読めるようにする。アニメーションは `opacity: 0` で待たせない
- **タッチ端末でホバーに依存する操作**: ホバーなしで操作できるようにする
- **横にスクロールできてしまう**: `min-width: 0`、`max-width: 100%`、はみ出す要素だけ `overflow-x: auto`
- **メニューを開いたまま背景がスクロールする**: 背景のスクロールを止める
- **フォントが読み込まれず代替フォントで表示される**: 代替フォントを指定し、読み込みを確かめる
- **長い名前・0件・大量・多言語で崩れる**: 表示が崩れやすいデータで確認する
