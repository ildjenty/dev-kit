Patterns are JSON files named `<name>.json` in `plans/`, maintained by the repository owner after `devkit init`. Prioritize one with `devkit start --plan <name>`. Patterns are references and do not constrain a plan. The planner may reference any available pattern and records its name and exact content hash in `pattern`. Omitting `--plan` uses `default_plan` in `devkit.toml`, whose default is `default`.

Patterns follow `schemas/plan-template.json`; task-specific plans follow `schemas/plan.json`, and planner responses follow `schemas/planner-result.json`. Patterns suggest stages, assignees, check names, gates with reasons, limits, and transitions. Gate reasons are free text; use the applicable classification name from `devkit.toml` or its defaults.

## Checks

Checks in patterns and plans select a configured aspect by name. Plans add required status, a target, completion condition IDs, and task-specific instructions:

```json
{"aspect": "test", "required": true, "target": "returned tree", "completion_condition_ids": ["C1"]}
```

`[checks.<aspect>]` in `devkit.toml` fixes runner, criteria, schemas, history, and brief_by_planner. Criteria select norm documents. An optional `description` supplies the planner check list text. When omitted or empty, devkit derives it from the first prose line of the first criteria document, or from the command runner.

A `command:<name>` check runs the registered verification command and has no criteria. If `command:<name>` is absent from the round-start `devkit.toml`, the check returns `FAIL` with an `auto-fixable` finding: "Verification command `<name>` is not registered. Create a verification method and register it in `[commands.<name>]` in `devkit.toml`." Registration is a loop edit, follows the human confirmation policy, and takes effect from the next round's snapshot. If a command changes the tree, its finding also instructs the worker to add generated output paths to the repository's Git ignore rules.

The `transitions.done` value is a stage ID to continue, `null` to finish, or `"replan"` to have the planner rebuild the remaining plan after that stage completes. Remaining work follows the completed stage run's bound plan and its transition order, including when a revised proposal is resubmitted. The name `replan` is reserved and cannot be a stage ID.

- `default`: purpose → replan → scope → architecture → increments → replan → design-k → implement-k → verification-k for each increment → acceptance → retrospective. Scope, architecture, and verification instances have human gates. Acceptance uses the verification definition. Optional candidates are research, prototype, and handoff.
- `fix`: implement → verification → retrospective. Optional candidates are research, prototype, and handoff. Implement requires `command:test`, `test`, and `diff`; verification requires `command:e2e` and `behavior`.
- `docs`: edit → retrospective. Edit selects `wording`.

In `default`, the first plan's completion conditions concern agreement on requirements and completion conditions. During purpose, clarify requirements with the human, record them in `requirements.md`, and output an agreed proposal for completion conditions. After purpose completes, the planner rebuilds the remaining plan using those conditions, and the human approves it. After scope and architecture approval, increments divides the release and ends with replan. The planner turns its output into increment instances; the human reviews their division and order during plan approval. The `fix` and `docs` patterns do not use this initial agreement flow.

Retrospective requires `command:test`, `test`, and `harness` in `default` and `fix`, and only `harness` in `docs`. Judge-run checks use the `judge` role (agent `devkit-judge`); `command:test` and `command:e2e` checks use the registered commands of the same names. Each stage is assigned to the `worker` role (agent `devkit-worker`).

Verification runs the scenarios for the completion condition IDs assigned to that instance's checks, end to end through the user's entry point. Acceptance assigns all condition IDs to a verification instance; the last increment demo may also serve as acceptance when it covers them all. When `[commands.e2e]` is not registered, the worker creates an end-to-end script and registers it, the same path as `command:test`. The `behavior` check judges whether each scenario is confirmed by that run. Handoff writes the PR description for reviewers following `templates/pr.md.tmpl` and is checked by `wording`; it performs no git operations. Insert it before retrospective when the work ends in a pull request. Bundled stage inputs include `git` (`.devkit/git.md`) for branch, commit message, and integration rules, and `authority` (`.devkit/authority.md`) for human decisions and delegations. Planner and plan judge inputs also include authority.

In `default`, build increments around completion condition IDs, each small enough for one implement instance's limits. Start with a thin skeleton from the user interface through to data, including startup and testing with explicit verification conditions. One increment is enough for a small task. Give each increment matching design-k, implement-k, and verification-k instances in that order. Insert prototype before scope when UI needs a visual example, and research or prototype before architecture when a choice depends on unverified premises. Write completion conditions in prose with IDs, and assign each check a target and completion condition IDs. Give each completion condition a way to verify it: a check run by a verification command, a judge, or a judgment command, or a human gate. Checks are not necessarily mechanical. Verify conditions during requirements definition through judges and human gates. The plan judge assesses the suitability and coverage of verification, and the human reviews it during plan approval; devkit does not enforce a formal assignment of verification to every condition. Preserve task-specific irreversible decisions in the plan; shared decisions and their enforcement and grounds belong in `rules.md`. Use `requirements.md` as the repository's requirements source. Stages changing UI, data, or external communication need behavior checks. If requirements are ambiguous, list unresolved points in the optional `open_questions` string array instead of guessing.

The configured loop rules constrain plans independently of patterns. `[[loop.stage]]` selects one definition, a list of definitions, or `"*"`; it can require check names and a human gate, restrict allowed roles, lower max_rounds and max_no_progress ceilings, and fix report, history, and outputs. `[[loop.path]]` has exactly one of require (one definition or a list), definition plus follows, first, or last. The default rules fix human gates for scope, architecture, and verification, and `history = "all"` for retrospective. They require implement checks command:test, test, and diff; verification checks command:e2e and behavior; and retrospective check harness. Each implement instance must be followed by verification in the same segment, and retrospective must be last.

Rules use definition IDs. The path is ordered adopted completed instances followed by the plan's reachable done chain. Follows must be satisfied before the next replan or end; require and last are checked when the path ends at null. First uses the first adopted or proposed instance. Plans reject unreachable stages and cycles. Ask and scalar fix transitions target their own instance. Back targets may name only current plan instances or instances that ran in this work. A back-triggered proposal must include its return instance. Reuse an instance ID only to rerun that work; give new work a fresh ID.

The global stage ceilings are `[limits] max_rounds_ceiling = 3` and max_no_progress_ceiling = 2. `[limits] max_total_rounds` defaults to 40. `[planning] max_rounds` defaults to 3. Planner and plan judge inputs belong to `[planning] inputs` and `[plan_check] inputs`, not patterns.

With default `[approval] plan = "deviation"`, approval is required for the first plan, changed completion condition IDs or descriptions, structural changes against the previously approved remaining plan, declared external operations, and open_questions. Replanning after increments changes the structure and requires approval, as does later removal of stages or gates within the loop rules. `requirements` requires approval for the first plan, changed conditions, external operations, and open questions, without requiring approval for structural changes alone. `always` requires every version. Human-approved completion conditions define completion. Questions return to the planner as revision instructions.

The approval question shows the ordered plan with definitions, assignees, gates, required checks, and instructions, plus a symmetric structural difference against the previously approved remaining plan, or the referenced pattern for the first plan. It also includes the original request, task, completion conditions, irreversible decisions, external operations, and open questions. Present devkit's question without replacing it with an agent summary.

A pattern stage may opt into `split: true`. Its task plan may supply `units`, each with a unique plan-wide `id`, a `description`, and a prose `scope` naming the files or directories it owns. Units require a split stage assigned to a work role; without units, work follows the ordinary stage path. The plan judge reports overlapping unit scopes; devkit checks ID uniqueness, not scope overlap. The bundled patterns do not use splitting.

Devkit limits outstanding subagent instructions with `[parallel] max_concurrent` (default 3, minimum 1), creates detached worktrees keyed by instruction ID, and merges the fixed unit SHAs before the usual stage judgment. Independent unit work, judge checks after verification commands, and pre-judgment planner instructions may run concurrently within both the global limit and `[roles.<id>] max_concurrent` limits; count issued subagent instructions until accepted. Gates, loop-edit confirmation, limits, back/replan, and questions remain at stage level. Already completed instances are omitted when comparing remaining plans.

## Roles and correction rules

Assign stage `assignee`, configured check `runner`, and unit `role` using role IDs from `[roles.<id>]` in `devkit.toml`. Defaults are `worker` (agent `devkit-worker`), `judge` (agent `devkit-judge`), `planner` (agent `devkit-planner`), and `human`. Unit `role` defaults to `worker` and requires a work role with an agent. Human roles may be stage assignees; gates are always human. Judge and plan roles are read-only. `[planning] role` selects the planner and `[plan_check] runner` selects the independent plan judge. Agent names must start with `devkit-`.

A work assignee with an agent and no explicit split units runs in one devkit-created detached worktree as a single unit, using the same merge and judgment path as split work. The session agent orchestrates: it launches the returned subagents, waits for their results, presents questions to the human, and integrates the work following the git rules. A work role with an empty `agent` means the session itself works in the checkout. A split stage may use the default worker role. Merge conflicts return to the stage assignee: an agent-backed work role receives one repair unit in a detached worktree with the merge in progress and conflict markers present, and its fixed result is merged before the remaining unit SHAs. An empty-agent work role repairs conflicts in the session checkout.

Only `transitions.fix` accepts an ordered rule array instead of the current stage ID:

```json
"fix": [
  {"when": {"check": "diff", "failures_at_least": 2}, "assignee": "senior_worker"},
  {"when": {"human_rejected": true}, "assignee": "senior_worker"}
]
```

Conditions are combined with AND. `check` matches an aspect with FAIL or NOT ASSESSED in the current round, regardless of runner. `failures_at_least` counts rounds with any required FAIL in this StageRun, including command checks. `human_rejected` matches a rejected stage question. The first match changes the next correction round's assignee; no match returns to the stage's default assignee. Rules never change stage, comparison base, or cumulative diff. Limits take precedence. A limit question can offer `continue:<role>` for roles in the rules; only approval to continue or selection of an offered role restarts the limit window. Rejection leaves the stage waiting for a new plan, abort, or a corrected answer. Undoing rejected loop edits or read-only source edits preserves the preceding assignee without applying rules.

Assignee, fix rule, and unit changes appear in the structural difference shown in the approval question. A judge's blocking finding may set `premise_broken: true`; devkit recommends `back` in a human question, and only the human's back answer follows the back/replan path.

Sources outside the repository are read-only: omit `writable` or set it to false. Devkit fixes their documents for each instruction; it does not create editable copies or write changes back. Apply improvements only to writable sources inside the repository, and record improvements to read-only sources as lessons for their maintainers.

## Reports, instructions, and context

A stage may select `report`, `unit_report`, and `human_prompt` as single knowledge selections (`source` and `select`). Reports select JSON Schema documents in norm sources, such as `templates/reports/implement.json`. A completion claim must match the selected report schema; questions and stops may contain partial reports. `unit_report` is optional and applies independently to each unit report, retained with its unit ID. Schema conformance is not evidence of completion. Human-assigned stages use the selected `human_prompt` document as the question.

Stage `delegations` is an array of document selections passed verbatim with provenance to applicable judges. Keep these standing delegations distinct from human-answer approvals. They cannot delegate plan or completion-condition changes, external operations, loop edits, limits, or interruption.

Stages, checks, and units in task plans may contain `instructions` arrays of strings. Patterns cannot contain instructions. Include these instructions in the approval question and corresponding role briefs without reinterpretation. Instructions are supplementary and cannot narrow fixed criteria or judgment scope. A configured check may enable `brief_by_planner` to obtain additional guidance immediately before judgment; the bundled patterns leave it disabled. Guidance, history selection, and reissues are bound to the round, aspect, and runner.

Stage and configured check `history` selects `none`, `stage_run`, `check`, or `all`. Defaults are `stage_run` for workers and `check` for judges. Bundled retrospective stages and harness checks select `all`. That fixed history includes the complete human-input list as well as questions and answers. Supply history as a fixed index reference, not an inline transcript. Regardless of this setting, judges receive applicable command results, valid approvals, and cited evidence and references.

Stage and unit `outputs` select instance IDs or definition IDs (all instances of that definition) whose adopted outputs are inline. Omitted or null means all adopted outputs; an empty array means none inline. Other outputs remain accessible through a fixed index. Adopted outputs come from the active execution path after the latest back or replan, using each completed StageRun's last adopted round. Superseded runs belong to history.

Configured check `schemas` lists binary schema names, without paths or `.json`, needed as input contracts. Supply their union with contracts referenced by the output schema, once each. The configured plan check defaults to `plan`, `plan-template`, and `finding`. Fixed stage fields are enforced only by loop.stage rules; check settings are fixed by the registry. Units have no `after`; work depending on another result belongs in a later stage.

All request kinds respect `[briefs] max_bytes`, including pre-judgment planner instructions. Oversized bodies and contracts are moved whole to referenced files. A limit too small for the minimal instruction and file reference is a configuration error. Registered judgment commands receive the full JSON input when it fits; otherwise stdin contains `InstructionID`, `Kind`, and `request_path`, the absolute path of the complete JSON input. Read that whole file before evaluating the request.
