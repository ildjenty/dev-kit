# Brief request templates

These repository-owned Go `text/template` sources define work, judgment, and planning requests under `templates/brief/`.

- `templates/brief/work.md.tmpl`: The current stage, task and plan, verification, repository facts, fixed norms, previous outputs and findings, and command or pre-commit output. Change boundaries come from scope outputs and rules.md. Every work request references a work-history file fixed at instruction issue time; the stage definition determines its use. The file contains all judgments and findings, including nonblocking findings, FAIL and NOT ASSESSED history, round counts per stage run, human questions and answers, and lesson notes. Return the progress block using `schemas/progress.json` and `devkit submit <file>`.
- `templates/brief/judgment.md.tmpl`: The judgment content, instruction ID, repository requirements, relevant structure records, rules, fixed norms, and work-history file reference. Round judgments include the expanded round-start comparison base, changed-file list, and a patch file under the brief directory, with short patches also shown inline. The common judgment rules appear once in this template. Return a JSON-only final message using the supplied schema (`schemas/judgment.json`).
- `templates/brief/planner.md.tmpl`: The original user request, the task supplied to start, loop template, stage definitions, repository facts, fixed norms, available checks, and any current or remaining plan, human instructions, and previous findings. An unobserved original request is explicitly marked as absent. Unresolved requirements belong in `open_questions`, without guesses. Return a JSON-only final message using `schemas/planner-result.json` with a plan following `schemas/plan.json`.

The binary supplies self-contained output schemas as text, bundling all referenced definitions. Supporting schemas are limited to references from the output contract and explicitly selected input contracts (`schemas` on the check); each is supplied once. Inline inputs contain the applicable stage definition, the criteria documents explicitly selected by the check, rules.md, requirements.md, and relevant structure.json records. Other norms are listed by logical name and fixed snapshot path; read them when needed from that expansion, not from the working tree. Round norms are fixed at round start. Plan checks use committed norms from the work checkout HEAD fixed at instruction issue time.

Template inputs use `Norms` for selected inline norm documents (`Path` and `Content`) and `NormPaths` for the remaining norms (`Path` for the logical name and `SnapshotPath` for the fixed expansion path). `Repository.Requirements` supplies the requirements reference and content when the role selects the default requirements input. Repository product references show the actual working-tree paths and whether each product exists; a missing requirements file is identified as not created yet with the path at which to create it. `Repository.LayoutGuides` supplies selected structure records; `Repository.Rules` supplies rules.md when selected. Unselected repository fields are omitted from the rendered brief. Judgment content supplies the applicable stage and check name. `Criteria` supplies the selected criteria documents, each with `Path` (source name and document ID or path) and `Content` (the fixed body). `OriginalRequest` preserves the original user text for planning, or is empty if none was observed. Work-history references are generic inputs; stage definitions and criteria decide how to use them.

Read the full generated request and its references, and retain its `instruction_id` in the result. Follow `stages/README.md` for work submission and completion, `principles/review/README.md` for review documents and the judgment template for common judgment rules, and `plans/README.md` for planning.

`templates/brief/unit.md.tmpl` uses the work inputs plus `Unit` (`ID`, `Description`, `Scope`) and the absolute `WorktreePath`. It directs a `devkit-worker` to edit only that worktree and scope and return `schemas/progress.json` as its final message instead of submitting. The parent accepts hook observations and merges fixed unit SHAs for one stage judgment.

Template `planner_inputs` and `judge_inputs` select knowledge for planners and judges. Stage `inputs` selects worker knowledge. An omitted or null selection list defaults to requirements, rules, and structure; an explicit array replaces those defaults, and an empty array selects no knowledge. The bundled templates express the default selections as data. Rules section names and guidance belong in these distributed request templates.

## Flow context

Work and unit template inputs add `CurrentMaterial` (string) and `ReportSchema` (string containing the selected stage or unit report schema). Plan instructions use `Stage.Instructions` and, for units, `Unit.Instructions`. `PreviousOutputs` contains adopted reports and fixed artifact references, not superseded StageRuns. `WorkHistoryPath` points to the fixed optional history index; it is not an inline transcript.

Judgment inputs add `Instructions` and `PreJudgmentInstructions` (string arrays), `PreviousOutputs` (stage outputs), `CurrentMaterial` (string), `WorkHistoryPath` (fixed index path), and `Delegations` (documents with `Path` provenance and `Content`). Planner instructions supplement fixed criteria without narrowing judgment scope; original diff, reports, plan, and requirements remain separate inputs. Applicable command results, valid approvals, and cited evidence and references are always current material, independently of history selection. Retain every unit report with its unit ID for the merged judgment.

Work and unit requests contain confirmation guidance for the fixed `confirmation` shape in progress: `text`, `options`, `recommendation`, `recommendation_reason`, and `evidence` references. The question is verbatim and human answers stay free-form. The optional stage-specific `report` is separate; validate its full shape only for completion claims and allow conforming partial fields for questions or stops.

The brief size limit is `[briefs] max_bytes` (default 200000). Move excess material to fixed files with a visible reference list and record the overflow; never silently truncate it. `outputs` limits inline adopted outputs only; other adopted outputs remain available from the fixed index. Avoid duplicate document and schema bodies, and keep machine-readable metadata to IDs and hashes.

`templates/brief/judgment-brief.md.tmpl` asks the planner how to check one round before a check with `brief_by_planner = true`. Its inputs are `InstructionID`, `InstructionIDJSON`, `Check`, `PlanJSON`, `Requirements`, `CurrentMaterial` (the round report and stage comparison), and `OutputSchema` (`schemas/judgment-brief.json`). The returned `instructions` reach the judge as `PreJudgmentInstructions`, keyed by round, aspect, and runner like the judgment itself.
