# Brief request templates

These repository-owned Go `text/template` sources define work, judgment, and planning requests under `templates/brief/`.

- `templates/brief/work.md.tmpl`: The current stage, task and plan, verification, repository facts, fixed norms, previous outputs and findings, and command or pre-commit output. Change boundaries come from scope outputs and rules.md. Every work request references a work-history file fixed at instruction issue time; the stage definition determines its use. The file contains all judgments and findings, including nonblocking findings, FAIL and NOT ASSESSED history, round counts per stage run, human questions and answers, and lesson notes. Return the progress block using `schemas/progress.json` and `devkit submit <file>`.
- `templates/brief/judgment.md.tmpl`: The judgment content, instruction ID, repository requirements, relevant structure records, rules, fixed norms, and work-history file reference. Round judgments include the expanded round-start comparison base, changed-file list, and a patch file under the brief directory, with short patches also shown inline. Detection tests supply example bodies without case kinds or expected judgments; devkit compares the returned actual judgments with expectations. Return a JSON-only final message using the supplied schema (`schemas/judgment.json`, or `schemas/detection-result.json` for detection tests).
- `templates/brief/planner.md.tmpl`: The original user request, the task supplied to start, loop template, stage definitions, repository facts, fixed norms, available checks, and any current or remaining plan, human instructions, and previous findings. An unobserved original request is explicitly marked as absent. Unresolved requirements belong in `open_questions`, without guesses. Return a JSON-only final message using `schemas/planner-result.json` with a plan following `schemas/plan.json`.

The binary supplies self-contained output schemas as text, bundling all referenced definitions. Work requests also supply supported `devkit note` kinds and their bundled schemas, and `schemas/structure.json`. Inline inputs contain the applicable stage definition, the aspects being judged and the principles they reference, rules.md, requirements.md, and relevant structure.json records. Other norms are listed by logical name and fixed snapshot path; read them when needed from that expansion, not from the working tree. Round norms are fixed at round start. Plan checks and detection tests use committed norms from the work branch HEAD fixed at instruction issue time.

Template inputs use `Norms` for selected inline norm documents (`Path` and `Content`) and `NormPaths` for the remaining norms (`Path` for the logical name and `SnapshotPath` for the fixed expansion path). `Repository.Requirements` supplies the requirements reference and content in all three briefs. Repository product references show the actual working-tree paths and whether each product exists; a missing requirements file is identified as not created yet with the path at which to create it. `Repository.LayoutGuides` supplies relevant structure records; `Repository.Rules` supplies rules.md. Judgment content supplies the applicable stage and aspect. `OriginalRequest` preserves the original user text for planning, or is empty if none was observed. Work-history references are generic inputs; stage definitions and aspects decide how to use them.

Read the full generated request and its references, and retain its `instruction_id` in the result. Follow `stages/README.md` for work submission and completion, `checks/README.md` for judgments, and `plans/README.md` for planning.

`templates/brief/unit.md.tmpl` uses the work inputs plus `Unit` (`ID`, `Description`, `Scope`) and the absolute `WorktreePath`. It directs a `devkit-worker` to edit only that worktree and scope and return `schemas/progress.json` as its final message instead of submitting. The parent accepts hook observations and merges fixed unit SHAs for one stage judgment.
