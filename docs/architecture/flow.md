# 処理の流れ

人が課題を渡すと、計画、作業、判定、完了時のコミットの順に進む。エージェントは `devkit` の指示を実行し、`devkit` は結果を記録して次の行動を決める。人の回答や外部操作を待つ間は現在地を保持し、別のセッションでも記録から再開する。各段階の進行には[中断](guarantees.md#中断)の照合を適用する。

## 作業の開始

`devkit init` は導入するファイルを示して人の確認を受け、導入したファイルをコミットする。`--no-commit` でコミットを省ける。

`start` は記録などの副作用より前に、HEAD の存在と、作業ツリーに存在する設定済みの規範のパス・`devkit.toml`・サブエージェント定義のディレクトリ(各[役割](data.md#役割-role)の agent の定義ファイルを含む)がすべてコミット済みで変更されていないことを確かめる。不成立なら対象パスの一覧と「devkit init の変更を先にコミットする」という直し方を返して拒否する。

作業中のチェックアウトでの2つ目の `start` は拒否する。別の worktree で新しいセッションを開けば、チェックアウトごとに独立したループを並行して回せる。それぞれが自分の `.devkit/run/` に記録を持つ。

人は通常どおりセッションを開き、kit の skill で課題を伝える。メインのエージェントは `devkit start --plan <name> <課題>` で作業を開始する。`--plan` は優先するパターンであり、省略時は `default_plan`(既定 default)を優先する。計画者はどのパターンも参考にできる。パターンは既定 `.devkit/plans/` に置き、設定で変更できる。まとめ役は git の規則に従い開始前に作業ブランチを用意する。engine はブランチを作らず、作業 ID、開始時のブランチ、基点コミット、kit_version をチェックアウトの記録に残してセッションを束縛する。返すのは計画者の指示 ID と `.devkit/run/work/<作業 ID>/brief/<指示 ID>.md` のパスである。開始は[hook の稼働確認](guarantees.md#再開と-hook-の稼働確認)も必要である。

メインのエージェントは壁打ちで合意した内容を `start` の課題に書く。`devkit start --task-file <ファイル>` は課題の本文をファイルから読む指定であり、課題引数と併用しない。途中の `devkit instruct <ファイル>` は指示を記録し、次の計画者・作業者へ渡す。判定者へは渡さない。計画や完了条件を変える場合は再計画と承認を通す。会話の写しは取らず、サブエージェントは1行の指示 ID だけで起動する。

既定のパターンは次の構成であり、ステージの担当には既定の役割 `worker`、check の runner には既定の役割 `judge`(agent は `init` が配る `devkit-judge`)を使う。

既定のパターンは複数単位への分割を使わない。計画者はパターンを参考に `split` と `units` を組み、採用済みの完了した実体は経路に保持して残りを計画する。

- `default`: purpose → scope → structure → contract → steps → implement → verification → retrospective が参考の並びである。候補は research・prototype・handoff、scope にゲートを置く。implement の必須 check は `command:test`・test・diff である。
- `fix`: implement → verification → retrospective。候補は research・prototype・handoff、implement の check は必須の `command:test` と観点 `test`・`diff` である。
- `docs`: edit → retrospective が参考の並びであり、文書編集の定義 edit に wording の check を置く。

`default` は `purpose` の遷移 `done` を `"replan"` にする。最初の計画の完了条件は、要件と完了条件の合意に関するものとする。`purpose` で人に確かめながら要件を詰め、requirements に書き、完了条件の案を作る。`purpose` の完了後、計画者が合意した完了条件で残りを作り直し、人が承認する。`fix` と `docs` はこの形を使わない。

エージェントは `[planning] role`(既定 planner、agent devkit-planner)を1行の指示 ID で起動する。計画者には優先パターンの本文、ほかのパターンの固定したパス、`stages/README.md` の定義 ID・名前と各定義の固定した参照、役割、check の名前と1行の説明、組み方の方針を渡す。計画者は定義済みの部品を使って、実体 ID と定義を分け、並び・担当・check・ゲート・上限・遷移・指示を毎回組む。曖昧な要求は `open_questions` に記す。SubagentStop が最終メッセージを保存し、次の next が JSON Schema、参照の解決、上限の天井、作業の経路の決まりを[計画の契約](data.md#計画-plan)に従って検証する。受理した計画を提案中として記録する。

## 計画の check と承認ゲート

計画の check の観点と runner は `[plan_check] aspect = "plan"`・`runner = "judge"` を既定とする。runner は `judge` の種類の役割の ID か、登録済みの判定コマンドの名前である。判定コマンドなら devkit がステージの判定と同じ経路で実行する。役割なら `devkit next` が指示 ID と判定依頼のパスを返し、エージェントがその役割の agent を起動する。runner の agent は計画者の役割の agent と違うものでなければならない。hook を経由した結果を次の `next` が受理して集約する。[判定値](data.md#check-の結果-judgment)が `FAIL` の場合の再提案と人への確認は[計画のバージョン](data.md#計画のバージョン)に従う。計画の判定のやり直しの上限は `[planning] max_rounds`(既定3)とする。

計画の判定依頼には、作業に記録した`start` の課題を固定入力として渡す。判定者は、完了条件と `open_questions` が課題の要求を漏らさず扱い、要求を追加していないかを確かめる。完了条件ごとの確認手段と、その妥当性・網羅性の判断は[計画](data.md#計画-plan)に従う。

計画の承認はパターンとの違いによらず、`[approval] plan` で定める。既定の `"requirements"` は最初の計画、直前に人が承認した完了条件の ID または文面が変わる計画、外部操作を宣言した計画を人に確認する。`"always"` はすべてのバージョンを確認する。`"deviation"` は最初の計画に加え、前に承認した計画の残りと構造が違う計画、外部操作を宣言した計画を確認する。`open_questions` が空でない計画はいずれの方針でも人の承認を必須とする。同じ完了条件で外部操作も未決事項もない再計画は、既定では再確認しない。

`open_questions` が空でない計画は、`[approval] plan` の値によらず人の承認を必須とする。

計画承認の問いは devkit が記録から組み立てる。`start` の課題、ID 付きの完了条件、計画の並びと各ステージの実体 ID・定義・担当・ゲート・必須 check・ステージと check と単位の指示、課題固有の元に戻せないもの、外部操作、`open_questions` を載せる。前に承認した計画の残りとの構造の差分を表示し、最初の計画では参考にしたパターンと比較する。差分には追加・除外・変更の両方向を含める。パターンとの違いは表示する判断材料であり、承認の理由にはしない。エージェントの要約に頼らない。

未決事項への人の回答は、計画の却下と作り直しの指示として計画者に渡す。この再提案の回数に上限は設けない。人が承認した完了条件を作業の完了の基準とする。

承認待ちからは[人の回答と再開](#人の回答と再開)に従って進める。実行可能になる条件と作り直しは[計画のバージョン](data.md#計画のバージョン)に従う。必要な[検出試験](guarantees.md#検出試験)(check の判定能力を確かめる試験)も、作業のラウンドを開く前に `next` の指示で済ませる。判定者には基準の文書、匿名の例の本文、出力の約束だけを渡す。仕様・期待判定・対応表と、それらを含む履歴や参照先を除き、`devkit` が期待と照合する。

## 作業の指示

`devkit next` は、ステージ開始時に実行可能な計画の経路を固定した規範で検査し、現在の [StageRun](data.md#ステージの実行-stagerun)(ステージの実行記録)と[ラウンド](data.md#ラウンド-round)(作業の指示から次の行動の確定までの往復)を特定する。[hook の稼働](guarantees.md#再開と-hook-の稼働確認)を確認し、[対象のバージョン](data.md#対象のバージョン-targetversion)(評価対象を識別する値)を取得して、識別したセッション ID をラウンドに結び付ける。既定ではラウンドを開く前に、その開始時のスナップショットに新たな未確認のループ自身の変更がないかを確かめ、あれば[人への確認](guarantees.md#人への確認対象)を受けるまで止める。却下された変更が同じまま残る場合は再確認を求めず、作業対象を保持して、変更ファイル一覧を添えた取り消しの作業ラウンドを指示する。engine は [brief](modules.md#brief)(作業や判定の依頼文)をファイルに書き、[出力上限](guarantees.md#性能と出力の上限)に応じて返す。人が担当するステージの扱いは[計画の担当](data.md#計画-plan)に従う。

ラウンドの担当は、直前の修正の判断に記録した担当であり、記録がなければステージの `assignee` である。担当が agent のない `work` の役割ならセッションのエージェントがチェックアウトで作業する。agent のある `work` の役割なら、そのラウンドを1つの単位として[分割した作業と合流](#分割した作業と合流)と同じ経路で動かす。

本文で渡す知識は、`[planning] inputs`・`[plan_check] inputs`・計画のステージの `inputs` と、`[checks.<観点>] criteria` で選ぶ。要件と規則を渡す既定値を用意する。ステージの実体の `definition` でステージ定義を解決する。規範はソース全体を固定し、成果は選んだ本文を固定する。その他の規範はソース名・文書 ID・固定した写しのパスの一覧で渡し、編集中の原本を読ませない。文中の参照を解析して入力を補わず、必要な文書は選び方に明示する。変更の範囲は scope の出力と rules で渡す。

依頼の入力は[依頼の入力](data.md#依頼の入力)に従い、採用された成果、今の材料、経緯に分ける。経緯は本文に入れず、`history` の範囲を記録から決定的に絞った固定した索引で渡す。ステージ・単位の `outputs` は本文に入れる採用された成果を選ぶ。判定者にも前のステージの採用された成果と直前のラウンドの報告への固定した参照を渡す。検証コマンドの実行結果、有効な承認、引用された証拠と参照先は `history` によらず必ず渡す。重複する本文は1回だけ載せる。出力スキーマと check の `schemas` の和集合、成果のパスと未作成時の案内は [brief](../parts/brief.md#入力と出力)に従う。検出試験には履歴を渡さない。

課題ごとの計画のステージ・check・単位にある `instructions` は、devkit が解釈せず対応する依頼文へそのまま入れる。`[briefs] max_bytes`(既定200000)を超える分はファイルにして一覧で渡し、超えた事実を記録する。黙って切り詰めない。

requirements はリポジトリが満たすべき要件の正本であり、既定 `.devkit/requirements.md` に置く。purpose が承認された完了条件と既存の要件を照らして更新する。structure は構造のステージが既定 `.devkit/structure.json` に記録する。複数の作業で守る変更困難な決定は既定 `.devkit/rules.md` に置き、ループ自身の変更として[確認の設定と時点](guarantees.md#人への確認対象)に従う。これらの場所と接続先は `[sources.requirements]`・`[sources.structure]`・`[sources.rules]` で変更できる。実行の記録は git 管理しない。各ステージは後の作業に効かせる決定を requirements・structure・rules のいずれかに残す。

既定の作業者は `devkit-worker` であり、devkit が作る自分の worktree で作業し、終了ブロックを SubagentStop 経由で返す。セッションのエージェントは起動・待機・人への問いの提示・git の規則に従う統合を担う。agent のない `work` の役割を定義した場合はセッション自身で作業でき、他の skill や plugin も使える。途中の決定や調査結果は `devkit note`、作業の[終了ブロック](data.md#進捗-progress)(作業結果を固定形式で返す JSON)は `devkit submit <ファイル>` で渡す。教訓も `note` で渡し、記録は [engine の責務](modules.md#engine)に従う。入力 JSON の場所と受理の条件は[状態遷移と受理条件](data.md#状態遷移と受理条件)に従う。コミットは[完了時の永続化](guarantees.md#判定対象の展開と完了時の永続化)に委ねる。

### 分割した作業と合流

`split: true` のステージに `units` があれば、`next` は単位ごとの作業指示を返す。単位がなければ通常のステージとして作業する。セッションのエージェントは、単位ごとにその単位の `role`(既定 `worker`、agent `devkit-worker`)の agent を、1行の `devkit-instruction <指示 ID>` で起動する。`init` は両ホストの `devkit-worker` の定義を配る。`work` の役割の agent は判定者用の書き込み禁止 `[deny] judge` の対象外であり、`judge`・`plan` の役割への禁止は維持する。

agent のある `work` の役割がステージの担当になったラウンドは、単位が1つの分割と同じ経路で動かす。devkit が worktree を作り、その役割の agent が作業し、結果を受理したら同じ手順で合流する。合流の競合はステージの作業担当が修正する。agent があれば修正用の worktree でサブエージェントが担う。

devkit は `git worktree add` で、ラウンド開始時のスナップショットのコミットを起点に、detached の作業場所を `.devkit/worktrees/<単位の指示 ID>/` に作る。ブランチは作らず、物理的な名前には計画者の単位 ID を使わない。作業場所は ignore し、記録の `.devkit/run/` と分けて記録の deny に重ならないようにする。Codex のサブエージェントには作業場所を指定する引数がないため、brief に絶対パスを載せ、そこだけを編集させる。

同時に動かす数は全体の `[parallel] max_concurrent`(既定3、1以上)と役割ごとの `[roles.<id>] max_concurrent`(指定時は1以上)の両方を満たす。数えるのは発行済みでまだ受理していないサブエージェントの指示である。互いに依存しない単位の作業、検証コマンド後の判定者の check、check ごとの判定直前の指示をまとめて返し、空いた分だけ次の `next` で発行する。役割の上限を省略した場合も全体の上限を守る。単位の作業者は最終メッセージに終了ブロックを返し、SubagentStop が保存する。単位ごとの判定はせず、結果を待つ間は Stop が停止を許す。

すべての単位の結果を受理したら、devkit は各作業場所のツリーをブランチには含めないコミットオブジェクトにして、SHA で固定して記録する。作業ブランチのチェックアウトで、その固定した SHA を順に、コミットしないマージで合流する。合流の記録には開始時の HEAD、入力の SHA、結果を持たせる。中断からの再開では、合流の記録と git のマージの状態を照合して続ける。

マージがぶつかったら、ステージの作業担当への修正指示にする。agent のある作業担当は、競合中のマージ状態と競合マーカーを持つ修正用 worktree で、1つの修正単位としてサブエージェントが直す。修正結果を合流してから残りの単位の SHA の取り込みを続ける。agent のない work の役割ならセッションのチェックアウトで直す。brief にぶつかったファイルと単位を載せる。合流後は、単位 ID を付けて欠けなく保持した各単位の終了ブロックを通常のステージのラウンドとして受理し、マージ後のツリーを返却後の対象にする。判定依頼はステージ開始時点からの累積差分とし、単位の変更とマージの結果を含める。判定・ゲート・ループ自身の変更の確認・上限・戻り・再計画・問いはステージのラウンド1つで扱い、依存の変更の分類と完了時のコミットも通常どおり行う。

中断中は新しい単位の指示と合流を始めず、作業場所を保持する。起動済みの作業者の結果は、受理条件を満たせば記録してよい。中止・作業完了時は、変更のない単位の worktree を削除する。変更の残る worktree は削除せず場所を知らせ、破棄は人が git で行う。

同じ runner の未受理の指示が複数あり、指示 ID のない不正な最終メッセージをどの指示にも結び付けられなければ、観測を残し、人に問う。

## 作業結果の提出

終了ブロックの `report` は計画のステージが選んだ JSON Schema に照らして形を検証する。完了を主張するときだけ必須とし、確認要求と停止では途中の報告を認める。確認を求める終了の種別では `confirmation` を必須とする。形に合わなければ理由を返して受理しない。単位の報告は単位 ID ごとに欠けなく保持し、`unit_report` の指定があればサブエージェントの結果受理時に検証する。形への適合を証拠や完了の根拠にはしない。

engine は `submit` で[状態遷移と受理条件](data.md#状態遷移と受理条件)に従って終了ブロックを受理し、返却後の[スナップショット](data.md#対象のバージョン-targetversion)を取得して成果物を記録する。終了の種別が「停止して確認」なら、検証・判定を通さず、その時点で問いを記録して StageRun を回答待ちにする。それ以外は StageRun を判定待ちにし、次の `next` が[作業結果の判定](#作業結果の判定)を進め、終了の種別を [router](modules.md#router)(次の行動を分類する部品)の判断にも渡す。

## 作業結果の判定

engine は `next` の中で、ステージに置いた `command:` の check(終了コードによる検証)をすべて判定者の check より先に実行する。計画の列挙順は同じ種類の中だけ有効とする。コマンドの実行場所と照合、不一致時の進行は[判定対象の展開と完了時の永続化](guarantees.md#判定対象の展開と完了時の永続化)に従う。環境変数 `DEVKIT_STAGE=<実体 ID>` と `DEVKIT_WORK=<作業 ID>` を渡す。照合を通った実行結果は、終了コードと出力を [Judgment](data.md#check-の結果-judgment)(check の結果)に変換し、終了コードが0なら `PASS`、0以外なら `FAIL`、期限超過は `NOT ASSESSED` とする。ラウンド開始時の `devkit.toml` に `command:<name>` が登録されていなければ、エラーで停止せず、その check を `FAIL` にする。auto-fixable の指摘として「検証コマンド `<name>` が登録されていない。検証の手段を作り `devkit.toml` の `[commands.<name>]` に登録する」を返す。作業者は検証の仕組みとコマンドを作って登録する。登録はループ自身の変更として[確認の設定と時点](guarantees.md#人への確認対象)に従い、次のラウンド開始時のスナップショットから使う。検証コマンドの期限は登録ごとに必須とし、共通の既定の期限は設けない。必須の `command:` の check が `FAIL` なら、判定者を実行せず、engine が「修正する」として記録して出力と指摘を次の brief に含める。

`devkit next` は判定依頼を `brief/<指示 ID>.md` に書き、[対象を展開](guarantees.md#判定対象の展開と完了時の永続化)して、指示 ID と展開先のパスを返す。そのラウンドの終了ブロックを含む判定依頼の内容は [check の契約](modules.md#check)、観点「差分」の有効な承認と出所付きの委任文書は[判定結果の受理](guarantees.md#判定結果の受理)に従う。

判定依頼には、返却後の対象と同じ方法で展開した、そのステージ実行の最初のラウンド開始時の比較元のパス、変更ファイルの一覧、その比較元から返却後への累積パッチを含める。修正ラウンドでも比較元を変えず、不合格のラウンドで行った変更も含める。判定後の依存の宣言とループ自身の変更の分類も、同じ比較元と返却後のツリーを比較する。判定の規範は各ラウンドの開始時に固定する。git の差分に外部の成果の文書の差分も添え、ソース名・ID・内容ハッシュを判定対象に結び付ける。devkit が git で生成したパッチを `brief/` 内のファイルに保存してパスを載せ、短い場合だけ本文にも載せる。

エージェントが判定者サブエージェントを起動し、結果はその最終メッセージで返る。hook が観測を添えて保存し、次の `next` が[判定結果の受理](guarantees.md#判定結果の受理)に従って Judgment を記録・集約する。判定コマンドを担当とする判定は `devkit` が実行し、同じ受理境界に従う。

check の一覧に `brief_by_planner = true` があれば、判定前に計画者へ差分・報告・計画・要件を渡し、その回の確かめ方を受理して記録する。1行の起動・SubagentStop・指示 ID の受理経路を使い、ラウンド・観点・runner の組へ結び付ける。判定依頼には補助の情報であり固定した基準や確認範囲を狭められないことを明記し、原資料も別に渡す。既定のパターンでは使わない。検証コマンドが終わった後の独立した判定者の check と、check ごとの計画者指示は、全体と役割ごとの並行数の上限を守ってまとめて指示する。

## router の判断

engine は [Finding と完了条件 ID](data.md#指摘-finding)の差分から進展を計算し、[router の入力](modules.md#router)を渡して判断を呼び出し、結果を記録する。終了ブロックの終了の種別の定義は[進捗](data.md#進捗-progress)に従う。前提に関する `FAIL` も通常の指摘として扱う。blocking の指摘に `premise_broken` が付いていれば、router は「人に確認する」を選び、前のステージへの戻りを推奨として問いに示す。戻るかどうかは人が `back` の答えで決め、判定者の指摘だけでは戻らない。

- **修正する**: engine が修正ラウンドを開く処理で[修正の担当の規則](data.md#修正の担当の規則)を当てはめ、当てはまった規則の番号と次のラウンドの担当を判断に記録する。次の `next` が指摘を取り込んだ brief をその担当に返す。必須の `command:` の check の `FAIL`、commit の失敗、コマンドが対象を変えた場合など、engine が直接「修正する」を記録する経路も同じ処理を通る。ラウンドの上限は規則より先に照合し、達したら人に確認する。上限の問いには、規則に書いた役割で続ける選択肢を含められる。
- **人に確認する**: 問いを記録し、StageRun を回答待ちにして、`next` が問いの指示を返す。[既定の分類](guarantees.md#人への確認対象)を使う。
- **前のステージに戻る**: [再計画の扱い](data.md#計画のバージョン)に従って旧 StageRun を再計画待ちにし、`next` が計画者への指示を返す。
- **完了する**: 既定では最後のラウンドで行った未確認のループ自身の変更は、判定後に人が確認してから完了時のコミットへ進む。[workspace](modules.md#workspace)(git 操作を担うモジュール)に完了処理を依頼する。確定と失敗時の扱いは[完了条件](guarantees.md#完了条件)に従う。ステージの完了が確定したら遷移 `done` に従い、ステージ ID ならそのステージへ進み、`null` なら作業完了を記録して `next` が完了の指示を返す。`"replan"` なら完了したステージの記録を残し、既存の再計画の経路で `next` が計画者への指示を返す。計画者が残りを作り直し、計画の check と承認の条件を満たしてから続ける。kit は要件定義を特別扱いしない。

既定のパターンは最後に作業者が担当する retrospective を置く。入力は、brief が参照する作業履歴ファイルと規範の一覧である。履歴には、その作業のすべての判定と指摘(blocking でないものを含む)、合格・不合格の検出試験の例ごとの判定・指摘・期待判定との照合結果、`FAIL` と `NOT ASSESSED` の経緯、ラウンド数、人の回答(却下・訂正・作り直しの指示)、人が `note` の教訓で伝えた見逃しを含む。

振り返りでは各問題をどこで捕まえるべきだったか、再発を防ぐ反映先を決め、反映しない場合は理由を記録する。[教訓の反映先](guarantees.md#教訓の反映先)の優先順でリポジトリ内の書き込めるソースの規範に反映し、リポジトリ外のソースと読み取り専用のソースへの改善は教訓として記録して管理者へ引き継ぐ。判定の基準を変えたら検出試験の例も更新する。規範が目的を果たしているか、原則がどの観点・パターンで使われているか、使われない仕組みや負担に見合わない仕組みがないかも確かめる。対象はその作業で起きた問題・見逃し・規範の不足や負担とし、規範全体の棚卸しは必要が見えたときだけ行う。

purpose がない計画でも、承認された完了条件のうち要件に当たるものを振り返りで requirements に反映する。purpose で反映済みなら重ねて更新しない。retrospective の必須 check は `default` と `fix` では `command:test`・`test`・`harness`、`docs` では `harness` だけである。`command:test` は振り返り後の最終のツリーで実行し、観点 `test` はテスト、`harness` は振り返りと前提を判定する。既定では規範を変えた場合に人の確認を通し、変えなければ確認なしで終わる。

## 人の回答と再開

作業者の確認要求は `confirmation` の問いの原文・選択肢・推奨・理由・材料への参照と、再開条件をすべて載せる。判定後の確認は判断を必要とした指摘の本文を載せる。人が担当するステージは `human_prompt` で選んだ目的・入力・返してほしいものを載せる。差分は固定したファイルへの参照で渡し、根拠のない推奨は付けない。人は自由な言葉で答え、質問返し、条件付きの答え、選択肢にない答えもできる。問いはエージェントが承認・却下・保留・戻り・文章として記録するまで開いたまま続く。

人の判断が必要なら、エージェントはチャットで問いを見せてターンを終える。人の入力を hook が観測し、エージェントが `devkit answer <問い ID>` で記録して `devkit next` で続ける。

ゲートの問いは devkit が計画のゲート理由、ステージの終了ブロックの実施内容・確認済み事項・未確認事項、差分ファイルのパスから組み立てる。ループ自身の変更の問いは変更したソース名・文書 ID と、規範・ホスト設定・skill のファイルを列挙し、差分ファイルを参照する。エージェントは生成された問いをそのまま提示する。ステージの問いで人が前のステージへ戻るよう求めた場合、`devkit answer --interpretation back <問い ID>` で記録する。engine は router の `back` を記録し、既存の戻りと再計画の経路を使う。観点名による特別扱いはしない。ステージの問いに人が却下と答えた記録は、修正の担当の規則の条件 `human_rejected` に使う。決定を確認する問いと回答の訂正も[回答の受理](guarantees.md#回答の受理)に従う。

人が計画の変更を提案する場合は、エージェントが `devkit plan <ファイル>` で提案を記録する。撤回は `devkit plan --withdraw` で記録し、その後の進行は[計画のバージョン](data.md#計画のバージョン)に従う。作業を中止する場合は、エージェントが `devkit abort` を呼ぶ。

セッションをまたぐ再開はホストのセッション再開と [SessionStart](hooks.md#sessionstart)の注入で現在地を引き継ぐ。人による中断からは `devkit resume` で再開し、条件は[中断](guarantees.md#中断)に従う。新しいセッションからの束縛とブランチ不一致時の扱いは[セッションとブランチ](data.md#セッションとブランチ)、指示の出し直しは[指示](data.md#指示-instruction)に従う。停止の可否は [Stop](hooks.md#stop)、引き継ぐ状態は [checkpoint](data.md#checkpoint)に従う。

作業全体の累計ラウンド数が、設定した `[limits] max_total_rounds` に達したら人に確認する。既定の上限は40である。続行の回答後は、その時点の累計に設定値を加えた値を次の停止点とする。戻り・作り直し・担当の変更でも累計を減らさない。

## 人による中断

人がチャットで止めるよう頼んだら、言い回しによらずエージェントが `devkit pause` を呼ぶ。再開を頼んだら `devkit resume` を呼ぶ。人がどちらもターミナルで直接実行してよい。中断・再開の記録、Stop の判断、中断中の `next` の応答と継続上限は[中断の保証](guarantees.md#中断)、中断前の現在地との関係は[状態遷移と受理条件](data.md#状態遷移と受理条件)に従う。

## 外部操作

リポジトリ外のソースは読み取り専用であり、devkit はこの経路でも書き込まない。

エージェントは `devkit external --target <対象> <種別> <入力ファイル>` を実行する。入力ファイルの場所は[状態遷移と受理条件](data.md#状態遷移と受理条件)を参照する。engine が[操作を識別](guarantees.md#外部操作の二重適用)し、必要な問いを起票する。開始直前の承認照合は[承認の条件](guarantees.md#外部操作の承認)に従う。確認待ちになれば、人の回答を `answer` で記録してから同じ呼び出しを再実行する。external が実行と結果の記録を担い、結果を返す。

## hook

各段階のホストイベントは [5つの hook](hooks.md)が処理する。入力・判断・出力・書く生成物と、サブエージェント内や束縛のないセッションでの扱いはそちらで定める。
