# データ

作業は1つの課題に対するループを所有し、計画、ステージの実行、ラウンドを通じて進む。対象のバージョンが、作業・検証・判定を結び付ける。バイナリが持つもの、リポジトリが育てる資産、追記する実行の記録、再生成できる生成物を分け、それぞれの所有者と更新の境界を定める。

## データ形式

計画・記録・指示・終了ブロック・結果・決定と証拠は JSON とし、JSON Schema で形式を制約する。

エージェントへ渡す出力スキーマは、使用するすべての `$ref` の参照先を同梱し、単独で解釈できる形にする。作業の brief には note の種別一覧と各種別の同梱済みスキーマも渡す。

## 所有と生存期間

データの所有と生存期間、整合性を守る境界は、[assets/principles/data.md](../../assets/principles/data.md) の原則5に従う。

- **バイナリが持つもの**: JSON Schema、分類表とロールの既定値、ホスト設定の断片である。JSON Schema は記録とバイナリの約束であり、リポジトリで育てる対象にしない。人への確認の分類は `devkit.toml` の `[router] human_confirmation` で上書き・追加・削除できる。check の結果から次の行動への対応とロールは固定である。
- **育てるもの**: リポジトリが所有する知識とループの資産である。知識は名前付きのソースで管理し、既定のリポジトリ内のファイルは git で共有する。原則、用途別の判定基準、ステージ定義、検出試験の例と仕様、ループの雛形、テンプレート、規則、要件、構造を含む。検出試験の合格の索引、`devkit.toml`、ホスト設定、サブエージェント定義、skill、AGENTS.md、CLAUDE.md はソースの外で管理する。作業範囲の記録への参照は[規則と強制手段](#規則と強制手段-rules)に従う。
- **実行の記録**: 作業が所有する。完了・中止後も StageRun、Judgment、決定、成果物、外部操作を読み取り専用で残す。人の判断である回答・承認・状態変更は完了後も追記を許す。
- **生成物**: brief と判定依頼、作業履歴ファイル、差分ファイル、対象の展開先、結果ファイル、停止の観測、view の HTML は作業の下に置く。停止の観測の保持条件はその定義に従い、それ以外は再生成または削除できる。セッションの観測と人の最新の入力の観測は作業の外にチェックアウトごとに置き、人の入力はセッションごとに1件保持する。展開先の削除時期は[性能と出力](guarantees.md#性能と出力の上限)、refs の生存期間は[対象のバージョン](#対象のバージョン-targetversion)に従う。

知識は `devkit.toml` の `[sources.<名前>]` で接続先を設定する。設定がなければ、`init` が初期内容を置く既定のソースを使う。既定のアダプタは `files` である。

- `principles`: `.devkit/principles`。原則と用途別の判定基準であり、`norm = true` である。
- `stages`: `.devkit/stages`。ステージ定義であり、`norm = true` である。
- `plans`: `.devkit/plans`。雛形であり、`norm = true` である。
- `rules`: `.devkit/rules.md` を1文書として扱い、`norm = true` である。
- `examples`: `.devkit/examples`。検出試験の例と `spec.json` の仕様であり、`norm = true` である。
- `templates`: `.devkit/templates`。brief と form のテンプレートであり、`norm = true` である。
- `requirements`: `.devkit/requirements.md`。要件の正本であり、`norm = false` である。
- `structure`: `.devkit/structure.json`。構造の記録であり、`norm = false` である。

置き場所と接続先はソースごとの設定で変更できる。検出試験の合格の索引はソースではなく、`[state] detect`(既定 `.devkit/detect.json`)で保存先を設定する。

skill は `.agents/skills/devkit/`、サブエージェントの定義は `.claude/agents/`・`.codex/agents/` に置く。実行の記録と生成物の場所 `.devkit/run/` は固定とし、git では管理しない。サブエージェントの定義、hook、保護の設定、ignore がこの場所を前提にし、作業の途中で変えると記録を見失うためである。

分割した単位の作業場所は、記録とは別の `.devkit/worktrees/<単位の指示 ID>/` に置き、ignore する。中断中は保持し、中止・作業完了時には変更のない worktree だけを削除する。変更の残る worktree は保持して場所を知らせ、破棄は人が git で行う。

原則・用途別の判定基準・ステージ定義にあるコード書式の `principles/…`・`stages/…`・`templates/…`・`rules.md` は、リポジトリ側の置き場所の論理名である。brief には論理名と実際のパスの対応を示す。`schemas/…` は、バイナリが出力スキーマの本文として brief に渡す。

## 知識のソース

ソースは名前とアダプタ、接続先、`norm`、書き込み能力 `writable` を持つ。`norm = true` は判定の規範、`norm = false` は要件・構造などの作業の成果である。規範のソースは空の選び方で全文書を列挙できなければならない。`devkit.toml`、指示ファイル、サブエージェント定義はソースの外の規範として固定する。

### アダプタの口

必須の「選ぶ」は、アダプタが解釈する文字列の選び方を受け取り、文書の一覧を返す。各文書はソース内で一意な文字列の ID とテキストの本文を持つ。devkit は知識の項目・構造・タグ・参照形式や選び方の言語を解釈しない。

「書く」は `writable = true` のソースだけが持つ任意の能力である。文書の ID、新しい本文または削除、期待する元の内容ハッシュを受け取り、現在の内容が一致するときだけ比較と更新を一体で行う。一致しなければ反映せず、作業者が取り直して差分を見直す。文書の元のバージョンの識別子も任意で返せる。git のコミットなどを来歴として記録に添え、固定した本文の内容ハッシュとは区別する。

`files` の選び方は設定した置き場所からの glob、ID はそこからの相対パス、本文はファイルの中身である。空の選び方は全文書を返す。単一ファイルのソースはそのファイルを1文書として扱う。リポジトリ内では固定したスナップショットの git のツリーから読み、元のバージョンの識別子にコミットを添える。リポジトリ外では、その時点のファイルを読む。書き込み能力がある場合はファイルへの書き込みと削除を扱う。

ほかのアダプタは外部コマンドとして登録する口を持つ。JSON の入力で選び方を受け取り、JSON の出力で ID・本文・任意の元のバージョンの識別子を返す。「書く」は JSON の入力で ID・新しい本文または削除・期待する元の内容ハッシュを受け取り、JSON の出力で反映結果または内容の不一致を返す。規範の列挙、比較して更新する条件、書き込み能力の有無は `files` と同じ契約である。提供するアダプタは `files` だけである。

### 固定と変化の検出

ラウンド開始時、ラウンド外の判定では指示を出す時点に、devkit が文書の本文を `.devkit/run/` の実行の記録の下へ写す。文書ごとの内容ハッシュと全体のハッシュをバージョンとし、判定者と作業者には固定した写しを渡す。規範はソース全体を列挙して固定し、次の時点の全文書の集合と本文を比べる。リポジトリ内の規範のソースの変更は、そのパスの git の差分で見る。成果のソースは選んだ範囲を固定し、同じ選び方の結果と比較する。選んでいない成果の文書の変化は保証の範囲に入らない。

### 書き込みの流れ

作業者は、実行の記録の下に置いた編集用の写しを直す。devkit は固定した本文との差分から追加・変更・削除を求める。規範の変更はループ自身の変更として確認し、承認後にアダプタの「書く」で反映する。リポジトリ外への書き込みは[外部操作](guarantees.md#外部操作の承認)として、操作 ID、承認への参照、実行前後の記録、結果不明からの回復、二重適用の防止を適用する。判定・承認・反映・完了は同じ対象の識別を指す。

リポジトリ内の `files` では作業者がファイルを直接編集し、git で差分を求め、完了時のコミットで反映する。いずれも反映直前の元の内容の一致を確かめ、不一致なら反映せず取り直して差分を見直す。

振り返りで改善を反映するソースは書き込めるものに限る。読み取り専用のソースへの改善は教訓として記録し、管理者へ引き継ぐ。

## エンティティ

### リポジトリ

dev-kit を導入した git リポジトリである。規範、設定ファイルと育てるものを所有する。

### 作業 (Work)

1つの課題に対して実行する1本のループである。

- [ULID](https://github.com/ulid/spec#specification)(時刻と乱数を26文字で表す識別子形式)の作業 ID、`start` に渡された課題への参照、要求の原文、ブランチを持つ。ブランチ名は `[git] branch`(既定 `"devkit/{work_id}"`)から作り、設定には `{work_id}` を必ず含める。
- `start` は、UserPromptSubmit が観測したそのセッションの人の最新の入力を要求の原文として作業に結び付ける。観測がなければ原文なしと記録する。計画者の brief と計画の承認の問いには、原文と `start` の課題の両方を渡す。
- 基点コミットは来歴を示す開始時のコミットである。記録形式とバイナリの互換性の識別として、開始時の `kit_version`(バイナリと `init` の設定値は `"v2"`)を持ち、作業内の記録形式を固定する。互換性は[バージョン互換性](guarantees.md#バージョン互換性)に従う。
- `start` が作業を作成してから完了または中止するまで存続し、作業範囲の記録を所有する。
- 中断の有無、中断前の状態への参照、`pause`・`resume` が直接追記する中断・再開の記録を持つ。再開の記録は中断の記録を参照する。計画待ちなど StageRun のない期間も含め、作業全体の中断を[状態遷移と受理条件](#状態遷移と受理条件)から導く。

### セッションの観測 (SessionObservation)

ホストのセッションと作業の束縛を保持する生成物である。

- ホスト名、セッション ID、観測時刻、束縛した作業 ID を持つ。作業単位の継続回数は[停止の観測](#停止の観測-stopobservation)に持つ。
- 保存先と更新は [hook の共通処理](hooks.md#共通処理)、コマンド側の識別は[セッションとブランチ](#セッションとブランチ)に従う。

### ループの雛形 (PlanTemplate)

利用者が組むループの定義であり、既定では `.devkit/plans/<name>.json` に置く。置き場所は `[sources.plans]` で変更できる。`--plan` を省いたときの名前は `default_plan`(既定 `"default"`)で定まる。

- 開始するステージとステージの列を持つ。
- 候補のステージ(`optional_stages`。調査・試作など)は既定では外しておき、計画者が必要に応じて足してよい。
- 各ステージは担当、check とその実行主体・必須か、ゲートの有無と理由、計数の上限、router の check の結果の4分類(修正する・人に確認する・前のステージに戻る・完了する)をキーにした遷移表を持つ。戻り先は遷移表の `back` の値で表す。条件式は書かせない。[ループ計画](../loop-plan.md)と[ステージ](../stages.md)の契約に従う。
- ステージに `split: true` を書くと、そのステージの作業を単位に分けてよい。分割の追加・削除は雛形からの逸脱とする。既定の雛形は分割を使わず、利用側が雛形で選ぶ。
- 遷移 `done` には、次のステージ ID、作業の終了を表す `null`、残りの計画の作り直しを表す `"replan"` を書ける。`"replan"` は、そのステージの完了後に既存の再計画の経路で計画者が残りを作り直す指定である。要件定義を先に行って再計画するかは雛形の組み方で決まり、kit は要件定義を特別扱いしない。
- 計画の再提案に用いるラウンド数の上限は[計画のバージョン](#計画のバージョン)に従う。
- ゲートの理由は自由記述でよく、router の分類表の項目に対応するときは項目名を書く。
- check は `criteria` と `examples` のソース名と選び方を持つ。ステージの `inputs` に作業者への入力を指定でき、雛形は計画者・作業者・判定者それぞれの入力の選び方を持つ。要件と規則を渡す既定値を用意する。
- 完了条件や課題の情報は持たない。バージョンは内容ハッシュ、履歴は git とする。

### 計画 (Plan)

雛形から作る課題ごとの実体であり、作業に属する、バージョンを持つ状態機械のデータである。

計画の JSON Schema はバージョンを持つ。

- 雛形の名前と内容ハッシュ、課題、ID 付きの完了条件の列、雛形から取捨したステージ(check の対象の指定を含む)を持つ。不採用のステージは、表示時に雛形と採用ステージの差分から求める。必須 check は各 check の `required` から導き、別の欄は持たない。雛形のパスは名前から[開始時の解決先](flow.md#作業の開始)に従って導く。作り直しも正式な操作とする。
- 要求のうち計画者が決められなかった点は、任意項目 `open_questions` に文字列の配列で持つ。要求が曖昧なら推測で埋めず、承認の問いで人に確かめる。人が承認した完了条件を作業の完了の基準とする。`open_questions` が空でなければ、承認方針によらず人の承認を必須とする。
- 課題固有の元に戻せないもの(変更困難な決定)の一覧の正本とし、設計案から参照・更新する。判断は [`assets/principles/designing.md` の原則1](../../assets/principles/designing.md#1-identify-decisions-that-are-hard-to-change-early-and-finalize-them-after-obtaining-the-evidence-needed)に従う。
- 担当のロールは作業者・人・判定者・計画者とする。雛形のステージの担当に書ける値は「作業者」「人」の2つである。通常の作業者はセッション自身であり、分割した単位はサブエージェント `devkit-worker` が担当する。判定者・計画者はステージの担当ではなく、check と計画の実行主体である。人が担当するステージは `next` が問いを起票して回答待ちにし、人の回答(文章)をそのステージの出力として記録する。
- `split` のステージに単位の一覧 `units` を書ける。各単位は計画内の名前である ID、説明、担当する範囲を持ち、計画者が記入する。範囲はファイルやディレクトリを文章で表してよい。単位の ID の重複は検証で拒否する。範囲の重なりは計画の観点の判定者が指摘し、機械では検査しない。単位がなければ通常のステージとして作業する。
- 各 check は判定の名前である観点 ID(`aspect`)、完了条件 ID、対象、必須か、実行主体(runner)を持つ。判定者の check は基準の選び方の一覧 `criteria` と検出試験の例の選び方 `examples` も持つ。`criteria` と `examples` はソース名 `source` と選び方 `select` で指定する。基準に使うソースは `norm = true` に限り、必須の基準の選び方が0件なら判定を始めず止める。成果の文書が未作成である場合とは区別する。runner は判定者のサブエージェント名、`[judges]` の判定コマンド名、`command:<name>`([config](modules.md#config)の `[commands]` に登録する検証コマンド)の3種とする。`command:` の check の観点 ID は `command:<name>` そのものとする。雛形の判定者サブエージェントは、`init` が配る `devkit-judge` とする。
- 完了条件は文章で書く。check は機械の検査とは限らず、検証コマンド・判定者・判定コマンドを実行主体とする。完了条件ごとに、それを確かめる check か人のゲートを置く。要件定義の段階の条件は、判定者と人のゲートで確かめる。どの手段が合うかと漏れがないかは、計画の観点の判定者が判断し、計画の承認で人が見る。形式的な割り当ての検査は kit に置かない。
- check の実行順・環境変数・失敗時の扱いは[作業結果の判定](flow.md#作業結果の判定)、コマンドの実行場所と照合は[判定対象の展開と完了時の永続化](guarantees.md#判定対象の展開と完了時の永続化)に従う。
- 雛形のステージを外すこと、候補にないステージの追加、ゲートの削除、遷移の変更、必須 check の削除、`criteria`・`examples` の選び方の変更、分割の追加・削除は雛形からの逸脱として計画の check が指摘し、人の承認がなければ実行可能にならない。再計画で完了済みのステージを残りの計画に含めないことは逸脱に数えない。
- 計画の承認で足りる外部操作の宣言として、種別・対象・入力のハッシュ、宣言時の登録定義と実行ファイルの内容ハッシュを持つ。外部操作を宣言した計画は、雛形からの逸脱の有無にかかわらず、人の承認ゲートを必須とする。操作の照合は[外部操作の承認](guarantees.md#外部操作の承認)で定める。
- 承認状態と提案の状態は[計画のバージョン](#計画のバージョン)から導く。

計画の検証では、`done` をたどって同じステージを再び通る循環を拒否する。`"replan"` または `null` で遷移の連鎖を終える。

### ステージの実行 (StageRun)

作業内の1回のステージ実行である。従う計画のバージョンは[計画のバージョン](#計画のバージョン)の束縛と切り替えの規則で定まる。

- 実行 ID、ラウンドの列、実行状態、停止理由、次に動く主体を持つ。
- 実行状態は作業中・判定待ち・回答待ち・承認待ち・外部操作の確認待ち・失効・完了。「前のステージに戻る」による「再計画待ち」は失効の一種である。`done: "replan"` では、完了した StageRun の記録を残して残りを再計画する。中断は StageRun の状態を書き換えず、[作業](#作業-work)の状態として重ねる。
- 完了記録は[完了条件](guarantees.md#完了条件)に従い、コミットのハッシュを持つ。

### ラウンド (Round)

`next` が brief を渡してから、作業結果に対する次の行動が確定するまでの往復である。

- ラウンド ID、結び付けたセッション ID、開始時と返却後の対象のバージョンを持つ。
- 終了ブロック、check の結果の集合、発行した指示の ID の集合と出し直し回数、次の行動の判断を持つ。通常は [router の判断](flow.md#router-の判断)を engine が記録し、engine が直接記録する経路は[作業結果の提出](flow.md#作業結果の提出)・[作業結果の判定](flow.md#作業結果の判定)・[完了条件](guarantees.md#完了条件)に従う。
- 分割した作業では、単位ごとの指示、作業場所、終了ブロックと、合流の開始時の HEAD・入力として固定した SHA・結果を記録する。単位ごとの判定は持たず、合流後のツリーと、単位の終了ブロックをまとめたステージの終了ブロックを通常のラウンドで扱う。判定・ゲート・ループ自身の変更の確認・上限・戻り・再計画・問いはステージ単位である。

### 指示 (Instruction)

`devkit next` が返す、エージェントへの1つの指示である。

- 指示 ID は(作業 ID、種別、対象のキー、出し直し回数)から導く派生値である。
- 対象のキーは、作業ならラウンド ID、単位の作業ならラウンド ID と単位 ID、判定ならラウンド ID と観点 ID、計画の check なら計画のバージョンと観点 ID、計画なら計画のバージョン、検出試験なら[合格記録の同一性を定める内容ハッシュ](#検出試験の記録-detectiontest)の集合とする。ラウンドを開く前の指示も識別する。
- 出し直しは作業の記録に追記する。ラウンドに結び付いたセッション ID と異なるセッションからの `next` では、新しい指示 ID で出し直す。結果の受理は、セッションからの終了ブロックなら[状態遷移と受理条件](#状態遷移と受理条件)、作業者・判定者・計画者のサブエージェントの結果なら[判定結果の受理](guarantees.md#判定結果の受理)に従う。指示本文の保存は[記録の範囲](#記録の範囲)、同じセッションへの返却は[状態遷移と受理条件](#状態遷移と受理条件)に従う。
- 種別は、作業(brief)、判定待ち、判定、計画の check(判定の一種)、検出試験、計画、問い、外部操作の確認、完了、中止である。判定には brief と対象の展開先のパス、問いには問い ID・文面・選択肢を持たせる。
- 指示の計算と結果の重複の扱いは[状態遷移と受理条件](#状態遷移と受理条件)および[判定結果の受理](guarantees.md#判定結果の受理)に従う。
- サブエージェントの結果がスキーマまたは内容の検証に失敗した場合は、失敗と結果の拒否を記録して再読せず、対象と依頼内容を保って出し直し回数を増やす。同じ対象へ2回出し直しても検証に失敗する場合は人への問いを起票する。最終メッセージの JSON の解析失敗も同じ扱いとする。
- 同じ runner の未受理の指示が複数あり、指示 ID のない不正な最終メッセージをどの指示にも結び付けられなければ、観測を残して人に問う。
- ステージ定義は `stages` ソースから選び、本文の入力は雛形の `inputs` と check の `criteria` で選ぶ。計画者・作業者・判定者それぞれの入力の選び方を雛形に書け、要件と規則を渡す既定値を持つ。その他の規範は固定した写しの一覧で渡す。基準の文書が別の文書を必要とする場合も、選び方へ明示する。文中の参照は解析しない。変更の範囲は scope の出力と rules で渡す。検出試験への資料は[検出試験](guarantees.md#検出試験)の制限に従う。

### 対象のバージョン (TargetVersion)

git のツリーと外部の成果の文書を組み合わせた識別、計画のバージョン、構造のバージョンの直和である。

- ツリーのスナップショットは、追跡ファイルと ignore されていない未追跡ファイルから一時インデックスで作る、ブランチには含めないコミットオブジェクトのツリーハッシュである。`[sources.<名前>]` で定まるリポジトリ内の資産、指示ファイル、skill、ホストの設定、サブエージェントの定義も追跡ファイルとして含む。ignore する `.devkit/run/`・`.devkit/worktrees/` は含めない。
- 判定の対象の識別は、このツリーハッシュに、リポジトリ外の `norm = false` の成果の文書のソース名・ID・内容ハッシュの集合を加えたものとする。写しを編集した成果は編集後の本文を判定対象とし、原本への反映時の元の内容との比較は別に行う。判定・承認・反映・完了は同じ識別を参照する。
- ラウンドの開始時と返却後に取得する。各ラウンドの開始時のものは[規範の固定](guarantees.md#規範の固定)に使う。判定依頼の差分と、判定後の依存の宣言・ループ自身の変更の分類には、そのステージ実行の最初のラウンド開始時のスナップショットと規範のソース全体の固定した文書を比較元として使い、修正ラウンドを通じた返却後までの変更を含める。返却後のものは判定・完了時のコミットに使う。commit 前後の照合と不一致時の更新・再判定は[commit 直前の対象の照合](guarantees.md#commit-直前の対象の照合)に従う。
- コミットに `refs/devkit/<作業 ID>/<対象のバージョン>` を付け、作業の完了・中止と成果物の永続化がそろうまで保持し、その後削除する。
- 計画のバージョンは作業内で識別する。構造のバージョンは[構造の記録](#構造の記録-structure)に従う。

### check の結果 (Judgment)

ある観点から対象を判定した結果である。

- 観点 ID、対象のバージョン、規範の識別、確認した完了条件 ID の集合、判定、指摘を持つ。判定は `PASS`・`FAIL`・`NOT ASSESSED` である。
- 確認した範囲と未確認の範囲、方法と環境、指示 ID、受理した内容と来歴を持つ。結果ファイルのパスは任意の診断情報とする。
- 実行主体(runner。check を実行する相手)は種類ごとに次の項目で表す。
  - サブエージェント: 名前。effort(Claude Code の推論の量を指定する設定項目)または model(Codex)の実測値は、取得できる場合に来歴として添える。取得元は [SubagentStop](hooks.md#subagentstop)に従い、取得できない項目は記録せず、必須にしない。設定値を観測値の代わりに使わない。
  - 判定コマンド(`[judges]`): 名前。
  - `command:` の check: `command:<name>`。
- 担当とコマンドの定義は runner と使用した規範から一意に特定し、定義のハッシュを重ねて保持しない。
- 規範は、`norm = true` の全ソースの全文書、`devkit.toml`、`.claude/agents/`・`.codex/agents/` の定義、AGENTS.md、CLAUDE.md の集合である。規範の識別は、固定した全文書の集合と内容ハッシュ、およびソースの外の規範のツリー ID・blob ID から定まる。
- requirements・structure・detect・`.devkit/run/` は規範に含めない。これらの変更では規範の識別は変わらず、それを理由に判定は失効しない。requirements の更新によって計画の判定をやり直すこともない。
- 対象のバージョンと規範の識別の両方が照合対象と一致するときだけ有効である。照合するスナップショットの取得時点は[規範の固定](guarantees.md#規範の固定)に従う。計画や構造の判定も選んだ基準や規則が変われば失効するが、評価対象コードだけの変更では規範の識別は変わらず、これらの判定は失効しない。
- `command:<name>` がラウンド開始時の `devkit.toml` に未登録なら、その check を `FAIL` とする。指摘は `auto-fixable` とし、「検証コマンド `<name>` が登録されていない。検証の手段を作り `devkit.toml` の `[commands.<name>]` に登録する」とする。登録はループ自身の変更として、既定では人が確認し、次のラウンド開始時のスナップショットから使う。`command:` の check がツリーを変えたときの指摘には、出力先を ignore する案内を含める。
- 受理と集約は[判定結果の受理](guarantees.md#判定結果の受理)に従う。

### 指摘 (Finding)

check が見つけた失敗や判断を要する点である。

- 指摘 ID、blocking かどうか、`auto-fixable` または `needs-decision`、失敗のシナリオを持つ。
- `auto-fixable` は人の判断を要さず修正できる指摘、`needs-decision` は人の判断が必要な指摘を表す。
- 適用除外の主張と根拠の有無、解決した指摘への参照を持つ。
- 修正ラウンドの依頼には前回の指摘 ID を渡す。解決した指摘への参照と、確認した完了条件 ID の増加から進展を計算する。

### 決定と証拠 (Decision / Evidence)

作業中に得た判断と、その判断を支える調査結果である。

- 決定は自然文の有効条件(`validity`)、置換、依存、適用条件、決定者、暫定か確定か、却下した案とその理由・具体例を持つ。証拠は出典と確認方法を持つ。
- 有効条件・適用条件と外部依存が満たされるかは、エージェントと人が判断する。`devkit` はこれらを評価せず、条件と参照を決定に添えて渡す。記録から導く承認・却下・保留、置換と記録内の依存関係の状態とは区別する。
- `devkit note <種別> <ファイル>` は、作業の特定とスキーマ検証だけで受け付ける。ブランチの一致は要求しない。種別には教訓を含む。
- 承認・却下・保留は、[問い](#問い-question)への[回答の受理](guarantees.md#回答の受理)で追記する状態変更から導く。

### 問い (Question)

form に従う、人への確認事項である。

- 問い ID、承認対象、選択肢、推奨、停止理由の分類、回答後に進むステージ、停止しているステージと理由、根拠への参照を持つ。
- 承認対象は git のツリーと外部の成果の文書を合わせた対象の識別、計画のバージョン、外部操作、決定 ID、継続上限の確認対象である作業 ID の直和である。外部操作の識別項目は[外部操作の承認](guarantees.md#外部操作の承認)に従う。
- 人の確認が必要な決定には、その決定 ID を承認対象として参照する問いを起票し、選択肢を承認・却下・保留とする。
- 計画の承認の問いには、`devkit` が要求の原文、`start` の課題、ID 付きの完了条件、採用したステージと外したステージ、各ステージの必須 check、課題固有の元に戻せないもの、宣言した外部操作、`open_questions` を組み立てて載せる。雛形からの逸脱を明示し、エージェントの要約には頼らない。
- ゲートの問いには、計画のゲート理由、終了ブロックの実施内容・確認済み事項・未確認事項、devkit が生成した差分ファイルのパスを載せる。ループ自身の変更の問いには、変更したソース名・文書 ID と、規範・ホスト設定・skill のファイル一覧と差分ファイルへの参照を載せる。エージェントは生成された問いを提示する。
- ループ自身の変更は、規範・ホスト設定・skill・リポジトリ内で git が追跡する有効な pre-commit の設定の変更であり、requirements と structure の変更は含めない。`[approval] meta_loop_edit` は `"confirm"`(既定)または `"allow"` とし、既定ではステージによらず、変更が効く最初の時点より前に確認する。
- `meta_loop_edit = "confirm"` では、ラウンド開始時のスナップショットに、作業の基点または直前に確認した時点からの未確認のループ自身の変更があれば、ラウンドを開く前に問いを起票して止める。最後のラウンドの変更は判定後、完了時のコミットの前に確認する。確認済みの範囲は、確認したスナップショットの規範の識別で表す。却下されても作業対象は保持し、確認済みの規範の識別を別に保持する。次の作業ラウンドで、却下した規範の変更ファイル一覧を渡して取り消させる。同じ変更が残る間は再確認を求めず作業者へ戻す。
- 画面のデザインを始める前のレビューゲートでは、画面 ID(画面の識別子)と表示内容を含むツリーのスナップショットを承認対象とする。画面のデザインの承認を求める問いは、画面 ID を説明に示す。
- `devkit` が記録して `next` の指示として返し、エージェントがチャットで人に見せる。form は問いの文面に、[回答の受理](guarantees.md#回答の受理)に従う自由な言葉での回答を案内する。
- 承認対象が変わったら新しい問い ID で起票し直し、古い問いへの回答は拒否する。
- [継続上限](guarantees.md#中断)の問いは[停止の観測](#停止の観測-stopobservation)への参照を持つ。

### 人の入力の観測 (PromptObservation)

ホストが受け取った入力の本文を保持する生成物である。

- 本文の採取と保存先は [UserPromptSubmit](hooks.md#userpromptsubmit)に従う。
- 作業への束縛の有無によらず、人の入力ごとにセッションの最新入力1件を更新する。束縛後は作業ごとの入力の観測も残す。`start` は最新入力を要求の原文として作業に結び付ける。
- 人以外の入力での発火と観測から除く本文は [UserPromptSubmit](hooks.md#userpromptsubmit)に従う。
- 観測した入力からの回答の記録は[回答の受理](guarantees.md#回答の受理)に従う。人が別のセッションから回答を送る経路は範囲外とする。

### 停止の観測 (StopObservation)

作業単位の継続回数と、上限到達時の問いを保持する生成物である。計数と停止の条件は[中断](guarantees.md#中断)に従う。

- 観測 ID、作業 ID、セッション ID、観測時刻、照合した ledger の末尾の記録 ID、継続回数、上限到達の有無を持つ。上限に達した場合は問い ID と問いの本文・選択肢・推奨・理由も持つ。
- 保存先は `stops/<ULID>.json` とし、Stop が公開する。計数の根拠となる最新の観測と、ledger に未取り込みの問いを含む観測は削除しない。
- 問い ID は作業 ID と計数の基点となる記録 ID から導き、同じ上限到達で重複起票しない。CLI が問いを ledger に取り込む際も同じ ID を使う。

### 回答・承認 (Answer / Approval)

観測した入力をもとに、問いへの人の判断を確定する記録である。

- 問い ID と承認対象を持つ。
- ステージの問いへの解釈 `back` は、前のステージへ戻る回答である。engine が router の `back` を記録し、戻りと再計画の経路へ進む。
- エージェントの解釈(承認・却下・保留など、または文章の回答)、UserPromptSubmit が観測した人の入力の原文と出所(セッション ID と時刻)を保存し、観測ファイルを削除した後も記録だけで根拠を確かめられるようにする。
- 受理と訂正は[回答の受理](guarantees.md#回答の受理)に従う。問いと承認を機械間で共有する経路は対象範囲に含めない。

### 外部への書き込み (ExternalOp)

kit が管理する、リポジトリ外への書き込み操作である。

- 種別、対象、入力のハッシュ、登録定義の内容ハッシュ、リポジトリ内の実行ファイルの内容ハッシュを持つ。
- 操作 ID、承認への参照、実行前の記録、実行結果、外部側の識別子を持つ。実行結果は成功・失敗・結果不明である。
- 操作 ID の導出と外部向けの冪等キーとしての兼用は[外部操作の二重適用](guarantees.md#外部操作の二重適用)、実行の条件は[外部操作の承認](guarantees.md#外部操作の承認)に従う。

### 進捗 (Progress)

ラウンドの終了ブロックである。

- セッションからは `devkit submit` の入力として受け取り、`devkit` が記録する。単位の作業者は `schemas/progress.json` に従う終了ブロックを最終メッセージで返し、SubagentStop が保存する。合流後は、単位の終了ブロックをまとめた作業者の終了ブロックをステージのラウンドとして受理する。
- 作業指示の指示 ID (`instruction_id`) を必須項目とし、実施内容、確認済み事項、未確認事項、障害、終了の種別、一時状態(確認方法・出典・無効になる条件)、再開条件を持つ。対象外の作業と変更理由は必要に応じて補足する。読めなかった入力とその影響は未確認事項に記録する。
- 一時状態が有効かどうかを判断する条件は自然文であり、エージェントと人が判断する。`devkit` は条件を評価せず、確認方法・出典・無効になる条件を一時状態に添えて引き継ぐ。
- 変更ファイルの一覧は[成果物](#成果物-artifact-record)の差分から生成する。判定と再開には正本の制約を直接引き継ぐ。次の行動は[指示](#指示-instruction)に従う。判定依頼での報告の扱いは[判定結果の受理](guarantees.md#判定結果の受理)に従う。
- 終了の種別は完了を主張・停止して確認・作業停止の申告とし、種別に応じた進行は[作業結果の提出](flow.md#作業結果の提出)に従う。「作業停止の申告」は作業者による報告であり、作業の中断・再開は[中断](guarantees.md#中断)の `pause`・`resume` で記録する。外部書き込みの要求は終了ブロックに含めず、[外部操作](flow.md#外部操作)で行う。

### checkpoint

再開のために記録から組み立てる現在地の派生値である。

- 作業の中断・再開、実行状態を持つ最新の StageRun、最新の進捗、条件と記録上の状態を添えた決定、未回答の問い、未受理の指示から組み立てる。未取り込みの停止の観測も照合する。上書きする記録は持たない。
- SessionStart の注入ごとに ledger から組み立て、一時状態は条件によって除外せず、確認方法・出典・無効になる条件をそのまま添えて渡す。有効かどうかはエージェントと人が判断する。出力上限への対応は[性能と出力](guarantees.md#性能と出力の上限)に従う。

### 成果物 (Artifact record)

作業が生んだ変更と、その永続化先を結び付ける記録である。

- 記録 ID、変更前後の対象のバージョン、完了条件 ID、変更の種類、決定への参照、永続化先であるコミットへの参照を持つ。
- 開始時と返却後のスナップショットの差分から `devkit` が作成する。

### 検出試験の記録 (DetectionTest)

判定者が check の基準に従って期待する判定を出せるか確かめた結果である。対象の範囲は[検出試験](guarantees.md#検出試験)に従う。

- check の `criteria`・`examples`、試験仕様、担当の定義、判定規則を含む判定依頼テンプレート、実際に渡した基準の文書の集合と内容ハッシュ、例の文書の内容ハッシュ、実際の判定と根拠を持つ。
- 合格の同一性には担当の定義、判定依頼テンプレート、基準と例の文書の内容ハッシュを含める。effort・model の来歴は [Judgment](#check-の結果-judgment)に従い、同一性には含めない。別の文書が必要なら `criteria` へ明示し、文中の参照は解析しない。
- 試験仕様は例のソース内の `spec.json` の文書であり、例の参照と devkit だけが読む期待判定の対応を持つ。判定者には基準の文書、匿名の例の本文、出力の約束だけを渡す。仕様・期待判定・対応表と、それらを含む作業履歴や参照先を渡さない。
- 合格の索引はソースではなく、`[state] detect`(既定 `.devkit/detect.json`)に保存する。読み出し・書き込み・復元は試験の指示に固定した同じ参照元の設定を使う。ledger には合格・不合格の両方の実行の事実を置き、通常の作業履歴には例ごとの判定・指摘・期待判定との照合結果を残す。基準を更新した check は、既定では次に必須として使うラウンドの前に試験する。

### 要件 (Requirements)

リポジトリが満たすべき要件の正本である。

- 既定では `.devkit/requirements.md` に置き、`[sources.requirements]` で置き場所を変更できる。
- 目的のステージが、承認された完了条件と既存の要件を照らして更新する。目的のステージがない雛形や、目的のステージを外した計画では、振り返りのステージが承認された完了条件のうち要件に当たるものを反映する。目的のステージで反映済みなら重ねて更新しない。
- 後の作業の計画者・作業者・判定者の brief では、雛形の入力の選び方の既定値で本文とソース名・ID・存在の有無を渡す。未作成なら作成先を案内する。要件の更新は作業の成果としてステージの判定で確認する。

### 構造の記録 (Structure)

[構造ステージ](../stages.md#2-構造)を使うリポジトリが育てる、モジュール・責務・配置・依存の向きを表す資産である。

- 構造のステージが更新する。既定では `.devkit/structure.json` の1ファイルとし、置き場所は `[sources.structure]` で変更できる。バージョンは内容ハッシュとし、元のバージョンの識別子を取得できれば来歴に添える。リポジトリ内のファイルは git で履歴を管理し、PR のレビューで承認する。

- 知識としての本文の形式は自由である。view は `schemas/structure.json` に従う JSON の場合だけ構造図を描き、それ以外は本文を表示する。この JSON では `modules` の各項目は `id`・`name`・`responsibility`・`path`、`dependencies` の各項目は `from`・`to` を持つ。brief は固定した本文とソース名・ID・存在の有無を示す。

### 規則と強制手段 (Rules)

複数の作業で守る、設計上の変更困難な決定と、それを守る手段の資産である。

- 既定では `.devkit/rules.md` を正本とし、置き場所は `[sources.rules]` で変更できる。現在の決定・強制手段・根拠を保持し、共有に必要な根拠は資産側に記載する。ローカルの作業記録だけに依存させず、作業 ID・決定 ID・課題や PR の URL は補助参照として添えてよい。更新はループ自身の変更として、既定では人が確認する。
- brief の「元に戻せないもの」には、規則の共有する変更困難な決定の節への参照と[計画](#計画-plan)にある項目を渡す。規則の本文は一度だけ載せる。`[deny]` はコマンドの規則であり、この決定の一覧ではない。
- 強制手段が未実装の項目と、振り返りで繰り返し見つかった違反は、テスト・lint・型・pre-commit・検証コマンドによる機械の検査に移す候補とする。

## 整合性の境界

### 記録の範囲

記録の範囲は作業だけとする。共通項目は記録 ID とし、所属する作業は記録ルートから導く。外部入力に作業 ID がある場合は束縛先と照合する。記録形式は[作業に記録した `kit_version`](#作業-work)から識別し、参照は[エンティティ](#エンティティ)の種別ごとの定義に従う。記録 ID は [ULID](#作業-work) で一意にし、参照先は存在する記録 ID に限るか、外部参照であることを明示する。checkpoint・指示の本文・観測は記録に含めない。書き手と公開方法は[記録の書き込みと排他](#記録の書き込みと排他)で定める。

### セッションとブランチ

同じリポジトリでも、別の worktree で新しいセッションを開けば、それぞれのチェックアウトでループを並行して回せる。作業中のチェックアウトでの2つ目の `start` は拒否する。各チェックアウトは自分の `.devkit/run/` を持つ。1ステージ内の単位用の worktree は、[分割した作業と合流](flow.md#分割した作業と合流)の作業場所である。

`start` は[開始の条件](guarantees.md#再開と-hook-の稼働確認)を満たしたセッションの観測に作業 ID を書いて束縛する。HEAD がない場合、または作業ツリーに存在する設定済みの規範・`devkit.toml`・サブエージェント定義が未コミットまたは変更されている場合は、理由と直し方を返して拒否する。以後のコマンド(`next`・`submit`・`answer`・`external`・`resume` を含む)と hook はこの束縛から作業を特定し、`next` は識別したセッション ID をラウンドに結び付ける。束縛のないセッションで `next` または `resume` が呼ばれ、cwd のブランチが作業に記録したブランチ(既定 `devkit/<作業 ID>`)なら、そのセッションを作業に束縛する。新しいセッションからはこの手順で作業を特定する。中断からの再開条件は[中断](guarantees.md#中断)に従う。

CLI は Bash の環境変数 `CLAUDE_CODE_SESSION_ID`(Claude Code)と `CODEX_THREAD_ID`(Codex)からセッションを直接識別する。前者は hook の `session_id`、後者は rollout のファイル名の ID と一致する。hook は入力のセッション ID を使う。

cwd のブランチが作業のブランチと違っても束縛は無効にしない。読む操作(`next`・`status`・`view`)は警告だけで続けるが、`submit`・`answer`・`external`・`plan`・`resume`・完了の確定は拒否する。`note` の受理は[決定と証拠](#決定と証拠-decision--evidence)に従う。不一致時の `next` は記録を行わず、結果を受理せず照会だけで警告付きの指示を返す。中断中の応答は[中断](guarantees.md#中断)に従う。

`pause` の作業の特定と、中断の記録に対するブランチ不一致時の扱いは[中断](guarantees.md#中断)に従う。

### 状態遷移と受理条件

作業の状態は、計画・StageRun・ラウンド・問い・外部操作から導く現在地に、中断の有無を重ねて表す。

- 終了前の任意の状態から中断に入り、中断前の現在地への参照を保持する。StageRun やラウンド、未受理の指示を中断だけで失効させない。
- 中断からの再開では中断前の状態に戻り、ledger に残った結果を照合して続ける。中断中に届いた結果も復元に含める。完了・中止後の `pause` は[中断](guarantees.md#中断)に従う。
- `pause`・`resume` による中断・再開の条件、新しい指示と処理の抑止は[中断](guarantees.md#中断)に従う。中断中の `next` は、中断中であることと `devkit resume` で再開できることだけを返し、作業を進めない。

中断中でなく、[セッションとブランチ](#セッションとブランチ)が一致する場合、`next` は未受理の結果(作業者・判定者・計画者サブエージェントの結果ファイル、判定コマンドの結果、`command:` の check の実行結果)を冪等に受理して状態を進め、ledger と計画から次の指示を計算する。同じ結果を二度受理せず、同じセッションで受理後の状態が同じなら同じ指示 ID と指示を返す。単位の結果がそろった後の合流と再開時の照合は[分割した作業と合流](flow.md#分割した作業と合流)に従う。

`submit`・`answer`・`external`・`plan` も状態を進める。遷移表にない遷移は行わない。`note` の受理は[決定と証拠](#決定と証拠-decision--evidence)に従う。`submit` は終了ブロックの「完了を主張」もそのまま受理し、完了の確定は `devkit` が[完了条件](guarantees.md#完了条件)に従って行う。`submit` には[セッションとブランチ](#セッションとブランチ)および [受理時の照合](guarantees.md#再開と-hook-の稼働確認)の共通条件を適用する。これらを満たした後、終了ブロックの受理で拒否するのは、開いているラウンドがない、終了ブロックの作業指示 ID がそのラウンドの現行の作業指示 ID と一致しない、未回答の問いがある、必須項目(作業指示 ID および終了の種別に応じた項目)が欠ける、の4つだけとし、理由を返す。未回答の間はそのステージの作業を止める。

エージェントが終了ブロック・計画・note の入力 JSON を書く既定の場所は、`.devkit/run/work/<作業 ID>/inbox/` とする。配置では拒否せず、内容・指示 ID・状態の受理条件は各入力の定義に従う。終了ブロックの必須項目はスキーマで検証する。

`devkit external` の入力ファイルは配置を受理条件とせず、`devkit` がその内容を実行の記録にコピーする。

### 作業の排他制御

同じ作業に対するプロセス間の排他制御は `.devkit/run/work/<作業 ID>/run.lock` で行う。`pause` による中断の記録と中断中の状態通知は作業ロックを要求せず、[中断](guarantees.md#中断)に従う。

### 計画のバージョン

バージョンは単調に増加させる。承認状態は承認の記録から、提案中・却下・撤回・実行可能の状態は計画の Judgment、撤回の記録、必要な承認から導く。実行可能なバージョンは、計画の check に合格し、必要なゲートの承認を得た最新のバージョンである。

計画の承認の条件は `[approval] plan = "requirements" | "always" | "deviation"` で定め、既定を `"requirements"` とする。

- `requirements`: 作業の最初の計画、完了条件の ID または文面が直前に人が承認したバージョンから変わった計画、雛形からの逸脱がある計画、外部操作を宣言した計画で人の承認を必須とする。完了条件が同じで逸脱も外部操作も未決事項もない作り直しは、承認済みの合意の範囲として再確認しない。
- `always`: すべてのバージョンで人の承認を必須とする。
- `deviation`: 雛形からの逸脱または外部操作の宣言がある場合に人の承認を必須とする。

`open_questions` が空でない計画は、いずれの設定でも人の承認を必須とする。

StageRun の開始時にバージョンを束縛し、実行中は使い続ける。切り替えはステージの開始時だけとし、提案中のバージョンがある間は古いバージョンを実行しない。`devkit plan <ファイル>` は提案を記録し、check と必要なゲートを `next` の指示で進める。`devkit plan --withdraw` は撤回を追記する。

撤回後も旧バージョンの実行を妨げないのは、人が自発的に起票して撤回した提案だけである。engine が router の「前のステージに戻る」を記録した時点で旧 StageRun を再計画待ちにし、計画者が残りを作り直す。計画の check と、設定に従って必要になる人の承認を経て、遷移表の `back` のステージから新しい StageRun を開き、旧バージョンを再開しない。提案が却下されても旧バージョンには戻らない。

ステージの遷移が `done: "replan"` なら、そのステージの完了後に既存の再計画の経路で計画者が残りを作り直す。作り直した計画の check と、`[approval] plan` に従う承認を経て、残りのステージを開始する。完了条件の ID または文面が変われば、既定では人の承認が必要である。完了済みのステージは完了のまま保持し、残りの計画に含めなくても雛形からの逸脱に数えない。

再計画の残りのステージは、完了した StageRun に束縛した計画と、そのステージの `done` からの遷移順で求める。最新の提案の配列位置からは求めない。再提案でも、再計画の依頼に結び付けた再計画の種別と残りの作業を保つ。計画の check が `NOT ASSESSED` になり、人が修正を指示した場合も、最初の計画の提案に戻さず、同じ再計画の種別と残りの作業で計画者へ再依頼する。

人が計画を却下した場合は、どう直すかという人の指示を計画者に渡して作り直させる。`open_questions` への人の回答も、計画の却下と作り直しの指示として同じ経路で渡す。この再提案の回数には上限を設けない。

計画の check が `FAIL` の場合は、指摘を計画者に戻して作り直させる。人を挟まずに計画の作成と check を繰り返すラウンド数には、ステージと同じ形で上限を設け、達したら人に確認する。上限の既定値は3とし、雛形で上書きできる。

### 資産の更新と共有

リポジトリ内のファイルは通常の変更としてコミット・PR・マージで更新し、機械間の直列化と競合は git と人のレビューで扱う。外部のソースは[書き込みの流れ](#書き込みの流れ)に従い、期待する元の内容ハッシュとの比較と更新を一体で行う。同じリポジトリで複数人が別々の作業を進める使い方も対象に含む。情報は PR 本文の計画の要約と決定、および育てるものを通じて共有する。並行作業の配置は[利用側のリポジトリ](layout.md#利用側のリポジトリ)に従う。

後の作業に効かせたい決定は、requirements・structure・rules のいずれかに残す。各ステージ定義は、この反映先を指定する。作業の記録だけを後の作業への引き継ぎ先にしない。

## 記録の書き込みと排他

ledger の書き手は `devkit` の CLI(engine と cmd)だけである。hook も同じバイナリで動くが、ledger は読むだけで、セッションの観測、人の入力の観測、停止の観測、判定者サブエージェントの結果ファイルなどの生成物だけを書く。セッションの観測は [hook の共通処理](hooks.md#共通処理)の追記型のファイルとし、他の生成物も各定義の識別項目で名前を一意にして、同時に動作する hook が衝突しない。

- **実行の記録と生成物の公開**: 記録は追記のみとし、記録 ID をファイル名とする独立した JSON ファイルに保存する。一時ファイルへ書いて rename で公開し、読み手は一時ファイルを無視する。壊れた記録はその場に残して処理を止め、対象と理由を報告する。生成物も同じ方法で公開するが、再生成できる view の HTML は通常の書き込みで保存する。
- **資産の調停**: [資産の更新と共有](#資産の更新と共有)の更新と競合の解決に従う。
