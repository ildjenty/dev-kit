# データ

作業は1つの課題に対するループを所有し、計画、ステージの実行、ラウンドを通じて進む。対象のバージョンが、作業・検証・判定を結び付ける。バイナリが持つもの、リポジトリが育てる資産、追記する実行の記録、再生成できる生成物を分け、それぞれの所有者と更新の境界を定める。

## データ形式

計画・記録・指示・終了ブロック・結果・決定と証拠は JSON とし、JSON Schema で形式を制約する。

エージェントへ渡す出力スキーマは、使用するすべての `$ref` の参照先を同梱し、単独で解釈できる形にする。補助のスキーマは、出力スキーマが参照するものと check の `schemas` に指定した入力契約の和集合だけを渡す。

## 所有と生存期間

データの所有と生存期間、整合性を守る境界は、[assets/principles/data.md](../../assets/principles/data.md) の原則5に従う。

- **バイナリが持つもの**: JSON Schema、分類表と[役割](#役割-role)の既定値、ホスト設定の断片である。記録と共通の出力の JSON Schema はバイナリとの約束であり、リポジトリで育てる対象にしない。ステージ固有の `report` と `unit_report` の形はソースから選ぶ。人への確認の分類は `devkit.toml` の `[router] human_confirmation` で上書き・追加・削除できる。check の結果から次の行動への対応は固定である。役割は `devkit.toml` の `[roles.<id>]` で定義し、既定の4つの役割を上書き・追加できる。
- **育てるもの**: リポジトリが所有する知識とループの資産である。知識は名前付きのソースで管理し、既定のリポジトリ内のファイルは git で共有する。原則、用途別の判定基準、ステージ定義、検出試験の例と仕様、ループのパターン、テンプレート、規則、git の運用の文書、報告の形、要件、構造を含む。検出試験の合格の索引、`devkit.toml`、ホスト設定、サブエージェント定義、skill、AGENTS.md、CLAUDE.md はソースの外で管理する。作業範囲の記録への参照は[規則と強制手段](#規則と強制手段-rules)に従う。
- **実行の記録**: 作業が所有する。完了・中止後も StageRun、Judgment、決定、成果物の既存記録を保持する。人の判断である回答・承認・状態変更は完了後も追記を許す。完了した作業の外部操作は同じ承認と記録の経路で受け付けるが、新しい作業ラウンドは開かない。中止した作業では新規の外部操作を受け付けない。
- **生成物**: brief と判定依頼、作業履歴ファイル、差分ファイル、対象の展開先、結果ファイル、停止の観測、view の HTML は作業の下に置く。停止の観測の保持条件はその定義に従い、それ以外は再生成または削除できる。セッションの観測は作業の外にチェックアウトごとに置く。問いの回答と訂正の入力は束縛先の作業で観測する。展開先の削除時期は[性能と出力](guarantees.md#性能と出力の上限)、refs の生存期間は[対象のバージョン](#対象のバージョン-targetversion)に従う。

知識は `devkit.toml` の `[sources.<名前>]` で接続先を設定する。設定がなければ、`init` が初期内容を置く既定のソースを使う。既定のアダプタは `files` である。

- `principles`: `.devkit/principles`。原則と用途別の判定基準であり、`norm = true` である。
- `stages`: `.devkit/stages`。ステージ定義であり、`norm = true` である。
- `plans`: `.devkit/plans`。パターンであり、`norm = true` である。
- `rules`: `.devkit/rules.md` を1文書として扱い、`norm = true` である。
- `git`: `.devkit/git.md` を1文書として扱い、`norm = true` である。git の運用を散文で定める。
- `examples`: `.devkit/checks`。検出試験の例と `spec.json` の仕様であり、`norm = true` である。
- `templates`: `.devkit/templates`。brief と form のテンプレートであり、`norm = true` である。
- `requirements`: `.devkit/requirements.md`。要件の正本であり、`norm = false` である。
- `structure`: `.devkit/structure.json`。構造の記録であり、`norm = false` である。

置き場所と接続先はソースごとの設定で変更できる。検出試験の合格の索引はソースではなく、`[state] detect`(既定 `.devkit/detect.json`)で保存先を設定する。

skill は `.agents/skills/devkit/`、サブエージェントの定義は `.claude/agents/`・`.codex/agents/` に置く。実行の記録と生成物の場所 `.devkit/run/` は固定とし、git では管理しない。サブエージェントの定義、hook、保護の設定、ignore がこの場所を前提にし、作業の途中で変えると記録を見失うためである。

分割した単位の作業場所は、記録とは別の `.devkit/worktrees/<単位の指示 ID>/` に置き、ignore する。中断中は保持し、中止・作業完了時には変更のない worktree だけを削除する。変更の残る worktree は保持して場所を知らせ、破棄は人が git で行う。

原則・用途別の判定基準・ステージ定義にあるコード書式の `principles/…`・`stages/…`・`templates/…`・`rules.md` は、リポジトリ側の置き場所の論理名である。brief には論理名と実際のパスの対応を示す。`schemas/…` は、バイナリが出力スキーマの本文として brief に渡す。

git の運用は規範のソース `git` の文書で定め、計画のステージの入力で選ぶ。既定の場所は `.devkit/git.md` であり、ソースの設定で変更できる。既定の規則は、作業ごとに `feat/`・`fix/`・`chore/`・`refactor/`・`docs/` と短い説明を組み合わせた作業ブランチを用意し、コミットメッセージにも同じ種類の接頭辞を付け、完了後に起点のブランチ(多くは main)へ統合するものである。セッションのまとめ役が `start` の前のブランチ準備と完了後の統合を担う。push と PR の作成は外部操作の経路を通す。

## 知識のソース

ソースは名前とアダプタ、接続先、`norm`、書き込み能力 `writable` を持つ。`norm = true` は判定の規範、`norm = false` は要件・構造などの作業の成果である。規範のソースは空の選び方で全文書を列挙できなければならない。`devkit.toml`、指示ファイル、サブエージェント定義はソースの外の規範として固定する。

リポジトリ外のソースは読み取り専用とする。devkit は読み、固定し、エージェントに渡すが、書き込まない。リポジトリ外のソースに `writable = true` を書くと設定エラーになる。書き込めるのはリポジトリ内の `writable = true` のソースだけであり、改善の反映先もそれに限る。

### アダプタの口

必須の「選ぶ」は、アダプタが解釈する文字列の選び方を受け取り、文書の一覧を返す。各文書はソース内で一意な文字列の ID とテキストの本文を持つ。devkit は知識の項目・構造・タグ・参照形式や選び方の言語を解釈しない。

「書く」は、比較と更新を一体で行えることを保証できるアダプタのための口の定義である。文書の ID、新しい本文または削除、期待する元の内容ハッシュを受け取り、現在の内容が一致するときだけ比較と更新を一体で行う。一致しなければ反映せず、内容の不一致を返す。devkit はリポジトリ外のソースを読み取り専用として扱い、この口を呼ばない。文書の元のバージョンの識別子も任意で返せる。git のコミットなどを来歴として記録に添え、固定した本文の内容ハッシュとは区別する。

`files` の選び方は設定した置き場所からの glob、ID はそこからの相対パス、本文はファイルの中身である。空の選び方は全文書を返す。単一ファイルのソースはそのファイルを1文書として扱う。リポジトリ内では固定したスナップショットの git のツリーから読み、元のバージョンの識別子にコミットを添える。リポジトリ外では、その時点のファイルを読んで固定する。

ほかのアダプタは外部コマンドとして登録する口を持つ。JSON の入力で選び方を受け取り、JSON の出力で ID・本文・任意の元のバージョンの識別子を返す。「書く」の口は JSON の入力で ID・新しい本文または削除・期待する元の内容ハッシュを受け取り、JSON の出力で反映結果または内容の不一致を返す形で定める。規範の列挙は `files` と同じ契約である。提供するアダプタは `files` だけである。

### 固定と変化の検出

ラウンド開始時、ラウンド外の判定では指示を出す時点に、devkit が文書の本文を `.devkit/run/` の実行の記録の下へ写す。文書ごとの内容ハッシュと全体のハッシュをバージョンとし、判定者と作業者には固定した写しを渡す。規範はソース全体を列挙して固定し、次の時点の全文書の集合と本文を比べる。リポジトリ内の規範のソースの変更は、そのパスの git の差分で見る。成果のソースは選んだ範囲を固定し、同じ選び方の結果と比較する。選んでいない成果の文書の変化は保証の範囲に入らない。

### 書き込みの流れ

作業者が直せるのは、リポジトリ内の `writable = true` のソースのファイルだけである。作業者はファイルを直接編集し、devkit は git で差分を求め、完了時のコミットで反映する。規範の変更はループ自身の変更として確認する。判定・承認・完了は同じ対象の識別を指す。

リポジトリ外のソースには編集用の写しを作らず、devkit は書き込まない。リポジトリ内の `writable = false` のソースの文書を作業者が変えた場合、devkit はその変更の取り消しと、改善を教訓として `devkit note` で記録することを求める修正ラウンドを開く。

振り返りで改善を反映するソースは、リポジトリ内の書き込めるものに限る。リポジトリ外のソースと読み取り専用のソースへの改善は教訓として記録し、管理者へ引き継ぐ。

## エンティティ

### リポジトリ

dev-kit を導入した git リポジトリである。規範、設定ファイルと育てるものを所有する。

### 作業 (Work)

1つの課題に対して実行する1本のループである。

- [ULID](https://github.com/ulid/spec#specification)(時刻と乱数を26文字で表す識別子形式)の作業 ID、`start` に渡された課題への参照、チェックアウトと開始時のブランチを持つ。作業ブランチは、セッションのまとめ役が git の規則に従って `start` の前に用意する。devkit はブランチを作らない。
- 課題はメインのエージェントが壁打ちで決まった内容をまとめる主な指示である。`--task-file <ファイル>` でも本文を渡せる。会話の写しは取らない。途中の `instruct` は記録として次の計画者・作業者へ渡す。
- 基点コミットは来歴を示す開始時のコミットである。記録形式とバイナリの互換性の識別として、開始時の `kit_version`(バイナリと `init` の設定値は `"v3"`)を持ち、作業内の記録形式を固定する。互換性は[バージョン互換性](guarantees.md#バージョン互換性)に従う。
- `start` が作業を作成してから完了または中止するまで存続し、作業範囲の記録を所有する。
- 中断の有無、中断前の状態への参照、`pause`・`resume` が直接追記する中断・再開の記録を持つ。再開の記録は中断の記録を参照する。計画待ちなど StageRun のない期間も含め、作業全体の中断を[状態遷移と受理条件](#状態遷移と受理条件)から導く。

### セッションの観測 (SessionObservation)

ホストのセッションと作業の束縛を保持する生成物である。

- ホスト名、セッション ID、観測時刻、束縛した作業 ID を持つ。作業単位の継続回数は[停止の観測](#停止の観測-stopobservation)に持つ。
- 保存先と更新は [hook の共通処理](hooks.md#共通処理)、コマンド側の識別は[セッションとブランチ](#セッションとブランチ)に従う。

### ループのパターン (PlanTemplate)

利用者が用意するループの参考であり、既定 `.devkit/plans/<name>.json` に置く。配置は設定で変更できる。パターンは計画を固定せず、計画者が毎回課題に合わせて組む。

- 開始ステージ、ステージの列、候補の例 `optional_stages` を持つ。
- ステージは実体の `id`、定義の `definition`、担当の役割 ID、観点名による check、ゲートと理由、上限、遷移、入力の選び方を持つ。`definition` を省くと `id` と同じ定義になる。
- `split` は単位への分割、`report`・`unit_report` は報告の形、`human_prompt` は人のステージの問い、`delegations` は前もって任せる判断の文書を選ぶ。`report` と `unit_report` は知識のソースの JSON Schema である。
- check の中身は `[checks.<観点>]` から解決する。パターンの check に書くのは観点名、必須か、対象、完了条件 ID である。
- 計画者と計画の判定者の入力は `[planning] inputs` と `[plan_check] inputs`、計画の判定のやり直しの上限は `[planning] max_rounds` に置く。パターンはこれらを持たない。
- 課題・完了条件・計画者の `instructions` は持たない。内容ハッシュで識別し、git で履歴を管理する。

`start --plan <name>` は優先するパターンであり、省略時は `default_plan`(既定 `"default"`)を優先する。計画者はほかのパターンも参考にできる。devkit は各パターンの名前・固定したパス・内容ハッシュを依頼文に載せ、計画者は計算せず転記する。計画の `pattern` は参考にした名前と内容ハッシュを持ち、指示の参照コミットで存在とハッシュを確かめる。

#### check の一覧

`devkit.toml` の `[checks.<観点>]` に、計画者の一覧用の任意の `description` と runner、基準の `criteria`、検出試験の `examples`、入力契約の `schemas`、経緯の `history`、判定直前の指示を使う `brief_by_planner` を置く。`description` が空か未指定なら、最初の基準文書の本文の先頭行または実行するコマンドから説明を導く。init は既定の check に説明を書く。計画の check は一覧の観点を参照し、必須か、対象、完了条件 ID、`instructions` だけを書く。

runner は judge の役割、登録済みの判定コマンド、`command:<name>` の検証コマンドである。`command:` の観点名と runner は一致する。基準は規範のソースから選ぶ。`brief_by_planner = true` は計画者にその回の差分・報告・計画・要件を渡して補助の指示を得る指定である。固定した基準や範囲を狭められず、判定者へ原資料も別に渡す。既定では使わない。

#### ループの決まり

`[[loop.stage]]` は定義を1つ、一覧、または `"*"` で選び、各実体の必須 check、ゲート、許可する役割、上限の天井、固定する `report`・`history`・`outputs` を定める。`[[loop.path]]` は必ず含める定義 `require`、定義の後続を定める `definition` と `follows`、先頭の `first`、最後の `last` のいずれかを持つ。

検査する経路は採用済みの完了した実体の列と、計画の開始から `done` で到達する列を結んだものである。`follows` は次の `replan` または終わりまでの同じ区切りで満たす。`require` と `last` は `null` で終わる区切りについてだけ確かめる。計画の受理時とステージ開始時に、固定した規範で再検査する。

既定は implement に `command:test`・test・diff、verification に `command:e2e`・behavior、retrospective に harness を必須とする。implement の後に同じ区切りの verification を置き、最後を retrospective にする。purpose・scope のゲートはパターンと人の承認に任せる。

ステージ上限の天井は `[limits] max_rounds_ceiling = 3` と `max_no_progress_ceiling = 2` が既定である。超える計画を拒否する。定義ごとの決まりでも天井を指定できる。作業全体の上限は `[limits] max_total_rounds = 40` が既定であり、計画の判定のやり直しは `[planning] max_rounds = 3` である。

#### 修正の担当の規則

`fix` の遷移は、ステージ ID の1つの値のほかに、上から順に当てはめる規則の一覧を取れる。各規則は条件 `when` と、次のラウンドの担当の役割 ID `assignee` を持つ。`assignee` にはステージの担当に書ける役割を書く。規則は `to` を持たず、行き先は常にそのステージ自身である。どの規則も当てはまらなければ、ステージの既定の担当に戻る。規則が変えるのは担当だけであり、別のステージへ行く修正は書けない。`ask`・`back`・`done` は1つの値のままである。

条件に書けるのは次の記録から決まる事実だけであり、書いた条件をすべて満たすと一致する。

- `check`: そのラウンドで `FAIL` または `NOT ASSESSED` だった check の観点 ID。runner の種類は問わない。
- `failures_at_least`: この StageRun で必須の check が `FAIL` になったラウンドの数がこの値以上であること。検証コマンドの `FAIL` も数える。
- `human_rejected`: このステージの問いに人が却下と答えたこと。

規則は、修正の判断を記録する1か所である修正ラウンドを開く処理で、修正になるすべての経路について当てはめる。当てはまった規則の番号と結果の担当をラウンドの判断に記録し、次のラウンドはその担当で動く。担当は次に規則が当てはまるまで続き、どの規則も当てはまらなければステージの `assignee` に戻る。ループ自身の変更の取り消しと、読み取り専用のソースの変更の取り消しのラウンドは、規則を当てはめず直前の担当のままとする。

担当が変わっても同じ StageRun の中のラウンドであり、比較元、累積の差分、規範の固定、上限の数え方は変わらない。上限(`max_rounds`・`max_no_progress`)は規則より先に効き、達したら人に確認する。担当を変え続けても上限を超えては続かない。上限の問いでは、そのステージに規則があれば、規則に書いた役割で続ける選択肢を含める。人が続行を承認した場合、または提示された役割での続行を選んだ場合だけ上限を数え直す。却下した場合は回答待ちを保ち、新しい計画の提出、中止、後の回答の訂正まで next はラウンドを開かない。

### 計画 (Plan)

計画者がパターンを参考に課題ごとに組む状態機械のデータであり、作業に属する。記録形式は `v3` である。

- バージョン、参考にした `pattern` の名前と内容ハッシュ、課題、ID 付きの文章の完了条件、開始する実体 ID、ステージの列を持つ。
- 各ステージの実体 `id` は計画内で一意とする。`definition` で定義を選び、省略時は `id` を使う。同じ定義を増分ごとに何度も使える。既に走った ID は同じ仕事の再実行にだけ使い、新しい仕事には新しい ID を使う。
- ステージの並び・担当・check・ゲート・上限・遷移・入力・指示を課題に合わせて組む。定義済みのステージ・役割・check と、知識のソースにある文書だけを使う。パターンとの差は計画を拒否する理由にせず、設定の決まりを確かめる。
- check は観点名、必須か、対象、完了条件 ID、任意の指示だけを持ち、runner と基準などは一覧から解決する。
- `assignee` は work または human の役割 ID である。agent のある work は1つの単位として専用 worktree で動き、agent のない work はセッションがチェックアウトで作業する。human のステージは `human_prompt` の目的・入力・返してほしいものを問いにし、人の文章の回答を出力として記録する。
- `split` のステージは `units` を持てる。単位は計画内で一意の ID、説明、担当範囲、任意の役割・指示・`outputs` を持つ。役割の既定は worker であり、agent のある work に限る。範囲の重なりは計画の判定者が判断する。単位の成果に依存する仕事は別のステージにする。
- 課題固有の元に戻せないものの一覧を持つ。共有する決定は規則に残す。
- 外部操作は種別・対象・入力ハッシュと宣言時の登録定義・実行ファイルの内容ハッシュを持つ。宣言した計画は人の承認を必要とし、操作の照合は[外部操作の承認](guarantees.md#外部操作の承認)に従う。
- `open_questions` は任意の文字列配列である。曖昧な要求を推測で埋めず、決められない点を記す。人の回答は計画の却下と再提案の指示として渡す。

完了条件ごとに、それを確かめる check または人のゲートを置く。検証コマンド・判定者・判定コマンドから手段を選び、要件定義の段階は判定者と人のゲートで確かめる。妥当性と漏れは計画の判定者と人が判断し、kit は形式的な割り当てを強制しない。人が承認した完了条件を作業の完了基準とする。

計画のステージ・check・単位の `instructions` は文字列の配列であり、devkit が解釈せず対応する依頼文と承認の問いに渡す。メインのエージェントの途中の指示は `devkit instruct <ファイル>` で別に記録し、次の計画者・作業者へ渡す。判定者には渡さず、計画と完了条件を直接変更しない。

遷移・`start_stage`・戻り先・`StoppedStage`・修正の担当の規則と単位の所属は実体 ID を使う。`outputs` に実体 ID を書くとその実体を、定義 ID を書くと同じ定義の実体をすべて選ぶ。決まりは定義 ID を使う。コミットメッセージの `{stage}` は実体 ID である。

`done` の行き先は実体 ID、`"replan"`、`null` のいずれかである。`fix` と `ask` の行き先は自分の実体だけとする。開始から `done` で到達できないステージと循環を拒否する。戻り先に使えるのは現在の計画の実体と、この作業で走った実体だけである。戻り後の計画には戻り先の ID を含める。

受理時には指示の参照コミットで、すべての定義と基準・例・報告・単位の報告・人の問い・入力の選び方が1件以上の文書に解決することを確かめる。例の観点と check の観点を照合し、検出試験を必須とする設定では必須の判定の check に例があることを確かめる。上限の天井と作業の経路の決まりも照合し、ステージの開始時にも固定した規範で経路を再検査する。

### 役割 (Role)

ループの中で誰が作業・判定・計画・回答を担うかを表す、リポジトリが定義する担当である。

- `devkit.toml` の `[roles.<id>]` に、種類 `kind` と任意の `agent` を書く。種類は `work`・`judge`・`plan`・`human` の4つである。`agent` はサブエージェントの定義名であり、`devkit-` で始まる名前に限る。定義は `.claude/agents/<agent>.md`・`.codex/agents/<agent>.toml` に置く。
- 既定の役割は `worker`(`work`、`devkit-worker`)、`judge`(`judge`、`devkit-judge`)、`planner`(`plan`、`devkit-planner`)、`human`(`human`)の4つである。`devkit.toml` で同じ ID を書けば上書きし、新しい ID を書けば追加する。既定のパターンは `judge`・`worker`・`human` を使う。
- 作業場所は種類と agent から決まり、別の欄は持たない。`judge` と `plan` の役割は読むだけである。agent のない `work` の役割はセッション自身であり、チェックアウトで作業する。agent のある `work` の役割は devkit が作る worktree で作業する。
- `human` の種類の役割は1つだけ定義でき、ステージの担当にだけ書ける。
- 人格、プロンプトの中身、モデルの選択は役割に持たせない。agent の定義はリポジトリのものである。

devkit は種類ごとに次の規則を守らせる。違反は `devkit.toml` の設定エラー、またはパターンと計画の検証エラーにする。

- `judge` と `plan` の役割は読み取り専用である。Claude Code では、agent の定義の `tools` が `[roles] read_only_tools`(既定 `Read`・`Glob`・`Grep`)の部分集合でなければ、PreToolUse が起動を拒否する。Codex では `[deny] judge` に列挙した書き込みのツールを禁じるだけであり、Claude Code より保証が弱い。詳細は [PreToolUse](hooks.md#pretooluse)に従う。
- サブエージェントによる check の runner は `judge` の種類の役割に限る。`[plan_check] runner`(既定 `judge`)も `judge` の種類の役割か `[judges]` の判定コマンド名である。`[planning] role`(既定 `planner`)は `plan` の種類の役割である。
- 単位の `role` は agent のある `work` の役割に限る。agent のない `work` の役割はセッション自身であり、単位には使えない。分割するステージにも agent のある `work` の役割を指定できる。
- 役割の agent は、PreToolUse の書き込みの禁止・1行の起動・`model`・`effort` の上書きの禁止と、SubagentStop の採取の対象になる。hook は agent の名前から役割の種類を引いて、これらを効かせる。

職務の分離として、次の重なりを拒否する。

- 同じ agent を種類の違う役割に重ねない。作業の担当と判定の runner は種類が違うため、同じ agent が自分の作業を判定することはない。
- 役割の ID と `[judges]` の判定コマンド名を重ねない。
- 計画の check の runner の agent は、計画者の役割の agent と違うものにする。

役割の定義と各役割の agent の定義ファイルは規範として扱う。指示を出す時点の固定した参照(ラウンドの開始時、ラウンド外は作業ブランチの `HEAD`)で解決し、規範の識別、ループ自身の変更の分類、`start` のコミット済みの確認、[doctor](modules.md#doctor-の確認項目)に含める。

### ステージの実行 (StageRun)

作業内の1回のステージ実行である。従う計画のバージョンは[計画のバージョン](#計画のバージョン)の束縛と切り替えの規則で定まる。

- 実行 ID、ステージの実体 ID と定義 ID、ラウンドの列、実行状態、停止理由、次に動く主体を持つ。
- 実行状態は作業中・判定待ち・回答待ち・承認待ち・外部操作の確認待ち・失効・完了。「前のステージに戻る」による「再計画待ち」は失効の一種である。`done: "replan"` では、完了した StageRun の記録を残して残りを再計画する。中断は StageRun の状態を書き換えず、[作業](#作業-work)の状態として重ねる。
- 完了記録は[完了条件](guarantees.md#完了条件)に従い、コミットのハッシュを持つ。

### ラウンド (Round)

`next` が brief を渡してから、作業結果に対する次の行動が確定するまでの往復である。

- ラウンド ID、結び付けたセッション ID、担当の役割 ID、開始時と返却後の対象のバージョンを持つ。
- 終了ブロック、check の結果の集合、発行した指示の ID の集合と出し直し回数、次の行動の判断を持つ。修正の判断には、当てはまった[修正の担当の規則](#修正の担当の規則)の番号と次のラウンドの担当を持ち、次のラウンドはそれを読んで担当を決める。通常は [router の判断](flow.md#router-の判断)を engine が記録し、engine が直接記録する経路は[作業結果の提出](flow.md#作業結果の提出)・[作業結果の判定](flow.md#作業結果の判定)・[完了条件](guarantees.md#完了条件)に従う。
- 分割した作業と、agent のある `work` の役割が担当するラウンドでは、単位ごとの役割、指示、作業場所、終了ブロックと、合流の開始時の HEAD・入力として固定した SHA・結果を記録する。単位ごとの判定は持たず、合流後のツリーと、単位 ID を付けて欠けなく保持した各単位の終了ブロックを通常のラウンドで扱う。判定・ゲート・ループ自身の変更の確認・上限・戻り・再計画・問いはステージ単位である。

### 指示 (Instruction)

`devkit next` が返す、エージェントへの1つの指示である。

- 指示 ID は(作業 ID、種別、対象のキー、出し直し回数)から導く派生値である。
- 対象のキーは、作業ならラウンド ID、単位の作業ならラウンド ID と単位 ID、判定ならラウンド ID・観点 ID・runner の組、計画の check なら計画のバージョン・観点 ID・runner の組、計画なら計画のバージョン、検出試験なら[合格記録の同一性を定める内容ハッシュ](#検出試験の記録-detectiontest)の集合とする。ラウンドを開く前の指示も識別する。
- 出し直しは作業の記録に追記する。ラウンドに結び付いたセッション ID と異なるセッションからの `next` では、新しい指示 ID で出し直す。結果の受理は、セッションからの終了ブロックなら[状態遷移と受理条件](#状態遷移と受理条件)、作業者・判定者・計画者のサブエージェントの結果なら[判定結果の受理](guarantees.md#判定結果の受理)に従う。指示本文の保存は[記録の範囲](#記録の範囲)、同じセッションへの返却は[状態遷移と受理条件](#状態遷移と受理条件)に従う。
- 種別は、作業(brief)、判定待ち、判定、計画の check(判定の一種)、検出試験、計画、判定直前の計画者指示、問い、外部操作の確認、完了、中止である。判定には brief と対象の展開先のパス、問いには問い ID・文面・選択肢を持たせる。
- 指示の計算と結果の重複の扱いは[状態遷移と受理条件](#状態遷移と受理条件)および[判定結果の受理](guarantees.md#判定結果の受理)に従う。
- サブエージェントの結果がスキーマまたは内容の検証に失敗した場合は、失敗と結果の拒否を記録して再読せず、対象と依頼内容を保って出し直し回数を増やす。同じ対象へ2回出し直しても検証に失敗する場合は人への問いを起票する。最終メッセージの JSON の解析失敗も同じ扱いとする。
- 同じ runner の未受理の指示が複数あり、指示 ID のない不正な最終メッセージをどの指示にも結び付けられなければ、観測を残して人に問う。

- 判定直前の指示、経緯の範囲、出し直しは、判定のラウンド・観点・runner と同じ識別に結び付ける。
- ステージ定義は `stages` ソースから選び、本文の入力は計画のステージの `inputs` と一覧の check の `criteria` で選ぶ。計画者と計画の判定者の入力を `[planning] inputs` と `[plan_check] inputs` に書け、要件と規則を渡す既定値を持つ。その他の規範は固定した写しの一覧で渡す。基準の文書が別の文書を必要とする場合も、選び方へ明示する。文中の参照は解析しない。変更の範囲は scope の出力と rules で渡す。検出試験への資料は[検出試験](guarantees.md#検出試験)の制限に従う。

#### 依頼の入力

依頼の入力は、採用された成果、今の材料、経緯に分ける。

- 採用された成果は、最新の戻り・作り直しの後の実行の経路で完了した StageRun の、各ステージの最後に採用されたラウンドの報告と成果物への固定した参照である。戻り先は採用済みの実行経路上で特定し、その実行と後続を失効させて経緯に回す。現在の計画の配列順によらず、過去の計画の戻り先にも同じ規則を適用する。
- 今の材料は、直前のラウンドの報告、未解決の指摘、検証コマンドの出力、人の答えなど、そのラウンドの修正に必要なものである。
- 経緯は本文に入れず、指示発行時点で固定した索引のファイルへの参照で渡す。記録から決定的に絞り、LLM による要約や検索、トークンの計算は行わない。

パターンのステージ・一覧の check の `history` は `"none"`・`"stage_run"`・`"check"`・`"all"` から選ぶ。既定は作業者が `"stage_run"`、判定者が `"check"`、振り返りが `"all"` である。判定対象に対応する検証コマンドの実行結果、有効な承認、引用された証拠とその参照先は、この設定によらず必ず判定者に渡す。`history` はそれ以外の経緯だけに効く。既定の harness の check は `history = "all"` を明示する。

ステージ・単位の `outputs` に実体 ID または定義 ID の一覧を書き、本文に入れる採用された成果を選べる。既定は採用された成果のすべてである。それ以外も固定した索引から読めるようにする。判定者にも採用された前のステージの成果と、直前のラウンドの報告への固定した参照を渡す。

規則・要件・構造・基準・出力スキーマの同じ本文は、依頼文に1回だけ載せる。機械が読む JSON の部分は ID とハッシュだけとし、本文は人と LLM が読む部分にだけ置く。補助のスキーマは、出力スキーマが参照するものと check の `schemas` に指定した入力契約のスキーマの和集合だけを渡す。計画の判定とその検出試験の既定の `schemas` は `plan`・`plan-template`・`finding` である。

依頼文の本文は `[briefs] max_bytes`(既定200000)で上限を設ける。超える分は別のファイルにして一覧で参照を渡し、上限を超えた事実を記録する。黙って切り詰めない。

同時に発行する指示は、全体の `[parallel] max_concurrent`(既定3、1以上)と役割ごとの `[roles.<id>] max_concurrent`(指定時は1以上)の両方で制限する。発行済みで未受理のサブエージェントの指示を数える。互いに依存しない単位の作業、検証コマンド後の判定者の check、check ごとの判定直前の指示をまとめて返し、空いた分だけ次の `next` で発行する。

### 対象のバージョン (TargetVersion)

git のツリーと外部の成果の文書を組み合わせた識別、計画のバージョン、構造のバージョンの直和である。

- ツリーのスナップショットは、追跡ファイルと ignore されていない未追跡ファイルから一時インデックスで作る、ブランチには含めないコミットオブジェクトのツリーハッシュである。`[sources.<名前>]` で定まるリポジトリ内の資産、指示ファイル、skill、ホストの設定、サブエージェントの定義も追跡ファイルとして含む。ignore する `.devkit/run/`・`.devkit/worktrees/` は含めない。
- 判定の対象の識別は、このツリーハッシュに、リポジトリ外の `norm = false` の成果の文書のソース名・ID・内容ハッシュの集合を加えたものとする。リポジトリ外の成果は読み取り専用であり、固定した本文を判定対象に含める。判定・承認・完了は同じ識別を参照する。
- ラウンドの開始時と返却後に取得する。各ラウンドの開始時のものは[規範の固定](guarantees.md#規範の固定)に使う。判定依頼の差分と、判定後の依存の宣言・ループ自身の変更の分類には、そのステージ実行の最初のラウンド開始時のスナップショットと規範のソース全体の固定した文書を比較元として使い、修正ラウンドを通じた返却後までの変更を含める。返却後のものは判定・完了時のコミットに使う。commit 前後の照合と不一致時の更新・再判定は[commit 直前の対象の照合](guarantees.md#commit-直前の対象の照合)に従う。
- コミットに `refs/devkit/<作業 ID>/<対象のバージョン>` を付け、作業の完了・中止と成果物の永続化がそろうまで保持し、その後削除する。
- 計画のバージョンは作業内で識別する。構造のバージョンは[構造の記録](#構造の記録-structure)に従う。

### check の結果 (Judgment)

ある観点から対象を判定した結果である。

- 観点 ID、対象のバージョン、規範の識別、確認した完了条件 ID の集合、判定、指摘を持つ。判定は `PASS`・`FAIL`・`NOT ASSESSED` である。
- 確認した範囲と未確認の範囲、方法と環境、指示 ID、受理した内容と来歴を持つ。結果ファイルのパスは任意の診断情報とする。
- 実行主体(runner。check を実行する相手)は種類ごとに次の項目で表す。
  - サブエージェント: 役割の ID と agent の名前。effort(Claude Code の推論の量を指定する設定項目)または model(Codex)の実測値は、取得できる場合に来歴として添える。取得元は [SubagentStop](hooks.md#subagentstop)に従い、取得できない項目は記録せず、必須にしない。設定値を観測値の代わりに使わない。
  - 判定コマンド(`[judges]`): 名前。
  - `command:` の check: `command:<name>`。
- 担当とコマンドの定義は runner と使用した規範から一意に特定し、定義のハッシュを重ねて保持しない。
- 規範は、`norm = true` の全ソースの全文書、`devkit.toml`、`.claude/agents/`・`.codex/agents/` の定義、AGENTS.md、CLAUDE.md の集合である。規範の識別は、固定した全文書の集合と内容ハッシュ、およびソースの外の規範のツリー ID・blob ID から定まる。
- requirements・structure・detect・`.devkit/run/` は規範に含めない。これらの変更では規範の識別は変わらず、それを理由に判定は失効しない。requirements の更新によって計画の判定をやり直すこともない。
- 対象のバージョンと規範の識別の両方が照合対象と一致するときだけ有効である。照合するスナップショットの取得時点は[規範の固定](guarantees.md#規範の固定)に従う。計画や構造の判定も選んだ基準や規則が変われば失効するが、評価対象コードだけの変更では規範の識別は変わらず、これらの判定は失効しない。
- `command:<name>` がラウンド開始時の `devkit.toml` に未登録なら、その check を `FAIL` とする。指摘は `auto-fixable` とし、「検証コマンド `<name>` が登録されていない。検証の手段を作り `devkit.toml` の `[commands.<name>]` に登録する」とする。登録はループ自身の変更として、既定では人が確認し、次のラウンド開始時のスナップショットから使う。`command:` の check がツリーを変えたときの指摘には、出力先を ignore する案内を含める。
- 受理と集約は[判定結果の受理](guarantees.md#判定結果の受理)に従う。

### 指摘 (Finding)

check が見つけた失敗や判断を要する点である。

- 指摘 ID、blocking かどうか、`auto-fixable` または `needs-decision`、失敗のシナリオを持つ。
- `auto-fixable` は人の判断を要さず修正できる指摘、`needs-decision` は人の判断が必要な指摘を表す。
- 任意の真偽値 `premise_broken` は、前のステージの前提が崩れたという判定者の申告である。blocking の指摘にこれが付いていれば、router は人への問いにし、前のステージへの戻りを推奨として示す。戻るかどうかは人が `back` の答えで決め、判定者の指摘だけでは戻らない。
- 適用除外の主張と根拠の有無、解決した指摘への参照を持つ。
- 修正ラウンドの依頼には前回の指摘 ID を渡す。解決した指摘への参照と、確認した完了条件 ID の増加から進展を計算する。

### 決定と証拠 (Decision / Evidence)

作業中に得た判断と、その判断を支える調査結果である。

- 決定は自然文の有効条件(`validity`)、置換、依存、適用条件、決定者、暫定か確定か、却下した案とその理由・具体例を持つ。証拠は出典と確認方法を持つ。
- 有効条件・適用条件と外部依存が満たされるかは、エージェントと人が判断する。`devkit` はこれらを評価せず、条件と参照を決定に添えて渡す。記録から導く承認・却下・保留、置換と記録内の依存関係の状態とは区別する。
- `devkit note <種別> <ファイル>` は、作業の特定とスキーマ検証だけで受け付ける。ブランチの一致は要求しない。種別には教訓を含む。
- 承認・却下・保留は、[問い](#問い-question)への[回答の受理](guarantees.md#回答の受理)で追記する状態変更から導く。

### メインのエージェントの指示

`devkit instruct <ファイル>` は JSON の指示を作業に記録する。本文の `text` を次の計画者・作業者の依頼文へそのまま渡し、判定者と検出試験へは渡さない。任意の `audience` は planner または worker、`stage_id` は対象の実体を選ぶ。すでに発行した依頼文は変えない。計画や完了条件の変更は再計画と承認を通す。

### 問い (Question)

form に従う、人への確認事項である。

- 問い ID、承認対象、選択肢、推奨、停止理由の分類、回答後に進むステージ、停止しているステージと理由、根拠への参照を持つ。
- 承認対象は git のツリーと外部の成果の文書を合わせた対象の識別、計画のバージョン、外部操作、決定 ID、継続上限の確認対象である作業 ID の直和である。外部操作の識別項目は[外部操作の承認](guarantees.md#外部操作の承認)に従う。
- 人の確認が必要な決定には、その決定 ID を承認対象として参照する問いを起票し、選択肢を承認・却下・保留とする。
- 計画承認の問いには課題、ID 付き完了条件、各実体の定義・担当・ゲート・必須 check・指示の並び、元に戻せないもの、外部操作、未決事項を載せる。前に承認した計画の残りとの構造の差分を表示し、最初の計画は参考パターンと比較する。パターンとの差は承認の理由にしない。
- ゲートの問いには、計画のゲート理由、終了ブロックの実施内容・確認済み事項・未確認事項、devkit が生成した差分ファイルのパスを載せる。ループ自身の変更の問いには、変更したソース名・文書 ID と、規範・ホスト設定・skill のファイル一覧と差分ファイルへの参照を載せる。エージェントは生成された問いを提示する。
- ループ自身の変更は、規範・ホスト設定・skill・リポジトリ内で git が追跡する有効な pre-commit の設定の変更であり、requirements と structure の変更は含めない。`[approval] meta_loop_edit` は `"confirm"`(既定)または `"allow"` とし、既定ではステージによらず、変更が効く最初の時点より前に確認する。
- `meta_loop_edit = "confirm"` では、ラウンド開始時のスナップショットに、作業の基点または直前に確認した時点からの未確認のループ自身の変更があれば、ラウンドを開く前に問いを起票して止める。最後のラウンドの変更は判定後、完了時のコミットの前に確認する。確認済みの範囲は、確認したスナップショットの規範の識別で表す。却下されても作業対象は保持し、確認済みの規範の識別を別に保持する。次の作業ラウンドで、却下した規範の変更ファイル一覧を渡して取り消させる。同じ変更が残る間は再確認を求めず作業者へ戻す。
- 画面のデザインを始める前のレビューゲートでは、画面 ID(画面の識別子)と表示内容を含むツリーのスナップショットを承認対象とする。画面のデザインの承認を求める問いは、画面 ID を説明に示す。
- `devkit` が記録して `next` の指示として返し、エージェントがチャットで人に見せる。form は問いの文面に、[回答の受理](guarantees.md#回答の受理)に従う自由な言葉での回答を案内する。
- 承認対象が変わったら新しい問い ID で起票し直し、古い問いへの回答は拒否する。
- [継続上限](guarantees.md#中断)の問いは[停止の観測](#停止の観測-stopobservation)への参照を持つ。

作業者からの確認要求では、`confirmation` の問いの原文、選択肢、推奨と理由、材料への参照、終了ブロックの再開条件をすべて提示する。判定後の確認では、その判断を必要とした指摘の本文を載せる。人が担当するステージでは、`human_prompt` で選んだ文書の目的・入力・返してほしいものを提示する。差分は固定したファイルへの参照で渡す。問いは、エージェントが承認・却下・保留・戻り・文章のいずれかとして記録するまで開いたまま続く。

### 人の入力の観測 (PromptObservation)

ホストが受け取った入力の本文を保持する生成物である。

- 本文の採取と保存先は [UserPromptSubmit](hooks.md#userpromptsubmit)に従う。
- 束縛された作業の問いへの回答と訂正の入力を観測する。`start` の課題のために束縛前の入力や会話の写しを保持しない。
- 人以外の入力での発火と観測から除く本文は [UserPromptSubmit](hooks.md#userpromptsubmit)に従う。
- 観測した入力からの回答の記録は[回答の受理](guarantees.md#回答の受理)に従う。人が別のセッションから回答を送る経路は範囲外とする。

### 停止の観測 (StopObservation)

作業単位の継続回数と、上限到達時の問いを保持する生成物である。計数と停止の条件は[中断](guarantees.md#中断)に従う。

- 観測 ID、作業 ID、セッション ID、観測時刻、照合した ledger の末尾の記録 ID、継続回数、上限到達の有無を持つ。上限に達した場合は問い ID と問いの本文・選択肢・推奨・理由も持つ。
- 保存先は `stops/<ULID>.json` とし、Stop が公開する。計数の根拠となる最新の観測と、ledger に未取り込みの問いを含む観測は削除しない。
- 問い ID は作業 ID と計数の基点となる記録 ID から導き、同じ上限到達で重複起票しない。CLI が問いを ledger に取り込む際も同じ ID を使う。

### 回答・承認 (Answer / Approval)

観測した入力をもとに、問いへの人の判断を確定する記録である。

- 問い ID と承認対象を持つ。
- ステージの問いへの解釈 `back` は、前のステージへ戻る回答である。engine が router の `back` を記録し、戻りと再計画の経路へ進む。
- エージェントの解釈(承認・却下・保留など、または文章の回答)、UserPromptSubmit が観測した人の入力の原文と出所(セッション ID と時刻)を保存し、観測ファイルを削除した後も記録だけで根拠を確かめられるようにする。
- 受理と訂正は[回答の受理](guarantees.md#回答の受理)に従う。問いと承認を機械間で共有する経路は対象範囲に含めない。

### 外部への書き込み (ExternalOp)

kit が管理する、リポジトリ外への書き込み操作である。

- 種別、対象、入力のハッシュ、登録定義の内容ハッシュ、リポジトリ内の実行ファイルの内容ハッシュを持つ。
- 操作 ID、承認への参照、実行前の記録、実行結果、外部側の識別子を持つ。実行結果は成功・失敗・結果不明である。
- 操作 ID の導出と外部向けの冪等キーとしての兼用は[外部操作の二重適用](guarantees.md#外部操作の二重適用)、実行の条件は[外部操作の承認](guarantees.md#外部操作の承認)に従う。

### 進捗 (Progress)

ラウンドの終了ブロックである。

- セッションからは `devkit submit` の入力として受け取り、`devkit` が記録する。単位の作業者は `schemas/progress.json` に従う終了ブロックを最終メッセージで返し、SubagentStop が保存する。合流後は、単位 ID を付けて欠けなく保持した各単位の終了ブロックをステージのラウンドとして受理する。
- 作業指示の指示 ID (`instruction_id`) を必須項目とし、実施内容、確認済み事項、未確認事項、障害、終了の種別、一時状態(確認方法・出典・無効になる条件)、再開条件を持つ。対象外の作業と変更理由は必要に応じて補足する。読めなかった入力とその影響は未確認事項に記録する。
- 一時状態が有効かどうかを判断する条件は自然文であり、エージェントと人が判断する。`devkit` は条件を評価せず、確認方法・出典・無効になる条件を一時状態に添えて引き継ぐ。
- 変更ファイルの一覧は[成果物](#成果物-artifact-record)の差分から生成する。判定と再開には正本の制約を直接引き継ぐ。次の行動は[指示](#指示-instruction)に従う。判定依頼での報告の扱いは[判定結果の受理](guarantees.md#判定結果の受理)に従う。
- 終了の種別は完了を主張・停止して確認・作業停止の申告とし、種別に応じた進行は[作業結果の提出](flow.md#作業結果の提出)に従う。「作業停止の申告」は作業者による報告であり、作業の中断・再開は[中断](guarantees.md#中断)の `pause`・`resume` で記録する。外部書き込みの要求は終了ブロックに含めず、[外部操作](flow.md#外部操作)で行う。

ステージ固有の `report` は、計画のステージが選んだ JSON Schema で形を検証する。完了を主張する終了ブロックでは必須であり、確認の要求や停止では、その形に合う範囲の途中の報告を認める。`submit` は形に合わない報告を理由付きで拒否する。形式への適合は作業者の申告の形だけを表し、証拠や完了の根拠にはしない。採用された報告は後のステージと判定者へそのまま渡す。

既定の報告の内容は、purpose が要件と完了条件の案、scope が含めるもの・含めないもの・元に戻せないもの、structure・contract・steps がそれぞれの成果、implement が完了条件ごとのテストと実行した検証、verification が完了条件ごとの利用場面の通しの確認、retrospective が問題ごとの捕まえるべきだった所と反映先である。

確認の要求は、ステージ固有の `report` と別の `confirmation` に書く。devkit がその形を定め、問い、選択肢、推奨、理由、材料への参照を持つ。確認を求める終了の種別では必須である。問いの原文をそのまま人への問いに載せ、再開条件も提示する。根拠のない推奨は付けない。

単位の報告は単位 ID を付けて欠けなく保持し、合流後の判定に渡す。ステージの報告へまとめ直さない。任意の `unit_report` があれば、サブエージェントの結果を受理するときに形を検証する。

作業者は任意の `commit_message` に git の規則に沿ったステージ完了時のコミットメッセージを書ける。省略時は設定のテンプレートで補う。

### checkpoint

再開のために記録から組み立てる現在地の派生値である。

- 作業の中断・再開、実行状態を持つ最新の StageRun、最新の進捗、条件と記録上の状態を添えた決定、未回答の問い、未受理の指示から組み立てる。未取り込みの停止の観測も照合する。上書きする記録は持たない。
- SessionStart の注入ごとに ledger から組み立て、一時状態は条件によって除外せず、確認方法・出典・無効になる条件をそのまま添えて渡す。有効かどうかはエージェントと人が判断する。出力上限への対応は[性能と出力](guarantees.md#性能と出力の上限)に従う。

### 成果物 (Artifact record)

作業が生んだ変更と、その永続化先を結び付ける記録である。

- 記録 ID、変更前後の対象のバージョン、完了条件 ID、変更の種類、決定への参照、永続化先であるコミットへの参照を持つ。
- 開始時と返却後のスナップショットの差分から `devkit` が作成する。

### 検出試験の記録 (DetectionTest)

判定者が check の基準に従って期待する判定を出せるか確かめた結果である。対象の範囲は[検出試験](guarantees.md#検出試験)に従う。

- `[checks.<観点>]` の定義、試験仕様、担当の定義、判定規則を含む判定依頼テンプレート、実際に渡した基準の文書の集合と内容ハッシュ、例の文書の内容ハッシュ、実際の判定と根拠を持つ。
- 合格の同一性には担当の定義、判定依頼テンプレート、基準と例の文書の内容ハッシュを含める。agent の定義に書かれたモデルと推論量の指定も同一性に含める。親から引き継ぐ指定では、実行時に観測できたモデル・推論量だけを来歴に残し、観測値を同一性に含めない。合格はその agent の定義での合格として扱い、観測できない値は推測しない。別の文書が必要なら `criteria` へ明示し、文中の参照は解析しない。
- 試験仕様は例のソース内の `spec.json` の文書であり、例の参照と devkit だけが読む期待判定の対応を持つ。判定者には基準の文書、匿名の例の本文、選択した入力契約のスキーマ、出力の約束を渡す。仕様・期待判定・対応表と、それらを含む作業履歴や参照先を渡さない。
- 結果は例の ID ごとの判定値、blocking の指摘、根拠だけの専用の小さい形式とし、通常の判定結果の全項目を繰り返さない。指示 ID などの共通の識別は結果全体で1回だけ扱う。
- 合格の索引はソースではなく、`[state] detect`(既定 `.devkit/detect.json`)に保存する。読み出し・書き込み・復元は試験の指示に固定した同じ参照元の設定を使う。ledger には合格・不合格の両方の実行の事実を置き、通常の作業履歴には例ごとの判定・指摘・期待判定との照合結果を残す。基準を更新した check は、既定では次に必須として使うラウンドの前に試験する。

### 要件 (Requirements)

リポジトリが満たすべき要件の正本である。

- 既定では `.devkit/requirements.md` に置き、`[sources.requirements]` で置き場所を変更できる。
- 目的のステージが、承認された完了条件と既存の要件を照らして更新する。目的のステージがないパターンや、目的のステージを外した計画では、振り返りのステージが承認された完了条件のうち要件に当たるものを反映する。目的のステージで反映済みなら重ねて更新しない。
- 後の作業の計画者・作業者・判定者の brief では、パターンの入力の選び方の既定値で本文とソース名・ID・存在の有無を渡す。未作成なら作成先を案内する。要件の更新は作業の成果としてステージの判定で確認する。

### 構造の記録 (Structure)

[構造ステージ](../stages.md#2-構造)を使うリポジトリが育てる、モジュール・責務・配置・依存の向きを表す資産である。

- 構造のステージが更新する。既定では `.devkit/structure.json` の1ファイルとし、置き場所は `[sources.structure]` で変更できる。バージョンは内容ハッシュとし、元のバージョンの識別子を取得できれば来歴に添える。リポジトリ内のファイルは git で履歴を管理し、PR のレビューで承認する。

- 知識としての本文の形式は自由である。view は `schemas/structure.json` に従う JSON の場合だけ構造図を描き、それ以外は本文を表示する。この JSON では `modules` の各項目は `id`・`name`・`responsibility`・`path`、`dependencies` の各項目は `from`・`to` を持つ。brief は固定した本文とソース名・ID・存在の有無を示す。

### 規則と強制手段 (Rules)

複数の作業で守る、設計上の変更困難な決定と、それを守る手段の資産である。

- 既定では `.devkit/rules.md` を正本とし、置き場所は `[sources.rules]` で変更できる。現在の決定・強制手段・根拠を保持し、共有に必要な根拠は資産側に記載する。ローカルの作業記録だけに依存させず、作業 ID・決定 ID・課題や PR の URL は補助参照として添えてよい。更新はループ自身の変更として、既定では人が確認する。
- brief の「元に戻せないもの」には、規則の共有する変更困難な決定の節への参照と[計画](#計画-plan)にある項目を渡す。規則の本文は一度だけ載せる。`[deny]` はコマンドの規則であり、この決定の一覧ではない。
- 強制手段が未実装の項目と、振り返りで繰り返し見つかった違反は、テスト・lint・型・pre-commit・検証コマンドによる機械の検査に移す候補とする。

## 整合性の境界

### 記録の範囲

記録の範囲は作業だけとする。共通項目は記録 ID とし、所属する作業は記録ルートから導く。外部入力に作業 ID がある場合は束縛先と照合する。記録形式は[作業に記録した `kit_version`](#作業-work)から識別し、参照は[エンティティ](#エンティティ)の種別ごとの定義に従う。記録 ID は [ULID](#作業-work) で一意にし、参照先は存在する記録 ID に限るか、外部参照であることを明示する。checkpoint・指示の本文・観測は記録に含めない。書き手と公開方法は[記録の書き込みと排他](#記録の書き込みと排他)で定める。

### セッションとブランチ

同じリポジトリでも、別の worktree で新しいセッションを開けば、それぞれのチェックアウトでループを並行して回せる。作業中のチェックアウトでの2つ目の `start` は拒否する。各チェックアウトは自分の `.devkit/run/` を持つ。devkit が作る `.devkit/worktrees/...` 内から呼ぶ CLI は hook と同じく親のチェックアウトとその未完了の作業を解決し、note と適用可能な読み取り・記録コマンドを親の作業に結び付ける。入力ファイルの相対パスは呼び出した cwd を基準にする。1ステージ内の単位用の worktree は、[分割した作業と合流](flow.md#分割した作業と合流)の作業場所である。

`start` は[開始の条件](guarantees.md#再開と-hook-の稼働確認)を満たしたセッションの観測に作業 ID を書いて束縛する。HEAD がない場合、または作業ツリーに存在する設定済みの規範・`devkit.toml`・サブエージェント定義が未コミットまたは変更されている場合は、理由と直し方を返して拒否する。以後のコマンド(`next`・`submit`・`answer`・`external`・`resume` を含む)と hook はこの束縛から作業を特定し、`next` は識別したセッション ID をラウンドに結び付ける。束縛のないセッションで `next` または `resume` が呼ばれたら、cwd のチェックアウトの記録から終わっていない1つの作業を特定し、そのセッションを束縛する。作業の特定にブランチ名は使わない。中断からの再開条件は[中断](guarantees.md#中断)に従う。

CLI は Bash の環境変数 `CLAUDE_CODE_SESSION_ID`(Claude Code)と `CODEX_THREAD_ID`(Codex)からセッションを直接識別する。前者は hook の `session_id`、後者は rollout のファイル名の ID と一致する。hook は入力のセッション ID を使う。

cwd のブランチが作業の開始時に記録したブランチと違っても束縛は無効にしない。読む操作(`next`・`status`・`view`)は警告だけで続けるが、`submit`・`answer`・`external`・`plan`・`resume`・完了の確定は拒否する。`note` の受理は[決定と証拠](#決定と証拠-decision--evidence)に従う。不一致時の `next` は記録を行わず、結果を受理せず照会だけで警告付きの指示を返す。中断中の応答は[中断](guarantees.md#中断)に従う。

`pause` の作業の特定と、中断の記録に対するブランチ不一致時の扱いは[中断](guarantees.md#中断)に従う。

### 状態遷移と受理条件

作業の状態は、計画・StageRun・ラウンド・問い・外部操作から導く現在地に、中断の有無を重ねて表す。

- 終了前の任意の状態から中断に入り、中断前の現在地への参照を保持する。StageRun やラウンド、未受理の指示を中断だけで失効させない。
- 中断からの再開では中断前の状態に戻り、ledger に残った結果を照合して続ける。中断中に届いた結果も復元に含める。完了・中止後の `pause` は[中断](guarantees.md#中断)に従う。
- `pause`・`resume` による中断・再開の条件、新しい指示と処理の抑止は[中断](guarantees.md#中断)に従う。中断中の `next` は、中断中であることと `devkit resume` で再開できることだけを返し、作業を進めない。

中断中でなく、[セッションとブランチ](#セッションとブランチ)が一致する場合、`next` は未受理の結果(作業者・判定者・計画者サブエージェントの結果ファイル、判定コマンドの結果、`command:` の check の実行結果)を冪等に受理して状態を進め、ledger と計画から次の指示を計算する。同じ結果を二度受理せず、同じセッションで受理後の状態が同じなら同じ指示 ID と指示を返す。単位の結果がそろった後の合流と再開時の照合は[分割した作業と合流](flow.md#分割した作業と合流)に従う。

`submit`・`answer`・`external`・`plan` も状態を進める。遷移表にない遷移は行わない。`note` の受理は[決定と証拠](#決定と証拠-decision--evidence)に従う。`submit` は終了ブロックの「完了を主張」もそのまま受理し、完了の確定は `devkit` が[完了条件](guarantees.md#完了条件)に従って行う。`submit` には[セッションとブランチ](#セッションとブランチ)および [受理時の照合](guarantees.md#再開と-hook-の稼働確認)の共通条件を適用する。これらを満たした後、終了ブロックの受理で拒否するのは、開いているラウンドがない、終了ブロックの作業指示 ID がそのラウンドの現行の作業指示 ID と一致しない、未回答の問いがある、必須項目(作業指示 ID および終了の種別に応じた項目)が欠ける、`report` または `confirmation` が指定された形に合わない場合とし、理由を返す。未回答の間はそのステージの作業を止める。

エージェントが終了ブロック・計画・note の入力 JSON を書く既定の場所は、`.devkit/run/work/<作業 ID>/inbox/` とする。配置では拒否せず、内容・指示 ID・状態の受理条件は各入力の定義に従う。終了ブロックの必須項目はスキーマで検証する。

`devkit external` の入力ファイルは配置を受理条件とせず、`devkit` がその内容を実行の記録にコピーする。

### 作業の排他制御

同じ作業に対するプロセス間の排他制御は `.devkit/run/work/<作業 ID>/run.lock` で行う。`pause` による中断の記録と中断中の状態通知は作業ロックを要求せず、[中断](guarantees.md#中断)に従う。

### 計画のバージョン

バージョンは単調に増加させる。承認状態は承認の記録から、提案中・却下・撤回・実行可能の状態は計画の Judgment、撤回の記録、必要な承認から導く。実行可能なバージョンは、計画の check に合格し、必要なゲートの承認を得た最新のバージョンである。

計画の承認の条件は `[approval] plan = "requirements" | "always" | "deviation"` で定め、既定を `"requirements"` とする。

- `requirements`: 作業の最初の計画、完了条件の ID または文面が直前に人が承認したバージョンから変わった計画、外部操作を宣言した計画で人の承認を必須とする。完了条件が同じで外部操作も未決事項もない作り直しは、承認済みの合意の範囲として再確認しない。
- `always`: すべてのバージョンで人の承認を必須とする。
- `deviation`: 最初の計画、前に承認した計画の残りと構造が違う計画、外部操作を宣言した計画で人の承認を必須とする。

`open_questions` が空でない計画は、いずれの設定でも人の承認を必須とする。

StageRun の開始時に固定した規範で経路の決まりを再検査してバージョンを束縛し、実行中は使い続ける。切り替えはステージの開始時だけとし、提案中のバージョンがある間は古いバージョンを実行しない。`devkit plan <ファイル>` は提案を記録し、check と必要なゲートを `next` の指示で進める。`devkit plan --withdraw` は撤回を追記する。

撤回後も旧バージョンの実行を妨げないのは、人が自発的に起票して撤回した提案だけである。engine が router の「前のステージに戻る」を記録した時点で旧 StageRun を再計画待ちにし、計画者が残りを作り直す。計画の check と、設定に従って必要になる人の承認を経て、遷移表の `back` のステージから新しい StageRun を開き、旧バージョンを再開しない。提案が却下されても旧バージョンには戻らない。

ステージの遷移が `done: "replan"` なら、そのステージの完了後に既存の再計画の経路で計画者が残りを作り直す。作り直した計画の check と、`[approval] plan` に従う承認を経て、残りのステージを開始する。完了条件の ID または文面が変われば、既定では人の承認が必要である。完了済みの実体は採用された経路に保持する。新しい仕事には新しい実体 ID を使う。

再計画の残りのステージは、完了した StageRun に束縛した計画と、そのステージの `done` からの遷移順で求める。最新の提案の配列位置からは求めない。再提案でも、再計画の依頼に結び付けた再計画の種別と残りの作業を保つ。計画の check が `NOT ASSESSED` になり、人が修正を指示した場合も、最初の計画の提案に戻さず、同じ再計画の種別と残りの作業で計画者へ再依頼する。

人が計画を却下した場合は、どう直すかという人の指示を計画者に渡して作り直させる。`open_questions` への人の回答も、計画の却下と作り直しの指示として同じ経路で渡す。この再提案の回数には上限を設けない。

計画の check が `FAIL` の場合は、指摘を計画者に戻して作り直させる。人を挟まずに計画の作成と check を繰り返すラウンド数には、ステージと同じ形で上限を設け、達したら人に確認する。上限は `[planning] max_rounds`(既定3)で設定する。

作業全体のラウンド数は記録から累計する。`[limits] max_total_rounds` の既定値は40であり、累計が上限に達した時点で人に確認する。人が続けると答えたら、次に止める値はその時点の累計に設定値を加えたラウンド数である。戻り・作り直し・担当の変更でも累計は減らさない。

### 資産の更新と共有

リポジトリ内のファイルは通常の変更としてコミット・PR・マージで更新し、機械間の直列化と競合は git と人のレビューで扱う。リポジトリ外のソースは読み取り専用であり、devkit は書き込まない([書き込みの流れ](#書き込みの流れ))。同じリポジトリで複数人が別々の作業を進める使い方も対象に含む。情報は PR 本文の計画の要約と決定、および育てるものを通じて共有する。並行作業の配置は[利用側のリポジトリ](layout.md#利用側のリポジトリ)に従う。

後の作業に効かせたい決定は、requirements・structure・rules のいずれかに残す。各ステージ定義は、この反映先を指定する。作業の記録だけを後の作業への引き継ぎ先にしない。

## 記録の書き込みと排他

ledger の書き手は `devkit` の CLI(engine と cmd)だけである。hook も同じバイナリで動くが、ledger は読むだけで、セッションの観測、人の入力の観測、停止の観測、判定者サブエージェントの結果ファイルなどの生成物だけを書く。セッションの観測は [hook の共通処理](hooks.md#共通処理)の追記型のファイルとし、他の生成物も各定義の識別項目で名前を一意にして、同時に動作する hook が衝突しない。

- **実行の記録と生成物の公開**: 記録は追記のみとし、記録 ID をファイル名とする独立した JSON ファイルに保存する。一時ファイルへ書いて rename で公開し、読み手は一時ファイルを無視する。壊れた記録はその場に残して処理を止め、対象と理由を報告する。生成物も同じ方法で公開するが、再生成できる view の HTML は通常の書き込みで保存する。
- **資産の調停**: [資産の更新と共有](#資産の更新と共有)の更新と競合の解決に従う。
