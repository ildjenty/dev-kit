# データ

作業は1つの課題に対するループを所有し、計画、ステージの実行、ラウンドを通じて進む。対象のバージョンが、作業・検証・判定を結び付ける。固定物と育てるもの、追記する実行の記録、再生成できる生成物を分け、それぞれの所有者と更新の境界を定める。

## 所有と生存期間

データの所有と生存期間、整合性を守る境界は、[principles/data.md](../../principles/data.md) の原則5に従う。

- **固定物**: kit が提供する、バージョンを持つ skill、観点ファイル、テンプレート、hook の登録、サブエージェントの定義など。供給は [kit](modules.md#kit)が担う。
- **育てるもの**: リポジトリが所有して git で管理する資産。`devkit.toml`、ホストの設定とサブエージェントの定義、観点ファイルと違反例・適合例、rules.md、検出試験の合格記録の索引、構造、kit のコピー、skill を含む。作業範囲の記録への参照は作業 ID・課題の URL・PR の URL による外部参照だけとし、共有に必要な決定の根拠は資産側に転記する。
- **実行の記録**: 作業が所有する。完了・中止後も StageRun、Judgment、決定、成果物、外部操作を読み取り専用で残す。閲覧を兼ねる人の判断である回答・承認・状態変更は完了後も追記を許す。
- **生成物**: brief と判定依頼、対象の展開先、結果ファイル、人の入力の観測、view の HTML は作業の下に置き、再生成または削除できる。セッションの観測は作業の外にチェックアウトごとに置く。展開先の削除時期は[性能と出力](guarantees.md#性能と出力の上限)、refs の生存期間は[対象のバージョン](#対象のバージョン-targetversion)に従う。

## エンティティ

### リポジトリ

kit を導入した git リポジトリである。設定ファイルと育てるものを所有する。

### 作業 (Work)

1つの課題に対して実行する1本のループである。

- ULID の作業 ID、課題への参照、ブランチ `devkit/<作業 ID>` を持つ。
- 基点コミットは来歴を示す開始時のコミットである。開始時の kit のバージョンと記録形式のバージョンを持つ。
- 最初の計画のバージョンを作成してから完了または中止するまで存続し、作業範囲の記録を所有する。

### セッションの観測 (SessionObservation)

ホストのセッションと作業の束縛を保持する生成物である。

- ホスト名、セッション ID、観測時刻、PreToolUse と UserPromptSubmit の最終観測時刻、Stop の継続回数、束縛した作業 ID を持つ。
- 保存先と更新は [hook の共通処理](hooks.md#共通処理)、コマンド側の識別は[セッションとブランチ](#セッションとブランチ)に従う。

### 計画 (Plan)

作業に属する、バージョンを持つ状態機械のデータである。

- ID 付きの完了条件の列、ステージの列、必須 check の集合を持つ。
- 各ステージは担当・観点・ゲート・遷移表・計数の上限・戻り先を持つ。遷移表は router の分類をキーとし、条件式は書かせない。作り直しも正式な操作とする。[ループ計画](../loop-plan.md)と[ステージ](../stages.md)の契約に従う。
- 担当はロール(作業者・判定者・計画者)とサブエージェントの名前、または登録コマンドの名前を持つ。作業者はセッション自身であり、名前は持たない。観点は完了条件 ID と実行主体(判定者のサブエージェント、登録コマンド)を持つ。
- 計画の承認で足りる外部操作の宣言として、種別・対象・入力のハッシュ、宣言時の登録定義と実行ファイルの内容ハッシュを持つ。照合は[外部操作の承認](guarantees.md#外部操作の承認)で定める。
- 承認状態と提案の状態は[計画のバージョン](#計画のバージョン)から導く。

### ステージの実行 (StageRun)

作業内で、開始時に束縛した計画のバージョンに従う1回のステージ実行である。

- 実行 ID、ラウンドの列、実行状態、観測時刻、停止理由、次に動く主体を持つ。
- 実行状態は作業中・判定待ち・回答待ち・承認待ち・外部操作の確認待ち・中断・失効・完了。「再計画待ち」は失効の一種である。
- 完了記録は[完了条件](guarantees.md#完了条件)に従い、コミットのハッシュを持つ。
- 「異常終了・不明」という状態は設けず、最後の観測時刻で表す。

### ラウンド (Round)

`next` が brief を渡してから、`submit` の結果に対して router が判断を下すまでの往復である。

- ラウンド ID、結び付けたセッション ID、brief のバージョン(内容ハッシュ)、開始時と返却後の対象のバージョンを持つ。
- 終了ブロック、check の結果の集合、発行した指示の ID の集合と出し直し回数、router の判断を持つ。

### 指示 (Instruction)

`devkit next` が返す、エージェントへの1つの指示である。

- 指示 ID は(作業 ID、種別、対象のキー、出し直し回数)から導く派生値である。
- 対象のキーは、作業ならラウンド ID、判定ならラウンド ID と観点 ID、計画の check なら計画のバージョンと観点 ID、計画なら提案番号、検出試験なら観点・試験仕様・定義ファイルのハッシュとする。ラウンドを開く前の指示も識別する。
- 出し直しは作業の記録に追記する。記録に含めないのは指示の本文である。再開後の出し直しは新しい指示 ID を持ち、古い指示 ID の結果は無視する。
- 種別は、作業(brief)、判定待ち、hook の稼働を確認する、判定、検出試験、計画、問い、外部操作の確認、完了、中止である。判定には brief と対象の展開先のパス、問いには問い ID・文面・選択肢を持たせる。
- 指示の計算と結果の重複の扱いは[状態遷移と受理条件](#状態遷移と受理条件)および[判定結果の受理](guarantees.md#判定結果の受理)に従う。

### 対象のバージョン (TargetVersion)

ツリーのスナップショット、計画のバージョン、構造のバージョンの直和である。

- ツリーのスナップショットは、追跡ファイルと ignore されていない未追跡ファイルから一時インデックスで作る、ブランチには含めないコミットオブジェクトのツリーハッシュである。`.devkit/`、指示ファイル、kit のコピー、サブエージェントの定義も追跡ファイルとして含む。
- ラウンドの開始時と返却後に取得する。開始時のものは[規範の固定](guarantees.md#規範の固定)とラウンドの差分に使い、返却後のものは判定・完了時のコミットに使う。commit 直前の照合と更新は[完了条件](guarantees.md#完了条件)に従う。
- コミットに `refs/devkit/<作業 ID>/<対象のバージョン>` を付け、作業の完了・中止と成果物の永続化がそろうまで保持し、その後削除する。
- 計画のバージョンは作業内で識別する。構造のバージョンは[構造の記録](#構造の記録-structure)に従う。

### check の結果 (Judgment)

ある観点から対象を判定した結果である。

- 観点 ID、対象のバージョン、規範の識別、確認した完了条件 ID の集合、判定、指摘を持つ。判定は `PASS`・`FAIL`・`NOT ASSESSED` である。
- 確認した範囲と未確認の範囲、方法と環境、指示 ID、結果ファイルのパスを持つ。
- 実行主体は、サブエージェントの名前・定義ファイルの内容ハッシュ・観測した effort(Claude Code)または model(Codex)、または登録コマンドの名前で表す。
- 規範の識別は、開始時のスナップショットの `.devkit/`・`devkit.toml`・`.claude/agents/`・`.codex/agents/`・AGENTS.md のツリー ID と blob ID の集合である。
- 対象のバージョンと規範の識別の両方が現在と一致するときだけ有効である。計画や構造の判定も観点や規則が変われば失効するが、評価対象コードだけの変更では規範の識別は変わらず、これらの判定は失効しない。
- 受理と集約は[判定結果の受理](guarantees.md#判定結果の受理)に従う。

### 指摘 (Finding)

check が見つけた失敗や判断を要する点である。

- 指摘 ID、blocking かどうか、`auto-fixable` または `needs-decision`、失敗のシナリオを持つ。
- 適用除外の主張と根拠の有無、解決した指摘への参照を持つ。
- 修正ラウンドの依頼には前回の指摘 ID を渡す。解決した指摘への参照と、確認した完了条件 ID の増加から進展を計算する。

### 決定と証拠 (Decision / Evidence)

作業中に得た判断と、その判断を支える調査結果である。

- 決定は有効性、置換、依存、適用条件、決定者、暫定か確定かを持つ。証拠は出典と確認方法を持つ。
- `devkit note <種別> <ファイル>` で途中でも記録でき、`devkit` がスキーマを検証する。
- 未読・承認・却下・保留は `devkit answer` で追記する状態変更から導く。未読から承認・却下・保留への変更が閲覧の記録を兼ね、確認済みの集合もそこから導く。

### 問い (Question)

form に従う、人への確認事項である。

- 問い ID、承認対象、選択肢、推奨、停止理由の分類、回答後に進むステージ、停止する範囲と進められる範囲、根拠への参照を持つ。
- 承認対象はツリーのスナップショット、計画のバージョン、外部操作の直和である。外部操作の識別項目は[外部操作の承認](guarantees.md#外部操作の承認)に従う。
- `devkit` が記録して `next` の指示として返し、エージェントがチャットで人に見せる。form は文面に「回答は『問い ID 選択肢』だけの1行で書く」と記載する。
- 承認対象が変わったら新しい問い ID で起票し直し、古い問いへの回答は拒否する。

### 人の入力の観測 (PromptObservation)

ホストが受け取った入力の本文を保持する生成物である。

- 本文の採取と保存先は [UserPromptSubmit](hooks.md#userpromptsubmit)に従う。
- UserPromptSubmit はサブエージェントの報告、他のセッションからのメッセージ、定期タスクでも発火し、人が打った入力と区別する項目がない。これは Claude Code では確認済みであり、Codex は[未確認の前提](decisions.md#未確認の前提)に残す。
- 選択肢の回答は[回答の受理](guarantees.md#回答の受理)で区別する。人が別のセッションから定型を送る経路は範囲外とする。

### 回答・承認 (Answer / Approval)

観測した入力をもとに、問いへの人の判断を確定する記録である。

- 同一性は(問い ID、承認対象、承認者)である。承認者は `git config user.name` から得て、空なら `answer` を拒否する。
- 観測した入力の本文と出所(セッション ID と時刻)を保存し、観測ファイルを削除した後も記録だけで根拠を確かめられるようにする。
- 前の回答と内容が異なる再回答は、置換元への参照を持つ新しい記録として追記する。同じ置換元を複数の訂正が置換した場合は未解決とし、問いを再起票する。
- 受理と訂正の期限は[回答の受理](guarantees.md#回答の受理)に従う。問いと承認を機械間で共有する経路は対象範囲に含めない。

### 外部への書き込み (ExternalOp)

kit が管理する、リポジトリ外への書き込み操作である。

- 種別、対象、入力のハッシュ、登録定義の内容ハッシュ、リポジトリ内の実行ファイルの内容ハッシュを持つ。
- 操作 ID、要求 ID、承認への参照、冪等キー、実行前の記録、実行結果、外部側の識別子を持つ。実行結果は成功・失敗・結果不明である。
- 操作 ID と要求 ID の扱いは[外部操作の二重適用](guarantees.md#外部操作の二重適用)、実行の条件は[外部操作の承認](guarantees.md#外部操作の承認)に従う。

### 進捗 (Progress)

ラウンドの終了ブロックである。

- `devkit submit` の入力として受け取り、`devkit` が記録する。
- 判定、終了の種別、次のアクション、変更したファイル、確認済み事項、未確認事項、変更禁止事項、一時状態(確認方法・出典・無効になる条件)、再開条件を持つ。
- 終了の種別は完了を主張・停止して確認・中断とする。外部書き込みの要求は終了ブロックに含めず、[外部操作](flow.md#外部操作)で行う。

### checkpoint

再開のために記録から組み立てる現在地の派生値である。

- 実行状態を持つ最新の StageRun、最新の進捗、未回答の問い、未受理の指示から組み立てる。上書きする記録は持たない。
- SessionStart の注入ごとに ledger から組み立て、一時状態の無効条件を照合して無効なものを除く。出力上限への対応は[性能と出力](guarantees.md#性能と出力の上限)に従う。

### 成果物 (Artifact record)

作業が生んだ変更と、その永続化先を結び付ける記録である。

- 成果物 ID とバージョン、変更前後、完了条件 ID、変更の種類、決定への参照、永続化先であるコミットへの参照を持つ。
- 開始時と返却後のスナップショットの差分から `devkit` が作成する。

### 検出試験の記録 (DetectionTest)

観点ファイルが期待する判定を出せるか確かめた結果である。

- 観点ファイル、試験仕様(違反例・適合例・許容例と期待判定)、担当(サブエージェントの定義ファイル、または登録コマンドの定義)の内容ハッシュ、実際の判定、根拠を持つ。
- 観測した effort(Claude Code)または model(Codex)は来歴とし、合格記録の同一性には含めない。同一性は観点・試験仕様・担当の定義の内容ハッシュで決まる。
- 合格記録の正本は git 管理の資産 `.devkit/detect.json` の索引とし、ledger には実行の事実だけを置く。対象と実行時期は[検出試験](guarantees.md#検出試験)に従う。

### 構造の記録 (Structure)

構造ステージを使うリポジトリが育てる、構造の資産である。

- `.devkit/structure.json` の1ファイルとし、バージョンは内容ハッシュ、履歴は git、承認は PR のレビューとする。

### 規則と強制手段 (Rules)

設計上の変更困難な決定と、それを守る手段の資産である。

- `.devkit/rules.md` を正本とし、移行記録もその項目として残す。
- brief の「元に戻せないもの」には、ここと計画にある項目を渡す。`[deny]` はコマンドの規則であり、この決定の一覧ではない。

### 記録形式のバージョン

各記録の読み書きの互換性を示す値である。

- 各記録が持ち、バイナリは読めるバージョンの範囲と書くバージョンを宣言する。互換性の扱いは[ロールアウト](guarantees.md#ロールアウト)に従う。

## 整合性の境界

### 記録の範囲

記録の範囲は作業だけとする。記録 ID は ULID で一意にし、参照先は存在する記録 ID に限るか、外部参照であることを明示する。checkpoint・指示の本文・観測は記録に含めない。書き手と公開方法は[記録の書き込みと排他](#記録の書き込みと排他)で定める。

### セッションとブランチ

`start` はセッションの観測に作業 ID を書いて束縛する。以後のコマンド(`next`・`submit`・`answer`・`external` を含む)と hook はこの束縛から作業を特定し、`next` は識別したセッション ID をラウンドに結び付ける。ブランチ名だけでは束縛しない。

Claude Code の環境変数の設定は [SessionStart](hooks.md#sessionstart)に従い、CLI は `DEVKIT_SESSION_ID` でセッションを識別する。環境変数がなければ最新の観測を使い、指示に警告を含める。cwd のブランチが作業のブランチと違っても束縛は無効にしない。読む操作(`next`・`status`・`view`)は警告だけで続けるが、書く操作(`submit`・`external`・`plan`・`note`・完了の確定)は拒否する。

### 状態遷移と受理条件

`next` は未受理の結果(判定者の結果ファイル、登録コマンドの判定結果)を冪等に受理して状態を進め、ledger と計画から次の指示を計算する。同じ結果を二度受理せず、受理後の状態が同じなら同じ指示 ID と指示を返す。

`submit`・`answer`・`external`・`plan`・`note` も状態を進めるが、遷移表にない遷移、[完了条件](guarantees.md#完了条件)を満たさない完了の主張、未回答の問いがあるときの作業の結果、開いているラウンドのない `submit` は受け付けず、理由を返す。問いの「進められる範囲」は表示の情報にとどめ、当面は未回答の間、そのステージの作業を止める。

エージェントが終了ブロック・計画・note の入力 JSON を書く場所は、`.devkit/run/work/<作業 ID>/inbox/` だけとする。`submit`・`plan`・`note` はその下のファイルだけを受け取る。終了ブロックは終了の種別に応じた必須項目をスキーマで検証し、欠けていれば理由を返して拒否する。

### 作業の排他制御

同じ作業に対するプロセス間の排他制御は `.devkit/run/work/<作業 ID>/run.lock` で行う。

### 計画のバージョン

バージョンは単調に増加させる。承認状態は承認の記録から、提案中・却下・撤回・実行可能の状態は計画の Judgment、撤回の記録、必要な承認から導く。実行可能なバージョンは、計画の check に合格し、必要なゲートの承認を得た最新のバージョンである。

StageRun の開始時にバージョンを束縛し、実行中は使い続ける。切り替えはステージの開始時だけとし、提案中のバージョンがある間は古いバージョンを実行しない。`devkit plan <ファイル>` は提案を記録し、check と必要なゲートを `next` の指示で進める。`devkit plan --withdraw` は撤回を追記する。

撤回後も旧バージョンの実行を妨げないのは、人が自発的に起票して撤回した提案だけである。router が「前のステージに戻る」を記録した時点で旧 StageRun を再計画待ちにし、旧バージョンを再開しない。提案が却下されても旧バージョンには戻らず、指摘を渡して計画の上限内で再提案するか人に確認する。

### 資産の更新と共有

育てるものは通常の変更としてコミット・PR・マージで更新し、機械間の直列化は git に任せる。同じリポジトリで複数人が別々の作業を進める使い方も対象に含む。情報は PR 本文の計画の要約と決定、および育てるものを通じて共有する。並行作業の配置は[利用側のリポジトリ](layout.md#利用側のリポジトリ)に従う。

## 記録の書き込みと排他

ledger の書き手は `devkit` の CLI(engine と cmd)だけである。hook も同じバイナリで動くが、ledger は読むだけで、セッションの観測、人の入力の観測、判定者の結果ファイルなどの生成物だけを書く。生成物の名前はセッション ID・agent ID・時刻で一意になり、同時に動作する hook が衝突しない。

- **実行の記録と生成物の公開**: 記録は追記のみとし、記録 ID をファイル名とする独立した JSON ファイルに保存する。一時ファイルへ書いて rename で公開し、読み手は一時ファイルを無視する。壊れた記録は隔離ディレクトリへ移して報告する。生成物も同じ方法で公開する。
- **資産の調停**: 通常の git の変更として更新し、競合は git のマージと人のレビューで解決する。
