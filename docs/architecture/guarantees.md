# 保証と対策

kit は事故、自己評価の偏り、再開時の食い違い、バージョンの不一致を防ぐ。保証の対象は、記録上、正しくない完了・承認・外部操作が成立しないことと、人による中断と再開である。作業者と評価対象のコードに悪意がないことを前提に、ホストの権限管理と `devkit` の受理境界を組み合わせる。

## 信頼の前提

作業者(セッションのエージェントと、`work` の種類の[役割](data.md#役割-role)の agent)と評価対象のコードに悪意はないものとする。記録や承認の偽造、規範を書き換えて check を通す細工、資格情報の窃取は、同じ OS 利用者の権限で動く kit では防げないため範囲外とする。チームでは育てるものを git 管理し、PR レビューで確認できるようにする。[assets/principles/harness.md](../../assets/principles/harness.md) の原則5に従い、この前提を超える保証の仕組みは設けない。記録には秘密情報を書かない。

pre-commit hook・判定コマンド・検証コマンドの権限および人のレビューは[権限の境界](#権限の境界)に従う。エージェントが書いたテストコードも同じ権限で動くことを信頼の前提に含める。

決定の有効条件・適用条件と一時状態が有効かどうかを判断する条件は自然文であり、エージェントと人が読む。`devkit` は条件や外部依存の充足を判定せず、checkpoint の注入、brief、view では条件と出典・参照を項目に添えて渡す。観測できない入力を前提とする評価関数は設けない。記録上の承認状態や置換・依存の解決と、[Judgment の対象と規範の照合](data.md#check-の結果-judgment)は `devkit` が行う。

## ホスト・git と kit の責務分担

git と、Claude Code・Codex CLI の両方にある機能で賄えるものは kit で実装しない。[assets/principles/designing.md](../../assets/principles/designing.md) の原則5に従う。

- ブランチ、worktree、ignore、履歴、アーカイブ、利用者の名前の仕組みは git に任せる。単位の作業用 worktree の作成、ツリーの SHA の固定、合流と再開時の照合、終了時の worktree の扱いは、engine が workspace の git 操作を使って進める。ループを並行して回すための別の worktree とセッションは利用者が開く。
- sandbox、hook の登録と実行の仕組み、permissions、skill、指示ファイル、サブエージェントの起動と隔離、セッション再開と compaction、人とのやり取りはホストに任せる。
- kit が持つのは、計画・依頼・判定・分類・形式(plan・brief・check・router・form)、記録と保存(ledger・ledger/fsstore)、進行と外部操作(engine・external)、ホストとの接続(hook・host/event)、git 操作(workspace)、設定・導入・固定物(config・install・kit)、表示(view)、組み立て(cmd/devkit)である。契約は[モジュール](modules.md#モジュールごとの契約)に従う。
- `[deny]` は束縛のあるセッションに限って効かせるため kit が照合する。`permissions.deny` では範囲が広すぎる。

## 防ぐ失敗と対策

### 手順の省略と完了の過大申告

- **失敗**: エージェントが進行を決め、手順を飛ばしたり、完了条件を満たさず完了を主張したりする。
- **仕組み**: ステージ・ラウンド、次の指示、完了条件、記録、結果と答えの受理は `devkit` が計算する。エージェントは実行と返却を担う。手順を飛ばしても記録上の状態は進まない。[状態遷移と受理条件](data.md#状態遷移と受理条件)に従って同じ指示を返す。
- **置き場所**: `internal/engine/` の `next`・`submit` と `internal/plan/`・`internal/router/` の遷移、[完了条件](#完了条件)。

### 完了条件

- **失敗**: 未検証の変更や未判定の要求を完了に含める。
- **仕組み**: ステージの完了には、返却後の対象のバージョンに対するすべての必須 check(`command:` の check を含む)の `PASS`、[検出試験の設定](#検出試験)に従う合格記録、そして `devkit` が行う完了時の永続化と[対象の照合](#commit-直前の対象の照合)が必要である。人が承認した完了条件を作業の完了の基準とする。完了条件ごとの確認手段と、その妥当性・網羅性の判断は[計画](data.md#計画-plan)に従う。検出試験の対象は[検出試験](#検出試験)に従う。Judgment の有効性は [check の結果](data.md#check-の結果-judgment)に従う。Stop hook はこの条件を照合しない。
- **置き場所**: `internal/plan/` の完了条件の規則を `internal/router/` が照合し、`internal/engine/` が `internal/workspace/` にコミットを依頼してステージ完了を記録する。

完了の確定では、条件を満たさない完了の主張を完了として扱わない。ステージごとに選ぶ検証は雛形の check として置き、判定前に早く結果を知りたい検証は `command:` の check に置く。pre-commit は完了時のコミットで通る検証である。devkit は検証の集合を自分で決めず、省略も監視しない。何を置くかは雛形を組む人が決め、[雛形からの逸脱](data.md#計画-plan)は計画の check と人のゲートで見る。

`default` と `fix` の implement には必須の `command:test` と観点 `test`・`diff` を置く。観点 `test` は、原則 `principles/testing.md` に照らし、完了条件ごとの具体的なテスト、登録済みコマンドからの実行、利用者から見える入口での契約の検証、実装をなぞらないテストを判定する。最後の retrospective には、`default` と `fix` は必須の `command:test`・`test`・`harness`、`docs` は必須の `harness` だけを置く。`default` と `fix` は、振り返りで検証の手段や対象を変えた場合も最終のツリーで検査を通す。未登録の `command:<name>` はエラーで停止せず、その check を `FAIL` とする。登録の指摘と次のラウンドでの適用は[作業結果の判定](flow.md#作業結果の判定)に従う。

ステージの遷移 `done` が `"replan"` なら、ステージの完了後に既存の再計画の経路で計画者が残りを作り直す。作り直した計画にも[計画の承認の条件](data.md#計画のバージョン)を適用する。完了条件の ID または文面が変われば、既定では人の承認を必須とする。要件定義を先に行って再計画するかは雛形が決め、kit は特別扱いしない。

`devkit` は完了時に、返却後のスナップショットと同じ内容の index で本物の `git commit` を実行する。`--no-verify` は使わず、pre-commit hook がリポジトリで定義した検証を走らせる。commit の失敗は router に渡さず engine が「修正する」として記録し、hook の出力を次の brief に含める。[対象の照合](#commit-直前の対象の照合)を満たした commit の成功を、その対象のバージョンに対する pre-commit の検証の記録とし、保存項目は [StageRun の完了記録](data.md#ステージの実行-stagerun)に従う。pre-commit の別の検証結果の記録は持たない。

commit 時には環境変数 `DEVKIT_STAGE=<ステージ名>` と `DEVKIT_WORK=<作業 ID>` を渡す。

`[git] allow_empty_commit` は既定 `true` である。`true` では成果のないステージも空のコミットを作る。`false` で変更のないステージはコミットせず、判定済みのツリーとその時点の `HEAD` の一致を確かめ、完了をその `HEAD` で記録する。ステージの完了時には、判定した対象を現在のブランチに devkit がコミットする。メッセージは作業者が終了ブロックの `commit_message` に git の規則に沿って書いた値を使う。省略時は `[git] commit_message`(既定 `"devkit: {stage} ({work_id})"`)のテンプレートで補い、`{stage}`・`{work_id}`・`{task}` を使える。

devkit は `core.hooksPath` を設定せず、git hook のファイルも用意しない。リポジトリが使っている `.git/hooks`、husky、pre-commit フレームワークなどの仕組みをそのまま使い、完了時の `git commit` がそれを実行する。husky は自分のディレクトリを `core.hooksPath` に設定し、pre-commit フレームワークは `core.hooksPath` が設定されているとインストールを拒否するため、kit がこの設定を持つと衝突する。

フォーマッタが pre-commit でファイルを書き換え、hook が非0で終了した場合は commit が失敗し、作業ツリーに差分が残る。commit の失敗は前述の扱いで次のラウンドに渡す。[Git の pre-commit の仕様](https://git-scm.com/docs/githooks#_pre_commit)では、ファイルの書き換えだけで commit の失敗は保証されない。

### 規範の固定

- **失敗**: ラウンド中に規範を書き換え、そのラウンドの判定を有利にする。
- **仕組み**: `norm = true` のソースは空の選び方で全体を列挙し、全文書の集合と本文をラウンド開始時に固定する。ソースの外の `devkit.toml`・サブエージェント定義・AGENTS.md・CLAUDE.md も固定する。リポジトリ内の `files` は固定した git のツリーから読み、リポジトリ外のソースはその時点の本文を実行の記録の下へ写す。検証コマンド・判定コマンド・分類表・`[deny]`・`[roles]` は設定の一部として固定し、各役割の agent の定義ファイルも同じ参照で解決する。編集中の値は次のラウンドから適用する。変更の確認は[人への確認対象](#人への確認対象)に従う。
- **置き場所**: engine のラウンド開始と[ソースの固定](data.md#固定と変化の検出)、workspace の git の読み出し・展開である。hook の deny も同じ境界で読む。

既定の規範のソースは principles・stages・plans・rules・git・examples・templates、成果のソースは requirements・structure である。配置は[所有と生存期間](data.md#所有と生存期間)に従い、`[sources.<名前>]` で変更できる。検出試験の索引はソースではなく `[state] detect`(既定 `.devkit/detect.json`)で設定する。成果・索引・実行の記録は規範の識別に含めない。成果の変更は規範の変更による失効を起こさないが、判定対象の識別には含める。

規範の変化は選んだ入力だけでなくソース全体で検出する。リポジトリ内はそのパスの git の差分、外部は文書の集合と本文の内容ハッシュで比較する。成果は同じ選び方の結果を比較する。ラウンド外の判定では指示を出す時点に固定し、リポジトリ内は作業ブランチの `HEAD` にあるコミット済みの内容を読む。ソースの外の設定も、ラウンド外では今の `HEAD` から読む。

brief の本文に入れる知識は、雛形の計画者・作業者・判定者それぞれの `inputs` と check の `criteria` で選ぶ。ステージ定義は `stages` ソースから選ぶ。要件と規則を渡す既定値を用意する。その他の規範は固定した写しの一覧で渡し、作業ツリーの編集中の本文や、固定した後に変わったリポジトリ外の原本を読ませない。文中の参照を解析して入力を補わず、必要な文書は選び方に明示する。必須の基準の選び方が0件なら判定を始めず止め、成果が未作成の場合とは区別する。

`schemas/…` はバイナリが出力スキーマの本文として渡す。参照先をすべて同梱し、check の `schemas` に指定した入力契約も含め、それ以外の補助のスキーマは渡さない。知識の本文の構造は自由であり、計画・雛形・結果・テンプレート・スキーマの機械で扱う形式とは分ける。実行の記録と生成物は固定の `.devkit/run/` に置く。

### 判定結果の受理

- **失敗**: 作成者自身が `PASS` を付けたり、自己評価を依頼文に混ぜたり、別の条件で得た判定を流用したりする。
- **仕組み**: [役割](data.md#役割-role)の agent であるサブエージェントの起動時の prompt は、実行しない固定文字列 `devkit-instruction <指示 ID>` だけの1行とする。これはサブコマンドではない。起動の制限は [PreToolUse](hooks.md#pretooluse)、最終メッセージと来歴の採取は [SubagentStop](hooks.md#subagentstop)に従う。
- **置き場所**: `.claude/agents/<agent>.md`・`.codex/agents/<agent>.toml` の定義、`internal/check/` の受理、`internal/engine/` の `next`。

サブエージェントの定義には、指示 ID に含まれる作業 ID から `.devkit/run/work/<作業 ID>/brief/<指示 ID>.md` を解決し、依頼の本文を読む手順と、最終メッセージの結果に指示 ID (`instruction_id`)を含める手順を記載する。両ホストとも、結果側の指示 ID と SubagentStop の `agent_type` の照合を受理の根拠とし、起動時の本文や transcript の照合を根拠にしない。

`next` はサブエージェントの結果を受け取る際、SubagentStop hook が書いた結果ファイルだけを読み、スキーマ、採取時に検証済みの指示 ID・担当、対象のバージョン、規範の識別を照合する。起動条件は [PreToolUse](hooks.md#pretooluse)で担当定義と照合し、実測値の扱いは [Judgment](data.md#check-の結果-judgment)に従う。不一致は受理せず、エージェントが書いたファイルや標準出力も受理しない。

同じ指示 ID の結果は最初のものだけを受理し、後着の結果は進行に使わず、食い違いによるエスカレーションもしない。判定コマンドの判定と `command:` の check は `devkit` が実行し、同じ受理境界で Judgment に変換する。`command:` の結果の変換と実行順は[作業結果の判定](flow.md#作業結果の判定)に従う。

指示に対するサブエージェントの結果がスキーマまたは内容の検証に失敗した場合は、失敗を記録し、その結果を拒否済みとして再読しない。対象と依頼内容を保ち、出し直し回数を増やした新しい指示 ID で再指示する。同じ対象に対して2回出し直しても結果が検証に失敗する場合は、人への問いを起票して止める。最終メッセージを JSON として解析できない場合も、SubagentStop が失敗の観測を公開し、`next` が同じ規則を適用する。

同じ runner の未受理の指示が複数あり、指示 ID のない不正な最終メッセージをどの指示にも結び付けられなければ、その観測を残して人に問う。`work` の役割の agent の終了ブロックも SubagentStop の採取からだけ受理する。単位ごとの判定は行わず、合流後の作業者の終了ブロックとツリーをステージのラウンドとして判定する。

適用除外の主張と根拠がある場合は、それによって対象から外れる要求に限って違反としない。判定は、`FAIL`、`NOT ASSESSED`、`PASS` の優先順で集約する。

ラウンドの判定依頼には、そのラウンドの[終了ブロック](data.md#進捗-progress)(作業者の報告)を含める。作成者の説明は [Judgment](data.md#check-の結果-judgment)(判定者の結果)の代わりにならず、その扱いは [`assets/principles/harness.md` の原則1](../../assets/principles/harness.md#1-compare-the-target-against-agreed-conditions-independently-of-its-authors-explanation)に従う。

判定依頼には、そのステージ実行の最初のラウンド開始時の比較元の展開先、変更ファイル一覧、その比較元から返却後への累積差分ファイルのパス、指示発行時点の作業履歴ファイルを渡す。修正ラウンドでも比較元を変えず、不合格のラウンドで行った変更を含める。規範は各ラウンドの開始時に固定する。パッチは devkit が git で生成し、`brief/` 内に保存する。短い場合だけ本文にも載せる。

計画の判定依頼には、作業に記録した要求の原文と `start` の課題を固定入力として渡す。完了条件と `open_questions` が原文の要求を漏らさず扱い、要求を追加していないかを観点 `plan` で確かめる。

観点「差分」の判定依頼には、有効な[承認](data.md#回答承認-answer--approval)と、雛形の `delegations` で選んだ委任文書の原文と出所を含め、判定者が対象と範囲を照合できるようにする。委任の判断基準は [`assets/principles/working.md` の原則6](../../assets/principles/working.md#6-proceed-with-execution-decisions-within-agreement-and-delegation-and-seek-necessary-approval)・[原則7](../../assets/principles/working.md#7-do-not-make-unrequested-changes)に従う。

委任文書は人の答えから得た承認と区別して示し、機械で一覧に変換しない。計画・完了条件の変更、外部操作、ループ自身の変更、上限、中断は任せる対象にしない。

判定者には採用された前のステージの成果と直前のラウンドの報告への固定した参照を渡す。対象に対応する検証コマンドの実行結果、有効な承認、引用された証拠と参照先は `history` によらず必ず渡す。単位の報告は単位 ID ごとに欠けなく保持し、ステージの報告へまとめ直さない。`report` と `unit_report` の形への適合は、証拠や完了の根拠にはしない。判定直前の計画者指示は補助の情報であり、固定した基準や確認範囲を狭めない。

### 検出試験

- **失敗**: 違反を検出できるか確かめていない基準と担当を、必須 check に使う。
- **仕組み**: 判定者サブエージェントと判定コマンドの check を対象とし、`command:` の check は検出試験を要しない。`[detection] required = true`(既定)では、例を持たない判定者の check は必須にできない。必要な合格記録がなければ `next` がラウンドを開く前に試験を指示する。不合格なら基準や例を修正するか、必須から外すかを人に問い、停止する。
- **置き場所**: check の試験仕様と結果の照合、engine の指示、`[state] detect` の合格の索引である。索引の既定は `.devkit/detect.json` であり、設定で変更できる。

基準は check の `criteria`、例と試験仕様は `examples` の選び方で指定する。試験仕様は `examples` ソース内の `spec.json` の文書とし、例の文書への参照と devkit だけが読む期待判定の対応を持つ。違反例は `FAIL`、適合例・許容例は `PASS` を期待する。

検出試験の判定者には、基準の文書、匿名の例の本文、出力の約束だけを渡す。試験仕様・種別・期待判定・対応表と、それらを含む作業履歴や参照先は資料から除く。通常の作業履歴には例ごとの判定・指摘・期待判定との照合結果を残し、振り返りで使う。期待との照合は devkit が行う。

合格の識別には、担当の定義、判定規則を含む判定依頼テンプレート、実際に基準として渡した文書の集合と内容ハッシュ、例の文書の内容ハッシュを含める。別の文書を読む必要がある場合は選び方に明示し、文中の参照は解析しない。agent の定義に書かれたモデル・推論量の指定は同一性に含める。指定がなく親から引き継ぐ場合は、観測できたモデル・推論量を来歴にだけ残し、合格はその定義での合格とする。観測値を同一性に含めず、観測できない値は推測しない。識別に含める内容が変われば、次にその check を必須として使うラウンドの前に試験する。基準を変えたら例も更新し、既存の違反例・適合例・許容例の期待判定が保たれることを確かめる。

`criteria` と `examples` の選び方は check の約束の一部であり、雛形と異なる選び方は逸脱として承認の問いに差分を載せる。基準は規範のソースに限り、必須の基準の選び方が0件なら判定を始めず止める。

`[detection] required = false` なら検出試験を指示せず、合格記録なしで判定を受理する。索引の読み出し・書き込み・復元には、試験の指示に固定した同じ参照元の `[state] detect` を使う。未コミットの設定で保存先を変えない。

作業ラウンドを一度も開いていない時点で不合格なら、リポジトリ内の基準や例は人が修正してコミットしてから続行することを問いに示す。雛形で check を必須から外す方法と、`[detection] required = false` も選択肢に載せる。

検出試験が証明するのは、例に対する判定値と期待判定の一致までである。意図した理由で違反を検出したことまでは証明しない。

検出試験の結果は、例 ID ごとの判定値、blocking の指摘、根拠だけの専用の小さい形式とし、共通の識別は1回だけ扱う。合格の保証の範囲には、識別した agent の定義での試験であることを記録する。

### 回答の受理

- **失敗**: 人の曖昧な答え、引用、説明、別の主体の報告を、都合よく承認と解釈する。
- **仕組み**: 人は自由な言葉で答え、選択肢にない答え、条件付きの答え、質問返しもできる。エージェントが意味を読み、`devkit answer <問い ID>` で[回答・承認](data.md#回答承認-answer--approval)を記録する。
- **置き場所**: [UserPromptSubmit](hooks.md#userpromptsubmit)が書く観測、`internal/engine/` の `answer`、[回答・承認](data.md#回答承認-answer--approval)の記録。

人が後から言い直したら、エージェントが新しい回答として記録し、置換元を参照する。

ステージの問いに前のステージへの戻りを求める回答があれば、`--interpretation back` で記録し、router の `back` と既存の戻り・再計画の経路へ進む。

承認対象が決定 ID の[問い](data.md#問い-question)では、エージェントの解釈が承認・却下・保留なら、engine がその決定 ID と回答への参照を持つ状態変更を追記し、解釈に対応する状態にする。文章の回答だけでは決定の状態を変えない。

### commit 直前の対象の照合

- **失敗**: 判定後にファイルが変更され、判定・完了・コミットの対象が食い違う。
- **仕組み**: commit の直前に、作業ツリーの `write-tree` と、リポジトリ外の成果の文書の固定した本文のソース名・ID・内容ハッシュの集合を取り、返却後の判定済みの対象の識別と一致することを確かめる。一致しなければ commit せず、変更後のツリーで返却後の対象と成果物を更新し、すべての必須 check をやり直す。
- **置き場所**: `internal/engine/` の完了の確定と、`internal/workspace/` の一時インデックス。

commit が成功したら、生成されたコミットのツリーハッシュを返却後の判定済みスナップショットと照合し、リポジトリ外の成果の文書も同じ識別を指すことを確認してから engine がステージ完了を記録する。pre-commit が整形や `git add` で内容を変えるなどして不一致になった場合は、完了を記録せず、コミットは取り消さない。そのコミットのツリーを新しい対象のバージョンとして返却後のスナップショットと成果物を更新し、すべての必須 check をやり直す。

commit 前後の不一致による取り直しは合わせて1回だけとし、取り直し後も対象が変わった場合の人への確認は[人への確認対象](#人への確認対象)に従う。人への確認の分類にかかわらず、判定済みの対象との一致を確認できないまま完了を記録しない。

### 職務の重なりと担当の切り替え

- **失敗**: 作業した agent が自分の作業を判定する、計画者が自分の計画を判定する、判定者や計画者が対象を書き換える、担当を変えながら修正を際限なく続ける。
- **仕組み**: [役割](data.md#役割-role)の種類ごとの規則を devkit が守らせる。サブエージェントによる check の runner は `judge` の種類の役割に限り、同じ agent を種類の違う役割に重ねず、計画の check の runner の agent を計画者の agent と分ける。`judge`・`plan` の役割の agent は読み取り専用として起動を制限する。[修正の担当の規則](data.md#修正の担当の規則)が変えるのは同じステージの次のラウンドの担当だけであり、ラウンドの上限は規則より先に効く。
- **置き場所**: `internal/config/` の役割の検証、`internal/plan/` の雛形と計画の検証、`internal/hook/` の PreToolUse と SubagentStop、`internal/engine/` の修正ラウンドを開く処理。

読み取り専用の強さはホストで異なる。Claude Code では agent の定義の `tools` を `[roles] read_only_tools` と照合して起動を拒否できる。Codex では `[deny] judge` に列挙した書き込みのツールの禁止に留まり、exec などを通じた書き込みは信頼の前提の範囲とする。

### 判定対象の展開と完了時の永続化

- **失敗**: git の属性で判定対象が変わったり、完了時に未判定の変更を取り込んだり、index と HEAD が食い違ったりする。
- **仕組み**: 返却後のスナップショットを一時インデックスから `git read-tree` と `git checkout-index --prefix` で `snap/<対象のバージョン>/` に展開し、判定者サブエージェントには git の対象をその読み取り専用の場所だけで読ませる。外部の成果の文書も固定した本文を渡し、ソース名・ID・内容ハッシュを対象の識別に含める。`.gitattributes` の `export-ignore`・`export-subst` の影響を受けない。
- **置き場所**: `internal/workspace/` の展開と永続化、`internal/engine/` の判定指示と完了の確定。

`command:` の check と `[judges]` の判定コマンドは作業ツリーで実行する。コマンド列の開始前と各実行後に、作業ツリーから一時 index の `write-tree` を取り、リポジトリ外の成果の文書の固定した内容ハッシュと合わせて[対象のバージョン](data.md#対象のバージョン-targetversion)を求め、判定対象の識別と照合する。開始前の一致を確認してから列を実行し、各実行後の一致を確認してから結果を受理する。いずれかの照合で不一致なら対象を取り直さず、その check を `FAIL` とし、「コマンドが対象を変えた」指摘に出力先を ignore する案内を含めて「修正する」に回す。繰り返しは[ステージのラウンド数の上限](data.md#ループの雛形-plantemplate)で止める。

ソースへの反映は[書き込みの流れ](data.md#書き込みの流れ)に従う。反映するのはリポジトリ内の書き込めるソースだけであり、完了時のコミットで永続化する。規範はループ自身の変更の確認を経る。リポジトリ外のソースは読み取り専用であり、devkit は書き込まない。

コミットを作らないステージでも、判定・承認・完了が同じ対象の識別を指すことを確かめる。

完了時の永続化と変更のないステージの扱いは[完了条件](#完了条件)に従う。ステージの完了時のコミットは devkit が現在のブランチに作り、ブランチ準備と作業完了後の統合はセッションのまとめ役が git の規則に従って行う。

分割した作業の場所は、`.devkit/run/` の読み取り専用の展開先とは別の `.devkit/worktrees/<単位の指示 ID>/` とする。devkit がラウンド開始時のスナップショットのコミットから detached の worktree を作る。単位の結果をすべて受理した後、各ツリーをブランチには含めないコミットオブジェクトにして SHA で固定し、作業ブランチのチェックアウトに順に、コミットしないマージで合流する。合流の記録は開始時の HEAD・入力の SHA・結果を持ち、再開時には git のマージの状態と照合する。ぶつかったファイルと単位は、統合を担うまとめ役への修正指示の brief に載せる。この統合はセッションのまとめ役が git の規則に従って担う。agent のある `work` の役割がステージの担当になったラウンドも、単位が1つのこの手順で動かす。

合流後のマージ結果を返却後の対象とし、ステージ開始時点からの累積差分に単位の変更とマージの結果を含める。必須 check・ゲート・ループ自身の変更の確認・依存の変更の分類・上限・戻り・再計画・問い・完了時のコミットはステージのラウンドで扱う。同時に動かす数は全体の `[parallel] max_concurrent`(既定3、1以上)と役割ごとの `[roles.<id>] max_concurrent`(指定時は1以上)の両方を満たす。数えるのは発行済みでまだ受理していないサブエージェントの指示である。互いに依存しない単位の作業、検証コマンド後の判定者の check、check ごとの判定直前の指示をまとめて返し、空いた分だけ次の `next` で発行する。役割の上限を省略した場合も全体の上限を守る。

### 外部操作の承認

- **失敗**: 未承認の対象や、承認時と異なるコマンドで外部に書き込む。
- **仕組み**: 承認対象には操作の種別と具体的な対象を示し、操作 ID・入力のハッシュ・登録定義とリポジトリ内の実行ファイルの内容ハッシュで識別する。計画の承認で足りるのは、計画に宣言した種別・対象・入力のハッシュと、宣言時の登録定義・実行ファイルの内容ハッシュがすべて一致する操作だけであり、それ以外は操作ごとに問いを起票して「外部操作の確認待ち」で止める。
- **置き場所**: `internal/plan/` の宣言の照合、`internal/engine/` の `external` の問いの起票、`internal/external/` の開始直前の照合。

開始直前の1回で有効な承認と操作の対象・入力・登録定義・実行ファイルの内容ハッシュを照合し、不一致なら新しい問いを起票する。承認への参照、実行前の記録、実行、結果の記録の順を守る。入力の渡し方は [external](modules.md#external)に従う。

### 外部操作の二重適用

- **失敗**: 再送や中断後の再実行により、同じ書き込みを二重に適用する。
- **仕組み**: 操作 ID は(種別、対象、入力のハッシュ)から導く。同じ入力で正当に繰り返す操作(コメントの追加など)は、登録に「発生単位」として要求ごとに変わる入力の項目を宣言し、導出に含める。外部向けの冪等キーには操作 ID を兼用する。
- **置き場所**: `internal/engine/` の `external` の要求受理、`internal/external/` の冪等キー・実行前後の記録・回復手続き。

同じ操作 ID が実行中または結果不明なら、新規には受理せず記録済みの状態を返す。成功済みなら記録済みの成功を返し、再実行しない。実行と照会には登録ごとの期限を設け、超えれば結果不明とする。外部側で識別・照会できるときだけ照会して確定し、できなければ再実行せず人に確認する。

### 誤った場所への書き込みと危険な操作

- **失敗**: チェックアウト外への書き込み、元に戻せない操作、external を迂回する外部書き込み、結果ファイルへの通常の書き込みが起きる。
- **仕組み**: 書き込み先と外部通信は[権限の境界](#権限の境界)で制限する。危険な操作と迂回は [PreToolUse](hooks.md#pretooluse)の `[deny]` で止める。結果ファイルの保護は[操作の禁止](#操作の禁止とサブエージェントの制限)の `permissions.deny` と、SubagentStop の採取からだけ受理する[判定結果の受理境界](#判定結果の受理)による。それ以外は信頼の前提の範囲とする。
- **置き場所**: ホストの sandbox と permissions、`devkit.toml` の `[deny]`、`internal/hook/` の PreToolUse、`internal/install/` の設定の追記。

### 中断

人は終了前の作業を、どの状態からでも、いつでも中断できる。完了・中止後の `pause` は終了済みとして正常応答し、中断の記録を追加しない。ラウンド中、判定待ち、計画待ち、問い待ち、外部操作の実行中、修正ラウンド中、Stop hook の `block` 中にも例外を設けない。中断は作業と記録を残して止める操作であり、作業を捨てる中止(`devkit abort`)とは別である。終了ブロックの提出を前提にしない。

中断の入口は `devkit pause` だけとする。人がチャットで止めるよう頼んだら、言い回しによらずエージェントが呼ぶ。人がターミナルで直接実行してもよく、Claude Code / Codex の `!` 経由も含む。束縛があればその作業を対象とし、なければ cwd のチェックアウトの記録から終わっていない1つの作業を特定する。ブランチ名には頼らない。

`pause` は中断と中断前の現在地への参照を ledger に直接追記し、[記録の公開方法](data.md#記録の書き込みと排他)に従って公開してから応答する。中断の記録と中断中の状態通知には作業ロックの取得、ブランチの一致を要求せず、実行中の外部操作も待たない。PreToolUse の deny は `devkit pause` を妨げない。Stop と engine は ledger の中断の記録を参照する。中断の時点はその記録の公開時点とする。

中断が記録された作業では、Stop は常に停止を許し、`block` しない。engine は指示の返却と新しい処理の開始前に中断を照合し、中断中は単位の作業を含む新しい指示を出さず、ラウンド・合流・判定・計画・検証・外部操作・完了処理を新たに開始しない。実行中の外部操作は取り消さず、届いた結果を [ExternalOp](data.md#外部への書き込み-externalop) の規則で記録する。起動済みの作業者・判定者・計画者サブエージェントの結果も、受理条件を満たせば記録してよい。結果の到着や記録の追加は中断を解除しない。

単位の結果を待つ間も Stop は停止を許す。単位の worktree は中断中に保持する。中止と作業の完了では、変更のない単位の worktree を削除し、変更の残るものは削除せず場所を知らせる。破棄は人が git で行う。合流中の中断からは、合流の記録と git のマージの状態を照合して続ける。

再開の入口は `devkit resume` とし、人の明示だけによる。人がチャットで再開を頼んだらエージェントが呼び、人がターミナルで直接実行してもよい。`resume` は中断への参照を持つ再開を ledger に記録する。再開時もブランチと hook の稼働の照合を通し、ledger から組み立てた状態で中断前の続きから進む。

中断中の `next` は、中断中であることと `devkit resume` で再開できることだけを返す。`next` の反復、ツール呼び出し、結果の到着、SessionStart や compaction だけでは再開しない。SessionStart の注入には中断中であることを含める。

kit はホストと別に継続上限を持つ。同じ作業で ledger への記録の追加がないまま Stop の `block` 判定が連続して上限に達したら、その回は `block` を返さず停止を許し、続行してよいかを人に確認する問いを起票する。上限は `[limits] stop_continuation` で設定し、既定は3回、1以上を必須とする。継続上限は無効にできない。記録の追加を境に数え直し、ツール呼び出し、セッションの切り替え、観測の追加だけではリセットしない。計数は作業ごとの[停止の観測](data.md#停止の観測-stopobservation)に残す。上限到達時はその観測に問いも公開し、停止を許す出力に問いを含める。CLI は中断中でない `next` または `answer` で問いを ledger に一度だけ取り込み、通常の回答の受理で人の判断を待つ。取り込み前も未回答の問いとして扱い、`next` の反復で作業や `block` を再開しない。

### 再開と hook の稼働確認

- **失敗**: 再開時に別の作業・計画・指示で進めたり、hook が動いていないまま承認や完了へ進んだりする。
- **仕組み**: [StageRun の束縛](data.md#計画のバージョン)、[指示 ID](data.md#指示-instruction)、[セッションとブランチ](data.md#セッションとブランチ)、[checkpoint](data.md#checkpoint)で現在地を復元する。途中でセッションが終わっても作業の状態を保持し、次のセッションに引き継ぐ。人による停止と継続の歯止めは[中断](#中断)に従う。継続は [Stop](hooks.md#stop)が補助し、唯一の保証とはしない。
- **置き場所**: `internal/engine/` の受理前の照合、セッションの観測、`internal/hook/` の SessionStart と Stop。

受理時には、必要な結果・入力原文・指示・担当・対象を、それぞれ[判定結果の受理](#判定結果の受理)・[回答の受理](#回答の受理)・[状態遷移と受理条件](data.md#状態遷移と受理条件)に従って照合する。不足があれば、それを必要とする前進操作だけを拒否し、不足した観測と理由を示す。`note` の受理は[決定と証拠](data.md#決定と証拠-decision--evidence)、`pause` の記録と中断中の `next` の応答の優先は[中断](#中断)に従う。

SessionStart の観測がないセッションでは `devkit start` を拒否し、`devkit doctor` で hook の設定を確かめるよう案内する。セッションの識別は[セッションとブランチ](data.md#セッションとブランチ)に従い、識別できても観測の代わりにはしない。

### 人への確認対象

- **失敗**: 依存やループ自身の変更を、確認なしに進める。
- **仕組み**: `[router] human_confirmation` で人への確認の分類を上書き・追加・削除できる。分類名は依存の宣言(ロックファイル・マニフェスト)の差分を表す `dependency_changed` と、[commit 直前の対象の照合](#commit-直前の対象の照合)で取り直した後の再変化を表す `target_changed_again` だけであり、未知の分類名は設定エラーにする。check の結果から次の行動への対応は固定である。blocking の指摘に `premise_broken` があれば、check の結果によらず人への問いにして、前のステージへの戻りを推奨として示す。依存の宣言として扱うファイルの glob は `[classification] dependency_files` で設定し、既定はバイナリが持つ依存のマニフェストとロックファイルの一覧である。
- **置き場所**: バイナリが持つ分類表の既定、`devkit.toml` の設定、`internal/router/` の分類。hook の稼働を確認できない場合は[再開と hook の稼働確認](#再開と-hook-の稼働確認)で扱う。

ループ自身の変更は、[規範](#規範の固定)・ホスト設定・skill・リポジトリ内で git が追跡する有効な pre-commit の設定の変更である。requirements と structure の変更は作業の成果としてステージの判定で扱い、ループ自身の変更に含めない。skill は `.agents/skills/devkit/`、サブエージェント定義は `.claude/agents/`・`.codex/agents/` に置く。

pre-commit の設定のうち、ループ自身の変更として検出するのは git が追跡する設定だけである。`core.hooksPath` で指定された場所もリポジトリ内の追跡対象に限り、追跡されない `.git/hooks` の変更は検出対象外である。

判定後の依存の宣言とループ自身の変更の分類は、そのステージ実行の最初のラウンド開始時のスナップショットと返却後のツリー、および規範のソース全体の文書の集合と内容ハッシュを比較する。修正ラウンドでも比較元を保ち、不合格のラウンドで行った変更も分類する。

`[approval] meta_loop_edit = "confirm" | "allow"` の既定は `confirm` である。`allow` はループ自身の変更を確認なしで許可する。`confirm` では、どのステージでもループ自身の変更を人が確認する。確認は変更が効く最初の時点より前に行う。ラウンド開始時のスナップショットに、作業の基点または直前に確認した時点からの未確認の変更があれば、ラウンドを開く前に問いを起票して止める。最後のラウンドで行った変更は、判定後の分類で完了時のコミット前に確認する。確認済みの範囲は、確認したスナップショットの規範の識別で表す。却下された変更は作業者に戻して取り消させる。この取り消しのラウンドには[修正の担当の規則](data.md#修正の担当の規則)を当てはめず、直前の担当のままとする。

ループ自身の変更の確認は `[approval] meta_loop_edit` だけに従い、ラウンド前と完了時のコミット前で同じ実効値を使う。`meta_loop_edit` は `[router] human_confirmation` から削除できる項目ではない。問いには変更したソース名・文書 ID、規範・ホスト設定・skill のファイル一覧と、devkit が生成した差分ファイルへの参照を載せる。

却下されても作業の対象を古いツリーに差し替えず、確認済みの規範の識別を作業対象とは別に保持する。次の指示は、却下された規範の変更ファイル一覧を添え、変更を取り消すよう作業者に指示するラウンドである。開始時のスナップショットに却下済みの変更がそのまま残っていれば、同じ確認を繰り返さず作業者へ戻す。

分類表で「暫定判断で進めてレビューで確認する」とした場合は、問いを起票せず、暫定の決定を `devkit note` で記録して進み、次のゲートまたは PR レビューで人が確認する。router の分類の出力としては「修正する」または「完了する」で返す。

#### 教訓の反映先

教訓の反映先の優先順は、機械の検査(hook・lint・型・検証コマンド) → [ループの雛形](data.md#ループの雛形-plantemplate) → 用途別の判定基準 → 原則 → skill とし、`[lessons] destinations` で変更できる。ソースへの反映先はリポジトリ内の `writable = true` の規範に限り、リポジトリ外のソースと読み取り専用のソースへの改善は教訓として記録して管理者へ引き継ぐ。規範はリポジトリが所有し、dev-kit 本体へ戻す経路は持たない。判定の基準を変えたら検出試験の例も更新する。rules の「強制は未実装」の項目と繰り返し見つかった違反は、テスト・lint・型・pre-commit・検証コマンドへ移す候補とする。既定では振り返りで規範を変えた場合にループ自身の変更として人が確認し、変えなければ確認なしで終わる。

### 記録の破損と競合

- **失敗**: 書きかけの記録を読んだり、並行する操作が状態を食い違わせたりする。
- **仕組み**: [記録の書き込みと排他](data.md#記録の書き込みと排他)の公開方法と[作業の排他制御](data.md#作業の排他制御)を使う。共有資産の競合は[資産の更新と共有](data.md#資産の更新と共有)で扱う。
- **置き場所**: `internal/ledger/fsstore/` の公開・破損の検出・ロック、git のマージと人のレビュー。

### バージョンの不一致

- **失敗**: 別の kit や互換性のない形式を使い、作業やチーム内の前提が食い違う。
- **仕組み**: 作業に記録した `kit_version` とバイナリの読み取り可能な記録形式を[バージョン互換性](#バージョン互換性)の境界で照合し、互換性がなければ拒否する。
- **置き場所**: `internal/kit/`、`devkit doctor`、記録の読み込み。

## 権限の境界

### ホスト設定と実行権限

ホスト設定の正本はリポジトリ内の `.claude/settings.json`・`.claude/agents/`・`.codex/hooks.json`・`.codex/config.toml`・`.codex/agents/`・`.codex/rules/` とする。`init` は kit の断片を追記し、リポジトリ全体に適用する項目を差分として示して人の確認を待つ。起動時に kit はホストへ設定を渡さない。hook の登録先はリポジトリ内に統一する。

Codex のプロジェクトの `.codex/hooks.json` は、プロジェクトの信頼と hook ごとの信頼が保存されていないと読み込まれない。`init` の後に、利用者が Codex を対話モードで開いてプロジェクトを信頼し、`/hooks` で各 hook を信頼する。`exec` の `-c` によるその場の信頼の上書きと `--dangerously-bypass-hook-trust` ではプロジェクトの hook は読み込まれない。稼働の確認と案内は [doctor](modules.md#doctor-の確認項目)に従う。

hook のコマンドでインタプリタを使う場合は絶対パスで呼ぶ。hook は sandbox の制約下で動くことがあり、`/usr/bin/env python3` から pyenv の shim を経由すると失敗することがある。

エージェントの書き込み先と外部通信はホストの sandbox が制限する。`devkit` 自身は git への書き込み(スナップショット、refs、コミット)と外部操作のために sandbox の外で動く。

pre-commit hook・判定コマンド・検証コマンドは `devkit` の子プロセスとして sandbox の外で動き、専用の隔離は行わない。pre-commit hook はリポジトリが所有して人がレビューする。判定コマンドは `devkit.toml` の `[judges]`、検証コマンドは `[commands]` に登録する育てるものであり、登録の変更はループ自身の変更として[人への確認対象](#人への確認対象)に従う。

- Codex は `.codex/rules/devkit.rules` の `prefix_rule(pattern=["devkit"], decision="allow")` を使う。escalation を要さない呼び出しにも適用され、許可したコマンドは承認なしに sandbox の外へ書き込める。experimental であることは確認済みである。
- Claude Code は `sandbox.excludedCommands` の `devkit *` と `permissions.allow` の `Bash(devkit *)` を併用する。前者だけでは権限の問い合わせが残る。この挙動と、プロジェクト設定の `sandbox` が効くことは確認済みである。`init` は利便性のためこの allow を提案し、記録上の保証には使わない。

`devkit` は `cd`・リダイレクト・連結・置換を付けず、単独のコマンドとして呼ぶ。付けた場合は sandbox の中で動く。skill にこの呼び方を書く。必要な git 操作が失敗したら理由を報告し、失敗した処理を完了扱いしない。中断の記録と状態通知の扱いは[中断](#中断)に従う。

### 操作の禁止とサブエージェントの制限

リポジトリ全体に適用する操作の deny は、人がリポジトリの方針として `.claude/settings.json` に書く。kit が `permissions.deny` に追加するのは `Edit(.devkit/run/**/records/**)`・`Edit(.devkit/run/**/results/**)` に限る。kit の `[deny]` とサブエージェントの起動の制限は [PreToolUse](hooks.md#pretooluse)で適用し、settings には足さない。観測用 hook の失敗で一律に block せず、観測が不足した操作の扱いは[受理時の照合](#再開と-hook-の稼働確認)に従う。生成物は[書き手の分離と指定先](data.md#記録の書き込みと排他)を守る。

Claude Code の `judge`・`plan` の種類の役割の agent は、定義の `tools` を `[roles] read_only_tools`(既定 `Read`・`Glob`・`Grep`)の範囲に限定し、外れる定義の起動は PreToolUse が拒否する。このツール制限が効くことは確認済みである。Codex は親の sandbox を継承し、書き込みツールの制限と両ホストの起動条件の制限は [PreToolUse](hooks.md#pretooluse)に従う。Codex での読み取り専用の保証は Claude Code より弱い。

`work` の役割の agent は判定者用の書き込み禁止 `[deny] judge` の対象外とし、`judge`・`plan` の役割への禁止は維持する。作業場所は `.devkit/worktrees/<単位の指示 ID>/` に分け、`.devkit/run/` の記録を守る deny と重ならないようにする。brief に作業場所の絶対パスを渡し、そこでだけ編集させる。

起動・操作を要する check(動作検証)の runner は必要な確認能力で選ぶ。確認できなければ `NOT ASSESSED` とする。

## 性能と出力の上限

依頼文の本文は `[briefs] max_bytes`(既定200000)で制限する。超える分は別のファイルにして一覧で渡し、上限を超えた事実を記録する。黙って切り詰めず、規則・要件・構造・基準・スキーマの本文を二重に載せない。経緯は固定した索引への参照で渡す。

運用上の制約と対策は [assets/principles/designing.md](../../assets/principles/designing.md) の原則6に従う。

作業ごとの記録数は少ないため、独立したファイルを一覧して読み込む方式で足りる。`next` は毎回 ledger を全走査する。対象のバージョンの計算は、追跡ファイルと ignore されていない未追跡ファイルを走査してコミットオブジェクトを作れる規模のリポジトリを前提とする。判定対象の展開は対象のバージョンごとに1回行い、作業の完了・中止時に削除する。

`command:` の check、完了時の commit を実行する `next` の呼び出しでは、処理の期限に合わせてホストの timeout を指定する。期限超過や結果不明を成功扱いしない。

Claude Code の Bash の出力上限は正常時が約3万字、失敗時が約1万字である。Codex の Bash の出力は、モデルに渡るときに先頭と末尾を残して約4KB に切り詰められる(約50万トークンの出力で確認済み)。`devkit` のコマンドの出力は短く保ち、長い出力はファイルに書いて要点とそのパスを返す。

hook の出力上限は Claude Code が約1万字、Codex が約2,500トークンと確認済みである。checkpoint は上限内なら本文を注入し、超えるなら要約と「`devkit status` で全文」の案内を注入する。

## 観測性

`status` と view は既存の記録から、ステージごとのラウンド数、人に止められた回数と理由、担当の切り替え、検出試験の回数、依頼文の大きさを作業ごとに集計する。新しい記録は足さない。`[limits] max_total_rounds` を設定した作業は累計が達したとき人に確認し、続行ならその時点の累計に設定値を足した値で次に止める。未設定なら作業全体の上限は使わない。戻り・作り直し・担当の変更でも累計を減らさない。

記録そのものを観測の基盤とし、`devkit status` と view で状態を確認する。プロセスのログは標準エラー出力に出す。記録の網羅性は[成果物を記録した範囲](modules.md#view)として示す。

## バージョン互換性

`kit_version` は記録形式とバイナリの互換性の識別であり、[Work](data.md#作業-work)に記録する。バイナリの値と `init` が設定に書く値は `"v3"` である。非互換の作業は、理由を示すバージョン不一致のエラーで拒否する。バイナリは読み取り可能な記録形式のバージョンの範囲を宣言する。リポジトリが所有する規範の内容は配布物との一致を求めず、作業開始時と doctor も kit のコピーを照合しない。未知のバージョンや互換性のない組み合わせは、失敗を隠さずエラーにする。読めない記録は失敗として報告し、記録形式の移行の仕組みは設けない。読めなくなった作業は古いバイナリで終えるか `abort` する。
