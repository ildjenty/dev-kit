# 設計上の決定

実装前の選択は仮決定として番号を付け、保存済みデータや利用側の設定に影響する選択は不可逆な決定として扱う。採用案が決まっていない問いは未決事項とする。不採用の案には、採らない理由を残す。ホストの挙動など確認が必要な条件は、未確認の前提として切り分ける。

## 仮決定

1. Go のパッケージを実装単位に選ぶ([モジュール](modules.md#モジュールごとの契約))。
2. バイナリは単一の `devkit`、設定ファイルは `devkit.toml` とする。設定は TOML、計画・記録・指示・終了ブロック・結果・決定と証拠は JSON とし、JSON Schema で形式を制約する。
3. セッション内の skill から作業を始める。[作業の開始](flow.md#作業の開始)と [CLI の呼び分け](modules.md#cmddevkit)を採用する。
4. 進行を CLI に集める。[手順の省略と完了の過大申告](guarantees.md#手順の省略と完了の過大申告)、[状態遷移と受理条件](data.md#状態遷移と受理条件)に従う。
5. サブエージェントを定型の依頼で起動し、結果を hook 経由で受ける。[判定結果の受理](guarantees.md#判定結果の受理)に従う。別系統のエンジンによる判定は判定コマンドとして表し、`codex exec --output-schema` などを `devkit` が子プロセスとして実行する。
6. 人の回答は観測を根拠にする。[回答の受理](guarantees.md#回答の受理)、[回答・承認](data.md#回答承認-answer--approval)、[UserPromptSubmit](hooks.md#userpromptsubmit)に従う。
7. CLI の呼び出しは git と外部操作に必要な権限を前提とする([ホスト設定と実行権限](guarantees.md#ホスト設定と実行権限)、[信頼の前提](guarantees.md#信頼の前提))。
8. 作業の場所と再開をセッションに結び付ける([利用側の配置](layout.md#利用側のリポジトリ)、[セッションとブランチ](data.md#セッションとブランチ)、[SessionStart](hooks.md#sessionstart))。
9. 実行の記録を共有資産から分ける([記録の書き込みと排他](data.md#記録の書き込みと排他)、[利用側の配置](layout.md#利用側のリポジトリ))。
10. 対象はツリーのスナップショットなどで識別し、規範を固定する。[対象のバージョン](data.md#対象のバージョン-targetversion)、[規範の固定](guarantees.md#規範の固定)、[展開と永続化](guarantees.md#判定対象の展開と完了時の永続化)に従う。
11. 判定の有効性を対象と規範に結び付ける([Judgment](data.md#check-の結果-judgment)(観点ごとの判定結果))。
12. 検証とコミットをステージの完了に結び付ける([作業結果の判定](flow.md#作業結果の判定)、[完了条件](guarantees.md#完了条件)、[コマンドの定義と責務](modules.md#config))。
13. 承認の同一性と訂正の履歴を保つ([回答・承認](data.md#回答承認-answer--approval)、[回答の受理](guarantees.md#回答の受理))。
14. 外部操作は承認を照合し、同じ操作を二重に実行しない。[承認](guarantees.md#外部操作の承認)と[二重適用の防止](guarantees.md#外部操作の二重適用)に従う。
15. Stop による停止の補助とサブエージェント内の処理を分ける([Stop](hooks.md#stop)、[hook の共通処理](hooks.md#共通処理))。
16. deny は束縛のあるセッションで固定した規範から照合する。[PreToolUse](hooks.md#pretooluse)と[規範の固定](guarantees.md#規範の固定)に従う。
17. 束縛のないセッションでは処理を限定し、受理前に hook の稼働を確認する。[hook の共通処理](hooks.md#共通処理)と[稼働確認](guarantees.md#再開と-hook-の稼働確認)に従う。
18. 再開用の現在地は記録から組み立て、上限に応じて要約する。[checkpoint](data.md#checkpoint)と[性能と出力](guarantees.md#性能と出力の上限)に従う。
19. devkit の操作手順をリポジトリ自身の指示から分ける([指示ファイルとホスト設定](layout.md#指示ファイルとホスト設定))。
20. 固定物はバイナリに埋め込み、利用側のコピーから供給する。[kit](modules.md#kit)と[ルートパッケージ](modules.md#ルートパッケージ)に従う。
21. 人の確認状況を記録から表示する([view](modules.md#view)、[状態変更](data.md#決定と証拠-decision--evidence)、[問いの停止範囲](data.md#状態遷移と受理条件))。
22. 構造の履歴と承認を git と PR レビューに委ねる([構造の記録](data.md#構造の記録-structure))。
23. 必須の観点の検出能力を使用前に確かめる([検出試験](guarantees.md#検出試験)、[記録の識別](data.md#検出試験の記録-detectiontest))。
24. 確認事項は既定の分類表と利用側の追記で決める。[人への確認対象](guarantees.md#人への確認対象)に従い、hook の稼働不足は[稼働確認](guarantees.md#再開と-hook-の稼働確認)で扱う。
25. バージョンの不一致を暗黙に吸収しない([バージョン互換性](guarantees.md#バージョン互換性))。
26. [メタループ](../meta-loop.md#メタループ)(ループの仕組み自体を改善するループ)は専用モジュールを持たず、kit の固定物と router の「教訓の反映先」で表す。
27. [バイナリの配布方法](#バイナリの配布方法)は未決事項とする。
28. ホスト設定の所有権を利用側に残す([ホスト設定と実行権限](guarantees.md#ホスト設定と実行権限)、[install](modules.md#install))。
29. ラウンドの終了と外部操作の要求を分ける([進捗](data.md#進捗-progress))。
30. 書き込みの調停を作業内に閉じる([作業の排他制御](data.md#作業の排他制御))。
31. 作業途中の判断も所定の入力経路で記録する([決定と証拠](data.md#決定と証拠-decision--evidence)、[状態遷移と受理条件](data.md#状態遷移と受理条件))。
32. 指示と結果の対応を再開後も保つ([指示](data.md#指示-instruction))。
33. 結果の重複と判定の食い違いを分けて扱う([判定結果の受理](guarantees.md#判定結果の受理))。
34. 利用者が育てる[ループの雛形](data.md#ループの雛形-plantemplate)(ループの定義)から課題ごとの計画を作る([作業の開始](flow.md#作業の開始)、[計画の逸脱と承認](data.md#計画-plan))。
35. 検証コマンドを雛形の check に接続する([登録定義](modules.md#config)、[計画](data.md#計画-plan)、[作業結果の判定](flow.md#作業結果の判定))。
36. [Bash の一律拒否と他の skill の共存](#bash-の一律拒否と他の-skill-の共存)は未決事項とする。
37. [計画の提案番号](#計画の提案番号)は未決事項とする。
38. [計画の再提案に適用する上限](#計画の再提案に適用する上限)は未決事項とする。

## 不可逆な決定

- **記録の形式**: 記録ごとの独立ファイル、JSON、記録 ID の形式、参照の列は保存済みデータに影響する。形式のバージョンと読み取り可能な範囲の宣言方法を定める。
- **計画の JSON Schema**: スキーマにバージョンを持たせる。
- **設定ファイルの名前と形式**、**利用側のディレクトリ名**、**ブランチ名の規則** `devkit/<作業 ID>`: 導入済みリポジトリに影響する。
- **CLI のサブコマンド名と `next`・`submit`・`answer` の入出力の形式、回答の定型**: skill と hook から呼ばれ、人がチャットで使う公開契約である。
- **サブエージェントの定義の名前(`devkit-` 接頭辞)と結果の形式**: ホストの設定と判定者の出力に影響する。
- **外部書き込みと判定の登録形式**: `devkit.toml` の節はリポジトリ側の実装との契約になる。
- **ホストの設定への依存**: [PreToolUse](hooks.md#pretooluse)の規則の構文と起動制限、SubagentStop・UserPromptSubmit の入力項目に依存する。

## 変更可能な内部の決定

モジュールの内部構造、view の見た目、ledger/fsstore の最適化は、後から変更できる。

## 不採用の案

- **表記だけの修正で検出試験の合格記録を引き継ぐ方式**: 判定条件を変えたかを機械で判別できないため、[合格記録を識別する内容ハッシュ](data.md#検出試験の記録-detectiontest)が変われば試験をやり直す。
- **課題ごとに計画者がゼロからループを組む方式**: ループを組む主体が利用者でなくなり、ループを育てる場所がない。
- **`devkit` が検証の集合を決めて省略を監視する方式**: 検証を選ぶのは雛形を組む人である。check と pre-commit の役割は[完了条件](guarantees.md#完了条件)に従う。
- **ラウンド ID・種別・出し直し回数だけで指示を識別する方式**: ラウンド前の計画や検出試験、同じラウンドの異なる観点を識別できない。採用した識別は[指示](data.md#指示-instruction)に従う。
- **ブランチが一致しない場合も書く操作を許す方式**: 異なるチェックアウトで結果の記録・検証・外部操作・完了が進んでしまう。[セッションとブランチ](data.md#セッションとブランチ)の境界を使う。
- **完了時にブランチの参照だけを進める方式**: index が受理済みのスナップショットと一致せず、pre-commit も実行されない。[完了条件](guarantees.md#完了条件)に従う。
- **未回答の問いがあるときだけ入力を観測する方式、承認後の訂正を期限なく受理する方式**: 回答後の訂正を見落とすか、実行済みの操作・開始済みのステージの承認を後から置き換えてしまう。[UserPromptSubmit](hooks.md#userpromptsubmit)と[回答の受理](guarantees.md#回答の受理)で扱う。
- **commit 直前にツリーが変わっても返却後のスナップショットを取り直さない方式**: 判定・完了・コミットの対象が一致しない。[commit 直前の対象の照合](guarantees.md#commit-直前の対象の照合)に従う。
- **外側のプロセスが `claude -p` や `codex exec` を起動してループを回す方式(前のバージョン)**: ホストのサブエージェント、セッション再開、compaction、チャットでの確認を子プロセスと結果ファイルで再実装し、他の skill や plugin と同じセッションで使えない。
- **セッションのエージェントが進行を決める方式**: 計画の順序と完了条件をエージェントに委ね、決定的だった部分の性質が損なわれる。
- **判定者サブエージェントが結果ファイルを自分で書く方式**: [読み取り専用の判定者サブエージェント](guarantees.md#操作の禁止とサブエージェントの制限)は書き込めず、作業者が同じファイルを書いても区別できない。[SubagentStop](hooks.md#subagentstop)を使う。
- **エージェントが人の答えを転記するだけの `answer`**: 曖昧な答えを都合よく解釈する偏りを防げない。[回答の受理](guarantees.md#回答の受理)に従う。
- **Stop hook を唯一の強制手段とする言い方**: 他の hook の優先、継続回数のリセット、hook 停止の未検知がある。[Stop](hooks.md#stop)と[再開と hook の稼働確認](guarantees.md#再開と-hook-の稼働確認)の役割に分ける。
- **`devkit` を sandbox の中で動かす方式**: Codex の workspace-write は `.git` を再帰的に読み取り専用にし、ネットワークも既定で無効なので、スナップショット・refs・コミット・外部操作ができない。[権限の境界](guarantees.md#権限の境界)に従う。
- **規範を返却後のスナップショットから読む方式**: ラウンド中の書き換えがそのラウンドに適用される。[規範の固定](guarantees.md#規範の固定)に従う。
- **SQLite による ledger**: cgo または純 Go ドライバの依存が増え、作業ごとの記録数に対して過剰である。[独立したファイルの走査](guarantees.md#性能と出力の上限)で足りる。
- **Markdown を正本とする計画**: 散文と構造が食い違うため、[plan](modules.md#plan)が検証する構造化データを使う。
- **メタループ専用モジュール**: 既存の部品で表せるため、[kit の固定物](modules.md#kit)と [router の分類](modules.md#router)を使う。
- **hook 内でモデルに判定させる check**: hook の時間と出力の制約に合わないため、[hook](modules.md#hook)の決定的な処理と [check](modules.md#check)の判定を分ける。
- **ホストごとに分けた skill の正本**: ホスト間でバージョンがずれるため、[共通の skill とリンク](layout.md#指示ファイルとホスト設定)を使う。
- **checkpoint の上書き記録**: 古い状態で新しい状態を上書きする競合を避けるため、[checkpoint](data.md#checkpoint)(記録から組み立てる現在地)を使う。
- **問い ID だけで同定する承認**: 承認対象の違いを区別できないため、[回答・承認の同一性](data.md#回答承認-answer--approval)を使う。
- **担当のツールに任せる外部への書き込み**: 承認と二重適用の防止を迂回できるため、[external の経路](modules.md#external)に集める。
- **共有の記録を ledger に置く方式**: 機械間での記録の調停が必要になるため、[育てるものの更新と共有](data.md#資産の更新と共有)に委ねる。
- **実行の記録の git 管理**: 機械ごとの作業履歴の統合を持ち込むため、[利用側の固定配置](layout.md#利用側のリポジトリ)と[資産による共有](data.md#資産の更新と共有)を使う。
- **kit 自身による隔離とホスト能力の試験**: 作業者を敵対とみなして隔離を保証する仕組みは[信頼の前提](guarantees.md#信頼の前提)に対して過剰であり、同じ OS 利用者の権限では保証もできない。[ホストの権限管理](guarantees.md#ホスト設定と実行権限)に委ねる。
- **ステージング経由の記録**: 担当の CLI と hook が一時領域に書き、別の進行プロセスが取り込む方式は、記録の偽造防止を目的とし、[信頼の前提](guarantees.md#信頼の前提)では不要である。[CLI による記録と hook による生成物の公開](data.md#記録の書き込みと排他)を使う。
- **基点コミットからの規範の実体化**: 作業開始時の規範・設定・skill を別の状態ディレクトリへ書き出して評価対象から隔離する方式は、悪意ある改変の防止を目的とし、[信頼の前提](guarantees.md#信頼の前提)では不要である。ラウンド中の変更への対策は[規範の固定](guarantees.md#規範の固定)で扱う。
- **端末での外部操作の開始確定**: 承認の記録とは別に端末で対話確認を要求する方式は、承認の偽造防止を目的とし、[信頼の前提](guarantees.md#信頼の前提)では不要である。[外部操作の承認](guarantees.md#外部操作の承認)を使う。
- **状態ディレクトリ全体の flock**: すべての書き手の公開と移行・掃除を共有・排他ロックで調停する方式は、[一意なファイル名による追記](data.md#記録の書き込みと排他)には不要である。[作業内の排他制御](data.md#作業の排他制御)を使う。
- **構造の current ポインタと履歴の連鎖**: 現在のバージョンを指すファイルと本文の履歴を別管理し、その連鎖を照合する方式は、[構造の記録](data.md#構造の記録-structure)の git 履歴と PR レビューで足りる。
- **実行の記録をチェックアウトの外に置く方式**: 保護用の識別子の解決と移設の手順が増えるため、[チェックアウト内の固定配置](layout.md#利用側のリポジトリ)を使う。
- **起動時の埋め込み固定物の書き出し**: 埋め込みを別の状態ディレクトリへ書き出して実行時の供給源にする方式は、[kit のコピー](modules.md#kit)を唯一の供給源とすれば不要である。`init` が利用側へコピーを書き出す操作は採用する。
- **上書きするカーソル**: 閲覧者と作業ごとの閲覧位置を別ファイルで更新する方式は、[状態変更から導く確認済みの集合](data.md#決定と証拠-decision--evidence)で足りる。
- **環境の記録**: 利用者名・作業の束縛・hook の登録状態などを専用の永続記録にまとめる方式は、[git の利用者名](data.md#回答承認-answer--approval)、[セッションの観測](data.md#セッションの観測-sessionobservation)、[doctor](modules.md#doctor-の確認項目)で得られる情報と重複する。
- **ホストの設定を起動時にテンプレートで上書きする方式**: 利用側が所有する設定を失うため、[ホスト設定の正本と導入時の追記](guarantees.md#ホスト設定と実行権限)を使う。
- **部品ごとの登録ファイル**: 検証コマンド・deny・外部操作・分類表の追記は登録の形が同じなので、[config](modules.md#config)が扱う `devkit.toml` の節にまとめる。
- **kit が worktree を作る方式**: git とホストに対応する機能があるため、[ホスト・git と kit の責務分担](guarantees.md#ホストgit-と-kit-の責務分担)に含め、[別のチェックアウトでの並行作業](layout.md#利用側のリポジトリ)を使う。
- **記録形式の `migrate`**: 互換性のない記録の移行機構を kit に増やさず、[バージョン互換性](guarantees.md#バージョン互換性)の扱いに従う。
- **依存物の有効条件・再構築・掃除を kit で管理する方式**: リポジトリ固有の準備と掃除を kit の責務に増やさず、[判定コマンドと検証コマンド](modules.md#config)に委ねる。
- **`devkit progress`・`record`・`check`・`detect`・`ledger` のサブコマンド**: 進捗の提出・途中の記録・判定・検出試験・照会は[現在の CLI の操作](modules.md#cmddevkit)で扱えるため、呼び出し口を増やさない。
- **Judgment の規範の内容ハッシュ(ツリーに含まれないものの照合)**: 規範はすべて[規範の固定](guarantees.md#規範の固定)で定めるスナップショットに含まれる。[Judgment の規範の識別](data.md#check-の結果-judgment)を使う。
- **リポジトリ全体の `permissions.deny` に kit の `[deny]` を足す方式**: 束縛のないセッションや他の skill にも効く。[PreToolUse](hooks.md#pretooluse)で適用する。
- **`.claude/skills` 全体をリンクにする方式**: 既存の skill と衝突する。[skill 単位の配置](layout.md#指示ファイルとホスト設定)を使う。
- **サブエージェントの依頼文をエージェントに書かせる方式**: 作業者の説明や自己評価が依頼に混ざる。[判定結果の受理](guarantees.md#判定結果の受理)に従う。
- **観測した入力に定型が含まれるだけで受理する方式**: 引用や説明、サブエージェントの報告を承認として扱えてしまう。[回答の受理](guarantees.md#回答の受理)に従う。
- **hook がブランチ名だけでセッションを自動的に束縛する方式**: 同じチェックアウトの別セッションにも hook が効く。新しいセッションは `next` で明示的に再開し、束縛後はブランチを切り替えても無効にしない。[セッションとブランチ](data.md#セッションとブランチ)に従う。
- **`git archive` による対象の展開**: 属性によって内容が変わる。[判定対象の展開](guarantees.md#判定対象の展開と完了時の永続化)を使う。
- **リポジトリ全体のツリーハッシュを規範の識別にする方式**: 無関係な変更で判定が失効する。[Judgment の規範の識別](data.md#check-の結果-judgment)を使う。

## 未決事項

### バイナリの配布方法

インストーラによるバイナリの配置を含む配布方法は未決定とする。

### Bash の一律拒否と他の skill の共存

問いは、[PreToolUse](hooks.md#pretooluse)のリダイレクト・置換・制御構文の拒否範囲を維持するか、狭めるかである。現行の範囲は `[deny]` への一致にかかわらず、通常のリダイレクトや heredoc を使う他の skill の手順も止め、「分けて実行する」だけでは続行できない場合がある。当面は現行の拒否範囲を維持し、他の skill との共存にはこの制約が残るものとする。

### 計画の提案番号

問いは、[計画の指示](data.md#指示-instruction)に使う提案番号を計画のバージョンと同じ値にするか、別の値にするか、いつ採番してどこに記録し、指示の出し直し時にどう保持するかである。当面は[状態遷移と受理条件](data.md#状態遷移と受理条件)を維持し、これらは未確定とする。

### 計画の再提案に適用する上限

問いは、[再提案](data.md#計画のバージョン)で何を数え、どこから上限を取得し、計数のリセット条件と人への確認に切り替える条件をどうするか、ステージの計数と上限を使うならどのステージに対応させるかである。当面は再提案に適用する計数・上限の取得元・リセット条件と人への確認に切り替える条件を未確定とする。

### 計画の外部操作宣言と承認

問いは、雛形からの逸脱がなくても外部操作の宣言があれば計画の承認ゲートを必須とするか、それ以外の経路で承認を得るかである。当面は宣言だけで承認済みとは扱わず、有効な計画の承認を確認できない操作は[外部操作の承認](guarantees.md#外部操作の承認)に従って操作ごとの問いで確認する。

### 検証前の対象の不一致

問いは、[コマンドの実行前後の照合](guarantees.md#判定対象の展開と完了時の永続化)や判定前の pre-commit の実行前の照合で不一致になった場合に、対象を取り直すか、その場合の回数と上限をどうするかである。不一致時の遷移は未確定とする。[commit 直前の対象の照合](guarantees.md#commit-直前の対象の照合)の取り直し回数を検証時にも適用するとは決めない。

### 外部操作の入力場所

問いは、`external` の入力ファイルも `inbox/` の下に限定するか、別の場所を認めるかである。当面は[状態遷移と受理条件](data.md#状態遷移と受理条件)の場所の制約を `external` に拡張せず、受け取れる場所は未確定とする。

### 観測のないセッションでの開始

問いは、セッションの観測が1件もない場合、`start` を拒否するか、どの情報から束縛先を識別するかである。当面は[セッションとブランチ](data.md#セッションとブランチ)で定めた識別元を維持し、識別できない場合の開始手順は未確定とする。`start` を[hook の稼働確認](guarantees.md#再開と-hook-の稼働確認)の対象へ加えるかも、この問いで決める。

### kit の継続上限

問いは、ホストの上限とは別に kit が継続上限を持つ必要があるか、持つなら値と継続回数のリセット条件をどうするかである。当面は[Stop](hooks.md#stop)にあるホストの確認済みの上限と区別し、kit 独自の値とリセット条件、および独自の上限による停止条件は未確定とする。

### 指示のない期間の規範

問いは、ラウンドも判定指示もない期間に、`[deny]` などの規範をどの時点のスナップショットから読むかである。計画者への指示だけがある期間も含める。当面は[規範の固定](guarantees.md#規範の固定)で定まる取得時点を維持し、それに該当しない期間の参照元とフォールバックは未確定とする。

### サブエージェント定義の変更と完了

問いは、必須 check のサブエージェント定義を編集したラウンドを、固定した旧定義で判定して完了させるか、指示を失効させて次のラウンドへ移すか、その手順をどうするかである。[SubagentStop](hooks.md#subagentstop)が採取する終了時点の定義のハッシュは、編集によって開始時点のものと一致しなくなる。当面は[判定結果の受理](guarantees.md#判定結果の受理)のハッシュ照合を維持し、不一致の結果を受理しない。この変更を含むラウンドの完了手順は未確定とする。

## 未確認の前提

- `git hook run pre-commit` が、`core.hooksPath` や husky・pre-commit フレームワークの構成でも commit 時と同じ hook を実行すること。
- husky・pre-commit フレームワークと `core.hooksPath` の共存。
- Codex で escalation を要さない呼び出しにも rules の allow が適用されること。
- Codex の SubagentStop の `agent_type` の値の形式が、サブエージェント定義の名前と照合できること。
- 両ホストの SubagentStop で `last_assistant_message` から結果の本文を取得できる条件と、null になるか、なる場合の条件。
- Codex の UserPromptSubmit が、回答後の訂正を含めて入力のたびに発火すること。
- Codex の UserPromptSubmit が、人以外のターンでも発火するか。
- Codex で SessionStart hook から後続のコマンドへ環境変数を渡せること。渡せなければ、Codex では同じチェックアウトで同時に複数のセッションを開かないことを前提とする。
- Codex に履歴を継承するサブエージェントの起動があるか、あるなら禁止できるか。禁止できなければ transcript の照合だけで代える。
- 両ホストの `agent_transcript_path` の形式から、最初の prompt を取り出せること。
- Codex の PreToolUse が、サブエージェントの起動を捕まえること。
- Claude Code の `-p` で `Agent(fork)` などの Agent の引数を PreToolUse で判定できること。
- Claude Code で `Agent(effort:*)` が effort の上書きを禁止できること。
- Claude Code の hook の登録に `onFailure: "block"` 相当の設定を使えること。
- settings の Stop hook がサブエージェントの終了で発火するか。発火する場合は `agent_id` で無視する。
- Codex の Stop の継続上限と、Bash の出力上限。
- Claude Code の skill がシンボリックリンクされたディレクトリをたどること。
- `features.shell_tool = false` の Codex の判定者サブエージェントが、展開先のファイルを読めること。読めなければ shell を残し、編集しない指示と `[deny]` で代える。

### effort と model の取得元

問いは、Claude Code の `effort.level` と Codex の `model` を、SubagentStop のイベント JSON または transcript のどの項目から取得できるかである。当面は取得元を確認済みとは扱わず、[判定結果の受理](guarantees.md#判定結果の受理)の照合条件を維持する。定義の設定値を観測値の代わりに使わない。
