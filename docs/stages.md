# ステージ

kit は、利用者が[ループの雛形](architecture/data.md#ループの雛形-plantemplate)(再利用するループの定義)に並べるステージ(作業を区切る単位)と[観点](checks.md)(check の確認の切り口)を定義する。[計画者](architecture/flow.md#作業の開始)(雛形から計画を作るサブエージェント)による取捨の範囲は[作業の開始](architecture/flow.md#作業の開始)に従う。

0〜5 は段階的な具体化の順序であり、最後に振り返りを行う。既定の `default`・`fix`・`docs` の構成と、調査・試作の候補としての扱いは[既定の雛形](loop-plan.md#既定の雛形)に従う。テストの仕組みがない場合は、実装の必須 `command:test` の指摘を受け、作業の中で検証の手段とコマンドの登録を用意する。

ステージ定義はリポジトリが所有する `.devkit/stages/` に置く。要件の正本は `.devkit/requirements.md`、構造の記録は `.devkit/structure.json`、規則は `.devkit/rules.md` であり、これらの配置は `devkit.toml` の `[paths]` で変更できる。各ステージで決めたことのうち、後の作業に効かせたい要件は要件の正本へ、構造は構造の記録へ、複数の作業で守る変更困難な決定は規則へ残す。固定の `.devkit/run/` の記録は git 管理しない。

元に戻せないもの(変更困難な決定)の判断は、[`assets/principles/designing.md` の原則1](../assets/principles/designing.md#1-変更困難な決定は先に特定し判断材料を得てから確定する)に従う。

## 0 目的

既定の `default` は、最初の計画に要件と完了条件の合意に関する完了条件を持たせ、`purpose` の遷移 `done` を `"replan"` にする。目的の完了後、計画者が合意した完了条件で残りを作り直し、既定では人が承認する。`fix` と `docs` はこの形を使わない。要件定義を先に行って再計画するかは雛形の組み方で決まり、kit は目的を特別扱いしない。

- **決めること**: 変更の利用者と目的、計画の完了条件の根拠。人が承認した完了条件と既存の要件を照らし、人に確かめながら要件を詰め、リポジトリが満たすべき要件を更新する。完了条件の案は利用者の言葉で文章にし、[計画の作り直し](architecture/data.md#計画のバージョン)で完了条件を変える場合は、既定では再び人の承認を得る。
- **決めずに次のステージへ渡すこと**: 手段全般。
- **元に戻せないもの**: なし。
- **成果物**: [目的と完了条件の対応の説明](checks.md#目的)、更新した `.devkit/requirements.md`、完了条件の案。再計画は雛形の遷移と計画の承認の条件に従う。

## 1 スコープ

- **決めること**: 含めるものと含めないもの。外部から見えるもの。
- **決めずに次のステージへ渡すこと**: 内部構造。
- **元に戻せないもの**: スキーマ、識別子、契約の型、外部への公開、データの保持のうち、該当すると判断したもの。
- **成果物**: スコープの明示と、元に戻せないものの一覧。保存先は[規則と強制手段](architecture/data.md#規則と強制手段-rules)と[計画](architecture/data.md#計画-plan)に従う。後続ステージの [brief](architecture/modules.md#brief)(入力から組み立てる依頼文)に渡す範囲は[規則と強制手段](architecture/data.md#規則と強制手段-rules)に従う。

## 2 構造

- **決めること**: モジュール、責務、配置、依存の向き。
- **決めずに次のステージへ渡すこと**: 関数の内部。
- **元に戻せないもの**: 配置のうち、該当すると判断したもの。
- **成果物**: brief に参照先を同梱した `schemas/structure.json` に従って更新した [`.devkit/structure.json`](architecture/data.md#構造の記録-structure)(図は [view](architecture/modules.md#view)(作業の表示を生成する部品)が生成する)、流儀を揃える既存の箇所、不採用とした案と理由、未確認の前提。git で戻せない作用や特別な復元順序がある場合は、その復元手段。

## 3 契約

- **決めること**: インターフェース、データ形式、失敗の種類。
- **決めずに次のステージへ渡すこと**: 実装方式。
- **元に戻せないもの**: 公開・内部の契約のうち、該当すると判断したもの。
- **成果物**: 型のシグネチャ。

## 4 手順

- **決めること**: ステップの分け方と、各ステップの検証方法。
- **決めずに次のステージへ渡すこと**: コード。
- **元に戻せないもの**: なし。
- **成果物**: 各ステップの目的・完了条件・根拠・スコープを記した一覧。後続ステージの brief への取り込みは[作業の指示](architecture/flow.md#作業の指示)に従う。

## 5 実装

- **決めること**: コードと、その完了条件を確かめるテスト。`default` と `fix` では必須の `command:test` と観点 `test`・`diff`、`docs` では観点 `wording` の check を置く。検証コマンドが未登録なら、テストの仕組みを作り `devkit.toml` の `[commands.test]` に登録する。登録はループ自身の変更として人が確認し、次のラウンドから使う。
- **決めずに次のステージへ渡すこと**: なし。
- **元に戻せないもの**: なし。
- **成果物**: 差分。

## 調査

- **決めること**: 起きている事象、動作の仕組み、既存の同種の処理の書き方。
- **決めずに次のステージへ渡すこと**: 修正方法。
- **元に戻せないもの**: なし。
- **成果物**: 調査結果を、観測と推論に分けた報告。

## 試作

- **決めること**: 未確認の前提の真偽。
- **決めずに次のステージへ渡すこと**: 本番のコード。
- **元に戻せないもの**: なし。
- **成果物**: 実験の結果と決定。決定は [`devkit note`](architecture/data.md#決定と証拠-decision--evidence) で記録する。試作は本番のコードから分離し、[`devkit submit`](architecture/flow.md#作業結果の提出)(作業結果を提出するコマンド)の実行前に削除するか、追跡対象外で ignore された場所に置いて[完了時のコミット](architecture/guarantees.md#完了条件)に含めない。

## 振り返り

ステージ ID は `retrospective` である。

- **担当**: 作業者。
- **入力**: brief が参照する、指示発行時点で固定した作業履歴ファイルと規範の一覧である。作業履歴には、作業全体の判定と指摘(blocking でないものも含む)、合格・不合格の検出試験の例ごとの判定・指摘・期待判定との照合結果、`FAIL` と `NOT ASSESSED` の経緯、ラウンド数、人の却下・訂正・作り直しの指示、`note` の教訓で伝えた見逃しを含む。
- **決めること**: 各問題をどこで捕まえるべきだったかと、再発防止の反映先。既定の優先順は機械の検査(hook・lint・型・検証コマンド)、雛形、観点、原則、skill であり、`[lessons] destinations` で変更できる。リポジトリの規範へ反映し、反映しない場合は理由を残す。観点を変えたら検出試験の例も更新する。規範全体が目的を果たしているか、原則がどの観点・雛形で使われるか、使われない仕組みや負担に見合わない仕組みがないかを確かめる。扱う対象はその作業の問題・見逃し・規範の不足や負担であり、全体の棚卸しは必要が見えたときだけ行う。
- **決めずに次のステージへ渡すこと**: なし。
- **元に戻せないもの**: なし。
- **成果物**: 再発防止の反映と、反映しない項目の理由。目的のステージがない場合や目的で未反映の場合は、承認された完了条件のうち要件に当たるものを `.devkit/requirements.md` に反映する。
- **check**: `default` と `fix` は必須の `command:test`・`test`・`harness`、`docs` は必須の `harness` だけを置く。`default` と `fix` では検証の手段や対象を変えた場合も、最終のツリーで検査する。変えた観点の検出試験の設定と実行時期は[検出試験](architecture/guarantees.md#検出試験)に従う。
- **人の確認**: 規範を変えた場合はループ自身の変更として、既定では効力を持つ最初のラウンドの前、最後のラウンドなら完了時のコミット前に人が確認する。規範を変えなければ、この確認は不要である。
