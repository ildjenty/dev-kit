# ループ計画

ループ計画は課題ごとに作る。kit 内で固定の手順とするのは、計画を作る手順だけである。それ以外の手順は、計画のデータとして表す。計画は [brief](parts/brief.md) の一種として、バージョンを付けて [ledger](parts/ledger.md) に保存する。

ループ計画は、ステージ、担当、観点ファイル、レビューゲート、遷移表、計数の上限、戻り先を持つ状態機械のデータである。遷移表は [router](parts/router.md) の分類をキーにして次のステージを決める。条件式やテンプレート言語は書かず、runtime は分類と計数だけを評価する。「check の `FAIL` が続いたらこうする」という条件は、エージェントが計画を書き直すことで表す。

計画は記録として扱い、既定は git 管理の外に置き、ステージの並び、担当、観点、ラウンド数は使い捨ての部分とし、残す価値がある不可逆な決定の一覧、揃えた既存の箇所、計画を作り直した理由は [form](parts/form.md) の PR 本文に「計画の要約と決定」として写す。

1ラウンドは、brief を受けた作業 → [check](parts/check.md) → [router](parts/router.md) の一往復である。router が「修正する」を返して作業に戻るたびに、ラウンド数が1つ増える。

## フォーマット

```text
課題: <1行>
変えるもの: <目的 / 範囲 / 構造 / 契約 / コード のどれに触るか>
開始するステージ: <ステージの候補から>
ステージ:
  - ステージ: <名前>
    担当: <役割 → エンジン>
    check: [<観点>...]    # 誰が走らせるか(機械 / 別文脈 / Codex)
    人が見る: <no / yes: 理由(router の「作業を停止して確認する」の分類)>
    最大ラウンド: <n>
止まる: <進まなくなった回数、人に聞くものに当たった>
戻る規則: <ステージ N で前提が崩れたら、どのステージに戻るか>
```

- **戻る規則**: router の分類をキーにして次のステージと戻り先を決める遷移表である。前提が崩れて router が「前のステージに戻る」と判断した場合は、戻り先に従って残りの計画を作り直す。エージェントが提案した場合も計画の作り直しを行い、新しいバージョン、差分、作り直した理由を ledger に記録し、計画の check を通してから続行する。
- **止まる**: 最大ラウンドや進まなくなった回数など、計数の上限を持つ。人に聞くものに当たった場合は、router の「作業を停止して確認する」の分類とレビューゲートに従って止まる。停止の条件式は書かない。

## 例

```text
課題: ボタンの文言の修正
変えるもの: コード(画面)
開始するステージ: 5
ステージ:
  - ステージ: 5 実装 / 担当: 作る → 軽いモデル / check: [差分, 動作検証(画面: 文言が収まるか), 終了時の状態] / 人が見る: no / 最大ラウンド: 1
```

```text
課題: 課金プランの追加
変えるもの: 目的・範囲・構造・契約・コード
開始するステージ: 0
ステージ:
  - 0 目的 / check: [目的] / 人が見る: yes(目的が合意されていない)
  - 1 スコープ / check: [不可逆な決定] / 人が見る: yes(戻せない: 料金テーブルのスキーマ、公開 API。課金)
  - 2 構造 / check: [構造 ← Codex, 整合] / 人が見る: yes(戻せない: 置き場所)
  - 3 契約 / check: [契約] / 人が見る: no(仮決定)
  - 4 手順 / check: [手順] / 人が見る: no
  - 5 実装 / 担当: 作る → 軽いモデル、批評 → Codex / check: [差分, 動作検証(保存の読み戻し、実際の決済サービス), 終了時の状態] / 人が見る: yes(課金・外部への書き込み: 決済に触る部分だけ) / 最大ラウンド: 3
戻る規則: ステージ5でステージ2の前提が崩れたらステージ2に戻り、残りを作り直す
```

## 作成ルール

計画への入力は、依頼内容とリポジトリの事実である。リポジトリの事実には、配置ガイド、元に戻せないものの一覧、利用可能な check を含める。

- **何を変えるか**に基づいて、開始する[ステージ](stages.md)を決める。目的やスコープが未確定ならステージ0、変更困難な決定（スキーマ、契約、外部への公開など）に触れるならステージ1、責務・配置・依存を変えるならステージ2、変更困難な決定に触れない内部の契約だけならステージ3、コードだけならステージ4または5から始める。公開契約・内部契約のいずれも、保存済みデータ、実行中の処理、利用者と呼び出し元への影響、再生成と復旧の可否から判断する（[`principles/designing.md`](../principles/designing.md) の原則1）。「修正方法を知っているか」では決めない。
- 修正方法が分からない場合は、調査を先に置く。前提が未確認なら、試作を置く。
- 画面・データ・外部との通信のどれに触れるかを確認し、それに対応する「動作検証」を含める。
- router の「作業を停止して確認する」に該当するステージには、人によるレビューゲートを設け、理由を書く。
- 画面のデザインを始める前に、画面 ID と表示内容のバージョンに対する人の承認をレビューゲートの通過条件とし、router の「目的が合意されていない」に当たる確認として扱う。
- ステージの追加は [`principles/harness.md`](../principles/harness.md) の原則3の適用除外に従い、変えるものだけを扱う最小の計画に保ち、戻り先を定めるためだけに不要なステージを足さない。
- check の追加・必須化は `principles/harness.md` の原則5「防ぐ失敗と運用負担から仕組みを選ぶ」に従う。
- 段階的に具体化し、前のステージの出力を次のステージの入力にする。行き詰まったときの戻り先と再計画は `principles/harness.md` の原則3に従う。

## 計画の check と人によるレビュー

計画自体にも、[観点](checks.md)「計画」の check を適用する。人が計画を確認するのは、「作業を停止して確認する」に該当するステージがある場合と、そのレビューゲートを省略する場合だけにする。文言の修正であれば、人による計画の確認を挟まずに実行する。

「計画を作るための計画」を際限なく作ることを避けるため、計画を作る手順だけは固定する。固定する手順は、それだけである。
