# brief — 依頼の組み立て

## 責務

brief は、[作業者](../architecture/data.md#役割-role)(`work` の種類の役割)への指示と、[判定者](../architecture/data.md#役割-role)(`judge` の種類の役割)・[計画者](../architecture/data.md#役割-role)(`plan` の種類の役割)への依頼文を組み立てる。公開する型と操作、他の部品との境界は [brief のモジュール契約](../architecture/modules.md#brief)に従い、計画の型と意味論は [plan](../architecture/modules.md#plan)(計画の意味論を扱う実装)が扱う。

## 入力と出力

### 入力

作業依頼の組み立てでは、[ステージ](../architecture/data.md#ループの雛形-plantemplate)(作業の段階)の定義や前のステージの出力などに加え、[計画](../architecture/data.md#計画-plan)(パターンを参考に課題ごとに組む実行内容)の完了条件と上限を入力として受け取る。基本の入力構成と[規範](../architecture/guarantees.md#規範の固定)(評価に用いる規則)の参照先は[作業の指示](../architecture/flow.md#作業の指示)に従う。

本文で渡す知識は、`[planning] inputs`・`[plan_check] inputs`・計画のステージの `inputs` と、`[checks.<観点>] criteria` で選ぶ。要件と規則を渡す既定値を用意する。ステージの実体の `definition` でステージ定義を解決する。規範はソース全体を固定し、成果は選んだ本文を固定する。その他の規範はソース名・文書 ID・固定した写しのパスの一覧で渡し、編集中の原本を読ませない。文中の参照を解析して入力を補わず、必要な文書は選び方に明示する。変更の範囲は scope の出力と rules で渡す。

出力スキーマは、すべての `$ref` の参照先を同梱して単独で解釈できる形で渡す。check の `schemas` に書いた入力契約のスキーマも含め、補助のスキーマはこの和集合だけにする。計画の判定とその検出試験の既定は `plan`・`plan-template`・`finding` である。同じ規則・要件・構造・基準・スキーマの本文を依頼文の中で繰り返さず、JSON の部分には ID とハッシュだけを置く。

リポジトリの事実として[配置ガイド](../architecture/layout.md#利用側のリポジトリ)(置き場所と役割の案内)と「元に戻せないもの」を受け取り、後者の取得元は[規則と強制手段](../architecture/data.md#規則と強制手段-rules)に従う。

requirements と structure は固定した本文、ソース名・文書 ID、存在の有無、編集先を示す。要件が未作成なら作成先を案内する。リポジトリ内の書き込める `files` は設定したパスを編集先とする。リポジトリ外のソースは読み取り専用であり、固定した写しだけを示して編集先は示さない。必須の基準の選び方が0件なら判定を始めず止める。計画者への規則の本文は一度だけ載せ、元に戻せないものは規則の共有する決定への参照と計画の項目に限る。計画者には未決事項を記入するよう指示する。

修正[ラウンド](../architecture/data.md#ラウンド-round)(作業と判定の往復)では、指摘と検証の失敗情報を受け取る。[修正の担当の規則](../architecture/data.md#修正の担当の規則)で担当が変わったラウンドも、同じ入力をその担当に渡す。入力の構成は[指摘の参照](../architecture/data.md#指摘-finding)、[brief のモジュール契約](../architecture/modules.md#brief)と[作業結果の判定](../architecture/flow.md#作業結果の判定)に従う。

分割した単位の作業依頼では、計画の単位 ID・説明・担当する範囲と、`.devkit/worktrees/<単位の指示 ID>/` に作る作業場所の絶対パスを受け取る。単位の役割の agent には、そこでだけ編集し、`schemas/progress.json` の終了ブロックを最終メッセージで返すよう指示する。agent のある `work` の役割がステージの担当になったラウンドも、単位が1つのこの形の依頼にする。合流がぶつかった場合のステージの作業担当への修正指示には、ぶつかったファイルと単位を載せる。

計画依頼には優先パターンの本文、すべてのパターンの名前・固定したパス・devkit が計算した内容ハッシュ、ステージ定義の一覧と固定した参照、役割、check の名前と1行の説明、組み方の方針、start の課題、要件を渡す。計画者の入力は `[planning] inputs` で選ぶ。再提案・再計画では人の修正指示、check の指摘、採用済みの経路と残りの実行内容も渡す。

ステージの遷移 `done` が `"replan"` の場合も、ステージの完了後に既存の再計画の経路で残りを作り直す依頼を組み立てる。要件定義を特別扱いせず、計画の遷移に従う。

判定依頼の組み立てでは、[check](check.md#入力と出力)(判定依頼の内容を決める部品)が決めた内容を入力として受け取る。

分割した作業の判定依頼は、単位 ID を付けて欠けなく保持した各単位の終了ブロックと合流後のツリーを対象とする。差分はステージ開始時点からの累積差分であり、単位の変更とマージの結果を含める。単位ごとの判定依頼は作らない。

計画の判定依頼には、作業に記録した`start` の課題を固定入力として渡す。再計画の依頼は、計画の check が `NOT ASSESSED` となった後に人が修正を指示した場合も、元の再計画の種別と残りの作業を保つ。

### 出力

brief の内容を返し、組み立て・書き出しの責務は [brief のモジュール契約](../architecture/modules.md#brief)、指示との対応と配置は[指示](../architecture/data.md#指示-instruction)と[利用側のリポジトリ](../architecture/layout.md#利用側のリポジトリ)に従う。作業の brief には、誰のために何を行い、scope の出力と rules に基づく作業範囲、文章で書いた完了条件と[計画](../architecture/data.md#計画-plan)に定める条件ごとの確認手段を既知の情報とともに示し、計画の上限と[終了ブロック](../architecture/data.md#進捗-progress)(作業結果の記録)の返却要件を含める。

計画承認の問いは devkit が記録から組み立てる。`start` の課題、ID 付きの完了条件、計画の並びと各ステージの実体 ID・定義・担当・ゲート・必須 check・ステージと check と単位の指示、課題固有の元に戻せないもの、外部操作、`open_questions` を載せる。前に承認した計画の残りとの構造の差分を表示し、最初の計画では参考にしたパターンと比較する。差分には追加・除外・変更の両方向を含める。パターンとの違いは表示する判断材料であり、承認の理由にはしない。エージェントの要約に頼らない。

依頼文の入力は[依頼の入力](../architecture/data.md#依頼の入力)に従い、採用された成果、今の材料、経緯に分ける。戻りで見直しになった古い StageRun の報告は経緯に回す。判定者にも採用された前のステージの成果と直前のラウンドの報告への固定した参照を渡す。経緯は本文に載せず、`history` で記録から決定的に絞った固定した索引への参照を渡す。既定は作業者が `stage_run`、判定者が `check`、振り返りが `all` である。`none` も選べる。既定の harness は `history = "all"` を明示する。

判定対象に対応する検証コマンドの実行結果、有効な承認、引用された証拠と参照先は `history` によらず必ず判定者へ渡す。ステージ・単位の `outputs` は本文に入れる採用された成果を実体 ID または定義 ID で選び、既定はすべてである。選ばなかった成果も固定した索引から読めるようにする。検出試験には履歴を渡さない。

`[briefs] max_bytes` は既定200000である。超える分はファイルにして一覧で参照を渡し、超えた事実を記録する。検出試験と判定直前の計画者指示を含むすべての依頼に適用し、残った本文もファイルへ移す。最小の指示と参照先さえ収まらない場合は設定エラーで発行を拒否する。黙って切り詰めず、LLM による要約や検索、トークンの計算を置かない。

課題ごとの計画のステージ・check・単位の `instructions` は対応する依頼文へそのまま入れる。check の `brief_by_planner = true` の場合は計画者の判定直前の指示も渡す。これは補助の情報であり、固定した基準や確かめる範囲を狭められないことを明記し、原資料の差分・報告・計画・要件を別に渡す。既定のパターンでは使わない。

`delegations` で計画のステージが選んだ文書は、出所付きで本文をそのまま diff などの判定者へ渡す。人の答えから得た有効な承認と区別し、機械で判断の一覧へ変換しない。

## 保証

同じ入力からは同じ内容を組み立てる。外部入出力の扱いは[モジュールごとの契約](../architecture/modules.md#モジュールごとの契約)に従い、規範の入力は[規範の固定](../architecture/guarantees.md#規範の固定)に従う。

決定の有効条件・適用条件と[一時状態](../architecture/data.md#進捗-progress)(再開まで引き継ぐ状況)の条件は、出典・参照とともにそのまま項目に添えて渡す。[ledger のモジュール契約](../architecture/modules.md#ledger)に従い、条件を評価して入力を除外することはせず、有効かどうかはエージェントと人が判断する。

役割の agent であるサブエージェントの起動方法と、[指示 ID](../architecture/data.md#指示-instruction)(依頼を識別する値)から依頼本文のファイルを特定して読む手順は[判定結果の受理](../architecture/guarantees.md#判定結果の受理)に従う。

停止の判断は [engine](../architecture/modules.md#engine) と [router](../architecture/modules.md#router)(次の行動を選ぶ部品)が担う。

brief 自身は具体的な進め方や原因の仮説を付け加えず、前のステージの出力は内容を変えずに渡す。
