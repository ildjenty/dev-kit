# form — 固定フォーマット

## 責務

form は固定フォーマットの型と、[スキーマ・テンプレート](../architecture/modules.md#form)(入力形式の定義と文面の定型)の適用、Markdown の描画を提供する。

## 入力と出力

[kit](../architecture/modules.md#kit) がバイナリから供給するスキーマ、リポジトリが所有するテンプレート、および適用・描画する値を受け取り、固定フォーマットの定義、適用結果、人向けの Markdown を返す。

### 固定フォーマット

スキーマの適用対象と形式は [form の定義](../architecture/modules.md#form)、各データの項目は[エンティティの定義](../architecture/data.md#エンティティ)に従う。[判定者](../architecture/data.md#役割-role)(評価を担う `judge` の種類の役割)の結果の項目は、[判定結果](../architecture/data.md#check-の結果-judgment)(観点から対象を判定した記録)と[指摘](../architecture/data.md#指摘-finding)(失敗や判断を要する点)に従う。指摘には任意の真偽値 `premise_broken` を含められる。

終了ブロックのスキーマは[進捗](../architecture/data.md#進捗-progress)の必須項目を含めて定義する。入力ファイルの場所と受理条件は[状態遷移と受理条件](../architecture/data.md#状態遷移と受理条件)に従う。

`work` の種類の役割の agent の最終メッセージにも、`schemas/progress.json` の終了ブロックを使う。単位の結果は SubagentStop が保存し、合流後は単位 ID を付けて欠けなく保持した各単位の終了ブロックをステージのラウンドとして扱う。

テンプレートの既定の置き場所は `.devkit/templates/` であり、`devkit.toml` の `[sources.templates]` で変更できる。記録と共通の出力の JSON Schema はバイナリとの約束である。ステージ固有の報告の形はリポジトリのソースから選ぶ。

エージェントに渡すスキーマは、すべての `$ref` の参照先を同梱して単独で解釈できる形にする。補助のスキーマは、出力スキーマが参照するものと check の `schemas` に指定した入力契約の和集合だけを渡す。知識の本文の形式は自由である。構造の記録は `schemas/structure.json` に従う JSON のときだけ view が図を描き、それ以外は本文を表示する。計画・パターン・結果・テンプレート・スキーマの形式は devkit の約束として固定する。

終了ブロックはステージ固有の `report` と、devkit が形を定める `confirmation`、任意の `commit_message` とワーカー用の `notes` を持つ。`notes` は `kind` と `payload` を持つ配列で、決定・証拠・教訓を既存の note と同じ形で返す。devkit が結果の受理時に検証して一度だけ記録する。`report` は計画のステージがソースから選ぶ JSON Schema で検証し、完了を主張するときだけ必須とする。確認要求や停止では途中の報告を認める。`confirmation` は問い・選択肢・推奨・理由・材料への参照を持ち、確認を求める終了の種別で必須である。形への適合は証拠や完了の根拠にしない。単位の報告は単位 ID ごとに欠けなく保持し、`unit_report` があれば結果受理時に検証する。ステージの報告へまとめ直さない。

#### 問い

問い(人への確認事項)の文面に添える回答の案内は[問いの定義](../architecture/data.md#問い-question)に従う。回答の受理と訂正は[回答の受理](../architecture/guarantees.md#回答の受理)、停止しているステージと理由の表示は[状態遷移と受理条件](../architecture/data.md#状態遷移と受理条件)に従う。

計画承認の問いは devkit が記録から組み立てる。`start` の課題、ID 付きの完了条件、計画の並びと各ステージの実体 ID・定義・担当・ゲート・必須 check・ステージと check と単位の指示、課題固有の元に戻せないもの、外部操作、`open_questions` を載せる。前に承認した計画の残りとの構造の差分を表示し、最初の計画では参考にしたパターンと比較する。差分には追加・除外・変更の両方向を含める。パターンとの違いは表示する判断材料であり、承認の理由にはしない。エージェントの要約に頼らない。

画面のデザインの承認時の表示要件は[問いの定義](../architecture/data.md#問い-question)に従う。

`premise_broken` の指摘による問いは、指摘と前のステージへの戻りの推奨を示す。ラウンドの上限に達した問いは、そのステージに[修正の担当の規則](../architecture/data.md#修正の担当の規則)があれば、規則に書いた役割で続ける選択肢を含める。

ゲートの問いは、計画のゲート理由、終了ブロックの実施内容・確認済み事項・未確認事項、差分ファイルのパスを記録から描画する。ループ自身の変更の問いは、変更したソース名・文書 ID と、規範・ホスト設定・skill のファイル一覧と差分ファイルへの参照を描画する。エージェントの要約には依存しない。

作業者からの確認要求には `confirmation` の原文とすべての欄、再開条件を載せる。判定後の確認には判断を必要とした指摘の本文を載せる。人が担当するステージでは `human_prompt` で選んだ目的・入力・返してほしいものを載せる。差分は固定したファイルを参照し、根拠のない推奨を足さない。自由な回答は、承認・却下・保留・戻り・文章のいずれかとして記録されるまで問いを閉じない。

### テンプレート

判定の出力形式と共通規則は判定依頼テンプレートに一度だけ書く。`NOT ASSESSED` の使い方や、指摘に失敗のシナリオが必要であることを含む。判定の範囲・確認事項・blocking・報告しない事項・適用除外は原則のソースの用途別文書で定める。

テンプレートの対象と PR 本文に含める情報は [form の定義](../architecture/modules.md#form)に従う。

判定の基準の選び方は[観点と判定](check.md#観点と判定)に従う。

PR 本文で共有する情報は[資産の更新と共有](../architecture/data.md#資産の更新と共有)、記載内容は [`assets/principles/writing.md` の原則1](../../assets/principles/writing.md#1-put-conclusions-and-information-needed-for-human-decisions-first)に従う。

設計案には供給されたテンプレートを適用し、元に戻せないもの(変更困難な決定)は[計画の一覧](../architecture/data.md#計画-plan)に従う。

## 保証

形式と意味論の境界、および供給された定義の扱いは [form の契約](../architecture/modules.md#form)、ファイルの読み書きの制約は[モジュールごとの契約](../architecture/modules.md#モジュールごとの契約)に従う。

計画の検証との責務の境界は [plan の契約](../architecture/modules.md#plan)(計画の意味論を扱う実装)に従う。
