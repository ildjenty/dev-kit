# dev-kit の設計

人は重要なことだけを決め、コードの変更は一か所に収まり、進め方は失敗から改善される。dev-kit は、この三つを支える開発キットである。Archon がワークフローと AI セッションを動かし、Go バイナリの `devkit` が開始条件、機械検査、記録、コミットを担当する。対象リポジトリごとのコマンドや規約は、設定と規範に置く。各ワークフローのノードと流れは [ワークフローの図](workflows.md) にある。

## 人に判断を戻す場所

まだ定まっていない依頼は、`devkit-discuss` の会話から始める。これは呼び出しから、決まった部分が作業単位の Issue、未決の問いがトピックの Issue になるまで続くモードである。人が会話を主導し、一度に一つの質問を扱い、聞いたことを言い直して確かめる。選択があるときだけ候補と推奨理由を示し、人の言葉と提案を分ける。`devkit decisions list` で判断ログを読み、矛盾があれば既存の判断 ID を示して覆すかを尋ねる。会話中にリポジトリのファイルは編集しない。

人が開始したい単位を示したら、その単位の blocked-by を読み、単位を止めているトピックを選ぶ。トピック内でも、そこで待っている単位に必要なことだけを質問する。本文に列挙された点は質問の候補であり、すべて答えるためのチェックリストではない。どの単位も止めていない点はメモの「未決のこと」に残し、refine が何もブロックしないトピックに分け、必要な作業が生じたときに決める。

会話には「所有者が決めたこと」「覆ったこと（判断 ID を含む）」「AI の提案」「未決のこと」を分けたメモを置き、合意や変更のたびに更新する。所有者の判断は原文、またはメモ上で本人が確認した表現のまま、題名・判断本文・元の発言を保持する。選んだトピック番号と進行中の refine ブランチ・質問・提案版も残し、要約後も引き継ぐ。別の依頼が入れば対応後にメモを再掲し、元の議論へ戻る。引き継ぐときは所有者の判断を言い換えず JSON ファイルに書き、確認済みメモとともに `refine` へ渡す。単位・トピック・暫定判断・拘束変更が必要な場合だけ AI の追加を依頼し、その起動、質問の取り次ぎ、追加分の承認もモード内で行う。メモの確認は AI の追加分への承認ではない。作成された Issue を確認し、議論の全体が Issue に収まったところでモードを終える。所有者の判断の記録だけを依頼した場合は、その PR の公開で終える。

`refine` の `owner_decisions` は JSON 配列で、各項目に `title`、`body`、元の発言である `owner_words` を必須とし、既存判断 ID の配列 `supersedes` と `depends_on` を任意で持つ。セッションはチェックアウト外のファイルから file-input パターンで渡す。未知のキー、不正型、空白だけの必須文、重複項目・参照、不正な ID、存在しない依存・置換元を拒否する。従来の `memo` と `owner_words` は文脈として残す。prepare は題名と本文をそのまま agreed・decided_by: owner の判断記録にし、固定の front matter と出典行だけを加える。`provenance: owner` と入力から求める識別子を持ち、同じブランチでの再実行では同じ入力の記録を再利用する。置き換え元は superseded にし、本文や出典は保持する。執筆者の起動前に refine ブランチへコミットする。

`ai` は `additions`（既定）または `none` とする。`ai=none` は空でない `owner_decisions` を必要とする明示信号で、メモや未決点から推測しない。prepare 後に writer・judge・承認をすべて飛ばし、所有者の判断記録を PR として公開して pass で終える。PR 題名は件数入りの固定文、概要は固定文と所有者が与えた題名の全件列挙とし、題名を短縮・翻訳しない。定型文は日本語と英語を用意し、ほかの言語は英語へ代替する。Issue の作成・変更は行わない。未承認の AI 提案が同じブランチにあれば公開せず、その提案の完了か新しい refine ブランチを求める。公開の再実行は記録と PR を再利用する。

AI 追加分が必要な `refine` は一回に一つのトピックを、`decide` だけの最大3ラウンドで扱う。`topic` は open かつ設定した topic ラベルを持つ GitHub Issue の番号で、省略時は依頼から親トピックの下書きを保持する。執筆者と fresh な読み取り専用の判定者は、依頼・補足・確認済みメモ・回答、既存の判断ログ全体、固定した基準を読む。所有者の判断は `fixed_owner_decisions` として固定入力にし、書き換え・再決定・審査・承認の対象にしない。superseded の記録は過去の判断として扱う。下書きの `decisions` は所有者が決めていない AI の暫定判断だけとし、`decided_by: provisional`、`source: derived` に限る。ほかにエージェントを拘束する変更の `bindings`、作業単位の `units`、未決の問いの `topics` と `summary` を持つ。単位には1 PR に収まる目標と観測可能な完了条件を含める。依存を表す `blocked_by` は同じ提案の Issue キーを参照する。決まった作業と別の未決トピックは共存できる。

拘束する変更は、エージェントの作業方法（工程、ツール、規約、検証）についての判断に限り、判断キーまたは ID と理由を対応させる。コマンド、またはファイル・設定の事実で適否を決められる規則は、機械判定可能とする。その規則を規範、CLAUDE.md・AGENTS.md、スキルに文章の指示として書かない。コマンドがあれば `.devkit/config.json` の checks に名前、コマンド、タイムアウト、適用パスを登録する。まだなければ、それを作る単位の `completion_conditions` に作成とチェック登録を含める。例えば基盤単位は「型検査と自動テストを `.devkit/config.json` の checks に登録し、テストはローカル PostgreSQL のみを使い、外部認証情報やネットワークなしで実行できる」を完了条件にする。文章による拘束変更は判断を要する作業方法の規則だけとし、設定のほかの項目は変更しない。

製品のデータ形状、不変条件、機能が守る規則は拘束変更に書かず、実装する単位の `completion_conditions` にテストで確認できる条件として書く。例えば「同じ人への重複するシフトの割当は拒否される」とする。複数単位に共通する性質は最初に実装する単位（基盤の単位など）に置き、後でその性質に触れる単位にも維持すべき条件を繰り返す。実装後はコードとテストが製品仕様を担う。

機械検査はスキーマ、判断と Issue の依存、引用、判断ファイルの直接編集、変更範囲、config、concerns を検査し、AI の暫定判断だけを proposed として生成して拘束する変更と同じ提案コミットにする。機械は AI 追加分だけの審査材料を refine/review.json に出し、所有者の判断 ID を審査対象から除く。独立した判定者は、追加分のコミットと Issue 下書きの意味・表現、所有者の判断との矛盾や再決定がないこと、拘束手段の適切さ、規範やハーネス変更の根拠と負担を判定する。各拘束変更が作業方法についてであることと、製品が守る性質が該当する単位のテスト可能な完了条件に揃っていることも確認する。製品ルールを拘束変更に書いた場合や完了条件が欠ける場合は blocking とする。通らなければ修正し、3ラウンドで通らなければ停止する。変更依頼は次版のコミットとし、履歴を書き換えない。

checks を編集する拘束変更は、設定検証後、提案の元のコミットに対して追加・変更されたチェックを基点ブランチの一時 worktree で実行する。optimize と同じ実装を使い、postCreate で準備し、パス選択にかかわらず実行する。失敗・未実行・準備不能は下書きを不合格にし、ログと `refine/verification.json`・ラウンド別の検証結果を残す。一時 worktree は削除する。refine・retro・optimize の判定者は、機械判定可能な規則を文章の拘束変更にした場合も blocking とする。

未決の問いのグループ化も独立判定者が確認する。異なる単位を止める問いの混在、単位を止めるトピックへのその単位が必要としない問いの混入、単位の下書きに残った未決の問い、トピックが止めると明記した単位と blocked-by の不一致は blocking とする。

下書きには `pr_title` と `pr_summary` を必須で持たせる。執筆者は設定の `language` で、PR の読者に向けた100文字以下・一行の題名と、マージによって基点へ届く内容とその理由を数文で書く。独立判定者が意味・表現・言語を確認し、機械は必須項目、空白だけでないこと、題名の文字数と一行であることを検査する。両項目は詳細に原文のまま保存する。ai=none の機械による定型文は前述の例外とし、AI 追加分では機械は提案の要約や承認質問を PR 用の文章として流用せず、題名や要約を短縮・代筆しない。

AI 追加分の判定を通った版は、追加分だけの短い承認質問を一つ返して終了する。所有者の判断は既に agreed であり、質問に再掲しない。質問は次の四つだけを含む。

1. 確認済みメモと人の原文を超えて執筆者が追加・導出した選択や規則。暫定判断、エージェント向けの導出規則、選んだ既定値を含め、各項目をキー付きの1〜2行で推奨と理由とともに示す。
2. 人が受け入れる必要のあるリスク。国外への個人データ保存、復旧可能期間が6時間だけであることなどを、各項目キー付きの1〜2行で示す。
3. 残りは確認済みメモと人の原文に従う旨と、詳細を読む `devkit proposal show <branch>` を一行で示す。
4. `approve=<version>`、または変更するキーを名指しする `answers` での回答方法。版はこの回答行だけに置く。

履歴、出典の全件一覧、コミット・mapping などの機械項目、JSON、判断の全文、拘束変更・Issue の全件一覧、判断不要な情報は質問に載せない。費用見積もりなどの事実は詳細に置く。下書きには判断全文、拘束パスと対応判断、親・blocked-by を含む Issue 下書き、PR 題名・概要をすべて残す。機械はこれらと版・コミットを含む提案全文を、ブランチの実行記録フォルダーの `proposals/<version>.details.json` に保存する。`devkit proposal show <branch>` は最新提案の詳細ファイルを表示し、`devkit status` と同じ方法で state を探す。判定者はメモ外の項目と受け入れるリスクの漏れを blocking、メモで決まったことの反復や不要な情報を削る指摘を nonblocking とする。`devkit-runs`・`devkit-discuss`・`devkit-optimize` は質問をそのまま取り次ぎ、詳細を求められたらこのコマンドの出力を示す。

`approve=<version>` は従来どおり最新の承認質問、開始済み run、記録済み承認回答、clean な HEAD と照合する。承認すると AI の暫定判断だけを agreed、置き換え元を superseded にするコミットの後、ブランチを push し、承認済みの `pr_title` と `pr_summary` で PR を作成または更新してから Issue を作る。親の指定がなければ topic Issue を作り、単位はその sub-issue、残る問いは新しい topic Issue とする。blocked-by を接続し、新しいトピックがなければ親をコメント付きで閉じ、あれば閉じずにコメントする。コメントには判断 ID と作成 Issue を列挙する。Issue 作成後、PR 本文の Issue 一覧を更新する。結果の `decision_ids`、`issue_numbers`、`pr_number`、`pr_url` を人に伝える。`decision_ids` は所有者の記録と承認した AI の記録を含み、`issue_numbers` には親トピックも含む。承認の再試行では所有者の記録を追加・変更しない。

人が refine の PR をマージして基点へ届ける。作業単位は、その PR のマージと blocked-by の条件を満たしてから開始できる。単位ごとにブランチを作る。

PR 本文の冒頭は承認済み（ai=none では機械が構成した）`pr_summary` をそのまま使い、続く一覧は承認済みの事実から機械が組み立てる。「レビュー対象」には拘束する変更の各パス、対応する判断 ID・題名と理由を載せる。「判断ログ」には所有者の記録と AI の記録の ID、題名、提案ブランチ上のファイルへのリンクと、人のための記録であり開発作業を拘束しない旨を載せる。「作成した Issue」には親トピック、作業単位、未決トピックの題名とリンク、blocked-by の参照先リンク、作業単位が PR マージ後に依存条件を満たすと開始可能になる旨を載せる。空の一覧は省略する。

見出しと説明の定型文は `language` に従い、日本語（`ja` とその地域指定）と英語を用意する。他の言語では定型文のみ英語を使い、執筆済みの題名・要約・理由は翻訳しない。英語の見出しは `What to review`、`Decision records`、`Issues created` とする。ブランチ上のファイルへの絶対リンクには、初回は `gh repo view --json url --jq .url` の URL、更新時は記録済みの PR URL のリポジトリ部分を使い、ブランチ名とパスを URL エンコードする。承認質問、提案の版、内部の失敗・変更履歴は本文へ転記しない。

refine・retro とも、PR 用の題名・要約を持たない旧提案の承認は、新提案での承認を求めて拒否する。承認 run の開始時と承認実行時に検査し、合意コミット、push、PR・Issue の書込みより前に止める。題名が100文字を超える場合や複数行の場合も再提案を求める。既存の承認・コミット照合や Issue 作成の再開記録は保持し、再実行でも既存 PR の題名と本文を現在承認された内容で更新する。

```text
devkit-discuss モード（壁打ち → refine → 承認 → Issue 化）→ refine PR のマージ
  → 単位ごとに requirements（issue=<number>）→ plan → implement → judge ⇄ fix → pr
  → 必要に応じて sync → needs_judge なら judge → pr
  → retro → 承認 → 改善 PR のマージ
```

`requirements` は依頼の未決点を、`plan` は人に残された設計判断を質問する。`implement`、`judge`、`fix` が新たな判断の必要に気づいた場合は、`back` で `plan` に戻し、そこで質問する。`pr` が尋ねるのは、設定の `ask` に該当し、既存の `decided_by: owner` の行の `touches` では覆われていない変更だけである。要件のないブランチの `judge` は報告だけを行い、`back` を返さない。判断や計画が必要なら、変更を説明して `requirements` から始めるよう `stop` で示す。`retro` も改善案を承認質問として返す。マージするかどうかは人が決める。

承認に伴う Issue 作成は、ブランチの実行記録の `issue-creation/<version>.json` に、初回承認 run ID、コミット、親、下書きキーと作成 Issue、完了した親子・blocked-by 接続とコメントを逐次保存する。refine のコミットは合意後、retro は提案コミットである。同じ承認を再実行すると記録済みの作成・接続を飛ばし、不足分から再開する。別 run でも元の承認回答を照合し、通常の再開始上限を適用する。

作成する Issue の本文末尾には、コミット・提案版の記録ファイル名・親か通常の下書きか・下書きキーから作った SHA-256 の識別子を `<!-- devkit:draft <識別子> -->` として付ける。作成済み Issue が記録になければ、open・closed の全ページを読み、PR を除外してラベルとマーカーが一致するものを採用する。一覧取得に失敗すれば新規作成へ進まない。応答の喪失やローカル保存失敗後も同じ承認の再実行で採用でき、closed の Issue は再作成・再オープンしない。関連付けは既存の接続を許容して不足分を補う。自動の作成リトライ、同時作成の排他、親コメントの重複抑止は行わず、マーカーのない旧 Issue は照合できない。

## 品質の担当を一つにする

品質の種類は `structure`、`data`、`contract`、`security`、`ui`、`cost`、`test`、`delivery`、`scope`、`readability`、`document` の十一個に固定する。コードでの定義は `internal/concerns` に集め、設定検証とスキーマの品質列挙をそこから導出し、テストで整合を確認する。

リポジトリが所有する `<standards>/concerns.json` は、それぞれの品質が何を決めるか、どの原則を担当するか、計画時と実装後にどの基準を読むかを結び付ける。計画時にすべての品質へ適用する原則は `every_quality`、品質以外の判定者や執筆者が担当するものは `others` に置く。

番号付き原則は必ず一度だけ割り当てる。共通の `every_quality` への割り当ても一回と数える。参照する文書は存在し、`review/README.md` を除くレビュー文書はすべてマップから参照されなければならない。`devkit concerns check` が検査し、`plan`、`judge`、`refine`、`retro` の準備でも、固定した基準のコピーに対して実行する。実在する材料の消費者だけを担当として認め、レビュー文書中の `<文書>#<番号>` 参照もその担当の原則に限る。違反があれば判定を始めない。

品質ごとの基準は `review/<quality>.md` の一つにまとめる。`Decisions` は判断行とスケルトンで決まること、`Code` は関数本体で決まることと判断への適合を扱い、`Blocking` と `Not reported` が指摘の境界を定める。計画で合格した選択を実装後に選び直さず、その選択どおりに動くかを調べる。リリース単位とテスト計画の網羅性は `delivery`、依頼と他の用途への適合は `scope`、名前やコメント、既存の書き方と、同時に変更すべき規則・振る舞いの重複は `readability` が担当する。

`devkit judge launch` は、返す `launch_<quality>` フラグと同じ起動判断から `$ARTIFACTS_DIR/judge/launched.json` に `{"launched": [品質名]}` を保存する。`devkit eval judge` も同じ起動処理で保存する。コード品質判定者はこの一覧と固定した `concerns.json` の原則の担当を読み、自品質の原則の失敗、または担当品質が起動していない失敗だけを自品質の指摘として報告する。担当が起動済みなら、その失敗は担当判定者に任せる。ただし、欠陥そのものを別品質が報告しても、その結果として必要なテストがないことは `test`、呼び出し元との契約が変わることは `contract` の失敗として、それぞれ報告する。

`designing.md#1` は `every_quality` に保持し、requirements・plan・implement・fix の材料へ渡す。`judge` と `devkit eval judge` のコード判定者には `every_quality` を渡さず、適用も求めない。コード時の判断漏れは、`decision_paths` に該当する変更が計画行に含まれないことを機械が検査し、`scope` が `working.md#6` で依頼と権限の範囲を判定する。

`data.md#1` は事実の正本と複製の同期を扱い、同時に変更すべき処理の定義共有は `engineering.md#8` として `readability` に割り当てる。追加された関数・変換・検査・規則ごとに、`judge/target.json` の `tree` が指す判定ツリー全体から同じ処理の既存定義を探す。同時に変わる必要がある規則や振る舞いを追加コードが再実装していれば blocking とする。文字列の類似だけでは共通化を求めず、変更理由や契約が異なる処理は独立させる。`designing.md#2` の早すぎる抽象化を避ける方針を保ち、配置・依存の判断は `structure` に残す。

共有か独立かの基準は `engineering.md#8` に集め、`designing.md#2` と既存 utility と同じ役割の helper 追加はそこを参照する。`data.md#4` はドメイン規則を散在する分岐で表す問題、構造の smells の「Changes spread」は境界や配置による変更の波及を扱い、規則の再実装は原則8へ委ねる。構造の原則と重なる兆候は原則側に置き、smells は原則番号を参照する。

構造だけでは表せない設計理由は、規範 README の原則衝突時の扱いに従い、計画の証拠やリポジトリの文書に記録して必要な場所から参照する。コードコメントでは補わない。原則の blocking が証拠への記載を問う場合、計画時は記載の有無を確認し、コード時はその記載と実装の一致も確認する。

文書を成果物とする依頼も通常の delivery で進める。`document` は README、ガイド、仕様書、設計文書など配達する文書を実装後に判定し、計画段階の判定者は持たない。`writing.md` の原則2・3・4・5・6・8・9を所有し、読者の前提、会話に依存しない説明、具体的な操作、必要な構造、正本と更新責任、現在と履歴、図、開示範囲を `review/document.md` で扱う。原則1は PR 本文、原則7は refine の提案承認が担当する。既定の起動パスは `**/*.md`、`docs/**`、`!.devkit/**`、`!.archon/**` で、先頭 `!` の除外が正のパターンより優先し、指定順には依存しない。

失敗シナリオ、停止条件、未評価、データと指示の区別などの共通判定規則は `review/README.md` に、人が決める範囲は `authority.md` に置く。プロンプトはそれらを参照し、入力、書き込み先、出力形式を指定する。執筆者と判定者に渡す材料は同じマップから作る。基準は依頼の開始時に基点ブランチのコミットへ固定し、その後の修正や同期でも同じコピーを使う。

基準のコピー元フォルダーは、固定コミットの `.devkit/config.json` にある `standards` から選ぶ。そのコミットに設定ファイルがなければ既定の `.devkit/standards` を使う。コピー済みの基準は `criteria/source.json` の `base` と `paths` を保持して再利用する。requirements・plan・implement・judge・fix・refine・retro・pr・sync は `internal/criteria` の同じコピー処理が返すパスで関心マップと材料を読み、基準フォルダーの移動後も固定した内容を使う。判定対象や入力に記録する基準のパスもこのコピー元情報に合わせる。現在の言語設定やチェック選択、refine・retro の編集先フォルダーは従来どおり適用する。`devkit eval judge` は依頼の固定コミットを持たず、後述の規範の選択順を使う。retro の評価検証も提案した規範を使う。

## 判断のログと作業の依存を分ける

リポジトリの判断は `<decisions>/D-<id>.md` に一件ずつ保存する。本文に背景、候補、選択、理由、不確実性を残し、フロントマターで状態、判断者、依存、置き換え元、依頼ブランチを表す。合意済みの判断を変える場合は、新しい判断から `supersedes` で参照する。人と devkit-discuss・refine が読むログであり、requirements・plan・implement・judge・fix・pr・sync の入力、引用元、制約、開始検査には使わない。作業方法を拘束する内容は人が確認する規範・指示・スキル・チェックに置き、製品が守る性質は単位 Issue のテスト可能な完了条件を経てコードとテストに置く。

判断 ID はブランチとドラフトのキーから作る小文字の16進数に `D-` を付け、最初は6桁、衝突すれば延ばす。再提案でも保持したキーの ID は維持し、撤回した未承認判断ファイルは削除する。refine は保存予定の最終集合に対して依存・引用・循環を検査してから書き換える。`devkit decisions` の list・check・affected・dependents が扱うのは判断ファイルだけで、文書の引用や Issue の状態は扱わない。

作業単位と未決のトピックは GitHub Issues に置き、既定のラベルは `devkit:unit` と `devkit:topic` とする。トピックから切り出した単位はその sub-issue にし、単位の順序と他のトピック待ちは blocked-by で表す。単位の作業内容には目標、観測可能な完了条件、維持すべき製品の性質だけを置き、未決の問いは置かない。トピックは問いと答えが定まる条件を本文に持ち、delivery に必要な内容を判断ログなしで読めるようにする。この単位の規則は retro の下書きにも適用し、未決の問いがあれば判定者は blocking とする。

同じ作業単位を同じ時点で止め、切り離して決められない問いを一つのトピックにまとめる。例えば技術スタック、ホスティング、月額費用の上限はいずれも基盤単位を止め、費用上限がホスティングの選択を左右するので同じトピックにする。止める単位が異なる問いや切り離して決められる問いは別のトピックにする。どの単位も止めない問いも、単位を止めるトピックから分け、何もブロックしないトピックとして必要になるまで残す。単位を止めない問い同士はテーマが近ければまとめられる。例えば契約の署名者とアカウントの管理者は「契約・運用体制」にまとめる。一問一 Issue にはせず、この規則でグループ化して Issue 数を抑える。各トピックの下書き本文には止める単位のキー、または止める単位がないことを明記する。待つ単位の `blocked_by` にそのトピックのキーを入れ、止める単位がないトピックからはどの単位も待たせない。

`devkit issues ready [--json]` は、open かつすべての blocker が closed の単位とトピックを示す。ラベルのない blocker や後続ページの blocker も検査し、親トピックが closed であることは要求しない。テキストは単位、トピックの順で、JSON は `units` と `topics` の配列を持ち、各要素に `number`、`title`、`url`、`parent` を返す。`devkit issues show <number> [--json]` は本文、状態、ラベルと親・sub-issue・blocked-by・blocking の関係を示す。JSON の関係は `sub_issues`、`blocked_by`、`blocking`、空配列は `[]`、親なしは `null`、状態は `open` または `closed` とする。

`requirements` は `issue=<number>` を受け取り、開始時と prepare 時に Issue の存在、open、unit ラベル、blocker の全件 closed を確認する。満たさなければ Issue と該当する blocker を示して開始を拒否する。Issue と親トピックの題名・本文は依頼データとして執筆者と判定者へ渡し、末尾の devkit マーカーと機械追加の空行だけを取り除く。単位を経由しない依頼には `owner_words` を使い、セッションの調査結果は `supplement` に分ける。

`requirements prepare` は準備ごとの識別子、run ID、読んだ依頼件数を入力へ保存し、`round` は同じ値をドラフト・判定とともに保存する。`finish` は現在の入力・run・依頼境界との対応を保存前に検証する。prepare のやり直し、別 run、prepare 後の依頼追加では旧 round を拒否し、要件・判定・結果・質問および成果物を変更しない。prepare と round をやり直してから完了する。束縛情報がない旧成果物も同じ手順で作り直す。

`requirements round` が初回として扱うのは `requirements/rounds/latest.json` の不在だけである。索引の読込・JSON 解析に失敗した場合は履歴を変更せずエラーを返す。番号付き履歴は排他的に作成し、同じ番号を上書きしない。履歴保存後の索引更新に失敗した場合、保存した履歴は保持され、同じ番号への再保存は拒否される。索引が欠落・古い状態でも、既存履歴を自動的に上書きして復旧しない。

計画の判断行は delivery の実行記録に残す。`provisional` は計画と PR 本文に示す。計画の合格時に判断ログを生成せず、要件版と内容に結び付いた owner 回答を検証して計画を保存する。

質問への回答は、質問時の要件版と行の内容ハッシュに結び付ける。同じ行 ID でも内容が変われば、古い回答は適用しない。構造承認は構造段階のスケルトン内容に結び付け、owner 行の `touches` が覆う構造変更はその行で一度だけ尋ねる。実装中に許される計画更新は、暫定行の追加と、後で決める行を暫定選択で確定することに限る。合格済み計画を `derived_from` に記録した派生版として保存し、次の開始条件でも受け付ける。それ以外の変更は計画へ戻す。

## 構造を先に決め、変更の広がりを調べる

`plan` は構造と詳細を別のループで進める。構造では配置、責務、依存方向、境界の判断行とスケルトンだけを書く。新しい構造行の `nature` には、種類、誰が何のために変えるか、変わりやすさ、呼び出し元を、パスや依頼文、呼び出し関係の証拠とともに書く。分からない項目は `unknown` にする。機械検査と構造判定が通ってから詳細に進む。

詳細では他の品質の行、リリース単位、テスト計画を書く。シグネチャは直せるが、構造段階で確定したファイルの追加、削除、移動や構造行の変更はできない。実際に変更すれば `stop` で変更点を示し、`plan` を始め直す。`uncertain` は判定済み構造に必要な変更に限定し、完了条件と検証箇所を伴う根拠を示す。一般的な疑問や構造内で修正できる詳細は含めない。非空なら詳細を合格にせず、既存の構造質問に原文を添えて所有者へ渡し、次の plan を構造段階から開始する。各ループは最大3回であり、合格には同じ実行の有効な構造段階と詳細段階の完了が必要になる。事実は判断行の `evidence` に機械または執筆者という出典と確認先を記録する。

`plan check` は、スケルトンをコミットしてから `skeleton_check` を実行する。チェック後に HEAD・作業ツリー・インデックスに変更があるか、未追跡ファイルが残っていれば、そのラウンドを無効とし、品質判定の材料を生成しない。変更後の内容で `plan check` を再実行し、判定し直す。`plan finish` も合格の保存前に判定対象コミットと現在の HEAD・作業ツリー・インデックスの一致と未追跡ファイルの不在を検査し、不一致なら計画・判定・結果の履歴を保存する前に拒否する。

`implement` ではリリース単位ごとに別セッションがテストとコードを書く。設定したチェックを通して単位をコミットし、同じチェックが続けて失敗すると、独立した step-back 判定者が崩れた前提と戻り先を示す。実装執筆者の非空 `uncertain` も、チェックの合否にかかわらず、コミット前に同じ判定者へ原文を渡す。`implement` の判定なら通常のチェック条件に従って続行し、`requirements`・`plan` なら当該単位をコミットせず診断とともに戻す。`environment` は停止し、空配列では追加の AI 判定を行わない。

`devkit checks` は、不合格のチェックだけを基点ブランチとの merge base の一時 detached worktree でも実行する。コマンド、タイムアウト、終了コードの扱いは同じで、合格済みチェックと環境エラーは比較しない。現在のリポジトリの `.archon/config.yaml` に `worktree.postCreate` があれば順番に実行し、各コマンドには `postCreateTimeout` ミリ秒（既定300000）を適用する。準備失敗は変更の不合格にせず比較不能とし、一時 worktree は削除する。不合格結果には `base: failed|passed|unavailable`、比較した場合は `base_log` を保存し、ゲートは両方で落ちる `preexisting` と基点では通る `regressed` を返す。`--no-base` は比較を省略し、スケルトン検査もこの扱いにする。`implement` と `fix` は `--base-on-repeat` で呼び、前のパスでも落ちていたチェックだけを比べる。実装中は最初に落ちるのが普通なので、その分の準備と再実行の費用をかけない。`judge` と `sync` は落ちたチェックをすべて比べる。比べなかったチェックは `base: not_compared` になる。

`implement` と `fix` は、そのパスの全不合格が `preexisting` なら即座に停止する。stuck や step-back 判定に進めず、そのパスは回数に加えない。`judge` は基点でも落ちるチェックを判定に明記し、一つでもあれば `fix` へ送らず同じ理由で停止する。停止には `base_failed: true` を記録し、ループの終了理由は `base_failed` にする。人には不合格チェックとログの場所を伝え、基点ブランチを先に直してから同じワークフローを再開始するよう案内する。その再開始は `retry_after_base` として `limits.restarts` に加算せず、既に上限でも許可する。`devkit status` の `next` と `devkit-runs` もこの案内を行う。基点を直す前に再試行しても解決しない。回帰と比較不能については、implement/fix の従来の失敗処理を維持する。

`judge` はコミットした差分を読み、設定パス、計画行、`devkit judge route` の Jev または代替の設定プロバイダー CLI による選択を合わせて品質判定者を起動する。`scope` は毎回、ソースやテストが変われば `test` と `readability` も動く。パスの指定だけで品質の変更を見落とすことを防ぐ。`devkit judge route` は固定した関心マップの `routing`(その品質に関わる変更の具体的な説明)を質問にし、ファイルごとの差分を TypeSafe API に送る。品質ごとの `routing_threshold` 以上の確率になった品質を選ぶ。既存品質の閾値は見落としたくない変更を見落とさない値を測って決めた。追加した `document` の 0.6 は未実測の指定値であり、リポジトリが関心マップで調整できる。ソース・テストの質問は確率 0.3 以上で `test` と `readability` を選ぶ。差分は行の境界で最大 8 KiB に分割し、送信 JSON も 24 KiB 以下に収め、同時実行は最大 4 件とする。各リクエストは 10 秒でタイムアウトし、タイムアウト・429・5xx のみ 100 ms 後に 1 回再試行する。1 件でも失敗、または回答が不正なら部分選択を破棄し、設定した provider の読み取り専用 CLI に切り替える。両方が利用できない場合は、見落としを避けるため、変更された各ファイルに対してコード判定可能な全品質を選び、理由に両失敗を記録する。出力の `source` は `jev`・`claude`・`codex`・`all` のいずれかになる。全確率は `judge/route-jev.json` に残す。`launch` はこの単一の出力を読む。任意の環境変数 `TYPESAFE_API_KEY` を設定した場合だけ送信し、キー未設定なら TypeSafe には何も送らない。キーは環境変数以外から読まず、記録にも出さない。代替経路には設定した provider の認証済み CLI を必要とする。

`structure` の routing はモジュール配置だけでなく、関数内の責務分割、繰り返す検査、保証の迂回、呼び出し順や状態の前提、振る舞いを切り替える引数、複数層を通る値も含む。`data` は保存データだけでなく、有効な状態や値を決める型・フィールド、複数箇所の分岐で表したドメイン規則も含む。差分だけでは分からない既存処理の再実装は、ソース変更で必ず起動する `readability` が判定ツリー全体を検索して調べる。

Jev の HTTP クライアントは `internal/jev` に置き、judge のルーティングだけに使う。`judge/route-jev.json` の保存失敗はパスと原因を返してルーティングを停止する。Jev が利用できない場合も監査用成果物の保存は必須であり、保存の失敗を別の選択経路で隠さない。

judge の target に `plan_version` があれば、changes・launch・completion・finish は同じ版の `judge/plan.json` を必須とする。欠落や版の不一致は prepare のやり直しを求める。初めから計画のない独立レビューだけは不在を認める。ゲートが checks 結果のパスを持つ場合も、判定・結果の保存前に読めることを必須とし、読める空の JSONL はチェック0件として扱う。

判定対象コミットの全ツリーは `$STATE_DIR/trees/<符号化したブランチ名>/` にブランチごとに一つ保持する。記録フォルダー内には置かない。`judge/target.json` と品質ごとの材料の `tree` に絶対パスを渡す。判定者は同時実行するチェックが変更し得るチェックアウトを使わず、このツリーを Read・Grep・Glob で読む。Claude の読み取りツールにはパスを限定せず、Codex のノードも状態フォルダーを読める。

初回は全量を export し、その後は保持コミットから判定対象への `git diff --name-status -z --no-renames` の差分だけを反映する。追加・変更ファイルは Git の blob からバイトを保持して書き、実行権限とシンボリックリンクも全量 export と同じにする。削除と空になったフォルダーを先に除去し、ファイルとフォルダーの相互置換も扱う。保持コミットのマーカーは、リポジトリ内のファイル名と衝突しない `$STATE_DIR/trees/.commits/<符号化したブランチ名>` に置く。更新前にマーカーを除去し、完了後に最後に書く。マーカーがない場合、記録したコミットが存在しない場合、差分更新中に失敗した場合はツリーを削除して全量を export し直す。prepare は `git show-ref --verify refs/heads/<ブランチ名>` が失敗するツリーも削除する。判定中のブランチは削除しない。`archon complete` やブランチ削除の後、次の prepare で領域が解放される。変更ファイルの基点版もバイトを保持して渡し、起動した判定の必須基準が欠ければ未評価にする。

機械は、どの判断行の `touches` にも入らない変更ファイルを `outside_plan` として示し、変更先のトップレベルと第2階層のフォルダー数、祖先の各階層の構成も構造判定へ渡す。新しい項目の受け入れ先と祖先上の構造欠陥は、既存でも停止対象になる。それ以外で見つかった欠陥は `deferred` とし、今回を止めずバックログへ送る。`deferred` は構造品質だけで認め、停止やowner判断のフラグと矛盾する出力は未評価にする。

## 指摘から仕組みを直す

`fix` は停止対象の指摘を修正する。誤った指摘には証拠付きで異議を出し、指摘にも修正にも関わっていない判定者が判断する。指摘の参照は `<judge-run>/<judge>/<finding-id>` とし、別の判定で同じローカル ID が使われても、以前の異議採用では消えない。

`fix objections` は、存在する `objections.json` の読込・JSON 解析・形状の検証に失敗した場合、ファイルを消費済みへ移動せず、ラウンド状態を保存せずにパスと原因を返す。オブジェクトには `objections` 配列が必須で、各要素は文字列の `finding` と `evidence` を持つ。ファイル不在または正常な空の異議配列は、異議0件として扱う。

implement・fix は、空・複数行・固定した `git.md` の prefix に合わない `CODE.commit_message` を拒否し、執筆者に書き直しを求める。implement は単位・完了条件の ID を含む題名も拒否する。機械は代わりの本文を作文せず、出典の trailer だけを加える。

PR 作成後のコメントや CI 失敗は、出典を含む原文を `review` 入力として同じブランチの `fix` に渡す。例は `Review comment by <login> on path:line: ...`、`CI job <name> failed: <log excerpt>` である。入力は開始に成功した run の `review.text` と `review.commit` に保存し、その fix の指摘は `source: review` とする。開始には合格した要件・計画と、有効な最新 judge の判定済み変更が HEAD と同一であることが必要で、blocking 指摘は要求しない。PR と同じ変更同一性を使うため、backlog だけのコミット後も開始できる。`review` のない fix の開始条件は従来どおりである。

レビューが要件・計画の範囲を超える場合と、執筆者が指摘に異議を持つ場合は、実装せず `outside_requirements` に `item` と `reason` を出す。異議の判定者には渡さず、その項目と理由を `premise`、レビュー原文を `observation` にした `back` で `requirements` に戻す。セッションは同じブランチで requirements を開始し、所有者がそこで決める。検査・回数上限・既存の step-back は維持し、この差し戻しでは修正コミットを作らない。合格した review fix は変更同一性が変わらなくても再度 judge が必要で、その後 pr が既存 PR を更新する。

依頼自体を追加・変更するコメントは、同じブランチの requirements に `owner_words` として渡し、通常の工程を進める。`devkit-runs` は `gh pr view <branch> --comments` と `gh pr checks <branch>`、実際のインラインコメント・失敗ログの読み取り、この振り分けを案内する。CI 失敗時には `devkit-optimize` でそのジョブを設定済み検査へ追加することを提案する。レビュー担当者の代わりに返信・解決済み化をせず、マージ後は `archon complete <branch>` で worktree とローカルブランチを削除し、リモートは保持する。定期的に `archon isolation cleanup --merged` も使う。

PR 本文の判定は、コードの commit・要件版・計画版とは別に、`pr-title.txt` と `pr.md` の全バイト列を SHA-256 で識別する。report judgment の `materials` に、既存の参照パスに加えて `pr/pr-title.txt#sha256=<64桁の16進数>` と `pr/pr.md#sha256=<64桁の16進数>` を記録する。コード差分の `target.change_id` は本文の識別に使わない。

`pr assemble` は既存の report state の合格状態を、ファイルを書き換える前に無効化する。内容が同一でも、再生成後は再判定が必要であり、ラウンド番号は引き継ぐ。`pr open` は既存の HEAD・clean・最新 report judgment の検査に加えて、合格状態とタイトル・本文の内容識別子を照合する。不一致、ファイル欠落、合格状態や内容識別子の欠落は、backlog コミット・push・gh 呼出しの前に拒否する。内容識別子を持たない旧 report judgment も再判定が必要になる。公開では照合済みのタイトルと本文を保持し、本文を `gh pr create/edit --body-file -` の標準入力へ渡すため、照合後の元ファイルの変更は公開内容に混入しない。

`pr` は本文の判定後、push の前に `.devkit/backlog/<エンコードしたブランチ>.json` をコミットする。保留した指摘、計画から持ち越した指摘、機械検査の候補になる指摘、採用した異議を、それぞれ元の判定への参照と保存する。review 入力は次の pr で任意の `review` 配列に保存する。各要素は原文の指摘と、`kind: review`、修正 run の `run_id`、`target.commit` を持つ出典であり、判定番号を捏造しない。既存4配列は必須のままで、retro は review 配列も読み取る。Issue のある依頼では本文末尾に `Closes #<number>` を付け、本文判定とハッシュの対象に含める。PR がマージされて Issue が閉じると単位は完了となり、`devkit issues ready` で次の作業を選ぶ。

backlog の保存先と checkout 内の祖先にシンボリックリンクがある場合、PR 公開を拒否する。保存は checkout を起点とする `os.Root` 内で通常ファイルを排他作成し、書込みと close の成功後に rename して確定する。祖先リンクの検査後の差し替えによる checkout 外へのパス解決は `os.Root` で防ぎ、既存宛先のリンク先やハードリンク元には直接書き込まない。保存に失敗した場合、backlog の commit、push、gh 呼出しには進まない。

計画・refine・retro の全ラウンドを記録し、後のラウンドで解消した指摘も機械化候補として収集する。各項目は `finding` と `source` を持ち、`source` は実行、判定番号、判定者、対象を保持する。plan の完了には各ラウンドの番号・run・phase・judgments が対応する `settled.json` が必要で、欠けた履歴を最新状態で代用しない。refine・retro の提案コミット成立前の失敗は、判定の `target.proposal_version` を明示的な null、`verdict` を `not_assessed` とし、版が成立していない理由を `observations` に残す。成立済みの版は正の整数とし、欠落や0を最新の版で補わない。

retro の空 backlog は、フォルダーが実際に不在か、正常に列挙できた一覧が空の場合に限る。列挙不能はパスと原因を返して停止する。refine・retro の既存ドラフトの JSON 解析失敗も不在として扱わず、パスと原因を返す。

retro は backlog の各配列を正規の backlog スキーマで検査する。指摘の `id` と空でない文字列の `text` は必須とし、判定由来の `source.judgment` は1以上の整数に限る。既存の外側メタデータと `review` 配列の省略は引き続き受け入れ、入力ファイルの内容と出典は保持する。

判定済みの変更と HEAD は、コミットが同じか、マージベースからの変更内容が一致する場合に同一とみなす。ファイル名、削除行、追加行とその空白を保持し、ハンクの位置は比較しない。バックログだけのコミットで判定が無効にならないよう、現在ブランチの `.devkit/backlog/<エンコードしたブランチ>.json` だけを、backlog スキーマに適合する場合に比較から除外し、判断変更検出にも適用する。完了マーカーの生成・検査・除外はなく、旧マーカーを含むほかのファイルは通常の変更として扱う。

`retro` は基点から作ったブランチのバックログを読み、修正用の作業単位、`.devkit/config.json` に加えるチェック、規範の修正、escape の評価ケースを提案する。規範とチェック設定の変更は作業方法についてに限り、製品が守る性質は refine と同じく実装する単位のテスト可能な完了条件に置く。共有する性質の初出と後続単位での維持条件も同じ扱いにする。各提案は元の項目を参照し、対応しない項目にも理由を残す。機械検査を通った提案は、実ファイルの編集と消費した backlog・escape ファイルの削除を一つのコミットにまとめ、版とコミットを提案記録へ保存する。単位の下書きは提案記録に保持し、ファイルのスナップショットは作らない。fresh な読み取り専用の判定者が `harness.md` と `review/harness.md` を使い、評価検証とともにコミット済みの提案を調べる。作業方法と製品の性質の振り分けも確認し、製品ルールを拘束変更に書いた場合や完了条件が欠ける場合は blocking とする。最大3ラウンドの後、refine と同じ四部構成の短い承認質問を返す。会話メモがないため、第一部は backlog の根拠や人の指示から機械的に導けない提案変更をすべて要約する。全文・版・コミット・評価結果は詳細に保存し、同じ表示コマンドで読む。項目やリスクの漏れは blocking、既に決まった内容や機械的に導ける変更の反復は削除を求める nonblocking とする。`approve=<version>` は、その版のコミットがブランチの HEAD のままで、作業ツリーが clean なことを確かめ、ブランチを push して PR を作成または更新し、親なしの unit Issue と blocked-by 接続を作る。PR 本文の Issue 一覧を更新してから pass・版・コミット・`issue_numbers`・`pr_number`・`pr_url` を記録する。ファイル変更や追加のコミットは行わない。変更依頼は前の提案コミットを引き継いだ次版としてコミットし、撤回は履歴の書換えではなく新しいコミットで取り消す。人が PR をマージして基点へ届け、単位はマージと依存条件を満たしてから開始する。旧スナップショット形式の保留提案は適用せず、新しい retro ブランチでの再開始を案内する。

retro の下書きにも `pr_title` と `pr_summary` を必須で持たせ、執筆・判定・機械検査・承認質問で refine と同じ扱いにする。PR 本文には、承認済みの要約に続けて規範の変更パスと理由・証拠、`.devkit/config.json` の追加チェックと理由、escape の追跡（出典・工程・品質・理由・証拠）、評価ケース名・提案ブランチ上の場所・元の escape、作成した作業単位と blocked-by のリンクを列挙する。escape と評価ケースの見出しは英語では `Escapes` と `Eval cases`、日本語では「流出した欠陥」と「評価ケース」とする。定型文の言語、空一覧の省略、リンク、再実行時の更新も refine と同じ扱いにする。

マージ後に発覚し、どの工程でも見つからなかった欠陥も、修正方法によらず記録する。小さな直接修正も対象にする。`devkit backlog escape --defect-file <path> --entered <commit|PR URL|PR number> [--fixed <commit|PR>]` は現在のチェックアウトの `.devkit/backlog/escapes/<短いランダム16進ID>.json` に一件を書く。`defect` はファイルから読んだ所有者の原文を保持し、コマンド引数で本文を受け取らない。`entered` は流入元、任意の `fixed` は修正元、`recorded_at` は RFC3339 の記録日時である。参照はローカルで解決できるコミット、未取得のコミットハッシュ、GitHub PR URL、正の PR 番号を認め、ローカルにあるコミットは完全ハッシュへ解決する。空の本文・不正な参照・未知のフィールドなどは拒否する。出力には保存先と、修正と一緒に、またはリポジトリの PR 手順でコミットして基点に届ける必要を示す。記録自体はコミットしない。

retro はこのファイルを `kind: escape`、ID `<path>#escape/0` の項目として読み、既存と同じ採用・理由付き却下の検査と提案コミットでの削除を適用する。執筆者は `git show`、PR なら利用可能な `gh pr view/diff` で `entered` の変更を読み、どちらでも取得できなければその制約を明記する。ドラフトの `escapes` に全件の `entry`、`stage`（`requirements`、`plan`、`routing`、`quality`、`check`、依頼の真の不足を示す `none`）、`quality`、`reason`、`evidence`、`judge_should_catch` を残す。どの工程・判定者・規範が止めるべきで、なぜ止めなかったかを追跡する。従来の単位・チェック・規範修正に加え、採用した routing の見逃しには該当品質の `concerns.json` の `routing` 文の編集を必須にする。

採用した escape のうち判定者が見つけるべきものは、一件につき一つの評価ケースをドラフトの `cases`（`entry` と `name`）に追加する。設定 `eval` の `judge/<name>/` に、流入時の欠陥を示す最小限の `base/`、`change.patch`、`case.json` を書き、少なくとも一つの期待指摘を持たせる。キット自身では `eval` を `eval` に設定して `eval/judge/` を使う。修正差分ではなく欠陥を導入する差分を再現する。既存ケースは変更せず、前の提案に含めたケースの保持・修正・撤回は次の提案コミットで扱う。retro check は `internal/judgeeval` のケース形式・パッチ適用・指摘ファイル存在の検証を再利用する。ケース・設定・規範と消費した backlog の削除は提案コミットに含める。

機械検査と独立判定に合格した後、`devkit retro verify` は新規ケースだけを、コミット済みの規範と `concerns.json` の一時コピーに対して `internal/judgeeval` で実行する。提案コミットが HEAD で作業ツリーが clean なこと、ドラフトと承認質問が判定時から変わっていないことを照合する。escape の評価ケースがなければプロバイダーを呼ばない。AI ノードが結果を設定言語で説明し、提案の詳細に保存する。期待指摘ごとの発見・見逃し、routing の見逃し、プロバイダー失敗による採点対象外とその理由を示す。見逃しや呼び出し失敗は提案の承認を妨げず、人は詳細を表示して結果を確認できる。評価結果は実行成果物と提案記録にも保存する。`devkit-runs` はマージ後の欠陥報告を受けたら所有者の説明をファイルに保存し、`git log`・`git blame` で流入元を探すか所有者に確認して記録し、修正または PR 手順で基点へ届ける。

sync では、pre-rebase hook による拒否など、競合停止に至らない rebase の失敗をエラーとし、完了にはしない。rebase の完了時は、記録した取り込み先コミットが HEAD の祖先であることを検証する。競合パスは Git の NUL 区切り出力から取得し、日本語、改行、前後の空白を保持する。競合マーカーが残っていれば stage と rebase の続行を行わない。

Git の参照・パスの不存在、無関係な履歴、origin の未設定は、正常な否定結果を確認した場合だけ認める。実行・オブジェクト・設定の障害は元の診断を返す。sync は失敗した `rebase --continue` を暗黙に繰り返さず、空の競合を作らない。競合時に `REBASE_HEAD` を読めない場合もエラーにする。

## 実行をまたぐ記録

記録は Git の外の `$STATE_DIR/records/<エンコードしたブランチ>/` に置く。依頼、提案、要件、計画、判定、開始、結果、質問、回答、許可、続行許可を保存する。機械が必要な内容を `$ARTIFACTS_DIR` に取り出し、AI に記録フォルダーを直接渡さない。スキーマは `internal/record/schemas/` を正本としてバイナリへ埋め込み、書込時と読込時に検証する。計画の執筆用スキーマも準備処理が成果物へ書き出す。小さな変更(誤字、原因の明らかな小さな不具合、テストや設定の修正)はワークフローを通さず、セッションが規範に従って直接直し、`devkit checks` で確かめる。`devkit checks` は実行の外でも動く。ワークフローを使うのは、人が決める判断、構造・データ・契約・セキュリティ・費用の変更、決まっていないトピックのときだけにする。セッションからは `devkit status` で読む。テキスト・JSON の両方で各ブランチの依頼の `issue` 番号と `issue_url` も示す。`archon project list --json` から状態のフォルダーを見つけ(`STATE_DIR` があればそれを使う)、ブランチごとに最後の結果、未回答の質問、停止や差し戻しの中身、次に起動するワークフローを示す。

番号付き記録と質問・回答の読込では、実ファイルの null・不足キー・不正型、途中の質問番号の欠落はパスと原因を返す。初回の記録不在と未回答は区別し、保存済み `request.issue` の正当な省略と既存スキーマが認める0は維持する。

成果物を扱う judge・pr・sync のコマンドは、`ARTIFACTS_DIR` がなければ読書きの前に停止する。プロバイダー CLI も `ARTIFACTS_DIR` と `PACK_DIR` を必須とし、不足名を返す。任意パス用の `Env.Path` の契約は変えず、必須パスをチェックアウトで補わない。単独の `devkit checks` は従来どおり新しい一時フォルダーを使える。

checks は、round 索引がなく番号付き履歴もない場合だけ初回とする。空・不正な索引、索引が指す結果の欠落、次番号の既存結果では履歴の修復を求め、初回扱いや上書きで復旧しない。

`devkit status --json` の各ブランチは文字列配列 `errors` を持つ。回答の読み取りに失敗すると、対象の質問 ID、回答ファイルのパス、失敗理由を格納する。設定の読み取り・検証に失敗すると、設定ファイル名、失敗理由、再開始上限が不明である旨を各ブランチに格納し、`restart_limit` は不明を表す `-1` とする。失敗がなければ `errors` は `[]` を返す。テキストではブランチの下に `unreadable: ...` と表示する。読めなかった回答を通常の未回答として扱わず、`next` は回答を読める状態にしてから status を再確認するよう案内する。設定が読めない場合は、設定を先に解決してから status を再確認するよう案内する。設定を読めた場合の `restart_limit` は1以上の有効値をそのまま示す。0・負数・不正な型は設定の検証エラーとして `errors` に含める。記録と設定は変更しない。

最後の結果が `judge` の `pass` で、その結果の `inputs.requirements_version` が null なら、`next` は独立レビューの完了と所有者への報告伝達を案内する。要件を入力した judge の合格では `pr` の開始を案内する。

Issue の一覧・ページ一覧と Archon の `projects` は正常な空配列を認め、null・非配列・不正なページを空一覧に変換しない。status の状態発見は、削除済みプロジェクトのパス不在だけを理由付きでスキップする。それ以外のパス解決失敗は診断に示し、不正なブランチ符号化は対象パスと原因を返す。doctor・status・eval judge の標準出力への書込失敗も、診断の合否や採点結果とは別に呼出し元へ返す。

配布スキルの watcher は `devkit watch <run-id> [<run-id> ...]` を呼ぶ。状態の変化だけを表示し、全 run が終端なら終了し、それ以外は従来どおり30秒間隔で確認する。`archon workflow get` の失敗や Status 欠落は、run ID と終了エラー・標準エラーなどの理由を示して非0で終了し、自動再試行しない。失敗前に出た部分的な Status は採用しない。

最後の結果が合格した `pr` のブランチでは、`devkit status` が gh を利用可能な場合に `gh pr view <branch> --json state,url,reviewDecision,statusCheckRollup` を15秒の制限で実行し、open・merged・closed、URL、レビュー判断、失敗した検査をテキストと JSON に示す。実行・タイムアウト・JSON 読み取りの失敗は表示し、status 自体は失敗させない。`next` は open で検査失敗ならログを `review` とした fix、変更要求ならコメントを `review` とした fix または依頼変更時の requirements、merged なら `archon complete <branch>` と `devkit issues ready`、closed なら未マージで閉じた旨を示す。検査失敗と変更要求が両方あれば検査失敗の案内を優先する。

開始条件は、前工程の結果、未回答質問、渡された回答、チェックアウトとワークフローの状態を検査する。開始が成功するまで回答を保存しない。前工程を再開始すると下流の結果を無効にする。`question` で終わった実行は、回答を付けた新しい実行で続ける。Archon 内の待機ノードは置かない。

`back` の前提と観測は、戻り先の準備処理が有効かつ未消費のものを `returned` に取り出し、執筆者が先に扱う。`back` は戻り先のワークフローを、`stop` は停止理由と未解決点を示す。再開始が設定上限に達した場合は、人が続行を認めた言葉を `continue` へ渡す。上限到達前には受け付けない。`devkit-runs` が結果を読み、次を起動し、質問と回答をそのまま取り次ぐ。

## 導入と設定

`kit/` は対象リポジトリに配るワークフロー、規範、スキル、初期設定を持つ。`cmd/devkit/` が CLI を登録し、`internal/` が機械処理を実装する。`devkit init [--yes | --no] [--dry-run] [--provider claude|codex] [--sessions claude,codex] [--language <code>] [dir]` はキットを展開するがコミットはしない。初めて導入したときは、最後に `devkit-optimize` の実行を促す。`devkit-optimize` は人の指示を原文のままファイル経由で `optimize` ワークフローへ渡し、質問と版を指定した承認を取り次ぎ、公開された PR を伝えるスキルである。起動・監視・再開の操作は `devkit-runs` に委ねる。

`--language <code>`（`--language=<code>` も可）は人が読む文章の言語を保存する。検証は設定と同じで、空文字列と空白だけの値を拒否する。新規導入で指定がなければ、`LC_ALL`、`LC_MESSAGES`、`LANG` の順で最初の空でない値を読み、`_`・`.`・`@` より前を小文字にする。`ja_JP.UTF-8` は `ja`、`pt_BR` は `pt` になる。`C`・`POSIX`・空なら `en` を使う。init は選んだ言語と出典、`devkit-optimize` でリポジトリに合わせられることを表示する。再導入では明示指定がなければ既存言語を保持し、指定があれば `--provider` と同じく設定全体の置換を断ってもその値だけ保存して他のキーと書式を保つ。

書き込み前に全対象を比較する。ワークフローの `.archon/workflows/dev/` と各スキルフォルダーでは、内容の異なるファイルとキットが配布しなくなったファイルを示し、フォルダーごとに一度、上書き件数と削除件数を尋ねる。既定は No であり、既存ファイルは保持し、欠落ファイルだけを追加する。削除対象はキット所有フォルダー内だけで探す。規範は設定の `standards` フォルダー全体をリポジトリが所有する。差分・欠落・余分なものが一つでもあれば全体の置き換えを尋ね、No なら欠落ファイルも追加せず、完全に保持する。Yes の場合だけ余分なものを削除する。内容が異なる `.devkit/config.json` と `.archon/config.yaml` はそれぞれ確認する。同一ファイルは表示も書き込みもせず、新規ファイルは確認なしで作る。

workflows がバイナリの配布内容と一致する新規導入・Yes・差分なしの場合、`.archon/workflows/dev/.devkit-installed.json` に `devkit_version` と `kit_digest` を記録する。No では欠落ファイルを補っても印を保持し、印がなければ作らない。印は workflows グループに含め、余分なファイルとして扱わない。workflow の手編集では印は変わらない。`devkit version` は版と埋め込みキットの SHA-256 ダイジェストを表示する。ファイルパスと内容を長さ付きで辞書順にハッシュするため、ビルド日時・ファイル時刻・権限によらず、埋め込み内容が同じなら一致する。

`devkit record start <workflow>` と refine・retro・optimize の専用 start は、記録・回答の保存前に `$PACK_DIR` 内の対象 workflow の YAML と commands を読み、呼ばれるコマンドが実行中バイナリに登録されているかを検査する。抽出処理は plumbing test と共用し、テスト fixture は除く。未登録なら `not_started` で終了し、コマンド名、workflow とバイナリの版違い、適合するバイナリでリポジトリ内の `devkit init` を実行するか導入時のバイナリを使う対処を示す。印があれば導入元の版も示す。`devkit-runs` は人に伝え、再試行しない。ダイジェストの相違だけでは開始を拒否しない。

`--skill devkit-runs=<名前> --skill devkit-discuss=<名前> --skill devkit-optimize=<名前>` でスキルの配置名を変更できる。小文字英字・数字・ハイフンだけからなる重複しない名前を `.devkit/config.json` の `skills` に保存し、次回から再利用する。フォルダー、フロントマターの `name`、スキル内の相互参照と `scripts/watch.sh` の呼び出しパスも置き換える。変更前の名前が新しい配置先として使われていなければ、旧フォルダーを削除対象として確認する。設定全体の置き換えを断っても、明示した `--skill` は `skills` の値だけを更新し、他のキーや書式を保つ。設定を置き換える場合も、既存の規範の配置先と選んだスキル名は引き継ぐ。本文中のスキル名は既定名を表す。

`--provider`、`--sessions`、`--language`、`--skill` を明示したとき、既存の `.devkit/config.json` が JSON オブジェクトで、その内部に重複キーがあれば、`devkit init` は質問・書き込み・削除の前に失敗する。更新対象以外の設定や配列内のオブジェクトも再帰的に検査し、JSON のエスケープを解釈した同じ名前を重複とする。エラーは重複キー名と、所有者が重複を取り除く必要を示す。`--yes` や `--dry-run` でも同じ検査を行い、拒否時は既存ファイルと書式を変更しない。JSON オブジェクトとして解析できない既存設定の全面置換は従来どおり扱う。

配置先やリポジトリ内の祖先にあるシンボリックリンクは名前を示して確認し、No なら影響する配置先を処理しない。Yes はリンク自体を通常のファイルやフォルダーに置き換え、リンク先には書き込まない。共有する祖先リンクの置き換えが拒否したグループのファイルを失わせる場合、そのリンクの置き換えも行わない。`--yes` と `--no` は全確認に同じ回答を適用する。標準入力が端末でなく、どちらもなければ、その旨を表示してすべて No とする。`--force` は廃止し、別名としても残さない。`--dry-run` は比較と予定する質問だけを表示し、書き込みも削除もしない。完了時に書いたもの・削除したもの・保持したものを列挙し、拒否だけでは失敗にしない。不正な JSON 設定は既定の配置先で比較することを警告し、保持または置き換えを選べる。ただし `skills` だけの更新には JSON オブジェクトが必要であり、壊れた設定のまま名前だけを変更することはできない。不正な配置先設定は書き込む前にエラーにする。

`standards` はパスを正規化したうえで、workflow・導入するスキル・旧スキルの配置先、`.devkit/config.json`、`.archon/config.yaml`、設定された `decisions`・`eval` と所有範囲が重ならないことを検査する。同一先と祖先・子孫の関係は、比較結果の表示・質問・書込みより前に具体的なパスを示して拒否する。`docs/standards` など、これらと衝突しない文書配下への配置は許可する。

Archon、Git、`devkit` と、設定チェック用のツールが必要になる。執筆・判定には設定した Archon provider、ルーティングの代替経路には同じ provider の認証済み CLI、Issue 操作と PR 公開には認証済みの `gh`、PR 公開には `origin` を使う。Issue を使うにはリポジトリで GitHub Issues、sub-issues、issue dependencies が利用でき、設定したラベルが存在し、`gh issue view --json parent` に対応した CLI が必要になる。不足時は機能の有効化、CLI 更新、ラベルの作成を人に依頼してからこの流れを使う。Go と mise は dev-kit 自体の開発に使い、対象リポジトリにはビルド済みバイナリを置ける。基点ブランチは `internal/gitx` の同じ関数で、Archon が渡す `BASE_BRANCH`、リポジトリの `.archon/config.yaml` の `worktree.baseBranch`、`git symbolic-ref refs/remotes/origin/HEAD` が返す origin の既定ブランチの順に解決する。設定ファイルの不在や基点の未指定では次の出典へ進み、既存設定の読込・解析エラーはそのパスと原因を返す。どれにも基点がなければ三つの出典を示して停止し、`main` は推測しない。採用した名前と出典は、開始の run 記録、judge の target、checks のゲート出力、sync の状態に `base_branch` と `base_branch_source` として残す。

`.devkit/config.json` の `provider` は `claude`（既定）または `codex`。`devkit init --provider <name>` が保存し、workflow の AI ノードを描画する。ソースは Claude のままにし、Codex 導入時は全 AI ノードを Codex にし、未対応の `allowed_tools`・`denied_tools`・`settingSources` を除く。変更後の再導入は通常の workflow フォルダー差分として y/N を尋ねる。全 AI 出力スキーマは、入れ子を含め全プロパティを required に列挙し、`additionalProperties: false` にする。適用しない値は空文字・空配列・false で表し、プロンプトと読み取り側もそれを扱う。

Codex の workflow 判定者は full access で動き、ツール制限で書き込みを防げない。両 provider とも `mutates_checkout: false` を保ち、checkout を変更したノードを Archon が失敗にする。これは変更後の検出である。別経路の CLI フォールバックは読み取り専用とし、Codex は `codex exec --sandbox read-only --cd <checkout> --output-schema <一時スキーマ> -o <一時回答> --skip-git-repo-check -`、Claude は `claude -p --json-schema <schema> --allowedTools Read,Grep,Glob --tools Read,Grep,Glob --permission-mode dontAsk --output-format json` を使う。ルーティングの Codex は Git 管理情報のない判定ツリーを作業ディレクトリにし、Claude は `--add-dir <判定ツリー>` を追加する。Claude は JSON 結果の `structured_output` を読み、通常の `result` 文字列を回答として扱わない。両者を10分で打ち切り、回答をスキーマで検証する。実行ファイルは `DEVKIT_CODEX`・`DEVKIT_CLAUDE` でテスト用に置換できる。プロンプトは `$PACK_DIR` 内の `commands/*.md` を読み、`$ARTIFACTS_DIR`・`$PACK_DIR` を絶対パスに置換して標準入力へ渡す。CLI の出力は成果物内のログへ保存し、標準エラーにはパスと失敗時の末尾4000文字までを出す。実行 fixture はキーを外して偽 CLI で両 provider の経路を通し、ソース・描画後の provider と strict schema も Go テストで検査する。

両 CLI へ渡す環境から `TYPESAFE_API_KEY` だけを除き、provider 自身の認証用環境は保持する。保存ログは書込みの分割位置をまたぐキーも保存前に伏せ字にする。回答は JSON のプロパティ名と文字列値を伏せ字にし、その最終回答もスキーマで検証する。伏せ字後の名前が衝突する場合やスキーマを満たせない場合は回答を返さず失敗とする。両 CLI とも、直接プロセスの終了または実行期限到達後のパイプ待機を100ミリ秒に制限する。kill 対象は子孫や無関係なプロセスへ広げない。

`sessions` はスキルを導入するセッションツールの配列で、未指定なら `claude` と `codex` の両方。`devkit init --sessions claude` などで一方に絞れ、空配列ならスキルは導入しない。Claude は `.claude/skills/<name>/`、Codex は `.agents/skills/<name>/` へ置き、内部参照も導入先に合わせる。明示された sessions は provider 変更時にも保持する。`--provider`・`--sessions` は `--skill` と同じく、設定全体の置換を断っても指定値だけ保存し、他の設定と書式を保つ。改名・差分確認・自分が導入したと確認できない旧フォルダーを削除候補にしない規則を、各配置先に適用する。

`devkit doctor [dir]` は required・needed for a part・optional の三段階で状態、不足で止まる用途、導入方法を出す。必須は Git とコミット済みリポジトリ、Archon とその版、設定 provider、PATH 上の devkit、導入ファイル、config と concerns 検査。部分利用は sessions の各 CLI、Issue と PR 用の gh 認証、PR 用の origin、キー未設定時の代替 CLI。任意は TypeSafe キーの有無と checks で、空なら検証が走らないことと設定された optimize 名を示す。キー自体は出さず、TypeSafe に送るルーティング用の差分を説明する。provider の導入は、最大20秒待つ `archon doctor` の `Installed providers:` 一覧で検査する。一覧がない、コマンドが失敗する、またはタイムアウトした場合は、`$ARCHON_HOME/plugins/archon-provider-<provider>`（既定 `~/.archon/plugins/`）に実行可能な通常ファイルがあるかで判定する。対象 provider の診断失敗行は警告として添え、導入済みの判定を失敗にはしない。他の外部コマンドは各3秒以内のままとする。必須不足だけ終了コード1。init はサマリー後に同じ診断を出すが、その結果では失敗せず、初回は続けて optimize 名を案内する。

診断の必須項目 `kit and binary` は導入済み workflows と設定された配置先の全スキルで呼ばれるコマンドを登録一覧と照合し、不足するコマンドを列挙する。別項目 `kit version` は needed for a part として印のダイジェストを比較し、不一致なら導入元と実行中バイナリの版、`devkit init` で差分を確認して置換を承認する対処を示す。印がない場合も明記し、この項目だけでは doctor を失敗にしない。

必須 provider は設定値に加え、導入済み workflow の `.yaml`・`.yml` を YAML として解析し、ループ内を含む AI ノードから列挙する。fixture は診断対象から除く。読込み・解析不能は必須診断 `workflow providers` の不足として表示し、doctor は終了コード1を返す。init は実行中のコマンド登録一覧を同じ診断へ引き継ぐ。

リポジトリごとの差異は `.devkit/config.json` に置き、`devkit config` で有効値を確認する。設定の正本となる既定値と検証処理は `internal/config` にある。

- `language` は人が読む文章の言語で、組み込みの既定は `en`。新規導入時は `--language` または環境のロケールから選ぶ。
- `provider` は `claude`（既定）または `codex`。`sessions` は skill を配るセッションツールで、未指定なら `claude` と `codex` の両方(`.claude/skills/` と `.agents/skills/`)。
- `skills` は `devkit-runs`、`devkit-discuss`、`devkit-optimize` を実際の配置名に対応させ、既定は同名。省略したスキルは個別に補完する。
- `standards`、`decisions`、`eval` はリポジトリ相対の保存先で、既定は順に `.devkit/standards`、`.devkit/decisions`、`.devkit/eval`。`eval` も他のフォルダーと同じ検証を行い、品質判定の評価ケースはその `judge/` 以下に置く。
- `issues.labels.unit` と `issues.labels.topic` は作業単位と未決の問いのラベルで、既定は `devkit:unit` と `devkit:topic`。各値は空でない文字列とし、一方だけの指定では他方の既定を保つ。ラベルは自動作成しない。
- `checks` は名前、シェルコマンド、タイムアウト秒数、任意の `paths` を持つ。初期値は空なので、実際の検証コマンドを追加する。`paths` の省略は毎回実行、空配列は対象なしを意味する。終了コード0は合格、75だけ一度再実行し、タイムアウトは環境エラー、77は未実行、ほかは不合格になる。
- `skeleton_check` はスケルトンに実行するチェック名で、既定は空。
- `qualities` は品質判定の起動パスを定める。判定するフェーズは関心マップが、差分からの追加選択はルーティングが担う。
- `decision_paths` は判断を伴う変更の `paths`、`quality`、`ask` を定める。既定では依存、マイグレーション、インフラ、CI、環境変数サンプル、ワークフロー、規範、設定自身を含む。基点の設定と現在の設定のチェックを合わせて実行するため、チェックを削除しても検査を回避できない。
- `limits.restarts` と `limits.fixes` は再開始と修正の上限で、既定はそれぞれ3。三つの上限はすべて1以上の整数とし、省略時だけ3を使う。不正な設定を別の上限で補わない。`limits.passes` は `implement` がリリース単位1つに使える回数で、既定は3。ある単位が使い切ると、その単位の名前と落ちたチェックを示して止まる。単位の数に関係なく、ほかの単位の回数は減らない。

廃止した `docs`・`units`・`topics` と `refine.relevance_threshold` は既存設定に残っていても受け入れて無視し、有効設定には出力しない。旧単位・トピックファイルの自動移行や削除、旧依頼の `unit` や計画行の `ref` の自動変換は行わず、新しい依頼は Issue 番号で requirements から作る。

省略した項目には既定値を使い、品質・上限は個別に補完する。それ以外の指定配列は既定の配列を置き換える。グロブは `**`、`*`、`?` を使える。

## リポジトリへの適合を独立判定する

`optimize` は `optimize/<name>` ブランチで動く。入力は、人の原文の `instructions`（空なら全体の適合）、`answers`、`approve`、`continue`。retro と同じ start・prepare、最大3ラウンドの write → check → fresh な読み取り専用 judge → round、finish・approve の流れを使う。AI ノードは執筆者と判定者だけである。

執筆者は CI 定義、タスク実行手段、配置、README・CONTRIBUTING、既存の規約と人が使う言語を読み、根拠付きで実ファイルを編集する。対象は `.devkit/config.json` のチェック・品質と判断を選ぶパス・ラベル・言語、`.archon/config.yaml` の基点ブランチと worktree.postCreate、既存の規約と照合した規範、concerns.json の routing、キットのスキルへ誘導する短いエージェント指示の節である。規範の食い違いは保持・適合・リポジトリの規則の採用から選ぶ。セキュリティ・データ喪失・人の権限に関する blocking は弱めない。人が求めた場合だけ workflow を編集し、provider・model・effort の指定を各ノードへ展開する。Codex にするノードから allowed_tools・denied_tools・settingSources を除き、mutates_checkout: false は維持する。製品コード・CI・スクリプト・判断ログは編集しない。

既存の open Issue のうち、設定した unit・topic ラベルのないものもすべて整理する。提案の triage は既存 Issue の番号、キー、分類、題名・本文、完了条件、held_units、parent、blocked_by、理由を持つ。分類は unit・topic・理由付きの対象外とする。足りない完了条件は依頼から確実に導けるものだけ補い、不明な要件は推測せず topic にする。問いのグループ化は固定した `review/purpose.md` に従う。新規 Issue は既存の親 topic の下で問いを分ける topic に限る。topic から切った unit は sub-issue とし、順序と待機は blocked-by で表す。topic 本文に止める unit のキーを明記し、止める単位がなければその旨を書く。held_units と unit 側の blocked_by を一致させる。

機械処理は `internal/optimize` に置く。config、編集後の concerns、編集範囲と根拠、PR 文面の必須項目と題名の上限、既存 open Issue だけを参照すること、分類の網羅、親子・依存の循環、topic が止める unit の構造を検査する。workflow の検証は `scripts/test-kit.sh` と同じ `archon validate workflows` を警告なしで通す。Archon がなければ既存の devkit plumbing 検査と YAML 解析へ代替し、どちらを使ったか記録する。提案の postCreate で準備した一時 worktree の基点上で、パス選択にかかわらず設定した全チェックを実行する。失敗・未実行・準備失敗をログ付きで報告し、検証済みとして承認へ進めない。一時 worktree は削除する。

通った下書きと実ファイルは `internal/proposal` で版ごとの提案コミットにする。独立判定者は編集前に固定した規範の `harness.md`・`review/harness.md`・`authority.md` と、Issue 整理には `review/purpose.md` を使い、人の指示への適合、規範の変更と負担、Issue の意味とグループ化を確認する。blocking または未評価が残れば執筆者へ戻し、3ラウンドで通らなければ stop とする。再提案は履歴を書き換えず次のコミットにする。

承認質問は refine・retro と同じ四部構成にする。会話メモがないため、第一部はリポジトリ・backlog の根拠や人の指示から機械的に導けない提案変更をすべて、キー付きの1〜2行で推奨と理由とともに示す。受け入れるリスクも各1〜2行、残りは根拠と人の指示に従う旨と詳細コマンドは一行、版は回答行だけに置く。項目やリスクの漏れは blocking、既に決まった内容や機械的に導ける変更の反復は削除を求める nonblocking とする。summary・owner_points、変更・整理の全文、pr_title・pr_summary、版とコミット、検証結果は同じ詳細ファイルと表示コマンドで確認できる。人に未判定の大量の変更一覧の検査を委ねない。承認は共通の開始条件・記録済み回答・最新の質問・clean な HEAD と照合する。承認前には外部へ書き込まない。承認後は共通の proposal 公開処理で push → PR 作成・更新 → Issue 整理の順に進み、ラベル、本文、必要な新規 topic、sub-issue、blocked-by を適用する。PR 本文の冒頭は承認済み pr_summary、その後の変更・整理の一覧は機械が組み立てる。Issue の操作は `internal/issues` を再利用し、`issue-creation/<version>.json` に適用済みの項目を保存する。新規 topic は共通の隠しマーカーでも照合し、再実行は作成・本文編集・接続の不足分だけを補う。対象外の Issue は変更しない。`devkit status` は承認への回答方法と公開 PR の次の手順を示し、人が PR をマージする。

## キットを検証する

ソースのチェックアウトで次を実行する。

```sh
mise exec -- go build ./...
mise exec -- go vet ./...
mise exec -- go test ./...
scripts/test-kit.sh
```

`scripts/test-kit.sh` は Claude と Codex それぞれの一時 Git リポジトリへ `devkit init --provider` し、警告なしの `archon validate workflows`、原則の所有検査、`archon workflow test` を実行する。次にソースの `test/fixtures/` を一時リポジトリへコピーし、AI だけをスタブ化して各ワークフローの主経路の bash を実行する。分岐ごとのスタブフィクスチャも用意する。引数で実行フィクスチャのワークフローを絞れる。

Archon のホームを分離し、プロバイダープラグインは既定で `$HOME/.archon/plugins`、必要なら `KIT_ARCHON_PLUGINS` から読む。別バイナリの `cmd/devkit-fixture` が事前記録と AI 執筆によるファイル出力を補い、終了前の記録を検証する。このヘルパーと実行フィクスチャは配布キットに含めない。PR 公開はスタブ化し、`sync` は実際のローカル競合を解消する。

Go テストは各機械処理の判断分岐とスキーマを検証する。評価のテストも偽 CLI を使い、ケース検証、一時リポジトリ、材料と YAML スキーマ、照合と集計、ルーティングによる見逃し、出力ファイルを確かめる。Issue のテストは偽 gh で作成応答の喪失・不正な応答・保存失敗後の採用、後続ページの closed Issue、ラベル・マーカーの照合、不足する関連付けの補完、requirements 入力の本文保持とマーカー除去を検証する。refine・retro の PR は fake gh とローカルの bare リモートで作成・更新を検証し、承認済みの題名・要約の使用、拘束変更・判断ログ・Issue・依存関係・retro の追跡と評価ケースの一覧、日本語・英語の定型文、題名の100文字境界、PR 用文面のない旧提案の外部書込み前の拒否を確かめる。plumbing テストは YAML とプロンプトが呼ぶ全 `devkit` サブコマンドを登録と照合する。実 AI の判断と外部への PR 公開はフィクスチャの検証範囲に含まれない。

## 判定者が見つけるものを測る

フィクスチャは AI を置き換えるため、品質判定のプロンプトと規範が必要な指摘を見つけることまでは確かめない。`devkit eval judge [--case <name>]... [--dir <cases folder>] [--out <folder>] [--standards <folder>]` は実プロバイダーでこれを測る。規範、ルーティング、判定プロンプトを変えた後、人が手動で実行する。実際のプロバイダー呼び出しの費用がかかる。Archon は起動せず、ノードの接続は評価しないと出力する。接続の検証には従来のフィクスチャを使う。チェックは実行しない。判定役には設定済みのチェックも渡さない。渡すと、チェックの検査対象だとして判定役が指摘を控え、評価では見逃しに数えられるためである。評価は判定役が自分で見つける力を測る。

キット自身のケースはソースの `eval/judge/` に置き、`devkit init` の配布対象に含めない。ソースでは `--dir eval/judge` を指定する。導入先では設定 `eval`（既定 `.devkit/eval`）の `judge/` 以下を使う。`--dir` はケースフォルダーを直接含む場所を指定し、`--case` はフォルダー名を複数指定できる。相対パスのフラグは実行ディレクトリから解決する。

各ケースは `case.json`、変更前の小さなリポジトリ `base/`、そこへ `git apply` で適用する `change.patch` を持つ。重複のケースには既存のヘルパーや変換も含める。`base/` は Git 管理情報を含まない通常のファイルで構成する。JSON は `description` と `expected` が必須であり、各指摘は `id`、`quality`、`file`、何が問題でなぜ影響するかを述べる `summary` を持つ。`expected: []` は問題のない変更を表す。任意の `not_expected` は同じ形で特定の誤検出を表す。未知のキー、不足項目、不正な型、空白だけの文章、リスト間を含む ID 重複、コード判定者のない品質、リポジトリ外のパス、変更前後のどちらにもないファイル、不正なパッチは明確なエラーにする。

ケースごとに一時 Git リポジトリを作り、`base/` と設定・規範を基点コミットに、パッチを別ブランチのコミットにする。ワークフローと同じ `judge prepare`、`changes`、`route`、`launch` の実装を使う。任意の `requirements` があるケースは、その原文を既存形式の要件の目的と完了条件に入れて `requirements.json` として渡す。ソースの `eval/judge/` の全ケースは、問題のない変更も含めて所有者の短い依頼文を `requirements` に持ち、`scope` が配達時と同じく合意済みの依頼に照らして判定できるようにする。省略した外部ケースは要件のないレビューとして扱う。計画は作らず、ケースの説明や期待指摘も判定者へ渡さない。

規範は `--standards`、導入済み規範、バイナリ内の規範の順で選ぶ。プロンプトと YAML は導入済みワークフローを優先し、なければ組み込みを使う。ルーティングは通常と同じく Jev、設定プロバイダーの読み取り専用 CLI、全品質の選択への代替経路を通る。起動対象は設定パスや常時起動も合わせた結果とする。各品質は `judge/commands/quality.md` の `$INPUTS.quality` を置換し、`judge.yaml` の対応する `judge-<quality>` の `output_format` を読み、既存の読み取り専用 CLI で一度判定する。スキーマを評価用に複製しない。

最後にケースごとに一度だけ、同じプロバイダーの読み取り専用 CLI に期待指摘、誤検出リスト、全報告指摘の品質・ファイル・行・失敗シナリオ・証拠を渡して照合する。strict schema で全期待 ID と全誤検出 ID に対する報告 ID または該当なしを必須にする。どちらにも一致しない報告は `other` として列挙し、未知の本当の問題かもしれないので誤りとして採点しない。

標準出力と `result.json` に、ケース別・品質別の発見／見逃しと期待の説明、誤検出、起動した品質と期待品質、合計を出す。起動しなかった品質の見逃しはルーティングによるものと明示する。`--out` の既定は新しい一時フォルダーで、その場所を表示し、材料、規範、プロンプト、各回答、照合、ログを残す。評価完了なら点数に関係なく終了コード0にする。あるケースでプロバイダーの時間切れや回答の不正が起きても評価全体は止めず、そのケースを採点対象外として記録し、残りのケースを続ける。採点対象外のケースは最後に一覧で示し、合計には含めない。判定役の時間切れは30分とする。ケースファイルの不正など、評価を始められないエラーだけ非0にする。テストは偽 CLI を使い、実プロバイダーを呼ばない。retro も同じ評価処理を使い、流出した欠陥から追加したケースの結果を承認前に示す。

## まだないもの

依存解析ツールから取得する事実は持たず、構造の材料は Git の変更と階層の情報に限られる。執筆者・判定者とルーティングの代替 CLI は設定した provider を使い、PR 公開先は GitHub のみである。リポジトリ固有のマイグレーション検証や依存監査などは、必要なチェックを設定して補う。
