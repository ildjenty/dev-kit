# dev-kit の設計

人は重要なことだけを決め、コードの変更は一か所に収まり、進め方は失敗から改善される。dev-kit は、この三つを支える開発キットである。Archon がワークフローと AI セッションを動かし、Go バイナリの `devkit` が開始条件、機械検査、記録、コミットを担当する。対象リポジトリごとのコマンドや規約は、設定と規範に置く。

## 人に判断を戻す場所

まだ定まっていない依頼は、`devkit-discuss` の会話から始める。既存の判断と文書を読み、決まったこと、覆ったこと、未決のことを分け、人が確認したメモを `refine` に渡す。会話の間は文書や判断の記録を書き換えない。

`refine` は一回に一つのトピックを扱う。`decide` でその問いへの判断と次のトピックを作り、`document` で文書へ反映する。それぞれに最大3回の機械検査と独立した判定がある。文書フェーズでは、機械検査が新しい判断ごとに最低1件の引用文書を要求した後、`devkit refine reflect` が Jev で反映を判定する。Jev が利用できない場合だけ設定した provider の読み取り専用 CLI が代行し、両方が利用できなければ両失敗の理由を示して終了コード1で停止する。続く設定プロバイダーの判定者は表現を判定する。反映不足は判断キーと検査した文書を示す blocking な `reflection` 指摘になり、解消するまでラウンドは通らない。未決点が残れば質問して終了し、提案がまとまれば、その版への承認を求めて終了する。人が承認した版を `approve=<version>` で再開始すると、開始済みの実行と承認回答を照合してから判断を合意済みにする。

トピックは `<topics>/T-<id>.md` に保存する。フロントマターは `id`、`title`、`status`、`depends_on`、本文は問いと、答えが定まったといえる条件を持つ。`status` は `open` または `settled` である。依存する判断がすべて合意済みのトピックだけを `devkit decisions topics` で選べる。領域のトピックが定まるまで、その領域の作業単位は切り出さない。

承認済みの refine ブランチは、リポジトリの手順で PR にしてマージする。`refine` 自体は PR を公開しない。その PR のマージ後、依存する単位の完了を確認し、単位ごとにブランチを作る。

```text
壁打ち → refine（トピックごとに承認）→ refine PR のマージ
  → 単位ごとに requirements（unit=<id>）→ plan → implement → judge ⇄ fix → pr
  → 必要に応じて sync → needs_judge なら judge → pr
  → retro → 承認 → 改善 PR のマージ
```

`requirements` は依頼の未決点を、`plan` は人に残された設計判断を質問する。`implement`、`judge`、`fix` が新たな判断の必要に気づいた場合は、`back` で `plan` に戻し、そこで質問する。`pr` が尋ねるのは、設定の `ask` に該当し、既存の `decided_by: owner` の行の `touches` では覆われていない変更だけである。要件のないブランチの `judge` は報告だけを行い、`back` を返さない。判断や計画が必要なら、変更を説明して `requirements` から始めるよう `stop` で示す。`retro` も改善案を承認質問として返す。マージするかどうかは人が決める。

`devkit refine prepare` は関連判断を一度だけ選び、decide・document の執筆者と判定者の全ラウンドで同じ集合を使う。`refine/input.json` の `decisions` は全判断の索引（`id`、`title`、`status`、`depends_on`、`supersedes`、`path`）、`relevant_decisions` は関連集合の全文とする。トピックの推移的な判断依存と引用、未承認提案と前回提案の判断、それらを置き換える・それらに置き換えられる判断(置き換えの連鎖は閉包までたどる)は必ず含める。さらに、これらを引用する未完了単位が併せて引用する判断を1段だけ加える。文書の共引用はたどらない。概要文書が多くの判断を引くと全件に広がるためで、関連性は次の判定に任せる。

それ以外の `agreed` 判断は一件ずつ、トピックの判断を制約する・重なる・依存する・衝突する可能性があるかを Jev の `noul` 質問で広く選ぶ。トピックの題名と本文、依頼の owner words、メモと supplement、判断の題名と本文を指示でなくデータとして送り、共有 `internal/jev` でバッチ処理する。確率が設定 `refine.relevance_threshold` 以上なら含める。既定0.2は、関連判断の見落としが衝突を隠すため再現率を優先した値である。`superseded`・`withdrawn` は Jev に送らず、必須規則からのみ含める。`refine/relevance.json` に全判断の採否と出典、Jev の確率、代替経路へ移った理由を記録する。キーは環境変数だけから読み、ログにも出さない。

キー未設定または Jev のクレジット切れ・エラー・不正回答なら、設定 provider の読み取り専用 CLI を一度呼ぶ。`refine/relevance-input.json` にトピックの材料と全 `agreed` 判断の ID・題名・パスの索引を渡し、判断ファイルの読み取りを許して strict schema の関連 ID 配列を求める。CLI も失敗すれば全 `agreed` 判断を含め、両失敗を記録する。執筆者と判定者は関連集合の全文を読み、ほかの判断も題名から関係がありそうなら索引のパスで読む。ドラフトが置き換える・依存する・引用する判断は必ず全文を読む。実際の判断は Codex・Claude が担う。`affected.decisions` も同じ索引形式にし、関連集合外の本文を重複して渡さない。機械検査と適用、反映判定、単位の領域検査はチェックアウトの全判断を使い、AI 入力の削減では検査を変えない。判断の直接編集検出は準備時の全レコードのハッシュとの照合を維持する。

## 品質の担当を一つにする

品質の種類は `structure`、`data`、`contract`、`security`、`ui`、`cost`、`test`、`delivery`、`scope`、`readability` の十個に固定する。コードでの定義は `internal/concerns` に集め、設定検証とスキーマの品質列挙をそこから導出し、テストで整合を確認する。

リポジトリが所有する `<standards>/concerns.json` は、それぞれの品質が何を決めるか、どの原則を担当するか、計画時と実装後にどの基準を読むかを結び付ける。すべての品質に適用する原則は `every_quality`、品質以外の判定者や執筆者が担当するものは `others` に置く。

番号付き原則は必ず一度だけ割り当てる。共通の `every_quality` への割り当ても一回と数える。参照する文書は存在し、`review/README.md` を除くレビュー文書はすべてマップから参照されなければならない。`devkit concerns check` が検査し、`plan`、`judge`、`refine`、`retro` の準備でも、固定した基準のコピーに対して実行する。実在する材料の消費者だけを担当として認め、レビュー文書中の `<文書>#<番号>` 参照もその担当の原則に限る。違反があれば判定を始めない。

品質ごとの基準は `review/<quality>.md` の一つにまとめる。`Decisions` は判断行とスケルトンで決まること、`Code` は関数本体で決まることと判断への適合を扱い、`Blocking` と `Not reported` が指摘の境界を定める。計画で合格した選択を実装後に選び直さず、その選択どおりに動くかを調べる。リリース単位とテスト計画の網羅性は `delivery`、依頼と他の用途への適合は `scope`、名前やコメント、既存の書き方は `readability` が担当する。

失敗シナリオ、停止条件、未評価、データと指示の区別などの共通判定規則は `review/README.md` に、人が決める範囲は `authority.md` に置く。プロンプトはそれらを参照し、入力、書き込み先、出力形式を指定する。執筆者と判定者に渡す材料は同じマップから作る。基準は依頼の開始時に基点ブランチのコミットへ固定し、その後の修正や同期でも同じコピーを使う。

## 判断を下流へ引き継ぐ

リポジトリの判断は `<decisions>/D-<id>.md` に一件ずつ保存する。本文に背景、候補、選択、理由、不確実性を残し、フロントマターで状態、判断者、依存、置き換え元、依頼ブランチを表す。合意済みの判断を変える場合は、新しい判断から `supersedes` で参照する。文書は根拠の判断 ID を引用する。

ID はブランチとドラフトのキーから作る小文字の16進数で、最初は6桁、衝突すれば延ばす。判断は `D-`、単位は `U-`、トピックは `T-` を付ける。再提案でも保持したキーの ID は維持し、撤回した未承認ファイルは削除する。置き換えの影響は判断の依存関係をたどり、間接的に引用する文書や単位にも伝える。

作業単位は `<units>/U-<id>.md` に目的、完了条件、根拠となる判断、単位の依存を持つ。`requirements` に `unit=<id>` を渡すと、準備処理が単位と引用先の合意済み判断を読み込む。それらは補足の候補ではなく、判断 ID を出典とする制約になる。`devkit decisions units` は各単位の `id`、`title`、`depends_on`、`state`、`ready` を示す。既定は1行ずつのテキストで開始可能な単位を明示し、`--json` で各フィールドを返す。チェックアウトに完了マーカーがあれば `done`、なければ `open` となり、未完了かつ依存単位がすべて完了した単位だけが `ready` になる。requirements は完了済み、または依存単位が未完了の場合、理由付きの `not_started` で終了する。

配達中のブランチが根拠とする判断は、単位の `decisions` と最新要件の引用（requirements）、最新計画の各行の `ref` および行内の引用（plan）から一つの収集処理で求め、判断 ID ごとに工程と引用項目を保持する。開始条件と `devkit status` は、ローカルにある `origin/<base>`、なければローカル基点ブランチの判断を `git show` で読む。判断フォルダーもその ref の設定から読み、省略時は `.devkit/decisions` とする。fetch は行わず、両 ref がなければ注記して検査を省略する。

根拠の判断が基点で `superseded` なら、引用する最初の工程へ戻す。単位または要件が引用すれば requirements、計画行だけなら plan、それ以外は戻さない。戻り先より後の plan・implement・judge・fix・pr は該当する範囲で開始を拒否し、旧判断と置き換え先、基点 ref、同じブランチで sync 後に開始する工程を示す。戻り先とそれ以前は通常の開始条件を使う。status も同じ検査で置き換えと次の手順を示す。

戻り先の `returned` には、旧判断と置き換え先の ID・題名・本文、引用した単位・要件項目・計画行を渡す。執筆者は旧判断に依存する項目だけを変更し、他を保持する。新判断による内容変更が不要なら引用だけを移す。要件の制約には ID がないため、引用項目は `constraints[1]` のような1始まりの位置で識別する。単位ファイルは refine が管理し、判断を置き換える文書段階では、旧判断を引用する未完了単位を後継判断の引用でドラフトに保持するか、既存の規則で撤回する。保持する既存単位は ID をキーにし、未承認提案の単位は以前のキーを引き継ぐ。機械検査は旧引用が残る未完了単位と判断を示して拒否し、適用時に保持した単位ファイルの引用を書き換える。完了済み単位は変更しない。requirements は合意済みでない判断を引用する単位を拒否する。単位がなくなった場合と完了済みの場合は、その理由を開始拒否に示す。

単位を経由しない依頼には `owner_words` を使い、セッションの調査結果は `supplement` に分ける。

計画の行が合意済み判断を適用する場合は `ref` で参照する。計画が合格すると、`when: now` の新しい `owner` または `principle` の行だけが合意済みの判断ファイルになり、参照した判断を `depends_on` に、ブランチを `request` に記録してスケルトンとコミットする。`provisional` は計画内に残し、PR 本文にも示す。実行記録は経過と版の証拠であり、リポジトリの判断の正本は判断ファイルである。

質問への回答は、質問時の要件版と行の内容ハッシュに結び付ける。同じ行 ID でも内容が変われば、古い回答は適用しない。構造承認は構造段階のスケルトン内容に結び付け、owner 行の `touches` が覆う構造変更はその行で一度だけ尋ねる。実装中に許される計画更新は、暫定行の追加と、後で決める行を暫定選択で確定することに限る。合格済み計画を `derived_from` に記録した派生版として保存し、次の開始条件でも受け付ける。それ以外の変更は計画へ戻す。

## 構造を先に決め、変更の広がりを調べる

`plan` は構造と詳細を別のループで進める。構造では配置、責務、依存方向、境界の判断行とスケルトンだけを書く。新しい構造行の `nature` には、種類、誰が何のために変えるか、変わりやすさ、呼び出し元を、パスや依頼文、呼び出し関係の証拠とともに書く。分からない項目は `unknown` にする。機械検査と構造判定が通ってから詳細に進む。

詳細では他の品質の行、リリース単位、テスト計画を書く。シグネチャは直せるが、構造段階で確定したファイルの追加、削除、移動はできない。必要になれば `stop` で変更点を示し、`plan` を始め直す。各ループは最大3回であり、合格には同じ実行の有効な構造段階と詳細段階の完了が必要になる。事実は判断行の `evidence` に機械または執筆者という出典と確認先を記録する。

`implement` ではリリース単位ごとに別セッションがテストとコードを書く。設定したチェックを通して単位をコミットし、同じチェックが続けて失敗すると、独立した判定者が崩れた前提と戻り先を示す。

`devkit checks` は、不合格のチェックだけを基点ブランチとの merge base の一時 detached worktree でも実行する。コマンド、タイムアウト、終了コードの扱いは同じで、合格済みチェックと環境エラーは比較しない。現在のリポジトリの `.archon/config.yaml` に `worktree.postCreate` があれば順番に実行し、各コマンドには `postCreateTimeout` ミリ秒（既定300000）を適用する。準備失敗は変更の不合格にせず比較不能とし、一時 worktree は削除する。不合格結果には `base: failed|passed|unavailable`、比較した場合は `base_log` を保存し、ゲートは両方で落ちる `preexisting` と基点では通る `regressed` を返す。`--no-base` は比較を省略し、スケルトン検査もこの扱いにする。`implement` と `fix` は `--base-on-repeat` で呼び、前のパスでも落ちていたチェックだけを比べる。実装中は最初に落ちるのが普通なので、その分の準備と再実行の費用をかけない。`judge` と `sync` は落ちたチェックをすべて比べる。比べなかったチェックは `base: not_compared` になる。

`implement` と `fix` は、そのパスの全不合格が `preexisting` なら即座に停止する。stuck や step-back 判定に進めず、そのパスは回数に加えない。`judge` は基点でも落ちるチェックを判定に明記し、一つでもあれば `fix` へ送らず同じ理由で停止する。停止には `base_failed: true` を記録し、ループの終了理由は `base_failed` にする。人には不合格チェックとログの場所を伝え、基点ブランチを先に直してから同じワークフローを再開始するよう案内する。その再開始は `retry_after_base` として `limits.restarts` に加算せず、既に上限でも許可する。`devkit status` の `next` と `devkit-runs` もこの案内を行う。基点を直す前に再試行しても解決しない。回帰と比較不能については、implement/fix の従来の失敗処理を維持する。

`judge` はコミットした差分を読み、設定パス、計画行、`devkit judge route` の Jev または代替の設定プロバイダー CLI による選択を合わせて品質判定者を起動する。`scope` は毎回、ソースやテストが変われば `test` と `readability` も動く。パスの指定だけで品質の変更を見落とすことを防ぐ。`devkit judge route` は固定した関心マップの `routing`(その品質に関わる変更の具体的な説明)を質問にし、ファイルごとの差分を TypeSafe API に送る。品質ごとの `routing_threshold` 以上の確率になった品質を選ぶ。閾値は、見落としたくない変更を見落とさない値を品質ごとに測って決めてあり、リポジトリが関心マップで調整できる。ソース・テストの質問は確率 0.3 以上で `test` と `readability` を選ぶ。差分は行の境界で最大 8 KiB に分割し、送信 JSON も 24 KiB 以下に収め、同時実行は最大 4 件とする。各リクエストは 10 秒でタイムアウトし、タイムアウト・429・5xx のみ 100 ms 後に 1 回再試行する。1 件でも失敗、または回答が不正なら部分選択を破棄し、設定した provider の読み取り専用 CLI に切り替える。両方が利用できない場合は、見落としを避けるため、変更された各ファイルに対してコード判定可能な全品質を選び、理由に両失敗を記録する。出力の `source` は `jev`・`claude`・`codex`・`all` のいずれかになる。全確率は `judge/route-jev.json` に残す。`launch` はこの単一の出力を読む。任意の環境変数 `TYPESAFE_API_KEY` を設定した場合だけ送信し、キー未設定なら TypeSafe には何も送らない。キーは環境変数以外から読まず、記録にも出さない。代替経路には設定した provider の認証済み CLI を必要とする。

Jev の HTTP クライアントは `internal/jev` に共有し、ルーティングの挙動は変えない。`refine` の反映判定では、新しい判断の題名・本文と、それを引用する文書の全文を TypeSafe に送る。判断中のキーは引用文書が使う表記へ置換する。文書は見出しを優先して最大 8 KiB に分割し、見出し内の長い部分は UTF-8 の境界で分割する。同じチャンクに対応する複数の判断は一度に問い合わせ、送信 JSON は 24 KiB 以下にする。同時実行・タイムアウト・再試行はルーティングと同じで、どれか一つの引用チャンクが確率 0.5 以上なら反映済みとする。全確率は `refine/reflect-jev.json` に保存する。1 件でも失敗や不正回答があれば部分判定を採用せず、設定した provider の CLI へ切り替える。機械検査は代替判定用の全文を `refine/reflect-input.json` に書く。判定基準の文言は Jev の質問と `refine/commands/reflect.md` に置き、文書の AI 判定と `review/purpose.md` から反映判定を外す。キー未設定なら、ルーティング・反映判定とも TypeSafe に送信しない。Jev はルーティング・反映判定・関連判断の選定に使う。

判定対象コミットの全ツリーは `$STATE_DIR/trees/<符号化したブランチ名>/` にブランチごとに一つ保持する。記録フォルダー内には置かない。`judge/target.json` と品質ごとの材料の `tree` に絶対パスを渡す。判定者は同時実行するチェックが変更し得るチェックアウトを使わず、このツリーを Read・Grep・Glob で読む。Claude の読み取りツールにはパスを限定せず、Codex のノードも状態フォルダーを読める。

初回は全量を export し、その後は保持コミットから判定対象への `git diff --name-status -z --no-renames` の差分だけを反映する。追加・変更ファイルは Git の blob からバイトを保持して書き、実行権限とシンボリックリンクも全量 export と同じにする。削除と空になったフォルダーを先に除去し、ファイルとフォルダーの相互置換も扱う。保持コミットのマーカーは、リポジトリ内のファイル名と衝突しない `$STATE_DIR/trees/.commits/<符号化したブランチ名>` に置く。更新前にマーカーを除去し、完了後に最後に書く。マーカーがない場合、記録したコミットが存在しない場合、差分更新中に失敗した場合はツリーを削除して全量を export し直す。prepare は `git show-ref --verify refs/heads/<ブランチ名>` が失敗するツリーも削除する。判定中のブランチは削除しない。`archon complete` やブランチ削除の後、次の prepare で領域が解放される。変更ファイルの基点版もバイトを保持して渡し、起動した判定の必須基準が欠ければ未評価にする。

機械は、どの判断行の `touches` にも入らない変更ファイルを `outside_plan` として示し、変更先のトップレベルと第2階層のフォルダー数、祖先の各階層の構成も構造判定へ渡す。新しい項目の受け入れ先と祖先上の構造欠陥は、既存でも停止対象になる。それ以外で見つかった欠陥は `deferred` とし、今回を止めずバックログへ送る。`deferred` は構造品質だけで認め、停止やowner判断のフラグと矛盾する出力は未評価にする。

## 指摘から仕組みを直す

`fix` は停止対象の指摘を修正する。誤った指摘には証拠付きで異議を出し、指摘にも修正にも関わっていない判定者が判断する。指摘の参照は `<judge-run>/<judge>/<finding-id>` とし、別の判定で同じローカル ID が使われても、以前の異議採用では消えない。

PR 作成後のコメントや CI 失敗は、出典を含む原文を `review` 入力として同じブランチの `fix` に渡す。例は `Review comment by <login> on path:line: ...`、`CI job <name> failed: <log excerpt>` である。入力は開始に成功した run の `review.text` と `review.commit` に保存し、その fix の指摘は `source: review` とする。開始には合格した要件・計画と、有効な最新 judge の判定済み変更が HEAD と同一であることが必要で、blocking 指摘は要求しない。PR と同じ変更同一性を使うため、backlog と done marker だけのコミット後も開始できる。`review` のない fix の開始条件は従来どおりである。

レビューが要件・計画の範囲を超える場合と、執筆者が指摘に異議を持つ場合は、実装せず `outside_requirements` に `item` と `reason` を出す。異議の判定者には渡さず、その項目と理由を `premise`、レビュー原文を `observation` にした `back` で `requirements` に戻す。セッションは同じブランチで requirements を開始し、所有者がそこで決める。検査・回数上限・既存の step-back は維持し、この差し戻しでは修正コミットを作らない。合格した review fix は変更同一性が変わらなくても再度 judge が必要で、その後 pr が既存 PR を更新する。

依頼自体を追加・変更するコメントは、同じブランチの requirements に `owner_words` として渡し、通常の工程を進める。単位に紐づく既存依頼では、過去に成功した PR があり、有効な done marker がそのブランチを指す場合に requirements の再開始を許可する。別ブランチの完了済み単位の新規開始は拒否する。`devkit-runs` は `gh pr view <branch> --comments` と `gh pr checks <branch>`、実際のインラインコメント・失敗ログの読み取り、この振り分けを案内する。CI 失敗時には `devkit-optimize` でそのジョブを設定済み検査へ追加することを提案する。レビュー担当者の代わりに返信・解決済み化をせず、マージ後は `archon complete <branch>` で worktree とローカルブランチを削除し、リモートは保持する。定期的に `archon isolation cleanup --merged` も使う。

`pr` は本文の判定後、push の前に `.devkit/backlog/<エンコードしたブランチ>.json` をコミットする。保留した指摘、計画から持ち越した指摘、機械検査の候補になる指摘、採用した異議を、それぞれ元の判定への参照と保存する。review 入力は次の pr で任意の `review` 配列に保存する。各要素は原文の指摘と、`kind: review`、修正 run の `run_id`、`target.commit` を持つ出典であり、判定番号を捏造しない。既存4配列は必須のままで、retro は review 配列も読み取る。依頼記録に単位がある場合、同じ `chore:` コミットに `<units>/<unit-id>.done.json` を含める。内容は `unit` と `branch` で、埋め込みスキーマで検証する。同じブランチで再実行しても既存マーカーは変更せず、単位のない依頼では作らない。PR がマージされると基点ブランチにもマーカーが届き、そこで単位は完了となる。基点のチェックアウトで一覧を読み、開始可能な単位を選ぶ。`devkit decisions check` は内容が不正なマーカーと、存在しない単位を指すマーカーを報告する。refine と retro は完了済み単位を編集・削除せず、追加作業には新しい単位を切る。refine の文書段階では影響対象に含まれていてもこの制約を適用し、インデックスと作業ツリーの変更を機械検査する。

計画・refine・retro の全ラウンドを記録し、後のラウンドで解消した指摘も機械化候補として収集する。各項目は `finding` と `source` を持ち、`source` は実行、判定番号、判定者、対象を保持する。

判定済みの変更と HEAD は、コミットが同じか、マージベースからの変更内容が一致する場合に同一とみなす。ファイル名、削除行、追加行とその空白を保持し、ハンクの位置は比較しない。バックログだけのコミットで判定が無効にならないよう、現在ブランチの `.devkit/backlog/<エンコードしたブランチ>.json` だけを、backlog スキーマに適合する場合に比較から除外する。さらに、このブランチの依頼記録が指す単位の `<units>/<unit-id>.done.json` だけを、埋め込み `unit-done.json` スキーマに適合し、このブランチを指す場合に除外する。両方の除外パスは1つの関数で算出し、判断変更検出にも適用する。他の単位ファイルや不正なマーカーは判定と判断変更検出の対象に残す。

`retro` は基点から作ったブランチのバックログを読み、修正用の作業単位、`.devkit/config.json` に加えるチェック、規範の修正を提案する。各提案は元の項目を参照し、対応しない項目にも理由を残す。機械検査の後、fresh な読み取り専用の判定者が `harness.md` と `review/harness.md` を使って調べる。最大3回の後、まとまった案を一つの承認質問として返す。提案中の設定と規範は元に戻し、承認時に適用する。消費したバックログファイルも同じコミットで削除する。

## 実行をまたぐ記録

記録は Git の外の `$STATE_DIR/records/<エンコードしたブランチ>/` に置く。依頼、提案、要件、計画、判定、開始、結果、質問、回答、許可、続行許可を保存する。機械が必要な内容を `$ARTIFACTS_DIR` に取り出し、AI に記録フォルダーを直接渡さない。スキーマは `internal/record/schemas/` を正本としてバイナリへ埋め込み、書き込みごとに検証する。計画の執筆用スキーマも準備処理が成果物へ書き出す。小さな変更(誤字、原因の明らかな小さな不具合、テストや設定の修正)はワークフローを通さず、セッションが規範に従って直接直し、`devkit checks` で確かめる。`devkit checks` は実行の外でも動く。ワークフローを使うのは、人が決める判断、構造・データ・契約・セキュリティ・費用の変更、決まっていないトピックのときだけにする。セッションからは `devkit status` で読む。テキスト・JSON の両方で各ブランチの依頼記録にある単位 ID も示す。`archon project list --json` から状態のフォルダーを見つけ(`STATE_DIR` があればそれを使う)、ブランチごとに最後の結果、未回答の質問、停止や差し戻しの中身、次に起動するワークフローを示す。

最後の結果が合格した `pr` のブランチでは、`devkit status` が gh を利用可能な場合に `gh pr view <branch> --json state,url,reviewDecision,statusCheckRollup` を15秒の制限で実行し、open・merged・closed、URL、レビュー判断、失敗した検査をテキストと JSON に示す。実行・タイムアウト・JSON 読み取りの失敗は表示し、status 自体は失敗させない。`next` は open で検査失敗ならログを `review` とした fix、変更要求ならコメントを `review` とした fix または依頼変更時の requirements、merged なら `archon complete <branch>`、closed なら未マージで閉じた旨を示す。検査失敗と変更要求が両方あれば検査失敗の案内を優先する。

開始条件は、前工程の結果、未回答質問、渡された回答、チェックアウトとワークフローの状態を検査する。開始が成功するまで回答を保存しない。前工程を再開始すると下流の結果を無効にする。`question` で終わった実行は、回答を付けた新しい実行で続ける。Archon 内の待機ノードは置かない。

`back` の前提と観測は、戻り先の準備処理が有効かつ未消費のものを `returned` に取り出し、執筆者が先に扱う。`back` は戻り先のワークフローを、`stop` は停止理由と未解決点を示す。再開始が設定上限に達した場合は、人が続行を認めた言葉を `continue` へ渡す。上限到達前には受け付けない。`devkit-runs` が結果を読み、次を起動し、質問と回答をそのまま取り次ぐ。

## 導入と設定

`kit/` は対象リポジトリに配るワークフロー、規範、スキル、初期設定を持つ。`cmd/devkit/` が CLI を登録し、`internal/` が機械処理を実装する。`devkit init [--yes | --no] [--dry-run] [--provider claude|codex] [--sessions claude,codex] [--language <code>] [dir]` はキットを展開するがコミットはしない。初めて導入したときは、最後に `devkit-optimize` の実行を促す。`devkit-optimize` はセッションで一度使うスキルで、リポジトリを読み、チェック、判定者と判断を選ぶパス、基点ブランチ、worktree の準備を提案し、配った規範とリポジトリの既存の決まりとの食い違いを洗い出し、人が承認したものだけを書く。

`--language <code>`（`--language=<code>` も可）は人が読む文章の言語を保存する。検証は設定と同じで、空文字列と空白だけの値を拒否する。新規導入で指定がなければ、`LC_ALL`、`LC_MESSAGES`、`LANG` の順で最初の空でない値を読み、`_`・`.`・`@` より前を小文字にする。`ja_JP.UTF-8` は `ja`、`pt_BR` は `pt` になる。`C`・`POSIX`・空なら `en` を使う。init は選んだ言語と出典、`devkit-optimize` でリポジトリに合わせられることを表示する。再導入では明示指定がなければ既存言語を保持し、指定があれば `--provider` と同じく設定全体の置換を断ってもその値だけ保存して他のキーと書式を保つ。

書き込み前に全対象を比較する。ワークフローの `.archon/workflows/dev/` と各スキルフォルダーでは、内容の異なるファイルとキットが配布しなくなったファイルを示し、フォルダーごとに一度、上書き件数と削除件数を尋ねる。既定は No であり、既存ファイルは保持し、欠落ファイルだけを追加する。削除対象はキット所有フォルダー内だけで探す。規範は設定の `standards` フォルダー全体をリポジトリが所有する。差分・欠落・余分なものが一つでもあれば全体の置き換えを尋ね、No なら欠落ファイルも追加せず、完全に保持する。Yes の場合だけ余分なものを削除する。内容が異なる `.devkit/config.json` と `.archon/config.yaml` はそれぞれ確認する。同一ファイルは表示も書き込みもせず、新規ファイルは確認なしで作る。

workflows がバイナリの配布内容と一致する新規導入・Yes・差分なしの場合、`.archon/workflows/dev/.devkit-installed.json` に `devkit_version` と `kit_digest` を記録する。No では欠落ファイルを補っても印を保持し、印がなければ作らない。印は workflows グループに含め、余分なファイルとして扱わない。workflow の手編集では印は変わらない。`devkit version` は版と埋め込みキットの SHA-256 ダイジェストを表示する。ファイルパスと内容を長さ付きで辞書順にハッシュするため、ビルド日時・ファイル時刻・権限によらず、埋め込み内容が同じなら一致する。

`devkit record start <workflow>` と refine・retro の専用 start は、記録・回答の保存前に `$PACK_DIR` 内の対象 workflow の YAML と commands を読み、呼ばれるコマンドが実行中バイナリに登録されているかを検査する。抽出処理は plumbing test と共用し、テスト fixture は除く。未登録なら `not_started` で終了し、コマンド名、workflow とバイナリの版違い、適合するバイナリでリポジトリ内の `devkit init` を実行するか導入時のバイナリを使う対処を示す。印があれば導入元の版も示す。`devkit-runs` は人に伝え、再試行しない。ダイジェストの相違だけでは開始を拒否しない。

`--skill devkit-runs=<名前> --skill devkit-discuss=<名前> --skill devkit-optimize=<名前>` でスキルの配置名を変更できる。小文字英字・数字・ハイフンだけからなる重複しない名前を `.devkit/config.json` の `skills` に保存し、次回から再利用する。フォルダー、フロントマターの `name`、スキル内の相互参照と `scripts/watch.sh` の呼び出しパスも置き換える。変更前の名前が新しい配置先として使われていなければ、旧フォルダーを削除対象として確認する。設定全体の置き換えを断っても、明示した `--skill` は `skills` の値だけを更新し、他のキーや書式を保つ。設定を置き換える場合も、既存の規範の配置先と選んだスキル名は引き継ぐ。本文中のスキル名は既定名を表す。

配置先やリポジトリ内の祖先にあるシンボリックリンクは名前を示して確認し、No なら影響する配置先を処理しない。Yes はリンク自体を通常のファイルやフォルダーに置き換え、リンク先には書き込まない。共有する祖先リンクの置き換えが拒否したグループのファイルを失わせる場合、そのリンクの置き換えも行わない。`--yes` と `--no` は全確認に同じ回答を適用する。標準入力が端末でなく、どちらもなければ、その旨を表示してすべて No とする。`--force` は廃止し、別名としても残さない。`--dry-run` は比較と予定する質問だけを表示し、書き込みも削除もしない。完了時に書いたもの・削除したもの・保持したものを列挙し、拒否だけでは失敗にしない。不正な JSON 設定は既定の配置先で比較することを警告し、保持または置き換えを選べる。ただし `skills` だけの更新には JSON オブジェクトが必要であり、壊れた設定のまま名前だけを変更することはできない。不正な配置先設定は書き込む前にエラーにする。

Archon、Git、`devkit` と、設定チェック用のツールが必要になる。執筆・判定には設定した Archon provider、ルーティングと文書反映判定の代替経路には同じ provider の認証済み CLI、PR 公開は認証済みの `gh` と `origin` を使う。Go と mise は dev-kit 自体の開発に使い、対象リポジトリにはビルド済みバイナリを置ける。基点ブランチは Archon の `worktree.baseBranch` で指定する。

`.devkit/config.json` の `provider` は `claude`（既定）または `codex`。`devkit init --provider <name>` が保存し、workflow の AI ノードを描画する。ソースは Claude のままにし、Codex 導入時は全 AI ノードを Codex にし、未対応の `allowed_tools`・`denied_tools`・`settingSources` を除く。変更後の再導入は通常の workflow フォルダー差分として y/N を尋ねる。全 AI 出力スキーマは、入れ子を含め全プロパティを required に列挙し、`additionalProperties: false` にする。適用しない値は空文字・空配列・false で表し、プロンプトと読み取り側もそれを扱う。

Codex の workflow 判定者は full access で動き、ツール制限で書き込みを防げない。両 provider とも `mutates_checkout: false` を保ち、checkout を変更したノードを Archon が失敗にする。これは変更後の検出である。別経路の CLI フォールバックは読み取り専用とし、Codex は `codex exec --sandbox read-only --cd <checkout> --output-schema <一時スキーマ> -o <一時回答> --skip-git-repo-check -`、Claude は `claude -p --json-schema <schema> --allowedTools Read,Grep,Glob --tools Read,Grep,Glob --permission-mode dontAsk --output-format json` を使う。ルーティングの Codex は Git 管理情報のない判定ツリーを作業ディレクトリにし、Claude は `--add-dir <判定ツリー>` を追加する。Claude は JSON 結果の `structured_output` を読み、通常の `result` 文字列を回答として扱わない。両者を10分で打ち切り、回答をスキーマで検証する。実行ファイルは `DEVKIT_CODEX`・`DEVKIT_CLAUDE` でテスト用に置換できる。プロンプトは `$PACK_DIR` 内の `commands/*.md` を読み、`$ARTIFACTS_DIR`・`$PACK_DIR` を絶対パスに置換して標準入力へ渡す。CLI の出力は成果物内のログへ保存し、標準エラーにはパスと失敗時の末尾4000文字までを出す。実行 fixture はキーを外して偽 CLI で両 provider の経路を通し、ソース・描画後の provider と strict schema も Go テストで検査する。

`sessions` はスキルを導入するセッションツールの配列で、未指定なら provider 一つ。`devkit init --sessions claude,codex` で両方へ導入でき、空配列ならスキルは導入しない。Claude は `.claude/skills/<name>/`、Codex は `.agents/skills/<name>/` へ置き、内部参照も導入先に合わせる。明示された sessions は provider 変更時にも保持する。`--provider`・`--sessions` は `--skill` と同じく、設定全体の置換を断っても指定値だけ保存し、他の設定と書式を保つ。改名・差分確認・自分が導入したと確認できない旧フォルダーを削除候補にしない規則を、各配置先に適用する。

`devkit doctor [dir]` は required・needed for a part・optional の三段階で状態、不足で止まる用途、導入方法を出す。必須は Git とコミット済みリポジトリ、Archon とその版、設定 provider、PATH 上の devkit、導入ファイル、config と concerns 検査。部分利用は sessions の各 CLI、PR 用の gh 認証と origin、キー未設定時の代替 CLI。任意は TypeSafe キーの有無と checks で、空なら検証が走らないことと設定された optimize 名を示す。キー自体は出さず、TypeSafe に送る差分・新判断・引用文書を説明する。provider の導入は、最大20秒待つ `archon doctor` の `Installed providers:` 一覧で検査する。一覧がない、コマンドが失敗する、またはタイムアウトした場合は、`$ARCHON_HOME/plugins/archon-provider-<provider>`（既定 `~/.archon/plugins/`）に実行可能な通常ファイルがあるかで判定する。対象 provider の診断失敗行は警告として添え、導入済みの判定を失敗にはしない。他の外部コマンドは各3秒以内のままとする。必須不足だけ終了コード1。init はサマリー後に同じ診断を出すが、その結果では失敗せず、初回は続けて optimize 名を案内する。

診断の必須項目 `kit and binary` は導入済み workflows と設定された配置先の全スキルで呼ばれるコマンドを登録一覧と照合し、不足するコマンドを列挙する。別項目 `kit version` は needed for a part として印のダイジェストを比較し、不一致なら導入元と実行中バイナリの版、`devkit init` で差分を確認して置換を承認する対処を示す。印がない場合も明記し、この項目だけでは doctor を失敗にしない。

リポジトリごとの差異は `.devkit/config.json` に置き、`devkit config` で有効値を確認する。設定の正本となる既定値と検証処理は `internal/config` にある。

- `language` は人が読む文章の言語で、組み込みの既定は `en`。新規導入時は `--language` または環境のロケールから選ぶ。
- `provider` は `claude`（既定）または `codex`。`sessions` は導入先のセッションツールで、未指定なら provider 一つ。
- `skills` は `devkit-runs`、`devkit-discuss`、`devkit-optimize` を実際の配置名に対応させ、既定は同名。省略したスキルは個別に補完する。
- `standards`、`docs`、`decisions`、`units`、`topics` は保存先で、既定は順に `.devkit/standards`、`docs`、`.devkit/decisions`、`.devkit/units`、`.devkit/topics`。
- `checks` は名前、シェルコマンド、タイムアウト秒数、任意の `paths` を持つ。初期値は空なので、実際の検証コマンドを追加する。`paths` の省略は毎回実行、空配列は対象なしを意味する。終了コード0は合格、75だけ一度再実行し、タイムアウトは環境エラー、77は未実行、ほかは不合格になる。
- `skeleton_check` はスケルトンに実行するチェック名で、既定は空。
- `qualities` は品質判定の起動パスを定める。判定するフェーズは関心マップが、差分からの追加選択はルーティングが担う。
- `decision_paths` は判断を伴う変更の `paths`、`quality`、`ask` を定める。既定では依存、マイグレーション、インフラ、CI、環境変数サンプル、ワークフロー、規範、設定自身を含む。基点の設定と現在の設定のチェックを合わせて実行するため、チェックを削除しても検査を回避できない。
- `refine.relevance_threshold` は関連判断の選定確率で、0以上1以下の数値。既定は0.2。省略時は個別に補完する。
- `limits.restarts` と `limits.fixes` は再開始と修正の上限で、既定はそれぞれ3。`limits.passes` は `implement` がリリース単位1つに使える回数で、既定は3。ある単位が使い切ると、その単位の名前と落ちたチェックを示して止まる。単位の数に関係なく、ほかの単位の回数は減らない。

省略した項目には既定値を使い、品質・上限・refine は個別に補完する。それ以外の指定配列は既定の配列を置き換える。グロブは `**`、`*`、`?` を使える。

## キットを検証する

ソースのチェックアウトで次を実行する。

```sh
mise exec -- go build ./...
mise exec -- go vet ./...
mise exec -- go test ./...
scripts/test-kit.sh
```

`scripts/test-kit.sh` は Claude と Codex それぞれの一時 Git リポジトリへ `devkit init --provider` し、警告なしの `archon validate workflows`、原則の所有検査、`archon workflow test` を実行する。次にソースの `test/fixtures/` を一時リポジトリへコピーし、AI だけをスタブ化して各ワークフローの主経路の bash を実行する。分岐ごとのスタブフィクスチャも用意する。引数で実行フィクスチャのワークフローを絞れる。

Archon のホームを分離し、プロバイダープラグインは既定で `$HOME/.archon/plugins`、必要なら `KIT_ARCHON_PLUGINS` から読む。別バイナリの `cmd/devkit-fixture` が事前記録と AI 執筆によるファイル出力を補い、終了前の記録を検証する。このヘルパーと実行フィクスチャは配布キットに含めない。PR 公開はスタブ化し、`sync` は実際のローカル競合を解消する。

Go テストは各機械処理の判断分岐とスキーマを検証する。plumbing テストは YAML とプロンプトが呼ぶ全 `devkit` サブコマンドを登録と照合する。実 AI の判断と外部への PR 公開はフィクスチャの検証範囲に含まれない。

## まだないもの

依存解析ツールから取得する事実は持たず、構造の材料は Git の変更と階層の情報に限られる。執筆者・判定者・ルーティングと文書反映判定の代替 CLI は設定した provider を使い、PR 公開先は GitHub のみである。リポジトリ固有のマイグレーション検証や依存監査などは、必要なチェックを設定して補う。
