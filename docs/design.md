# dev-kit の設計

Claude Code や Codex に開発を任せると、手順を飛ばす、自分で `PASS` を出す、未完了でも完了を主張する、セッションをまたぐと文脈を失うことがある。指示ファイルや skill で頼むだけでは、順序と完了条件を守らせる力がない。dev-kit は、リポジトリの持ち主が「どの順で進み、どこで check を通し、どこで人が見るか」をループの雛形として組み、エージェントが普段のセッションでそのループに従い、`devkit` が順序・完了・記録を決定的に守らせるための道具である。

kit が提供するのは、ループに組み込む要素（ステージの候補、観点ファイル、ゲート、判定者、コマンド、router の分類と遷移の規則）、部品と組み立てが満たす原則（[`principles/harness.md`](../principles/harness.md)）、既定のループの雛形、そして雛形から課題ごとの[計画](loop-plan.md)を作る手順である。ループそのものは利用者がリポジトリごとに組み、育てる。

## 基本方針

- 同じモデルを使っても、ループの組み方によって結果は変わる。うまくいかないときは、モデルを替える前にループを見直す。
- 手続きは、複雑にすればよいわけではない。既定では最も簡素な手順を採用し、必要な場合に限って追加する。
- [ステージ](stages.md)、[check](parts/check.md)、レビューゲートの組み合わせは利用者がループの雛形として組む。課題ごとには、雛形から計画を作り、完了条件を埋め、関係のないステージを外し、必要なら候補から足す。
- ループの外にいる人が、次の判断に必要な現在の前提を把握できていない状態を「理解の負債」と呼ぶ。その返済とは、未読の変更や決定をなくすことではなく、現在の前提を把握することである。人が戻ってきたときは、現在の要約と自分がすべきことを最初に読み、差分は経過を追うための補助として使う。
- 機械で決定的に判定できる規則は原則にしない。ループの仕組みに関するものは[部品の契約](#部品)に、対象のコードと文書に関するものは[規則と強制手段](rules.md)の一覧に置き、手段が実装されるまでは「未実装」として残す。

## 部品

部品は、契約（入力と出力の形式）、テンプレート、試験を持つ提供単位である。部品は `principles/harness.md` の原則を満たすように作り、どう満たすか（方式）は各部品の契約で定める。ステージ、[観点](checks.md)、担当、レビューゲートは雛形が定め、計画は課題に合わせて取捨する。部品そのものは選ばない。部品は次の7つとし、試験のない部品は kit に含めない。

- [brief](parts/brief.md) — 作業依頼のフォーマット
- [check](parts/check.md) — 評価と判定
- [router](parts/router.md) — 次のアクションの決定
- [ledger](parts/ledger.md) — 状態の外部保存
- [form](parts/form.md) — 固定フォーマット
- [view](parts/view.md) — 人向けの表示
- [runtime](parts/runtime.md) — 実行

各部品の実装モジュール(計画の意味論を扱う plan を含む)、kit の固定物、配置、依存は [architecture.md](architecture.md) で定める。設計の正本は [architecture.md](architecture.md) と [architecture/](architecture/) である。
