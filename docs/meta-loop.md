# メタループの運用

## メタループ

メタループは、ループの仕組み(部品、組み立て、計画)を評価して改善するためのループである。毎回の作業の最後に作業者が `retrospective` を担当し、リポジトリの規範と機械の検査を育てる。既定の `default`・`fix`・`docs` はいずれも振り返りで終わる。

- **入口**: brief が参照する、指示発行時点で固定した作業履歴ファイルと規範の一覧である。作業履歴には、作業のすべての判定と指摘(blocking でないものも含む)、`FAIL` と `NOT ASSESSED` の経緯、ラウンド数、人の却下・訂正・作り直しの指示、`note` の教訓で伝えた見逃しを含む。
- **振り返り**: 各問題をどこで捕まえるべきだったかを調べ、再発防止の反映先と理由を決める。反映しない場合も理由を残す。教訓は[決定と証拠](architecture/data.md#決定と証拠-decision--evidence)として記録する。
- **反映先**: 既定の優先順は機械の検査(hook・lint・型・検証コマンド)、雛形、観点、原則、skill であり、`[lessons] destinations` で変更できる。規則の「手段: 未実装」と繰り返す違反は、テスト・lint・型・pre-commit・検証コマンドへ移す候補にする。反映先はリポジトリが所有する資産であり、dev-kit 本体へ戻す経路は持たない。既定の `.devkit/plans/`・`.devkit/checks/`・`.devkit/principles/`・`.devkit/stages/`・`.devkit/templates/`・`.devkit/rules.md` は `devkit.toml` の `[paths]` で変更できる。skill は `.agents/skills/devkit/` に置く。
- **要件の維持**: 目的のステージがない場合や未反映の場合は、人が承認した完了条件のうち要件に当たるものを `.devkit/requirements.md` に反映する。構造の記録は `.devkit/structure.json`、複数の作業で守る変更困難な決定は `.devkit/rules.md` に残す。配置は `[paths]` で変更できる。固定の `.devkit/run/` は git 管理せず、後の作業へ渡す決定をローカルの記録だけに残さない。
- **検査**: `default` と `fix` は必須の `command:test`・`test`・[harness](checks.md#harness)、`docs` は必須の `harness` だけで確かめる。skill の試験の確認事項は「[skill の試験](checks.md#skill-の試験)」に従う。観点を変えたら検出試験の例も更新する。検出試験の設定と実行時期は[検出試験](architecture/guarantees.md#検出試験)に従う。
- **規範の働きと整理**: 原則がどの観点・雛形で使われているか、使われない仕組みや負担に見合わない仕組みがないかを確かめる。扱う対象はその作業で起きた問題・見逃し・規範の不足や負担であり、全体の棚卸しは必要が見えたときだけ行う。より単純な対案との比較は観点 `harness` で行う。削除するかどうかは、未使用の期間ではなく、その仕組みが必要になる代表的なケースで比較して決める。
- **人の確認**: 規範・ホスト設定・skill・有効な pre-commit の設定は、どのステージで変えてもループ自身の変更である。既定の `[approval] meta_loop_edit = "confirm"` では、効力を持つ最初の時点より前に人が確認する。ラウンド開始時のスナップショットに、作業の基点または直前に確認した時点からの未確認の変更があれば、ラウンドを開く前に問いを起票して止める。最後のラウンドで行った変更は完了時のコミット前に確認する。確認済みの範囲は確認したスナップショットの規範の識別で表し、却下されたら作業者が変更を取り消す。`"allow"` も設定できる。要件と構造の記録はこの変更に含めない。規範を変えなければ、その変更に対する確認なしで終わる。

完了後に見つかった見逃しは、新しい `fix` の課題として扱い、その振り返りで反映先を決める。人は check の結果から一部を選んで読み直し、自分の判断と判定を照合できる。

手がかりの自動集計は、何を測るべきかが分かるまで実装しない。

## 生成した設計の典型的な問題

生成した設計には、配置の不自然さや冗長さが生じることがある。[ステージ候補](stages.md)の「0 目的」「2 構造」では、次の問題が手がかりになる。検査と blocking の基準は観点「[構造](checks.md#構造)」に従う。

- **配置の誤り**: 成果物を本来の配置先と異なる場所に置く。配置ガイドの欠如が原因・兆候となる。ガイドの配置と取り込みは[リポジトリ側の構成](repository.md#リポジトリ側の構成)に従う。
- **冗長さ**(制約ごとに仕組みを足す、既存コードを変更せずにレイヤーを追加する): より単純な構造との比較は観点「[構造](checks.md#構造)」に従う。判断には [`assets/principles/designing.md`](../assets/principles/designing.md) の原則5と [`assets/principles/structure.md`](../assets/principles/structure.md) の原則7の違反・兆候を使う。
- **前提への固着**(Issue に書かれた手段に設計が縛られる): 目的と手段を決める範囲はステージ「[0 目的](stages.md#0-目的)」「[2 構造](stages.md#2-構造)」に従い、観点「[構造](checks.md#構造)」で前提を照合する。
- **1回だけの生成**(一度の生成で設計を済ませる): check の [`FAIL`](architecture/data.md#check-の結果-judgment)(不合格の判定)に対する修正ラウンドは[作業結果の判定](architecture/flow.md#作業結果の判定)と [router](architecture/modules.md#router)(次の行動を分類する部品)の[判断](architecture/flow.md#router-の判断)に従い、設計を作り直す。
- **既存の流儀の無視**(同じ種類の処理があるのに、既存の書き方と異なる実装を追加する): 調査と成果物はステージ「[調査](stages.md#調査)」「[2 構造](stages.md#2-構造)」、照合は観点「[構造](checks.md#構造)」「[差分](checks.md#差分)」に従う。

却下した設計案の記録は[決定と証拠](architecture/data.md#決定と証拠-decision--evidence)に従い、観点を改善する手がかりにする。
